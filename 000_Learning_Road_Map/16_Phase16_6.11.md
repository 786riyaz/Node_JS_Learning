# 2. Understanding SMTP

Before using Nodemailer, understand SMTP.

### What is SMTP?

SMTP stands for:

**Simple Mail Transfer Protocol.**

It is a communication protocol used to send emails between mail clients and mail servers.

When your Node.js application sends an email, it usually communicates with an SMTP server or an email delivery provider.

### Example

Suppose a user registers.

Your application needs to send:

```text
To: user@example.com

Subject: Welcome to Expense Tracker

Hello,

Your account has been created successfully.
```

The process:

```text
Node.js Application
        |
        v
    SMTP Server
        |
        v
 Recipient Mail Server
        |
        v
 User's Inbox
```

### Common SMTP Ports

| Port | Purpose |
|---|---|
| 25 | Traditional SMTP server communication |
| 465 | SMTP over implicit TLS |
| 587 | Message submission, commonly using STARTTLS |

Port 587 is commonly used for authenticated email submission.

### SMTP Authentication

Most email providers require authentication.

Your application may need:

- SMTP hostname.
- SMTP port.
- SMTP username.
- SMTP password or application-specific credential.
- TLS configuration.

Never hardcode SMTP credentials in your source code.

# 3. What Is Nodemailer?

**Nodemailer** is a popular Node.js library for sending emails.

It supports:

- SMTP.
- HTML emails.
- Text emails.
- Attachments.
- Multiple recipients.
- CC and BCC.
- Custom headers.
- Email transport configuration.

Official documentation: [Nodemailer](https://nodemailer.com/?utm_source=chatgpt.com)

### Install Nodemailer

```bash
npm install nodemailer
```

### Basic Example

```javascript
const nodemailer = require("nodemailer");


async function sendEmail() {

    const transporter = nodemailer.createTransport({

        host: "smtp.example.com",

        port: 587,

        secure: false,

        auth: {

            user: process.env.SMTP_USER,

            pass: process.env.SMTP_PASSWORD

        }

    });


    const info = await transporter.sendMail({

        from: process.env.EMAIL_FROM,

        to: "user@example.com",

        subject: "Test Email",

        text: "Hello! This is a test email."

    });


    console.log("Email sent:", info.messageId);

}


sendEmail();
```

### Understanding createTransport()

```javascript
nodemailer.createTransport()
```

This creates a reusable email transporter.

Think of it as a configured connection or delivery mechanism for sending emails.

### Understanding sendMail()

```javascript
transporter.sendMail()
```

This sends an email using the configured transporter.

# 4. Understanding SMTP Configuration

Let's understand the configuration.

```javascript
const transporter = nodemailer.createTransport({

    host: "smtp.example.com",

    port: 587,

    secure: false,

    auth: {

        user: "username",

        pass: "password"

    }

});
```

| Property | Description |
|---|---|
| `host` | SMTP server hostname |
| `port` | SMTP port |
| `secure` | Whether to use implicit TLS |
| `auth.user` | SMTP username |
| `auth.pass` | SMTP password |

### What does secure mean?

For common SMTP configurations:

**Port 465:**

```javascript
secure: true
```

This uses implicit TLS.

**Port 587:**

```javascript
secure: false
```

This normally starts with a plaintext connection and upgrades to TLS using STARTTLS.

Nodemailer can negotiate STARTTLS when the server supports it and the configuration permits it.

For production, require encryption rather than silently allowing an insecure connection.

### Rendering the Template

```javascript
const fs = require("fs");

const path = require("path");

const handlebars = require("handlebars");


function renderTemplate(templateName, data) {

    const templatePath = path.join(

        __dirname,

        "../templates/emails",

        `${templateName}.hbs`

    );


    const source = fs.readFileSync(templatePath, "utf8");

    const template = handlebars.compile(source);

    return template(data);

}
```

Usage:

```javascript
const html = renderTemplate("welcome", {

    name: "John",

    email: "john@example.com"

});
```

Output:

```html
<h1>Welcome, John!</h1>

<p>Your account has been created successfully.</p>

<p>Email: john@example.com</p>
```

Handlebars escapes ordinary interpolated values by default, which helps prevent HTML injection. Avoid unescaped expressions such as triple braces for untrusted user input.

### Why use templates?

- Consistent email design.
- Reusable layouts.
- Easier maintenance.
- Dynamic content.
- Separation of presentation and business logic.

**Production recommendation:** Use responsive HTML templates and always provide a plain-text alternative.

# 8. Email Verification System

Now let's implement a real-world feature.

When a user registers, we may want them to verify their email address.

### Workflow

```text
User Registers
      |
      v
Create User
      |
      v
Generate Verification Token
      |
      v
Store Token Hash
      |
      v
Send Verification Email
      |
      v
User Clicks Link
      |
      v
Backend Validates Token
      |
      v
Mark Email as Verified
```

### Why verify email?

- Confirm that the email address belongs to the user.
- Reduce fake accounts.
- Improve account recovery.
- Reduce incorrect email addresses.

## 8.1 Update User Model

Add:

```javascript
emailVerified: {

    type: DataTypes.BOOLEAN,

    defaultValue: false,

    field: "email_verified"

}
```

Create a migration for the new column.

## 8.2 Create Email Verification Token Table

Example:

```sql
CREATE TABLE email_verification_tokens (

    id BIGINT PRIMARY KEY AUTO_INCREMENT,

    user_id BIGINT NOT NULL,

    token_hash CHAR(64) NOT NULL,

    expires_at DATETIME NOT NULL,

    created_at DATETIME DEFAULT CURRENT_TIMESTAMP,

    CONSTRAINT fk_email_verification_user

        FOREIGN KEY (user_id)

        REFERENCES users(id)

        ON DELETE CASCADE,

    UNIQUE KEY unique_verification_token (token_hash)

);
```

For production, use migrations rather than manually modifying the database.

## 8.3 Generate Verification Token

We can use Node.js crypto.

```javascript
const crypto = require("crypto");


function generateVerificationToken() {

    const token = crypto.randomBytes(32).toString("hex");

    const tokenHash = crypto
        .createHash("sha256")
        .update(token)
        .digest("hex");


    return {

        token,

        tokenHash

    };

}
```

Here:

- `token` is sent to the user.
- `tokenHash` is stored in the database.

Why store only the hash?

If someone gains access to the database, they cannot directly use the stored hash as the original verification token.

## 8.4 Generate Verification URL

```javascript
const verificationUrl =
    `${process.env.FRONTEND_URL}/verify-email?token=${token}`;
```

Example:

```text
https://example.com/verify-email?token=abc123
```

Use HTTPS in production.

## 8.5 Verify Token

The backend should:

1. Receive the token.
2. Hash the received token.
3. Find the matching token hash.
4. Check expiration.
5. Verify that the token has not been used.
6. Mark the user's email as verified.
7. Consume the verification token.

These operations should be performed in a database transaction.

### Important security considerations

- Set a short expiration period.
- Use cryptographically random tokens.
- Store token hashes, not raw tokens.
- Make tokens single-use.
- Rate-limit resend requests.
- Avoid exposing whether a particular email address is registered.

This is another important authentication feature.

Suppose a user forgets their password.

### Workflow

```text
           |
           v

           |
           v
Generate Secure Token
           |
           v
Store Token Hash
           |
           v
Send Password Reset Email
           |
           v
User Opens Reset Link
           |
           v
Enter New Password
           |
           v
Validate Reset Token
           |
           v
Hash New Password
           |
           v
Update User Password
           |
           v
Invalidate Existing Refresh Tokens
```

### Example Email

```text
Subject: Reset Your Password

Hello,

We received a request to reset your password.

Click the link below:

https://example.com/reset-password?token=abc123

This link expires in 15 minutes.

If you did not request this change, you can ignore this email.
```

### Important Security Rules

1. Never send the user's existing password.
2. Never store plain-text reset tokens.
3. Use short token expiration.
4. Make reset tokens single-use.
5. Do not reveal whether an email exists.
6. Invalidate the token after successful password reset.
7. Revoke existing refresh tokens after resetting the password.
8. Rate-limit reset requests.

### Token expiration example

```javascript
const expiresAt = new Date(
    Date.now() + 15 * 60 * 1000
);
```

This represents 15 minutes.

### Important

A password reset token and an email verification token serve different purposes.

Keep their database records and validation logic separate unless you deliberately build a secure unified token system.

# 11. Why We Need Background Jobs

Let's understand an important backend architecture problem.

Suppose a user creates an expense.

Our API performs:

1. Insert expense.
2. Create audit log.
3. Send email.
4. Send notification.
5. Return API response.

If the email provider takes 5 seconds to respond, the API request may also take 5 seconds.

This creates unnecessary latency.

### Synchronous architecture

```text
API Request
    |
    v
Create Expense
    |
    v
Send Email
    |
    v
Create Notification
    |
    v
Return Response
```

Problem:

The API waits for email delivery.

### Asynchronous architecture

```text
API Request
    |
    v
Create Expense
    |
    v
Create Background Job
    |
    v
Return Response
    |
    |
    v
Background Worker
    |
    v
Send Email
    |
    v
Create Notification
```

Now the API can respond without waiting for email delivery.

This is where job queues become useful.

# 12. What Is a Job Queue?

A job queue stores tasks that need to be processed asynchronously.

Examples:

- Send email.
- Generate PDF.
- Process uploaded images.
- Send notifications.
- Generate monthly reports.
- Process payments through an appropriate workflow.

A worker takes jobs from the queue and processes them.

### Components

| Component | Responsibility |
|---|---|
| Producer | Creates jobs |
| Queue | Stores pending jobs |
| Worker | Processes jobs |
| Redis | Often used as queue storage |
| Job Scheduler | Schedules future or recurring jobs |

We will use BullMQ with Redis.

| `removeOnFail` | Retention of failed jobs |

# 16. Creating an Email Worker

Now the worker will process email jobs.

File:

```text
src/workers/email.worker.js
```

```javascript
const {
    Worker
} = require("bullmq");

const redisConnection = require("../config/redis");

const emailService = require("../services/email.service");


const emailWorker = new Worker(

    "email-queue",

    async (job) => {

        if (job.name === "send-email") {

            await emailService.sendEmail(job.data);

        }

    },

    {

        connection: redisConnection,

        concurrency: 5

    }

);


emailWorker.on("completed", (job) => {

    console.log(`Email job ${job.id} completed`);

});


emailWorker.on("failed", (job, error) => {

    console.error(
        `Email job ${job?.id} failed:`,
        error.message
    );

});


module.exports = emailWorker;
```

### What is concurrency?

```javascript
concurrency: 5
```

This means the worker can process up to five jobs concurrently.

The actual throughput depends on the email provider, network, CPU, and worker configuration.

### Important

Run workers as a separate process in production.

For example:

```bash
node src/workers/email.worker.js
```

However, this worker file should initialize all required configuration, including environment variables and the Redis connection.

Do not start a separate worker inside every API request.

# 17. Adding Email Jobs from the Service Layer

Now update our Expense Service.

Previously, we directly called the email service.

Instead, we will add a background job.

```javascript
const expenseRepository = require("./expense.repository");

const sequelize = require("../../database/connection");

const {
    addEmailJob
} = require("../../jobs/email.jobs");


class ExpenseService {

    async createExpense(userId, data) {

        const expense = await sequelize.transaction(
            async (transaction) => {

                return await expenseRepository.create(
                    {
                        ...data,
                        userId
                    },
                    transaction
                );

            }
        );


        await addEmailJob({

            to: data.userEmail,

            subject: "Expense Created",

            text: `Expense of ${expense.amount} created successfully.`

        });


        return expense;

    }

}


module.exports = new ExpenseService();
```

### Important Production Issue

There is a reliability gap here.

Suppose:

1. The expense transaction commits.
2. The application crashes before adding the email job.

The expense exists, but the email job was never created.

This is a classic problem in distributed systems.

We can address it with the **Transactional Outbox Pattern**, which we will discuss later.

Also, do not accept `userEmail` from the client as the authoritative recipient. Load the user's verified email from the database.

# 18. What Is the Transactional Outbox Pattern?

The Transactional Outbox Pattern helps ensure that database changes and event creation happen together.

Instead of directly publishing an event to Redis after committing the expense, we first store the event in an outbox table within the same database transaction.

### Architecture

```text
              CREATE EXPENSE
                    |
                    v
              DB TRANSACTION
                    |
           +--------+--------+
           |                 |
           v                 v
       Expense          Outbox Event
           |                 |
           +--------+--------+
                    |
                    v
                  COMMIT
                    |
                    v
              OUTBOX WORKER
                    |
                    v
              PUBLISH JOB
                    |
                    v
               REDIS QUEUE
                    |
                    v
               EMAIL WORKER
                    |
                    v
                SEND EMAIL
```

### Why is this useful?

Suppose Redis is unavailable.

The expense and outbox event are still safely committed in MySQL.

A worker can retry publishing the event later.

### Example Outbox Table

```sql
CREATE TABLE outbox_events (

    id BIGINT PRIMARY KEY AUTO_INCREMENT,

    event_type VARCHAR(100) NOT NULL,

    payload JSON NOT NULL,

    status VARCHAR(30) DEFAULT 'pending',

    created_at DATETIME DEFAULT CURRENT_TIMESTAMP,

    processed_at DATETIME NULL

);
```

### Creating Expense and Outbox Event

```javascript
await sequelize.transaction(async (transaction) => {

    const expense = await Expense.create(
        {
            userId,
            amount,
            description
        },
        {
            transaction
        }
    );


    await OutboxEvent.create(
        {
            eventType: "EXPENSE_CREATED",

            payload: {
                expenseId: String(expense.id),
                userId: String(userId)
            },

            status: "pending"
        },
        {
            transaction
        }
    );

});
```

A separate worker reads pending outbox events and publishes them to BullMQ.

### Important: Idempotency

Outbox events may be published more than once.

Therefore, consumers should be idempotent.

For example, an email worker should track processed event IDs or use an appropriate deduplication strategy.

The goal is to avoid sending duplicate notifications when a job is retried or republished.

```sql
    is_read BOOLEAN DEFAULT FALSE,

    read_at DATETIME NULL,

    CONSTRAINT fk_notification_user

        FOREIGN KEY (user_id)

        REFERENCES users(id)

        ON DELETE CASCADE

);
```

### Example Notification Record

```json
{
    "id": 1,
    "userId": 10,
    "title": "Budget Warning",
    "message": "You have used 90% of your food budget.",
    "type": "BUDGET_WARNING",
    "isRead": false
}
```

### Important Database Indexes

We frequently retrieve notifications for a user.

Create an index:

```sql
CREATE INDEX idx_notifications_user_created
ON notifications(user_id, created_at);
```

For unread notifications, another possible index is:

```sql
CREATE INDEX idx_notifications_user_read_created
ON notifications(user_id, is_read, created_at);
```

Choose indexes based on actual query patterns.

### Repository

```javascript
const {
    Notification
} = require("../../database/models");


class NotificationRepository {

    async findAll(userId, limit, offset) {

        return await Notification.findAndCountAll({

            where: {
                userId
            },

            order: [
                ["createdAt", "DESC"],
                ["id", "DESC"]
            ],

            limit,

            offset

        });

    }


    async getUnreadCount(userId) {

        return await Notification.count({

            where: {

                userId,

                isRead: false

            }

        });

    }


    async markAsRead(id, userId) {

        return await Notification.update(

            {
                isRead: true,
                readAt: new Date()
            },

            {
                where: {
                    id,
                    userId,
                    isRead: false
                }
            }

        );

    }


    async markAllAsRead(userId) {

        return await Notification.update(

            {
                isRead: true,
                readAt: new Date()
            },

            {
                where: {
                    userId,
                    isRead: false
                }
            }

        );

    }

}


module.exports = new NotificationRepository();
```

### Important Ownership Rule

Notice:

```javascript
where: {
    id,
    userId
}
```

We always scope notification operations to the authenticated user's ID.

Otherwise, one user might access another user's notifications by changing the ID.

This is another example of preventing Broken Object Level Authorization (BOLA).

### Controller Example

```javascript
const notificationRepository =
    require("./notification.repository");


class NotificationController {

    async getNotifications(req, res, next) {

        try {

            const userId = req.user.id;

            const limit = Number(req.query.limit) || 10;

            const page = Number(req.query.page) || 1;

            const offset = (page - 1) * limit;


            const result =
                await notificationRepository.findAll(
                    userId,
                    limit,
                    offset
                );


            res.json({

                data: result.rows,

                pagination: {

                    total: result.count,

                    page,

                    limit

                }

            });

        } catch (error) {

            next(error);

        }

    }

}


module.exports = new NotificationController();
```

For production, validate pagination parameters and enforce reasonable maximum limits.

# 24. Email Delivery Problems and Reliability

Sending an email successfully to an SMTP server does not guarantee delivery to the recipient's inbox.

Emails can:

- Be rejected.
- Bounce.
- Be delayed.
- Go to spam.
- Be suppressed by the provider.
- Fail due to invalid recipient addresses.

### Important Concepts

**1. Bounce**

An email cannot be delivered.

**2. Hard Bounce**

A permanent delivery failure, such as an invalid recipient address.

**3. Soft Bounce**

A temporary delivery failure, such as a full mailbox or temporary server problem.

**4. Spam**

The receiving provider classifies an email as unwanted.

**5. Email Suppression**

A provider prevents sending to addresses that previously bounced or unsubscribed, depending on the provider and message type.

### Production Best Practices

- Use a reputable transactional email provider.
- Configure SPF.
- Configure DKIM.
- Configure DMARC.
- Process bounce and complaint webhooks.
- Monitor delivery rates.
- Avoid sending duplicate emails.
- Maintain unsubscribe functionality for applicable marketing messages.
- Use verified sender domains.

### SPF

Sender Policy Framework helps receiving mail servers determine which servers are authorized to send emails for a domain.

### DKIM

DomainKeys Identified Mail adds a cryptographic signature to outgoing messages.

### DMARC

Domain-based Message Authentication, Reporting, and Conformance defines how receiving servers should handle messages that fail SPF/DKIM alignment checks.

These three mechanisms improve email authentication and help protect your domain from spoofing.

# 27. Interview Questions and Answers

### Q1. What is SMTP?

SMTP is a protocol used to send emails between mail clients and mail servers.

### Q2. What is Nodemailer?

Nodemailer is a Node.js library used to send emails through SMTP and supported transport mechanisms.

### Q3. What is a transporter?

A transporter is a configured Nodemailer object responsible for delivering messages.

### Q4. What is the difference between port 465 and 587?

Port 465 generally uses implicit TLS, while port 587 commonly uses STARTTLS for authenticated message submission.

### Q5. What is an HTML email template?

It is an HTML document used to define the visual structure and content of an email.

### Q6. What is email verification?

It is a process that confirms that a user can access a registered email address.

### Q7. Why should verification tokens be hashed?

To reduce the risk of token misuse if the database is compromised.

### Q8. What is a password reset token?

A temporary, single-use credential that authorizes a password reset.

### Q9. What is a transactional email?

An email triggered by a specific application event, such as registration, verification, or password reset.

### Q10. What is a background job?

A task processed asynchronously outside the main HTTP request-response lifecycle.

### Q11. What is a job queue?

A system that stores tasks until workers process them.

### Q12. What is Redis?

Redis is an in-memory data store that supports multiple data structures and is commonly used for caching and job queues.

### Q13. What is BullMQ?

BullMQ is a Node.js job queue library built on Redis.

### Q14. What is a worker?

A worker is a process that retrieves and executes jobs from a queue.

### Q15. What is job retry?

A mechanism that attempts to process a failed job again.

### Q16. What is exponential backoff?

A retry strategy in which the delay between attempts increases exponentially.

### Q17. What is the Transactional Outbox Pattern?

It stores business changes and corresponding events in the same database transaction, allowing another process to publish those events reliably.

### Q18. What is idempotency?

Idempotency means repeating an operation produces the same intended result without causing duplicate effects.

### Q19. What is an in-app notification?

A notification stored in the application and displayed through its user interface.

### Q20. What is a push notification?

A message delivered to a device or browser through a push notification service.

### Q21. What is SPF?

A DNS-based email authentication mechanism that identifies authorized sending servers.

### Q22. What is DKIM?

An email authentication mechanism that uses cryptographic signatures to verify message authenticity and integrity.

### Q23. What is DMARC?

An email authentication policy that uses SPF/DKIM alignment and defines how receiving servers should handle authentication failures.

### Q24. Why should email delivery happen in a background worker?

It prevents slow email delivery from unnecessarily delaying API responses.

### Q25. Can BullMQ guarantee that an email is delivered exactly once?

No. Job processing and external delivery can be repeated. Applications should use idempotency and provider-side deduplication where available.
