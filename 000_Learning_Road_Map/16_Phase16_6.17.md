## 1. Introduction to Containerization

When we develop a Node.js application, it depends on several things:

- Node.js runtime.
- NPM packages.
- MySQL database.
- Redis server.
- Environment variables.
- Operating system libraries.
- Configuration files.

Suppose your application works perfectly on your laptop but fails when deployed to another server.

Why?

Because the server environment may be different.

For example:

| Your Laptop | Production Server |
|---|---|
| Node.js 22 | Node.js 18 |
| MySQL 8.2 | MySQL 5.7 |
| Redis installed | Redis not installed |
| Windows 11 | Ubuntu Linux |
| Different environment variables | Missing configuration |

These differences can create deployment problems.

This is commonly described as:

**"It works on my machine!"**

Containerization helps solve this problem.

### What Is Containerization?

Containerization is a technology that packages an application and its required dependencies into an isolated, portable execution environment called a container.

A container can include:

- Application code.
- Runtime.
- Dependencies.
- Required libraries.
- Configuration.

The container can then run consistently across compatible environments.

### Without Containerization

```text
DEVELOPMENT MACHINE
    |
    +-- Node.js 22
    +-- MySQL 8
    +-- Redis
    +-- Application
    |
    v
Works Successfully


PRODUCTION SERVER
    |
    +-- Node.js 18
    +-- MySQL 5.7
    +-- Redis Missing
    +-- Application
    |
    v
Compatibility Problems
```

### With Containerization

```text
DEVELOPMENT MACHINE
    |
    v
  DOCKER
    |
    v
 APPLICATION CONTAINER
    |
    +-- Node.js
    +-- Dependencies
    +-- Application


PRODUCTION SERVER
    |
    v
  DOCKER
    |
    v
 APPLICATION CONTAINER
    |
    +-- Node.js
    +-- Dependencies
    +-- Application
```

The application environment is packaged into an image, reducing differences between development and production.

# 2. What Is Virtualization?

Before understanding Docker, we should understand virtualization.

### What Is Virtualization?

Virtualization is a technology that allows us to create virtual versions of computing resources.

For example, we can run multiple virtual machines on a single physical computer.

Suppose we have one physical computer:

```text
PHYSICAL COMPUTER
       |
       v
   HYPERVISOR
       |
       +------------------+
       |                  |
       v                  v
  VIRTUAL MACHINE 1  VIRTUAL MACHINE 2
       |                  |
       v                  v
   Ubuntu OS           Windows OS
       |                  |
       v                  v
   Applications        Applications
```

Each virtual machine has its own operating system.

### What Is a Hypervisor?

A hypervisor is software that creates and manages virtual machines.

Examples include:

- VMware.
- VirtualBox.
- Microsoft Hyper-V.

### Why Is Virtualization Useful?

It allows us to:

- Run multiple operating systems.
- Isolate applications.
- Test different environments.
- Allocate computing resources.
- Run separate workloads on one physical machine.

# 3. What Is the Difference Between Virtual Machines and Containers?

This is one of the most important Docker concepts.

Both virtual machines and containers provide isolated environments, but they work differently.

### Virtual Machine Architecture

```text
          PHYSICAL HARDWARE
                  |
                  v
              HYPERVISOR
                  |
          +-------+-------+
          |               |
          v               v
        VM 1             VM 2
          |               |
          v               v
      Guest OS         Guest OS
          |               |
          v               v
     Applications    Applications
```

Each virtual machine has its own guest operating system.

### Container Architecture

```text
          PHYSICAL HARDWARE
                  |
                  v
             HOST OS
                  |
                  v
          CONTAINER RUNTIME
                  |
          +-------+-------+
          |               |
          v               v
      Container 1     Container 2
          |               |
          v               v
      Application     Application
          |               |
          v               v
      Dependencies    Dependencies
```

Containers share the host operating system's kernel while maintaining isolated execution environments.

### Comparison

| Feature | Virtual Machine | Container |
|---|---|---|
| Virtualization | Hardware-level virtualization | OS-level virtualization |
| Operating System | Separate guest OS | Shares host kernel |
| Size | Usually larger | Usually smaller |
| Startup | Generally slower | Generally faster |
| Resource Usage | Generally higher | Generally lower |
| Isolation | Separate guest OS boundary | Process and resource isolation |
| Portability | Depends on VM configuration | Image-based portability |
| Use Case | Running different operating systems | Packaging and deploying applications |

### Example

Suppose you want to run:

1. Node.js backend.
2. MySQL database.
3. Redis server.

With Docker, you can run each service inside its own container.

You do not need to install all these services directly on your operating system.

**Important:** Containers are not completely isolated virtual machines. They share the host kernel, so their security and isolation characteristics are different.

# 5. Understanding Docker Architecture

Docker uses a client-server architecture.

The main components are:

1. Docker Client.
2. Docker Daemon.
3. Docker Images.
4. Docker Containers.
5. Docker Registry.

### Docker Architecture

```text
             DOCKER CLIENT
                  |
                  |
             Docker CLI
                  |
                  v
             DOCKER API
                  |
                  v
             DOCKER DAEMON
                  |
       +----------+----------+
       |          |          |
       v          v          v
    Images    Containers   Networks
                  |
                  v
               Volumes
```

### 5.1 Docker Client

The Docker client is the interface through which we interact with Docker.

Example:

```bash
docker run nginx
```

The Docker CLI sends instructions to the Docker daemon.

### 5.2 Docker Daemon

The Docker daemon manages Docker objects.

It handles operations such as:

- Building images.
- Creating containers.
- Starting containers.
- Stopping containers.
- Managing networks.
- Managing volumes.

### 5.3 Docker Image

An image is a read-only template used to create containers.

Example:

```text
node:22-alpine
mysql:8
redis:7
nginx:alpine
```

### 5.4 Docker Container

A container is a running or stopped instance created from an image.

Example:

```text
Image: node:22-alpine

        |
        v

Container 1
Container 2
Container 3
```

One image can be used to create multiple containers.

### 5.5 Docker Registry

A registry stores and distributes Docker images.

Examples:

- Docker Hub.
- Amazon Elastic Container Registry (ECR).
- GitHub Container Registry.

Docker Hub: [Docker Hub](https://hub.docker.com/?utm_source=chatgpt.com)

# 8. Understanding Docker Containers

A container is created from an image.

Let's run a Node.js container.

```bash
docker run node:22-alpine
```

This starts a container using the Node.js image.

However, the container will exit because no long-running command has been provided.

### Run a Container Interactively

```bash
docker run -it node:22-alpine sh
```

Explanation:

| Option | Meaning |
|---|---|

| `-t` | Allocate a terminal |
| `sh` | Start a shell |

```bash
node --version
```

Exit:

```bash
exit
```

### Run a Container in Background

```bash
docker run -d nginx
```

`-d` means detached mode.

### List Running Containers

# 9. Understanding Docker Container Lifecycle

A container can have different states.

| State | Meaning |
|---|---|
| Created | Container created but not started |
| Running | Container is executing |
| Paused | Container processes are paused |
| Restarting | Container is restarting |
| Exited | Container has stopped |
| Dead | Container failed to reach a usable state |

### Lifecycle Diagram

```text
          docker create
                |
                v
             CREATED
                |
                | docker start
                v
             RUNNING
                |
        +-------+-------+
        |               |
        v               v
     docker stop     docker pause
        |               |
        v               v
      EXITED          PAUSED
                        |
                        | docker unpause
                        v
                     RUNNING
```

A container may also exit because its main process finishes or crashes.

### Important Concept

A Docker container usually runs while its main process is running.

For example:

```bash
docker run node:22-alpine node -e "console.log('Hello')"
```

The command executes and finishes.

Therefore, the container exits after the command completes.

# 10. Understanding Dockerfile

Now we reach one of the most important Docker concepts.

### What Is a Dockerfile?

A Dockerfile is a text file containing instructions used to build a Docker image.

It defines:

- Base image.
- Working directory.
- Dependencies.
- Application files.
- Environment settings.
- Startup command.

### Example

Suppose we have a Node.js application:

```text
expense-tracker/
│
├── package.json
├── package-lock.json
├── src/
│   ├── app.js
│   └── server.js
│
└── Dockerfile
```

Create:

```text
Dockerfile
```

Content:

```dockerfile
FROM node:22-alpine

WORKDIR /app

COPY package*.json ./

RUN npm ci

COPY . .

EXPOSE 5000

CMD ["node", "src/server.js"]
```

Let's understand each instruction.

---

# 11. Dockerfile Instructions

## 11.1 FROM

Defines the base image.

```dockerfile
FROM node:22-alpine
```

This means we are building our image using Node.js 22 on Alpine Linux.

### What Is Alpine Linux?

Alpine is a lightweight Linux distribution.

It is commonly used as a base image for smaller containers.

However, some Node.js packages that depend on native libraries may need additional system dependencies when using Alpine.

For some projects, a Debian-based Node.js image may be easier to work with.

Example:

```dockerfile
FROM node:22-bookworm-slim
```

## 11.2 WORKDIR

Defines the working directory inside the container.

```dockerfile
WORKDIR /app
```

Subsequent commands run relative to `/app`, unless they specify another path.

If the directory does not exist, Docker creates it.

## 11.3 COPY

Copies files from the build context into the image.

```dockerfile
COPY package*.json ./
```

This copies:

- package.json
- package-lock.json

The destination is the current working directory.

## 11.4 RUN

Executes a command during image building.

```dockerfile
RUN npm ci
```

This installs the dependencies defined in the lockfile.

### RUN vs CMD

| RUN | CMD |
|---|---|
| Executes during image building | Defines the default runtime command |
| Creates image layers | Runs when container starts |
| Used for installation and build steps | Used to start the application |

## 11.5 EXPOSE

Documents the port the application is expected to listen on.

```dockerfile
EXPOSE 5000
```

Important: `EXPOSE` does not publish the port to your host machine.

You still need `-p` or Compose port mapping.

## 11.6 CMD

Defines the default command executed when the container starts.

```dockerfile
CMD ["node", "src/server.js"]
```

This is the exec form of CMD.

It is generally preferred for Node.js applications because it handles signals more predictably.

```bash
cd expense-tracker
```

| Part | Meaning |
|---|---|
| `docker build` | Build an image |
| `-t` | Assign an image name/tag |
| `expense-tracker-api` | Image name |

```bash
docker images
```

```text
REPOSITORY             TAG       IMAGE ID
```

### Run Your Image

```bash
docker run -p 5000:5000 expense-tracker-api
```

### What Does `-p` Mean?

```bash
-p 5000:5000
```

The syntax is:

```text
-p HOST_PORT:CONTAINER_PORT
```

So:

```text
Host Port      = 5000
Container Port = 5000
```

You can access the application using:

```text
http://localhost:5000
```

This assumes the Node.js application listens on `0.0.0.0` inside the container.

### Important Node.js Configuration

Make sure your application listens on an appropriate host interface.

Example:

```javascript
httpServer.listen(PORT, "0.0.0.0", () => {

    console.log(`Server running on ${PORT}`);

});
```

If your application binds only to `127.0.0.1` inside the container, external port mapping will not work as expected.

# 13. Understanding Docker Build Context

The build context is the set of files Docker can access during a build.

When you execute:

```bash
docker build -t my-app .
```

The `.` means the current directory is the build context.

Docker makes the context available to the build process.

### Why Does It Matter?

Suppose your project contains:

```text
expense-tracker/
│
├── node_modules/
├── .git/
├── .env
├── package.json
├── package-lock.json
├── src/
└── Dockerfile
```

We generally do not want to send all these files into the build context.

For example:

- `node_modules` can be large.
- `.git` is unnecessary for most builds.
- `.env` may contain secrets.
- Local development files may be unnecessary.

This is where `.dockerignore` helps.

---

# 14. Understanding .dockerignore

A `.dockerignore` file specifies files and directories that should be excluded from the Docker build context.

Create:

```text
.dockerignore
```

Example:

```text
node_modules
npm-debug.log
.git
.gitignore
.env
.env.*
coverage
.DS_Store
```

### Why Is This Important?

1. Reduces build context size.
2. Improves build performance.
3. Prevents unnecessary files from entering images.
4. Reduces accidental secret exposure.
5. Avoids copying local dependencies into the container.

### Important

Do not assume `.dockerignore` is a complete secrets-management solution.

Use environment variables, secret managers, and BuildKit secret mounts for sensitive build-time operations where needed.

# 15. Understanding Docker Port Mapping

A container has its own network environment.

Suppose your Node.js application runs inside a container on port `5000`.

Your host computer cannot automatically access that port unless you publish it.

### Example

```bash
docker run -d -p 8080:5000 expense-tracker-api
```

Here:

```text
Host Port      = 8080
Container Port = 5000
```

You can access:

```text
http://localhost:8080
```

### Port Mapping Diagram

```text
         HOST COMPUTER
              |
              |
        localhost:8080
              |
              v
         DOCKER PORT
              |
              v
       CONTAINER PORT 5000
              |
              v
        NODE.JS SERVER
```

### Multiple Port Mappings

```bash
docker run -d \
  -p 8080:5000 \
  -p 9229:9229 \
  expense-tracker-api
```

This publishes two container ports to the host.

Only publish ports that need to be accessible.

# 16. Understanding Docker Environment Variables

Our Node.js application uses environment variables.

Example:

```env
PORT=5000

DB_HOST=localhost

DB_PORT=3306

DB_NAME=expense_tracker

DB_USER=root

DB_PASSWORD=password
```

Inside Docker, the database host will usually not be `localhost`.

Why?

Because `localhost` inside a container refers to that same container.

It does not refer to another container.

We will solve this using Docker networking.

First, let's understand how to pass environment variables.

### Method 1: Using `-e`

```bash
docker run -d \
  -p 5000:5000 \
  -e PORT=5000 \
  -e NODE_ENV=production \
  expense-tracker-api
```

### Method 2: Using an Environment File

Create:

```text
.env.docker
```

Example:

```env
PORT=5000

NODE_ENV=production

DB_HOST=mysql

DB_PORT=3306

DB_NAME=expense_tracker

DB_USER=app_user

DB_PASSWORD=strong_password
```

Run:

```bash
docker run -d \
  -p 5000:5000 \
  --env-file .env.docker \
  expense-tracker-api
```

### Important

Environment files are useful for configuration, but do not commit files containing real production credentials to Git.

For production, use an appropriate secrets-management solution.

# 17. Understanding Docker Volumes

Containers are designed to be replaceable.

If a container is removed, data stored only in its writable container layer may be lost.

This creates a problem for databases.

Suppose MySQL runs inside a container.

```text
MYSQL CONTAINER
      |
      v
DATABASE FILES
      |
      v
CONTAINER STORAGE
```

If we remove the container, its writable data layer is removed too.

To persist data independently of the container, Docker provides volumes.

### What Is a Docker Volume?

A Docker volume is a persistent storage mechanism managed by Docker.

It allows data to survive container replacement.

### Architecture

```text
       MYSQL CONTAINER
              |
              v
        /var/lib/mysql
              |
              v
         DOCKER VOLUME
              |
              v
        PERSISTENT DATA
```

### Create a Volume

```bash
docker volume create mysql_data
```

### List Volumes

```bash
docker volume ls
```

### Inspect a Volume

```bash
docker volume inspect mysql_data
```

### Remove a Volume

```bash
docker volume rm mysql_data
```

A volume cannot normally be removed while it is in use by a container.

### Run MySQL with a Volume

```bash
docker run -d \
  --name mysql-container \
  -e MYSQL_ROOT_PASSWORD=strong_password \
  -e MYSQL_DATABASE=expense_tracker \
  -v mysql_data:/var/lib/mysql \
  -p 3306:3306 \
  mysql:8
```

Now MySQL data is stored in the `mysql_data` volume.

Removing and recreating the container will not remove the volume.

**Important:** Persistent volumes are not backups. You still need a proper database backup and recovery strategy.

# 18. Understanding Bind Mounts

A bind mount connects a specific directory or file from the host machine to a path inside the container.

Example:

```bash
docker run -d \
  -p 5000:5000 \
  -v "$(pwd)/src:/app/src" \
  expense-tracker-api
```

This maps:

```text
HOST:
project/src

       |
       v

CONTAINER:
/app/src
```

### Volume vs Bind Mount

| Docker Volume | Bind Mount |
|---|---|
| Managed by Docker | Uses a specific host path |
| Good for persistent application data | Good for development file sharing |
| Docker controls storage location | User chooses host path |
| Commonly used for databases | Commonly used for source code |

### Development Use Case

During development, we may want code changes on our laptop to appear inside the container immediately.

Bind mounts help with this.

Example:

```bash
docker run -d \
  -p 5000:5000 \
  -v "$(pwd):/app" \
  expense-tracker-api
```

However, be careful: mounting the entire project over `/app` can hide files that were installed into `/app` during image building.

A common development solution is to mount the source code while preserving container dependencies through a separate volume or another development-specific setup.

# 19. Understanding Docker Networking

Now let's understand an important concept.

Suppose we have three containers:

1. Node.js.
2. MySQL.
3. Redis.

They need to communicate with one another.

How?

Using Docker networking.

### What Is Docker Networking?

Docker networking allows containers to communicate with one another and with external networks.

### Create a Network

```bash
docker network create expense-network
```

### List Networks

```bash
docker network ls
```

### Inspect Network

```bash
docker network inspect expense-network
```

### Run MySQL on the Network

```bash
docker run -d \
  --name mysql \
  --network expense-network \
  -e MYSQL_ROOT_PASSWORD=strong_password \
  -e MYSQL_DATABASE=expense_tracker \
  mysql:8
```

### Run Redis on the Same Network

```bash
docker run -d \
  --name redis \
  --network expense-network \
  redis:7
```

### Run Node.js Application

```bash
docker run -d \
  --name expense-api \
  --network expense-network \
  -p 5000:5000 \
  -e DB_HOST=mysql \
  -e DB_PORT=3306 \
  -e REDIS_HOST=redis \
  expense-tracker-api
```

### Important Concept: Container DNS

Containers connected to the same user-defined Docker network can generally communicate using their container names.

For example:

```env
DB_HOST=mysql

REDIS_HOST=redis
```

The application can connect to:

```text
mysql:3306

redis:6379
```

### Why Not localhost?

Inside the Node.js container:

```text
localhost
```

means the Node.js container itself.

It does not mean the MySQL container.

This is one of the most common Docker networking mistakes.

# 20. Understanding Docker Compose

So far, we have been creating containers using separate commands.

For a real application, this can become complicated.

Suppose we need:

- Node.js API.
- MySQL.
- Redis.
- Background worker.

We need to configure:

- Images.
- Networks.
- Environment variables.
- Ports.

Docker Compose makes this easier.

### What Is Docker Compose?

Docker Compose is a tool used to define and run multi-container applications using a YAML configuration file.

Official documentation: [Docker Compose Documentation](https://docs.docker.com/compose/?utm_source=chatgpt.com)

### Without Docker Compose

We might execute:

```bash
docker network create expense-network
```

```bash
docker run -d mysql:8
```

```bash

```

```bash

```

Each command requires configuration.

### With Docker Compose

We define everything in one file.

```text
docker-compose.yml
```

And run:

```bash
docker compose up -d
```

Docker Compose creates and starts the required services.

# 21. Understanding docker-compose.yml

Let's create a Compose configuration for our Expense Tracker.

Project structure:

```text
expense-tracker/
│
├── src/
│
├── Dockerfile
│
├── .dockerignore
│
├── package.json
│
├── package-lock.json
│
└── compose.yaml
```

Modern Docker documentation commonly uses `compose.yaml`. The older `docker-compose.yml` filename is also supported.

### Example compose.yaml

```yaml
services:

  api:

    build:
      context: .
      dockerfile: Dockerfile

    container_name: expense-api

    ports:
      - "5000:5000"

    environment:
      NODE_ENV: development
      PORT: 5000

      DB_HOST: mysql
      DB_PORT: 3306
      DB_NAME: expense_tracker
      DB_USER: app_user
      DB_PASSWORD: strong_password

      REDIS_HOST: redis
      REDIS_PORT: 6379

    depends_on:
```

Defines the containers that make up the application.

```yaml
services:
  api:
  mysql:
  redis:
```

Each service describes a container or a group of containers.

### `build`

```yaml
build:
  context: .
  dockerfile: Dockerfile
```

This tells Docker Compose to build the API image using the Dockerfile in the current directory.

### `image`

You can use an existing image instead of building one.

Example:

```yaml
image: mysql:8
```

### `ports`

```yaml
ports:
  - "5000:5000"
```

Publishes a container port to the host.

### `environment`

Defines environment variables inside the container.

### `volumes`


Persists MySQL data.

### `depends_on`

Controls service startup order.



Configures the container's restart policy.

# 25. Understanding Docker Multi-Stage Builds

A production image should ideally contain only the files required to run the application.

Suppose our development environment contains:

```text
node_modules
tests
documentation
source files
development dependencies
```

We do not necessarily need all of these in the production image.

This is where multi-stage builds are useful.

### What Is a Multi-Stage Build?

A multi-stage build uses multiple `FROM` instructions in one Dockerfile.

Different stages can be used for:

- Installing dependencies.
- Building the application.
- Creating the final runtime image.

### Example

```dockerfile
# Stage 1: Dependencies

FROM node:22-bookworm-slim AS dependencies

WORKDIR /app

COPY package*.json ./

RUN npm ci


# Stage 2: Production Dependencies

FROM node:22-bookworm-slim AS production-dependencies

WORKDIR /app

COPY package*.json ./

RUN npm ci --omit=dev


# Stage 3: Production Runtime

FROM node:22-bookworm-slim AS production

WORKDIR /app

ENV NODE_ENV=production

COPY --from=production-dependencies \
    /app/node_modules \
    ./node_modules

COPY package*.json ./

COPY src ./src

USER node

EXPOSE 5000

CMD ["node", "src/server.js"]
```

### Understanding the Stages

**Stage 1: Dependencies**

Installs all dependencies, including development dependencies.

**Stage 2: Production Dependencies**

Installs only production dependencies.

**Stage 3: Production Runtime**

Copies only production dependencies and application source code.

The final image does not include the earlier stages' files unless they are explicitly copied.

### Why Use Multi-Stage Builds?

- Smaller final images.
- Fewer unnecessary files.
- Reduced attack surface.
- Better separation between build and runtime environments.

### Important

Our example is suitable for a typical JavaScript application that does not need a separate compilation step.

If you use TypeScript, Next.js, or another build system, you will need an additional build stage and copy the generated output into the runtime stage.

# 26. Understanding CMD vs ENTRYPOINT

Both `CMD` and `ENTRYPOINT` define commands associated with container startup.

### CMD

Defines the default command or arguments.

```dockerfile
CMD ["node", "src/server.js"]
```

You can override it:

```bash
docker run expense-tracker-api node --version
```

### ENTRYPOINT

Defines the main executable.

```dockerfile
ENTRYPOINT ["node"]
```

You can pass arguments:

```bash
docker run expense-tracker-api src/server.js
```

### Comparison

| CMD | ENTRYPOINT |
|---|---|
| Defines default command or arguments | Defines the main executable |
| Easily overridden by runtime command | Usually remains the main executable |
| Often used for default application startup | Often used to define a fixed executable |

### Can We Use Both?

Yes.

Example:

```dockerfile
ENTRYPOINT ["node"]

CMD ["src/server.js"]
```

Default execution:

```bash
node src/server.js
```

If you provide another command argument, it replaces the CMD arguments.

# 27. Docker Image Layers and Caching

Docker images are built using layers.

Each Dockerfile instruction may create a new image layer.

Example:

```dockerfile
FROM node:22-alpine

WORKDIR /app

COPY package*.json ./

RUN npm ci

COPY . .

CMD ["node", "src/server.js"]
```

### Layer Architecture

```text
       FINAL IMAGE
            |
            v
       CMD LAYER
            |
            v
       COPY SOURCE
            |
            v
       NPM INSTALL
            |
            v
       COPY PACKAGE FILES
            |
            v
       NODE BASE IMAGE
```

### Why Does Layer Caching Matter?

Suppose you modify only:

```text
src/controllers/user.controller.js
```

Your dependencies have not changed.

Docker can reuse the cached dependency-installation layer.

It only needs to rebuild the affected later layers.

### Correct Dockerfile Ordering

Prefer:

```dockerfile
COPY package*.json ./

RUN npm ci

COPY . .
```

Instead of:

```dockerfile
COPY . .

RUN npm ci
```

Why?

If you copy the entire project before installing dependencies, every source-code change may invalidate the dependency-installation layer.

The first approach generally produces faster rebuilds.

# 28. Docker Health Checks

A container being in the running state does not necessarily mean that the application is healthy.

For example:

```text
Container: Running

Node.js: Running

MySQL: Connection Failed
```

The application process is alive, but the application cannot perform its intended work.

### What Is a Health Check?

A health check periodically executes a command to evaluate whether a container is functioning correctly.

### Dockerfile Example

```dockerfile
FROM node:22-bookworm-slim

WORKDIR /app

COPY package*.json ./

RUN npm ci --omit=dev

COPY src ./src

EXPOSE 5000

HEALTHCHECK --interval=30s \
    --timeout=5s \
    --start-period=20s \
    --retries=3 \
    CMD node -e "fetch('http://127.0.0.1:5000/health').then(r => process.exit(r.ok ? 0 : 1)).catch(() => process.exit(1))"

CMD ["node", "src/server.js"]
```

This example uses Node.js's built-in `fetch()`.

The application should expose:

```text
GET /health
```

### Health Check Parameters

| Parameter | Meaning |
|---|---|
| `--interval` | Time between checks |
| `--timeout` | Maximum time allowed per check |
| `--start-period` | Initial startup grace period |
| `--retries` | Consecutive failures before unhealthy status |

### Important

A simple health endpoint should not necessarily verify every external dependency.

You may have separate endpoints:

```text
/health       → Process is alive

/ready        → Application can serve requests
```

This distinction is useful in production orchestration systems.

# 30. Docker Security Best Practices

Docker makes deployment easier, but containers still require security controls.

Follow these practices.

### 30.1 Use Official and Trusted Images

Prefer official images and pin specific versions.

Example:

```dockerfile
FROM node:22-bookworm-slim
```

Avoid using an untrusted image simply because it is small.

### 30.2 Avoid Running as Root

Where possible, use a non-root user.

Example:

```dockerfile
USER node
```

Ensure the application has the correct file permissions.

### 30.3 Do Not Store Secrets in Dockerfile

Incorrect:

```dockerfile
ENV DB_PASSWORD=my_password
```

Anyone with access to image metadata may be able to retrieve this information.

Use runtime secrets or a secrets-management solution.

### 30.4 Use .dockerignore

Exclude:

- `.env` files.
- `node_modules`.
- `.git`.
- Temporary files.

### 30.5 Keep Images Updated

Regularly update base images and dependencies.

### 30.6 Avoid Unnecessary Packages

Keep production images minimal.

### 30.7 Limit Exposed Ports

Do not expose MySQL and Redis publicly unless there is a specific requirement.

### 30.8 Use Resource Limits

Limit CPU and memory where appropriate.

### 30.9 Scan Images

Use image scanning tools to identify known vulnerabilities.

### 30.10 Use Read-Only Filesystems Where Practical

For applications that do not need to write to their container filesystem, consider read-only container filesystems and explicitly mounted writable locations.

# 32. Docker Compose vs Kubernetes

You may encounter Kubernetes while learning deployment.

Let's understand the difference.

| Docker Compose | Kubernetes |
|---|---|
| Manages multi-container applications | Orchestrates containerized workloads across a cluster |
| Commonly used for local development | Commonly used for production orchestration |
| Simpler configuration | More extensive configuration |
| Limited built-in orchestration capabilities | Advanced scheduling and orchestration |
| Suitable for small deployments | Suitable for larger distributed deployments |

### What Is Kubernetes?

Kubernetes is an open-source platform used to automate the deployment, scaling, and management of containerized applications.

Official documentation: [Kubernetes Documentation](https://kubernetes.io/docs/home/?utm_source=chatgpt.com)

### When Should You Use Docker Compose?

- Local development.
- Learning Docker.
- Running multiple services on one machine.
- Small application environments.
- Integration testing.

### When Should You Consider Kubernetes?

- Large distributed systems.
- Multiple application replicas.
- Advanced deployment requirements.
- Cluster-level orchestration.
- Automated workload scheduling.

Docker and Kubernetes solve related but different problems. Kubernetes can run containers created from Docker-compatible images without requiring Docker Engine on every node.

# 35. Interview Questions and Answers

### Q1. What is Docker?

Docker is a platform used to build, package, distribute, and run applications inside containers.

### Q2. What is containerization?

Containerization is the process of packaging an application and its dependencies into an isolated execution environment.

### Q3. What is virtualization?

Virtualization allows multiple virtual computing environments to run on shared physical hardware.

### Q4. What is the difference between a VM and a container?

A VM runs its own guest operating system, while a container shares the host kernel and isolates application processes.

### Q5. What is a Docker image?

A read-only template used to create containers.

### Q6. What is a Docker container?

An isolated instance created from a Docker image.

### Q7. What is a Dockerfile?

A text file containing instructions for building a Docker image.

### Q8. What is Docker Hub?

A registry used to store and distribute Docker images.

### Q9. What is Docker Daemon?

A background service that manages Docker objects and operations.

### Q10. What is Docker Compose?

A tool used to define and run multi-container applications through a YAML configuration file.

### Q11. What is a Docker volume?

A Docker-managed persistent storage mechanism.

### Q12. What is a bind mount?

A mechanism that mounts a specific host file or directory inside a container.

### Q13. What is Docker networking?

A system that enables containers to communicate with one another and external networks.

### Q14. Why can't we use localhost to connect to another container?

Because localhost inside a container refers to that same container, not another container.

### Q15. What is a Dockerfile `RUN` instruction?

It executes a command during image building.

### Q16. What is a Dockerfile `CMD` instruction?

It defines the default command executed when a container starts.

### Q17. What is the difference between `RUN` and `CMD`?

RUN executes during image building, while CMD defines the default runtime command.

### Q18. What is `.dockerignore`?

A file that excludes specified files and directories from the Docker build context.

### Q19. What is a multi-stage Docker build?

A build process that uses multiple stages to produce a cleaner and often smaller final image.

### Q20. What is port mapping?

Publishing a container port through a host port.

### Q21. What is a Docker health check?

A mechanism that periodically checks whether a container is functioning correctly.

### Q22. What is the purpose of Docker volumes?

To persist data independently of a container's writable filesystem.

### Q23. What is the difference between Docker Compose and Kubernetes?

Compose defines and runs multi-container applications, while Kubernetes orchestrates containerized workloads across clusters.

### Q24. Why should containers run as non-root users?

To reduce the potential impact of application vulnerabilities and limit privileges.

### Q25. What happens to container data when a container is removed?

Data in the container's writable layer is removed, but data stored in external volumes can persist.
