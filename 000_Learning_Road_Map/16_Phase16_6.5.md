# 3. Understanding the Expense Database Model

Before implementing APIs, let's understand our Expense model.

We previously designed an `expenses` table.

For this implementation, assume it contains:

| Column | Data Type | Description |
|---|---|---|
| id | BIGINT | Primary key |
| user_id | BIGINT | Expense owner |
| category_id | BIGINT | Expense category |
| amount | DECIMAL(12,2) | Expense amount |
| description | VARCHAR(500) | Expense description |
| expense_date | DATE | Date of expense |
| payment_method | VARCHAR(30) | Payment method |
| created_at | DATETIME | Creation timestamp |
| updated_at | DATETIME | Last update timestamp |

Example database record:

```json
{
    "id": "1",
    "userId": "10",
    "categoryId": "3",
    "amount": "1500.00",
    "description": "Monthly groceries",
    "expenseDate": "2026-11-24",
    "paymentMethod": "cash"
}
```

### Important: Why DECIMAL instead of FLOAT?

For financial applications, we should avoid floating-point inaccuracies.

For example:

```javascript
console.log(0.1 + 0.2);
```

Output:

```text
0.30000000000000004
```

This happens because JavaScript uses binary floating-point numbers for ordinary `Number` values.

For financial data, prefer:

```sql
amount DECIMAL(12,2)
```

However, remember that MySQL drivers may return DECIMAL values as strings.

For precise calculations, use a decimal arithmetic library or perform calculations in SQL.

Do not blindly convert financial values to JavaScript floating-point numbers.

# 4. Understanding Sequelize Associations

An expense belongs to a user and a category.

A user can have multiple expenses.

A category can be associated with multiple expenses.

The relationships are:

```text
User
  |
  | 1
  |
  | Many
  |
Expense
  |
  | Many
  |
  | 1
  |
Category
```

### Define associations

In your model association initialization:

```javascript
// User has many expenses

User.hasMany(Expense, {
    foreignKey: "userId",
    as: "expenses"
});

Expense.belongsTo(User, {
    foreignKey: "userId",
    as: "user"
});


// Category has many expenses

Category.hasMany(Expense, {
    foreignKey: "categoryId",
    as: "expenses"
});

Expense.belongsTo(Category, {
    foreignKey: "categoryId",
    as: "category"
});
```

Make sure these associations are initialized before executing queries that use `include`.

### What is Sequelize include?

Suppose we want an expense along with its category information.

Without `include`:

```javascript
const expense = await Expense.findByPk(1);
```

Response:

```json
{
    "id": "1",
    "categoryId": "3",
    "amount": "1500.00",
    "description": "Groceries"
}
```

With `include`:

```javascript
const expense = await Expense.findByPk(1, {
    include: [
        {
            model: Category,
            as: "category"
        }
    ]
});
```

Response:

```json
{
    "id": "1",
    "categoryId": "3",
    "amount": "1500.00",
    "description": "Groceries",
    "category": {
        "id": "3",
        "name": "Food"
    }
}
```

This is called **Eager Loading**.

Instead of retrieving the expense and category separately, Sequelize retrieves the associated data as part of the query.

### 5.1 Create Expense Schema

```javascript
const { z } = require("zod");

const idSchema = z.string().regex(/^[1-9]\d*$/, {
    message: "Invalid ID"
});

const createExpenseSchema = z.object({

    categoryId: idSchema,

    amount: z.string()
        .regex(/^(0|[1-9]\d{0,9})(\.\d{1,2})?$/)
        .refine(value => Number(value) > 0, {
            message: "Amount must be greater than zero"
        }),

    description: z.string()
        .trim()
        .min(2)
        .max(500),

    expenseDate: z.string()
        .date(),

    paymentMethod: z.enum([
        "cash",
        "card",
        "upi",
        "bank_transfer",
        "other"
    ])

}).strict();
```

### Why accept amount as a string?

Because we are dealing with financial data.

Accepting the amount as a decimal string avoids unnecessary JavaScript floating-point conversions.

Example request:

```json
{
    "categoryId": "3",
    "amount": "1500.50",
    "description": "Monthly groceries",
    "expenseDate": "2026-11-24",
    "paymentMethod": "upi"
}
```

### 5.2 Update Expense Schema

For updates, every field should be optional.

```javascript
const updateExpenseSchema = createExpenseSchema
    .partial()
    .refine(
        data => Object.keys(data).length > 0,
        {
            message: "At least one field must be provided"
        }
    );
```

This supports partial updates.

For example:

```json
{
    "amount": "1800.00"
}
```

Only the amount will be updated.

### 5.3 Expense ID Schema

```javascript
const expenseIdSchema = z.object({

    id: idSchema

});
```

### 5.4 Expense Query Schema

We will support:

- Pagination.
- Search.
- Category filtering.
- Date filtering.
- Amount filtering.
- Sorting.

```javascript
const expenseQuerySchema = z.object({

    page: z.coerce.number()
        .int()
        .min(1)
        .default(1),

    limit: z.coerce.number()
        .int()
        .min(1)
        .max(100)
        .default(10),

    search: z.string()
        .trim()
        .max(100)
        .optional(),

    categoryId: idSchema.optional(),

    startDate: z.string()
        .date()
        .optional(),

    endDate: z.string()
        .date()
        .optional(),

    minAmount: z.string()
        .regex(/^(0|[1-9]\d{0,9})(\.\d{1,2})?$/)
        .optional(),

    maxAmount: z.string()
        .regex(/^(0|[1-9]\d{0,9})(\.\d{1,2})?$/)
        .optional(),

    sortBy: z.enum([
        "expenseDate",
        "amount",
        "createdAt"
    ]).default("expenseDate"),

    sortOrder: z.enum([
        "ASC",
        "DESC"
    ]).default("DESC")

})
.strict()
.refine(
    data => {
        if (data.startDate && data.endDate) {
            return data.startDate <= data.endDate;
        }

        return true;
    },
    {
        message: "Start date cannot be after end date"
    }
)
.refine(
    data => {
        if (data.minAmount && data.maxAmount) {
            return Number(data.minAmount) <= Number(data.maxAmount);
        }

        return true;
    },
    {
        message: "Minimum amount cannot exceed maximum amount"
    }
);
```

Export all schemas:

```javascript
module.exports = {

    createExpenseSchema,
    updateExpenseSchema,
    expenseIdSchema,
    expenseQuerySchema

};
```

**Note:** The date comparison works for validated ISO date strings in `YYYY-MM-DD` format. The amount comparison above is used only for validation; actual financial calculations should use decimal-safe arithmetic.

# 6. Expense Repository

Now we will implement database operations.

Create:

```text
src/modules/expenses/expense.repository.js
```

```javascript
const {
    Op
} = require("sequelize");

const {
    Expense,
    Category
} = require("../../database/models");


class ExpenseRepository {

    // Create expense
    async create(data, transaction = null) {

        return await Expense.create(data, {
            transaction
        });

    }


    // Find expense by ID and owner
    async findById(id, userId) {

        return await Expense.findOne({

            where: {
                id,
                userId
            },

            include: [
                {
                    model: Category,
                    as: "category",
                    attributes: ["id", "name", "type"]
                }
            ]

        });

    }


    // Find all expenses with filters
    async findAll(userId, filters) {

        const {

            page,
            limit,
            search,
            categoryId,
            startDate,
            endDate,
            minAmount,
            maxAmount,
            sortBy,
            sortOrder

        } = filters;


        const where = {

            userId

        };


        // Search by description
        if (search) {

            const escapedSearch = search.replace(
                /[\\%_]/g,
                "\\$&"
            );

            where.description = {
                [Op.like]: `%${escapedSearch}%`
            };

        }


        // Category filter
        if (categoryId) {

            where.categoryId = categoryId;

        }


        // Date filter
        if (startDate || endDate) {

            where.expenseDate = {};

            if (startDate) {

                where.expenseDate[Op.gte] = startDate;

            }

            if (endDate) {

                where.expenseDate[Op.lte] = endDate;

            }

        }


        // Amount filter
        if (minAmount || maxAmount) {

            where.amount = {};

            if (minAmount) {

                where.amount[Op.gte] = minAmount;

            }

            if (maxAmount) {

                where.amount[Op.lte] = maxAmount;

            }

        }


        const offset = (page - 1) * limit;


        const result = await Expense.findAndCountAll({

            where,

            include: [
                {
                    model: Category,
                    as: "category",
                    attributes: ["id", "name", "type"]
                }
            ],

            limit,

            offset,

            order: [
                [sortBy, sortOrder],
                ["id", "DESC"]
            ]

        });


        return result;

    }


    // Update expense
    async update(id, userId, data, transaction = null) {

        const [updatedRows] = await Expense.update(data, {

            where: {
                id,
                userId
            },

            transaction

        });

        return updatedRows;

    }


    // Delete expense
    async delete(id, userId, transaction = null) {

        return await Expense.destroy({

            where: {
                id,
                userId
            },

            transaction

        });

    }


}

module.exports = new ExpenseRepository();
```

## Important Concepts

### 6.1 Why do we use `userId` in every query?

Consider:

```javascript
await Expense.findByPk(expenseId);
```

This only checks whether an expense exists.

It does not verify who owns it.

Instead:

```javascript
await Expense.findOne({

    where: {
        id: expenseId,
        userId: authenticatedUserId
    }

});
```

Now the database only returns the expense if both conditions match.

This is an important defense against BOLA/IDOR vulnerabilities.

### 6.2 What is Op.gte and Op.lte?

Sequelize provides operators for SQL comparison conditions.

| Operator | Meaning | SQL |
|---|---|---|
| Op.eq | Equal | = |
| Op.ne | Not equal | != |
| Op.gt | Greater than | > |
| Op.gte | Greater than or equal | >= |
| Op.lt | Less than | < |
| Op.lte | Less than or equal | <= |
| Op.in | Matches values in a list | IN |
| Op.like | Pattern matching | LIKE |
| Op.between | Between two values | BETWEEN |

Example:

```javascript
where: {
    amount: {
        [Op.gte]: "500",
        [Op.lte]: "2000"
    }
}
```

Equivalent SQL:

```sql
SELECT *
FROM expenses
WHERE amount >= 500
  AND amount <= 2000;
```

### 6.3 Why do we whitelist sorting fields?

Never directly accept arbitrary SQL column names from users.

Our validation only allows:

```javascript
sortBy: z.enum([
    "expenseDate",
    "amount",
    "createdAt"
])
```

This prevents users from requesting unexpected sorting expressions or fields.

# 7. Expense Service

The service layer contains the business rules.

For example, before creating an expense, we must verify that the selected category:

1. Exists.
2. Belongs to the logged-in user or is a global category.
3. Has the correct type: `expense`.

A user must not be able to assign an income category to an expense.

Create:

```text
src/modules/expenses/expense.service.js
```

```javascript
const expenseRepository = require("./expense.repository");

const {
    Category
} = require("../../database/models");

const ApiError = require("../../utils/ApiError");


class ExpenseService {


    // Validate category
    async validateCategory(categoryId, userId) {

        const category = await Category.findOne({

            where: {

                id: categoryId,

                type: "expense",

                [require("sequelize").Op.or]: [
                    { userId },
                    { userId: null }
                ]

            }

        });


        if (!category) {

            throw new ApiError(
                400,
                "Invalid expense category"
            );

        }

        return category;

    }


    // Create expense
    async createExpense(userId, data) {

        await this.validateCategory(
            data.categoryId,
            userId
        );


        const expense = await expenseRepository.create({

            userId,

            categoryId: data.categoryId,

            amount: data.amount,

            description: data.description,

            expenseDate: data.expenseDate,

            paymentMethod: data.paymentMethod

        });


        return await expenseRepository.findById(
            expense.id,
            userId
        );

    }


    // Get all expenses
    async getAllExpenses(userId, filters) {

        const result = await expenseRepository.findAll(
            userId,
            filters
        );


        const totalPages = Math.ceil(
            result.count / filters.limit
        );


        return {

            expenses: result.rows,

            pagination: {

                totalRecords: result.count,

                currentPage: filters.page,

                limit: filters.limit,

                totalPages

            }

        };

    }


    // Get expense by ID
    async getExpenseById(expenseId, userId) {

        const expense = await expenseRepository.findById(
            expenseId,
            userId
        );


        if (!expense) {

            throw new ApiError(
                404,
                "Expense not found"
            );

        }


        return expense;

    }


    // Update expense
    async updateExpense(expenseId, userId, data) {

        const existingExpense =
            await expenseRepository.findById(
                expenseId,
                userId
            );


        if (!existingExpense) {

            throw new ApiError(
                404,
                "Expense not found"
            );

        }


        // Validate new category if provided
        if (data.categoryId) {

            await this.validateCategory(
                data.categoryId,
                userId
            );

        }


        await expenseRepository.update(
            expenseId,
            userId,
            data
        );


        return await expenseRepository.findById(
            expenseId,
            userId
        );

    }


    // Delete expense
    async deleteExpense(expenseId, userId) {

        const existingExpense =
            await expenseRepository.findById(
                expenseId,
                userId
            );


        if (!existingExpense) {

            throw new ApiError(
                404,
                "Expense not found"
            );

        }


        await expenseRepository.delete(
            expenseId,
            userId
        );


        return {

            message: "Expense deleted successfully"

        };

    }


}


module.exports = new ExpenseService();
```

### Why do we validate the category?

Suppose the database contains:

| Category ID | User ID | Name | Type |
|---|---:|---|---|
| 1 | NULL | Food | expense |
| 2 | NULL | Salary | income |
| 3 | 10 | Shopping | expense |
| 4 | 20 | Travel | expense |

User 10 can use:

- Category 1: Food.
- Category 3: Shopping.

User 10 cannot use:

- Category 2: Salary, because it is an income category.
- Category 4: Travel, because it belongs to User 20.

This is called **resource ownership validation**.

It is important because a foreign key alone does not enforce the ownership relationship between a user and a category.

```javascript
const expenseService = require("./expense.service");


class ExpenseController {

        const result = await expenseService.getAllExpenses(

        res.status(200).json({

            success: true,

            data: result

        });

    }


    // Get expense by ID
    async getExpenseById(req, res) {

        const expense = await expenseService.getExpenseById(
            req.params.id,
            req.user.id
        );


        res.status(200).json({

            success: true,

            data: expense

        });

    }


    // Update expense
    async updateExpense(req, res) {

        const expense = await expenseService.updateExpense(

            req.params.id,

            req.user.id,

            req.body

        );


        res.status(200).json({

            success: true,

            message: "Expense updated successfully",

            data: expense

        });

    }


    // Delete expense
    async deleteExpense(req, res) {

        const result = await expenseService.deleteExpense(

            req.params.id,

            req.user.id

        );


        res.status(200).json({

            success: true,

            ...result

        });

    }

}


module.exports = new ExpenseController();
```

Notice that we are passing:

```javascript
req.user.id
```

to the service.

Where does `req.user` come from?

It is attached by our authentication middleware after successfully verifying the access token.

For example:

```javascript
req.user = {
    id: "10",
    role: "user"
};
```

We never accept the expense owner's ID directly from the request body.

The authenticated identity determines ownership.

```javascript
const express = require("express");

const router = express.Router();

const expenseController = require("./expense.controller");

const authenticate = require("../../middlewares/authenticate");

const validate = require("../../middlewares/validate");

const asyncHandler = require("../../utils/asyncHandler");

const {

    createExpenseSchema,

    updateExpenseSchema,

    expenseIdSchema,

    expenseQuerySchema

} = require("./expense.validation");


// All expense routes require authentication
router.use(authenticate);


// Create expense
router.post(

    "/",

    validate(createExpenseSchema),

    asyncHandler(expenseController.createExpense)

);


// Get all expenses
router.get(

    "/",

    validate(expenseQuerySchema, "query"),

    asyncHandler(expenseController.getAllExpenses)

);


// Get expense by ID
router.get(

    "/:id",

    validate(expenseIdSchema, "params"),

    asyncHandler(expenseController.getExpenseById)

);


// Update expense
router.patch(

    "/:id",

    validate(expenseIdSchema, "params"),

    validate(updateExpenseSchema),

    asyncHandler(expenseController.updateExpense)

);


// Delete expense
router.delete(

    "/:id",

    validate(expenseIdSchema, "params"),

    asyncHandler(expenseController.deleteExpense)

);


module.exports = router;
```

**Important:** This assumes your `asyncHandler` module exports a function directly. If your implementation exports an object, use the appropriate destructuring import instead.

Also, our `validate()` middleware must support validating `body`, `params`, and `query` separately.

# 12. Advanced Filtering

One of the most important features of a real-world Expense Tracker is filtering.

Let's understand each filter.

## 12.1 Filter by Category

```http
GET /expenses?categoryId=3
```

Returns expenses belonging to category 3.

## 12.2 Filter by Date Range

```http
GET /expenses?startDate=2026-11-01&endDate=2026-11-30
```

Returns expenses between November 1 and November 30, 2026, inclusive.

## 12.3 Filter by Minimum Amount

```http
GET /expenses?minAmount=500
```

Returns expenses with an amount greater than or equal to 500.

## 12.4 Filter by Maximum Amount

```http
GET /expenses?maxAmount=2000
```

Returns expenses with an amount less than or equal to 2,000.

## 12.5 Search by Description

```http
GET /expenses?search=groceries
```

Returns expenses whose descriptions contain the search term.

## 12.6 Sorting

Ascending amount:

```http
GET /expenses?sortBy=amount&sortOrder=ASC
```

Descending amount:

```http
GET /expenses?sortBy=amount&sortOrder=DESC
```

Newest expenses first:

```http
GET /expenses?sortBy=expenseDate&sortOrder=DESC
```

Oldest expenses first:

```http
GET /expenses?sortBy=expenseDate&sortOrder=ASC
```

## 12.7 Pagination

```http
GET /expenses?page=2&limit=10
```

Returns the second page containing 10 records.

## 12.8 Combine Multiple Filters

You can combine filters in one request:

```http
GET /expenses?page=1&limit=10&categoryId=3&startDate=2026-11-01&endDate=2026-11-30&minAmount=500&maxAmount=5000&sortBy=amount&sortOrder=DESC
```

This retrieves:

- Category 3 expenses.
- Between November 1 and November 30.
- Amount between 500 and 5,000.
- Sorted by amount, highest first.
- First 10 matching records.

This is how production REST APIs commonly implement filtering.

# 13. Important Improvements Before Production

Our implementation demonstrates the core architecture, but several improvements are important.

### 13.1 Prevent update/delete race conditions

Our service currently checks whether an expense exists and then updates or deletes it.

Between those two operations, another request could modify or delete the record.

A safer approach is to use the affected-row count:

```javascript
const updatedRows = await expenseRepository.update(
    expenseId,
    userId,
    data
);

if (updatedRows === 0) {
    throw new ApiError(404, "Expense not found");
}
```

The repository update query already includes both `id` and `userId`.

This makes the actual update ownership-safe.

Apply the same principle to deletion:

```javascript
const deletedRows = await expenseRepository.delete(
    expenseId,
    userId
);

if (deletedRows === 0) {
    throw new ApiError(404, "Expense not found");
}
```

### 13.2 Validate category ownership during updates

We already validate the category when `categoryId` is provided.

This is important because a user might attempt to update their expense using another user's category ID.

### 13.3 Database indexes

As our expense table grows, queries can become slower.

Consider these indexes:

```sql
CREATE INDEX idx_expenses_user_date
ON expenses(user_id, expense_date);

CREATE INDEX idx_expenses_user_category
ON expenses(user_id, category_id);

CREATE INDEX idx_expenses_user_amount
ON expenses(user_id, amount);
```

These indexes can help queries that filter by the relevant columns.

However, indexes consume storage and increase write costs. Choose them based on actual query patterns and verify performance using `EXPLAIN`.

### 13.4 Avoid unnecessary database queries

For example, when updating an expense, we currently:

1. Retrieve the expense.
2. Validate the category if necessary.
3. Update the expense.
4. Retrieve the expense again.

This is easy to understand, but it involves multiple queries.

Later, we can optimize this with transactions, conditional updates, and carefully selected queries.

### 13.5 Consider soft deletion

Instead of permanently deleting expenses, we can add:

```sql
deleted_at DATETIME NULL
```

Then:

```javascript
await Expense.update(
    {
        deletedAt: new Date()
    },
    {
        where: {
            id: expenseId,
            userId
        }
    }
);
```

This preserves historical records and makes recovery possible.

Sequelize also supports its built-in paranoid model functionality for soft deletion.

# 14. Important Interview Questions

### Q1. What is CRUD?

CRUD stands for:

- Create
- Read
- Update
- Delete

These are the four fundamental database operations.

### Q2. What is eager loading in Sequelize?

Eager loading retrieves associated model data using Sequelize's `include` option.

### Q3. What is lazy loading?

Lazy loading retrieves associated data only when it is explicitly requested.

### Q4. What is the purpose of Sequelize associations?

Associations define relationships between models and allow Sequelize to retrieve related records.

### Q5. Why should we include userId in expense queries?

To ensure users can only access records they own.

### Q6. What is BOLA?

Broken Object Level Authorization is a security vulnerability where an API does not properly verify access permissions for individual resources.

### Q7. What is the difference between PUT and PATCH?

PUT generally represents replacing a resource, while PATCH represents partially updating a resource.

### Q8. What is pagination?

Pagination divides a large dataset into smaller groups to improve API usability and performance.

### Q9. What is the difference between filtering and sorting?

Filtering determines which records are returned. Sorting determines the order in which those records appear.

### Q10. What is the difference between Op.gt and Op.gte?

`Op.gt` means greater than, while `Op.gte` means greater than or equal to.

### Q11. Why should we use database indexes?

Indexes help databases locate records more efficiently, particularly for frequently executed filtering and lookup queries.

### Q12. What is soft deletion?

Soft deletion marks a record as deleted without physically removing it.

### Q13. Why should we validate category ownership?

To prevent users from assigning expenses to categories belonging to other users.

### Q14. What is the Repository Pattern?

It separates database access logic from business logic.

### Q15. Why should we not accept userId from the request body?

Because the authenticated user's identity should determine resource ownership. Accepting it from the client can enable unauthorized access.
