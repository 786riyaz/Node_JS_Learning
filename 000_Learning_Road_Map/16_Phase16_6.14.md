## 1. Introduction to Real-Time Communication

In traditional web applications, the client sends a request to the server, and the server returns a response.

For example:

1. User opens the expense dashboard.
2. Frontend calls `GET /api/dashboard`.
3. Backend fetches data from MySQL.
4. Backend returns JSON.
5. Frontend displays the dashboard.

But what happens if the dashboard data changes after the page loads?

The frontend does not automatically know about that change.

It must send another request to the server.

This is where **Real-Time Communication** becomes useful.

### What is Real-Time Communication?

Real-time communication allows two or more systems to exchange information with very little delay.

Examples:

- WhatsApp messages.
- Live notifications.
- Online/offline user status.
- Typing indicators.
- Live order tracking.
- Multiplayer games.
- Collaborative editing.
- Live dashboards.

### Traditional Communication

```text
Client                    Server
  |                          |
  |------ HTTP Request ----->|
  |                          |
  |<----- HTTP Response -----|
  |                          |
  |                          |
  |       Connection         |
  |       Completed          |
```

The client must initiate another request to receive updated information.

### Real-Time Communication

```text
Client                    Server
  |                          |
  |------ Connect ---------->|
  |                          |
  |<---- Connection -------->|
  |                          |
  |<----- New Message -------|
  |                          |
  |------ Send Message ----->|
  |                          |
  |<----- Notification ------|
  |                          |
```

The connection remains available for communication in both directions.

# 2. HTTP vs WebSocket

Before learning Socket.IO, we need to understand HTTP and WebSocket.

### HTTP

HTTP is the protocol commonly used for communication between browsers and web servers.

Example:

```javascript
fetch("/api/expenses");
```

The browser sends a request, and the server returns a response.

HTTP traditionally follows a request-response model.

### WebSocket

WebSocket is a communication protocol that provides a persistent, bidirectional connection between a client and server.

Once the connection is established, both sides can send messages without creating a new HTTP request for every message.

### Comparison

| Feature | HTTP | WebSocket |
|---|---|---|
| Communication | Request-response | Bidirectional |
| Connection | Usually short-lived requests | Persistent connection |
| Server can initiate message | Not through the ordinary response flow | Yes |
| Full-duplex communication | No | Yes |
| Typical use | REST APIs | Real-time communication |
| Overhead for repeated messages | Higher due to repeated requests | Lower after connection establishment |

### Example: HTTP Chat Application

Suppose User A sends a message to User B.

```text
User A
   |
   v
POST /api/messages
   |
   v
Backend
   |
   v
Save Message in MySQL
   |
   v
User B must request messages
```

User B may need to poll the server repeatedly.

### Example: WebSocket Chat Application

```text
User A                  Server                  User B
   |                       |                       |
   |---- Send Message ---->|                       |
   |                       |                       |
   |                       |---- New Message ----->|
   |                       |                       |
   |                       |                       |
```

User B receives the message immediately through the existing connection.

# 3. What Is WebSocket Handshake?

A WebSocket connection typically starts with an HTTP handshake.

The client sends an HTTP request containing an upgrade request.

Example:

```http
GET /chat HTTP/1.1
Host: example.com
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Key: abc123
Sec-WebSocket-Version: 13
```

The server responds:

```http
HTTP/1.1 101 Switching Protocols
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Accept: xyz123
```

The status code `101 Switching Protocols` indicates that the server has agreed to switch protocols.

After the handshake, communication continues using the WebSocket protocol.

### Important Terms

| Term | Meaning |
|---|---|
| Handshake | Initial connection negotiation |
| Upgrade | Switching from HTTP to WebSocket |
| Full-duplex | Both sides can communicate independently |
| Persistent connection | Connection remains open until closed |
| Frame | Unit of WebSocket communication |

# 4. What Is Socket.IO?

Socket.IO is a JavaScript library that enables real-time, bidirectional communication between clients and servers.

Official documentation: [Socket.IO Documentation](https://socket.io/docs/v4/?utm_source=chatgpt.com)

Socket.IO is commonly used with:

- Node.js.
- Express.js.
- React.
- Next.js.
- Vue.
- Angular.

### What Does Socket.IO Provide?

1. Real-time event-based communication.
2. Automatic reconnection.
3. Rooms.
4. Namespaces.
5. Broadcasting.
6. Acknowledgements.
7. Connection management.
8. Middleware.
9. Transport fallback.
10. Redis-based scaling.

### Socket.IO vs WebSocket

These are not the same thing.

| WebSocket | Socket.IO |
|---|---|
| Communication protocol | Communication library |
| Provides bidirectional communication | Provides event-based bidirectional communication |
| Does not define rooms | Supports rooms |
| No built-in reconnection API | Supports automatic reconnection |
| Does not provide its own event abstraction | Provides named events |
| Can communicate with standard WebSocket clients | Requires Socket.IO-compatible clients |

**Important:** Socket.IO is not a plain WebSocket implementation. A standard WebSocket client cannot directly communicate with a Socket.IO server.

Socket.IO can use WebSocket as its transport, but it also supports HTTP long-polling and transport upgrades.

# 5. Understanding Socket.IO Architecture

Let's understand how the frontend and backend communicate.

```text
                 REACT APPLICATION
                        |
                        |
                   Socket Client
                        |
                        |
                        v
                  SOCKET CONNECTION
                        |
                        |
                        v
                  NODE.JS SERVER
                        |
                        |
                   Socket.IO
                        |
             +----------+----------+
             |                     |
             v                     v
         Event 1                Event 2
             |                     |
             v                     v
       Message Service       Notification Service
             |                     |
             v                     v
           MySQL                 MySQL
```

### Example

Suppose User A sends a message to User B.

1. User A connects to the Socket.IO server.
2. User B connects to the Socket.IO server.
3. User A emits a `send-message` event.
4. Server receives the event.
5. Server validates the message.
6. Server saves the message in MySQL.
7. Server emits a `new-message` event to User B.
8. User B receives the message immediately.

### Important Architecture Principle

**MySQL stores the actual messages. Socket.IO delivers real-time events.**

Socket.IO should not be treated as a permanent message database.

If a user disconnects, they should still be able to retrieve missed messages from the database when they reconnect.

# 7. Integrating Socket.IO with Express

We previously created:

```text
src/
│
├── app.js
└── server.js
```

Our Express application is created in `app.js`.

The actual HTTP server is started in `server.js`.

Socket.IO needs access to the HTTP server.

Therefore, we should initialize it in `server.js`.

### Step 1: Update server.js

```javascript
require("dotenv").config();

const http = require("http");

const app = require("./app");

const {
    Server
} = require("socket.io");


const PORT = process.env.PORT || 5000;


// Create HTTP Server

const httpServer = http.createServer(app);


// Create Socket.IO Server

const io = new Server(httpServer, {

    cors: {

        origin: process.env.FRONTEND_URL,

        methods: ["GET", "POST"],

        credentials: true

    }

});


// Register Socket.IO Events

io.on("connection", (socket) => {

    console.log("New client connected:", socket.id);


    socket.on("disconnect", (reason) => {

        console.log(
            "Client disconnected:",
            socket.id,
            reason
        );

    });

});


// Start Server

httpServer.listen(PORT, () => {

    console.log(
        `Server running on port ${PORT}`
    );

});
```

### Understanding the Code

#### Create HTTP Server

```javascript
const httpServer = http.createServer(app);
```

Instead of directly calling:

```javascript
app.listen(PORT);
```

We create an HTTP server using Node.js.

#### Initialize Socket.IO

```javascript
const io = new Server(httpServer);
```

Socket.IO attaches itself to the HTTP server.

#### Connection Event

```javascript
io.on("connection", (socket) => {

    console.log(socket.id);

});
```

This event executes whenever a new client successfully connects.

#### Socket ID

Every connected socket gets a unique socket ID.

Example:

```text
socket.id = "abc123xyz"
```

A socket ID identifies a particular connection.

It should not be treated as a permanent user ID because it can change after reconnection.

# 8. Understanding Socket.IO Events

Socket.IO uses an event-based communication model.

An event is an action or occurrence that one side communicates to the other.

Examples:

```text
send-message
new-message
user-online
user-offline
typing
stop-typing
notification
```

### Server-Side Event Listener

```javascript
socket.on("send-message", (data) => {

    console.log(data);

});
```

The server listens for the `send-message` event.

### Client-Side Event Emitter

```javascript
socket.emit("send-message", {

    message: "Hello Server"

});
```

The client emits the event.

### Server-to-Client Event

```javascript
socket.emit("notification", {

    message: "New notification"

});
```

### Client Listener

```javascript
socket.on("notification", (data) => {

    console.log(data);

});
```

### Important Methods

| Method | Purpose |
|---|---|
| `socket.emit()` | Send event to a particular socket |
| `socket.on()` | Listen for an event |
| `io.emit()` | Send event to all connected sockets |
| `socket.broadcast.emit()` | Send event to all other sockets |
| `io.to(room).emit()` | Send event to sockets in a room |
| `socket.join()` | Join a room |
| `socket.leave()` | Leave a room |

# 11. Broadcasting Messages

Sometimes we want to send an event to multiple connected clients.

This is called broadcasting.

### Send to All Connected Clients

```javascript
io.emit("announcement", {

    message: "Server maintenance at 10 PM"

});
```

Every connected client receives the event.

### Send to Everyone Except the Sender

```javascript
socket.broadcast.emit("user-joined", {

    message: "A new user joined"

});
```

The socket that emitted the event does not receive this broadcast.

### Comparison

| Method | Recipients |
|---|---|
| `socket.emit()` | Current socket |
| `io.emit()` | All connected sockets |
| `socket.broadcast.emit()` | All sockets except current socket |
| `io.to(room).emit()` | Sockets in a particular room |
| `socket.to(room).emit()` | Sockets in a room except the sender |

# 12. Understanding Rooms

Rooms are one of the most useful Socket.IO concepts.

A room is a logical group of sockets.

We can send events to all sockets belonging to a particular room.

### Example

Suppose we have three users:

```text
User A
User B
User C
```

User A and User B are discussing a project.

We can create a room:

```text
project-101
```

Both users join that room.

Now we can send a message only to that room.

### Join a Room

```javascript
socket.join("project-101");
```

### Send Message to a Room

```javascript
io.to("project-101").emit("new-message", {

    message: "Hello Project Team"

});
```

All sockets in the room receive the event.

### Leave a Room

```javascript
socket.leave("project-101");
```

### Room Architecture

```text
                 SOCKET.IO SERVER
                         |
                         |
                  project-101
                         |
              +----------+----------+
              |                     |
              v                     v
           User A                User B


                   project-102
                         |
                         |
                         v
                      User C
```

### Important

Rooms exist on the server side.

Clients cannot directly inspect the server's room membership or join arbitrary rooms through the server's internal API.

The server must validate whether a user is allowed to join a particular room.

# 14. Event Acknowledgements

Sometimes the client sends a message and wants confirmation from the server.

For example:

```text
Client sends message
        |
        v
Server validates message
        |
        v
Server saves message
        |
        v
Server confirms success
```

Socket.IO supports acknowledgements.

### Client

```javascript
socket.emit(

    "send-message",

    {
        message: "Hello"
    },

    (response) => {

        console.log(response);

    }

);
```

### Server

```javascript
socket.on("send-message", async (data, callback) => {

    try {

        // Save message

        callback({

            success: true,

            message: "Message sent successfully"

        });

    } catch (error) {

        callback({

            success: false,

            message: "Message sending failed"

        });

    }

});
```

### Acknowledgement with Timeout

Client:

```javascript
socket.timeout(5000).emit(

    "send-message",

    {
        message: "Hello"
    },

    (error, response) => {

        if (error) {

            console.log("Server acknowledgement timeout");

            return;

        }

        console.log(response);

    }

);
```

This waits up to five seconds for an acknowledgement.

### Important

An acknowledgement confirms that the server executed the callback.

It does not automatically guarantee that the data was permanently stored or delivered to another user.

Your server should send a success acknowledgement only after the required database operation succeeds.

# 15. Implementing Authentication in Socket.IO

This is one of the most important parts of a production application.

A user should not be allowed to access private rooms or messages without authentication.

We already implemented JWT authentication in Part 3.

Now we will reuse that architecture.

### Client-Side Authentication

If using an access token:

```javascript
const socket = io(SOCKET_URL, {

    auth: {

        token: accessToken

    }

});
```

The token is sent during the Socket.IO connection handshake.

### Server-Side Authentication Middleware

```javascript
const jwt = require("jsonwebtoken");


io.use((socket, next) => {

    try {

        const token = socket.handshake.auth.token;


        if (!token) {

            return next(
                new Error("Authentication required")
            );

        }


        const decoded = jwt.verify(
            token,
            process.env.JWT_ACCESS_SECRET
        );


        socket.user = {

            id: String(decoded.sub),

            role: decoded.role

        };


        next();

    } catch (error) {

        next(
            new Error("Invalid or expired token")
        );

    }

});
```

### Understanding `io.use()`

```javascript
io.use((socket, next) => {

});
```

This middleware executes when a client attempts to establish a connection.

If authentication succeeds:

```javascript
next();
```

If authentication fails:

```javascript
next(new Error("Authentication failed"));
```

The connection is rejected.

### Access Authenticated User

After authentication:

```javascript
io.on("connection", (socket) => {

    console.log(socket.user.id);

});
```

We can access the authenticated user through:

```javascript
socket.user
```

### Important Security Notes

1. Never trust a user ID sent by the client.
2. Verify JWT signatures and expiration.
3. Use secure transport with HTTPS/WSS in production.
4. Check authorization before joining private rooms.
5. Validate every incoming event payload.
6. Apply rate limits to sensitive events.
7. Handle expired tokens and reconnect authentication.
8. Avoid logging access tokens.

If your application uses HttpOnly cookies instead of a token in the Socket.IO `auth` object, authenticate through the handshake request's cookies. Configure CORS and cookie settings correctly, and consider CSRF protections because browsers may send cookies automatically.

# 17. Building a Real-Time Chat System

Now let's understand how a basic chat system works.

Suppose:

- User A sends a message.
- User B receives it.
- Message is saved in MySQL.

### Communication Flow

```text
User A
  |
  | send-message
  |
  v
Socket.IO Server
  |
  | Validate User
  |
  | Validate Recipient
  |
  | Save Message
  |
  v
MySQL
  |
  | Message Created
  |
  v
User B Private Room
  |
  | new-message
  |
  v
User B
```

### Example Database Table

```sql
CREATE TABLE messages (

    id BIGINT PRIMARY KEY AUTO_INCREMENT,

    sender_id BIGINT NOT NULL,

    receiver_id BIGINT NOT NULL,

    message TEXT NOT NULL,

    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,

    FOREIGN KEY (sender_id)
        REFERENCES users(id),

    FOREIGN KEY (receiver_id)
        REFERENCES users(id)

);
```

For a production group-chat application, you would generally use separate conversations and conversation-members tables instead of relying only on a sender/receiver structure.

### Socket Event

```javascript
socket.on("send-message", async (data, callback) => {

    try {

        const senderId = socket.user.id;

        const receiverId = String(data.receiverId);


        // Validate recipient and conversation permissions


        // Save message in database


        const message = {

            senderId,

            receiverId,

            text: data.message,

            createdAt: new Date()

        };


        // Send message to receiver

        io.to(`user:${receiverId}`).emit(
            "new-message",
            message
        );


        callback({

            success: true,

            data: message

        });

    } catch (error) {

        callback({

            success: false,

            message: "Message could not be sent"

        });

    }

});
```

This is a communication-flow example, not a complete production chat implementation.

Before broadcasting, the backend must validate:

- Recipient existence.
- Conversation membership.
- Message length.
- Message content.
- Sender authorization.

The message should be saved successfully before the server acknowledges it as sent.

### Why Save Messages in MySQL?

Socket.IO delivers messages, but it does not replace permanent storage.

If User B is offline, they should still be able to retrieve the message later through an API.

# 18. Online and Offline User Status

We can also track whether users are connected.

When a user connects:

```javascript
io.on("connection", (socket) => {

    const userId = socket.user.id;


    socket.join(`user:${userId}`);


    socket.broadcast.emit("user-online", {

        userId

    });

});
```

When a user disconnects:

```javascript
socket.on("disconnect", () => {

    const userId = socket.user.id;


    socket.broadcast.emit("user-offline", {

        userId

    });

});
```

However, there is an important problem.

Suppose a user logs in from:

- Laptop.
- Mobile.
- Tablet.

If the laptop disconnects, the user may still be connected from the other two devices.

Therefore, we should not mark the user offline simply because one socket disconnects.

### Better Approach

Track active socket connections per user.

For example:

```text
User 10
  |
  +---- Socket A
  |
  +---- Socket B
  |
  +---- Socket C
```

The user is online if at least one valid connection remains.

In a single-process demonstration, you can track socket counts in memory.

For multiple server instances, use shared presence storage such as Redis, with appropriate expiration and heartbeat handling.

**Production note:** Presence is often eventually consistent. Network failures and abrupt device shutdowns can delay offline detection.

# 20. Handling Disconnections and Reconnection

Network connections are not always reliable.

A user may disconnect because:

- Internet connection drops.
- Browser closes.
- Laptop sleeps.
- Mobile network changes.
- Server restarts.

Socket.IO supports automatic reconnection attempts on the client.

Example:

```javascript
const socket = io(SOCKET_URL, {

    reconnection: true,

    reconnectionAttempts: 5,

    reconnectionDelay: 1000,

    reconnectionDelayMax: 5000

});
```

### Listen for Connection Events

```javascript
socket.on("connect", () => {

    console.log("Connected:", socket.id);

});


socket.on("disconnect", (reason) => {

    console.log("Disconnected:", reason);

});


socket.on("connect_error", (error) => {

    console.error(
        "Connection error:",
        error.message
    );

});
```

### Important

Automatic reconnection does not mean every missed application message is automatically delivered.

If a client disconnects while messages are being sent, it should retrieve missed messages from the database after reconnecting.

For more advanced recovery, Socket.IO supports connection-state recovery in compatible configurations, but it has limitations and should not replace durable message storage.

# 21. Scaling Socket.IO with Redis

Suppose we have two Node.js server instances.

```text
              LOAD BALANCER
                    |
             +------+------+
             |             |
             v             v
          Server A      Server B
             |             |
             v             v
          Socket A      Socket B
```

User A connects to Server A.

User B connects to Server B.

Now User A sends a message to User B.

How does Server A know about the socket connected to Server B?

A normal in-memory Socket.IO room on Server A does not contain Server B's sockets.

This is where the Redis adapter becomes useful.

### What Is the Redis Adapter?

The Socket.IO Redis adapter allows multiple Socket.IO server instances to communicate through Redis Pub/Sub.

Official documentation: [Socket.IO Redis Adapter](https://socket.io/docs/v4/redis-adapter/?utm_source=chatgpt.com)

### Architecture

```text
                REDIS PUB/SUB
                      |
             +--------+--------+
             |                 |
             v                 v
          SERVER A          SERVER B
             |                 |
             v                 v
          SOCKET A          SOCKET B
```

An event emitted from one server can be propagated to relevant sockets connected to another server.

### Installation

```bash
npm install @socket.io/redis-adapter redis
```

### Example Configuration

```javascript
const { Server } = require("socket.io");

const {
    createClient
} = require("redis");

const {
    createAdapter
} = require("@socket.io/redis-adapter");


const io = new Server(httpServer, {

    cors: {

        origin: process.env.FRONTEND_URL,

        credentials: true

    }

});


const pubClient = createClient({

    url: process.env.REDIS_URL

});


const subClient = pubClient.duplicate();


async function initializeSocketAdapter() {

    await Promise.all([

        pubClient.connect(),

        subClient.connect()

    ]);


    io.adapter(
        createAdapter(pubClient, subClient)
    );

}


module.exports = {
    io,
    initializeSocketAdapter,
    pubClient,
    subClient
};
```

Call `initializeSocketAdapter()` and await it before accepting traffic.

### Important

The Redis adapter distributes Socket.IO events across instances.

It does not automatically make every part of your application state shared.

For example:

- In-memory user maps remain local.
- In-memory presence counters remain local.
- Database records still need to be shared.
- Authentication and authorization still need to be implemented.

Also, the Redis adapter uses Pub/Sub. Redis Pub/Sub does not provide durable message storage.

# 22. Sticky Sessions and Load Balancers

Socket.IO may use HTTP long-polling before upgrading to WebSocket.

When using multiple server instances, HTTP long-polling requests belonging to the same session generally need to reach the same server instance.

This is why load-balancer configuration matters.

### Sticky Sessions

Sticky sessions help ensure that requests belonging to a particular client session are routed consistently to the same server instance.

### Important Distinction

| Requirement | Solution |
|---|---|
| Broadcast events across servers | Redis adapter |
| Route polling requests consistently | Sticky sessions |
| Durable message storage | MySQL or another database |
| Shared online status | Redis or another shared store |
| Authentication | JWT/session middleware |

The Redis adapter alone does not solve every scaling problem.

If you configure Socket.IO for WebSocket-only transport, the polling sticky-session requirement changes, but you lose HTTP long-polling fallback.

# 23. Security Best Practices

Real-time applications require security at both the connection and event levels.

### 23.1 Authenticate Connections

Use JWT or session authentication.

### 23.2 Authorize Every Private Action

A connected user should not automatically have access to every room.

### 23.3 Validate Event Payloads

Never trust client-supplied data.

Example:

```javascript
socket.on("send-message", async (data) => {

    // Validate using Zod or another schema validator

});
```

### 23.4 Rate Limit Events

Prevent users from sending thousands of events within seconds.

### 23.5 Limit Message Size

Set reasonable maximum message lengths.

### 23.6 Use HTTPS/WSS

Protect communication in transit.

### 23.7 Prevent Room Enumeration

Do not allow users to join arbitrary private rooms.

### 23.8 Handle Expired Tokens

Reject new connections with expired tokens and implement an appropriate reauthentication flow.

### 23.9 Protect Against Cross-Site WebSocket Hijacking

If authentication relies on cookies, validate the request origin and implement appropriate CSRF protections.

### 23.10 Avoid Sensitive Logs

Do not log:

- JWT tokens.
- Passwords.
- Private messages unnecessarily.
- Session secrets.

# 24. Socket.IO vs REST API

You might be wondering:

Should we use Socket.IO instead of REST APIs?

No. They solve different problems and work well together.

| REST API | Socket.IO |
|---|---|
| Request-response communication | Real-time event communication |
| Fetch user profile | Receive live notification |
| Create expense | Receive expense update |
| Get message history | Receive new messages |
| Update profile | Receive online status |
| Upload receipt | Notify when processing completes |

### Recommended Architecture

Use REST APIs for:

- Login and registration.
- CRUD operations.
- Fetching historical data.
- Searching and filtering.
- File uploads.
- Report downloads.

Use Socket.IO for:

- Real-time notifications.
- Chat messages.
- Typing indicators.
- Online/offline status.
- Live dashboard updates.

**Remember:** Socket.IO complements REST APIs; it does not replace them.

# 26. Common Socket.IO Mistakes

| Mistake | Why It Is a Problem |
|---|---|
| Using `app.listen()` instead of attaching Socket.IO to an HTTP server | Socket.IO is not attached to the intended server |
| Treating socket ID as user ID | Socket IDs are temporary |
| Trusting client-supplied user IDs | Can expose private data |
| Not validating room membership | Unauthorized users may receive private events |
| Not storing messages in a database | Messages may be lost when users disconnect |
| Emitting before saving the message | Clients may receive data that was not persisted |
| Not handling reconnection | Users may remain disconnected |
| Using only in-memory state in a multi-server setup | Different servers have inconsistent state |
| Assuming Redis adapter provides message persistence | Pub/Sub is not durable storage |
| Sending too many events | Can overload clients and servers |
| Not removing event listeners in React | Can create duplicate event handling |

# 28. Interview Questions and Answers

### Q1. What is real-time communication?

Communication in which information is exchanged with very little delay.

### Q2. What is WebSocket?

A communication protocol that provides persistent, bidirectional communication between clients and servers.

### Q3. What is Socket.IO?

A JavaScript library for event-based, bidirectional real-time communication.

### Q4. Is Socket.IO the same as WebSocket?

No. WebSocket is a protocol, while Socket.IO is a higher-level communication library.

### Q5. What is a WebSocket handshake?

The initial HTTP upgrade negotiation used to establish a WebSocket connection.

### Q6. What is a Socket.IO event?

A named event used to communicate information between a client and server.

### Q7. What is broadcasting?

Sending an event to multiple connected clients.

### Q8. What is a Socket.IO room?

A server-side grouping of sockets that allows targeted event delivery.

### Q9. What is a namespace?

A logical communication endpoint that separates different parts of a Socket.IO application.

### Q10. What is the difference between rooms and namespaces?

Namespaces separate communication endpoints, while rooms group sockets within a namespace.

### Q11. What is an acknowledgement?

A callback-based mechanism that allows the sender to receive confirmation from the receiver.

### Q12. How do you authenticate Socket.IO connections?

By validating a JWT or session during the connection handshake using Socket.IO middleware.

### Q13. What is a private user room?

A room associated with an authenticated user, used to deliver events to that user's active connections.

### Q14. How do you implement online/offline status?

Track active socket connections per user and determine presence based on whether valid connections remain.

### Q15. What is the Redis adapter?

A Socket.IO adapter that enables communication between multiple Socket.IO server instances through Redis Pub/Sub.

### Q16. Does the Redis adapter store messages permanently?

No. It distributes events but does not provide durable message storage.

### Q17. What are sticky sessions?

A load-balancer technique that consistently routes requests from the same session to the same server instance.

### Q18. Why do we need REST APIs with Socket.IO?

REST APIs are useful for CRUD operations and historical data, while Socket.IO handles real-time updates.

### Q19. What happens when a Socket.IO client disconnects?

The server detects the disconnection, and the client may attempt automatic reconnection.

### Q20. Does Socket.IO guarantee delivery of every message?

No. Applications need appropriate acknowledgements, persistence, recovery, and retry strategies.
