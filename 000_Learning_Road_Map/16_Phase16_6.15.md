- E-commerce applications.

A payment gateway is a service that facilitates online payment processing between a customer, a merchant, and the payment infrastructure.

# 3. Important Payment Gateway Terminology

Before writing code, understand these concepts.

| Term | Meaning |
|---|---|
| Merchant | Business accepting payments |
| Customer | Person making the payment |
| Payment Gateway | Service facilitating payment processing |
| Payment Order | Gateway-side record representing a payment request |
| Payment ID | Unique identifier of a payment attempt |
| Order ID | Identifier of a payment order |
| Transaction | Financial operation associated with a payment |
| Capture | Finalizing an authorized payment |
| Refund | Returning money to the customer |
| Webhook | Server-to-server event notification |
| Settlement | Transfer of collected funds to the merchant |
| Signature | Cryptographic proof used to verify authenticity |
| Idempotency | Preventing duplicate processing of the same operation |

### Order ID vs Payment ID

These are different.

**Order ID:**

Identifies the order created for collecting a payment.

**Payment ID:**

Identifies an individual payment attempt associated with that order.

One order may have multiple payment attempts.

For example:

```text
Order: order_123
   |
   +---- Payment Attempt 1: Failed
   |
   +---- Payment Attempt 2: Failed
   |
   +---- Payment Attempt 3: Successful
```

Do not assume one order always has exactly one payment attempt.

# 4. Understanding Payment States

A payment does not necessarily become successful immediately.

It can move through different states.

### Typical Payment Lifecycle

```text
            CREATED
                |
                v
           PAYMENT INITIATED
                |
                v
           AUTHORIZATION
                |
          +-----+------+
          |            |
          v            v
      AUTHORIZED     FAILED
          |
          v
        CAPTURED
          |
          v
       SUCCESSFUL
```

This is a simplified conceptual flow. Actual gateway states and transitions depend on the payment method and gateway.

### Common Payment States

| Status | Meaning |
|---|---|
| created | Payment order or request created |
| pending | Payment processing is incomplete |
| authorized | Payment authorized |
| captured | Payment captured |
| failed | Payment attempt failed |
| refunded | Refund completed |
| partially_refunded | Part of the payment refunded |

### Authorized vs Captured

These are important differences.

**Authorized:**

The payment has been approved, but the funds may not yet have been captured.

**Captured:**

The payment has been finalized for collection.

Depending on gateway configuration, payments may be automatically captured or require explicit capture.

# 9. Understanding Razorpay Orders

Before collecting a payment, the backend creates an order through Razorpay.

Example:

```javascript
const order = await razorpay.orders.create({

    amount: 49900,

    currency: "INR",

    receipt: "receipt_001"

});
```

### Important: Amount Is in Paise

Razorpay expects the amount in the smallest currency unit for INR.

```text
₹1 = 100 Paise
```

Therefore:

| Amount | Value to Send |
|---|---:|
| ₹1 | 100 |
| ₹10 | 1000 |
| ₹100 | 10000 |
| ₹499 | 49900 |
| ₹999 | 99900 |
| ₹1500 | 150000 |

### Why Does Razorpay Use Paise?

Using integer minor units avoids many floating-point precision problems.

For example:

```javascript
const amount = 499 * 100;
```

Result:

```text
49900
```

For arbitrary decimal calculations, use a decimal arithmetic library and convert to an integer minor-unit amount carefully.

# 10. Database Design for Payments

Before implementing payment APIs, we need appropriate database tables.

For our subscription system, we will use three tables:

1. `payment_orders`
2. `payments`
3. `subscriptions`

### 10.1 Payment Orders Table

This stores our internal payment order records.

```sql
CREATE TABLE payment_orders (

    id BIGINT PRIMARY KEY AUTO_INCREMENT,

    user_id BIGINT NOT NULL,

    gateway_order_id VARCHAR(100) NOT NULL UNIQUE,

    amount DECIMAL(12,2) NOT NULL,

    currency VARCHAR(10) NOT NULL DEFAULT 'INR',

    status VARCHAR(30) NOT NULL DEFAULT 'created',

    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,

    updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
        ON UPDATE CURRENT_TIMESTAMP,

    FOREIGN KEY (user_id)
        REFERENCES users(id)

);
```

### 10.2 Payments Table

This stores individual payment attempts.

```sql
CREATE TABLE payments (

    id BIGINT PRIMARY KEY AUTO_INCREMENT,

    payment_order_id BIGINT NOT NULL,

    gateway_payment_id VARCHAR(100) NOT NULL UNIQUE,

    method VARCHAR(50),

    amount DECIMAL(12,2) NOT NULL,

    currency VARCHAR(10) NOT NULL,

    status VARCHAR(30) NOT NULL,

    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,

    updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
        ON UPDATE CURRENT_TIMESTAMP,

    FOREIGN KEY (payment_order_id)
        REFERENCES payment_orders(id)

);
```

### 10.3 Subscriptions Table

```sql
CREATE TABLE subscriptions (

    id BIGINT PRIMARY KEY AUTO_INCREMENT,

    user_id BIGINT NOT NULL,

    plan_name VARCHAR(100) NOT NULL,

    status VARCHAR(30) NOT NULL,

    start_date DATETIME NOT NULL,

    end_date DATETIME NOT NULL,

    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,

    updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
        ON UPDATE CURRENT_TIMESTAMP,

    FOREIGN KEY (user_id)
        REFERENCES users(id)

);
```

### Why Separate These Tables?

Because orders, payment attempts, and subscriptions represent different business entities.

| Table | Responsibility |
|---|---|
| payment_orders | Tracks the payment order |
| payments | Tracks individual payment attempts |
| subscriptions | Tracks the user's subscription |

A payment order may have multiple payment attempts.

A successful payment may activate a subscription.

Keeping these records separate makes the system easier to maintain.

### Additional Production Fields

A production payment system may also need:

- Internal idempotency keys.
- Gateway receipt references.
- Refund records.
- Webhook event IDs.
- Failure reasons.
- Captured timestamps.
- Subscription renewal information.
- Audit history.

We will introduce some of these concepts later in this lesson.

# 14. Understanding Payment Signature Verification

This is one of the most important security steps.

After a successful checkout flow, Razorpay returns information such as:

```json
{
    "razorpay_payment_id": "pay_abc123",
    "razorpay_order_id": "order_abc123",
    "razorpay_signature": "generated_signature"
}
```

The backend must verify that the signature is valid.

### What Is HMAC?

HMAC stands for:

**Hash-based Message Authentication Code.**

It uses:

- A cryptographic hash function.
- A secret key.
- A message.

It helps verify message authenticity and integrity.

### Razorpay Payment Signature Formula

For standard Razorpay order-based payment verification:

```text
HMAC-SHA256(
    order_id + "|" + payment_id,
    key_secret
)
```

The backend calculates the signature independently and compares it with the signature returned by Razorpay Checkout.

### Node.js Implementation

```javascript
const crypto = require("crypto");


function verifyPaymentSignature({

    orderId,

    paymentId,

    signature

}) {

    const body = `${orderId}|${paymentId}`;


    const expectedSignature = crypto

        .createHmac(
            "sha256",
            process.env.RAZORPAY_KEY_SECRET
        )

        .update(body)

        .digest("hex");


    const expectedBuffer = Buffer.from(
        expectedSignature,
        "hex"
    );


    const receivedBuffer = Buffer.from(
        signature,
        "hex"
    );


    if (
        expectedBuffer.length !== receivedBuffer.length
    ) {

        return false;

    }


    return crypto.timingSafeEqual(
        expectedBuffer,
        receivedBuffer
    );

}


module.exports = verifyPaymentSignature;
```

### Why Use `timingSafeEqual()`?

A normal string comparison can theoretically expose timing differences.

`crypto.timingSafeEqual()` is designed for constant-time comparison of equal-length buffers.

### Important

The backend must use the order ID associated with the authenticated user's stored payment order.

Do not trust an arbitrary order ID supplied by the frontend without checking ownership.

```json
    }
```

### Service

```javascript
const razorpay = require("../../config/razorpay");

const verifyPaymentSignature =
    require("./verify-payment-signature");


async function verifyPayment({

    userId,

    orderId,

    paymentId,

    signature

}) {

    // Step 1: Find internal order

    const paymentOrder =
        await paymentRepository.findByGatewayOrderId(
            orderId
        );


    if (!paymentOrder) {

        throw new Error("Payment order not found");

    }


    // Step 2: Verify ownership

    if (String(paymentOrder.userId) !== String(userId)) {

        throw new Error("Unauthorized payment order");

    }


    // Step 3: Verify signature

    const valid = verifyPaymentSignature({

        orderId,

        paymentId,

        signature

    });


    if (!valid) {

        throw new Error("Invalid payment signature");

    }


    // Step 4: Fetch payment from Razorpay

    const gatewayPayment =
        await razorpay.payments.fetch(paymentId);


    // Step 5: Validate gateway information

    if (gatewayPayment.order_id !== orderId) {

        throw new Error("Payment order mismatch");

    }


    if (
        gatewayPayment.status !== "captured"
    ) {

        throw new Error("Payment is not captured");

    }


    // Step 6: Verify amount and currency

    if (
        gatewayPayment.amount !==
        convertToPaise(paymentOrder.amount)
    ) {

        throw new Error("Payment amount mismatch");

    }


    if (
        gatewayPayment.currency !==
        paymentOrder.currency
    ) {

        throw new Error("Payment currency mismatch");

    }


    // Step 7: Update payment and activate subscription
    // Use a database transaction and idempotent processing.


    return {

        paymentId,

        status: "captured"

    };

}
```

This is an architectural example. The `paymentRepository` and `convertToPaise()` functions must be implemented, and the final database updates must be atomic.

### Important: Authorization vs Capture

Do not activate a paid subscription merely because a payment is authorized.

For a subscription activation workflow based on a captured one-time payment, verify the captured status.

If you use automatic capture, ensure the capture has actually completed before activating the subscription.

# 16. Updating Payment Records Safely

After payment verification, we need to update MySQL.

The important operations are:

1. Create or update payment record.
2. Mark the order as paid.
3. Activate the subscription.

These operations should happen within a single database transaction.

### Example

```javascript
await sequelize.transaction(async (transaction) => {

    const paymentOrder = await PaymentOrder.findOne({

        where: {

            gatewayOrderId: orderId

        },

        transaction,

        lock: transaction.LOCK.UPDATE

    });


    if (!paymentOrder) {

        throw new Error("Order not found");

    }


    if (paymentOrder.status === "paid") {

        return;

    }


    if (paymentOrder.status !== "created") {

        throw new Error("Invalid order state");

    }


    await Payment.create({

        paymentOrderId: paymentOrder.id,

        gatewayPaymentId: paymentId,

        amount: paymentOrder.amount,

        currency: paymentOrder.currency,

        status: "captured"

    }, {

        transaction

    });


    await paymentOrder.update({

        status: "paid"

    }, {

        transaction

    });


    await Subscription.create({

        userId: paymentOrder.userId,

        planName: paymentOrder.planName,

        status: "active",

        startDate: new Date(),

        endDate: calculateEndDate(
            paymentOrder.durationDays
        )

    }, {

        transaction

    });

});
```

### Why Use a Transaction?

Suppose payment is recorded successfully, but subscription activation fails.

Without a database transaction, we may end up with inconsistent data.

A transaction ensures that the related database changes either all commit or all roll back.

### Important Production Improvements

The example above is simplified.

A production implementation should also:

- Enforce unique gateway payment IDs.
- Prevent multiple subscription activations for the same order.
- Lock the order while processing.
- Handle concurrent verification requests.
- Use an explicit payment state machine.
- Store the gateway's payment method and timestamps.
- Use a unique constraint or idempotency record to prevent duplicate processing.

# 17. What Are Webhooks?

This is another very important concept.

Suppose the user completes payment, but closes the browser before the frontend receives the response.

What happens?

Your frontend may never call the verification API.

But the payment gateway may have successfully processed the payment.

How will your backend know?

This is where **Webhooks** are useful.

### What Is a Webhook?

A webhook is an HTTP callback sent by one system to another when a particular event occurs.

For example:

```text
Razorpay
   |
   | Payment Captured
   |
   v
POST /api/payments/webhook
   |
   v
Node.js Backend
   |
   v
Verify Webhook Signature
   |
   v
Update MySQL
   |
   v
Activate Subscription
```

### Common Payment Webhook Events

Examples include:

| Event | Meaning |
|---|---|
| `payment.authorized` | Payment authorized |
| `payment.captured` | Payment captured |
| `payment.failed` | Payment failed |
| `refund.created` | Refund created |
| `refund.processed` | Refund processed |
| `order.paid` | Order paid |

The exact event names and payloads depend on the gateway.

### Why Are Webhooks Important?

They help the backend receive payment updates independently of the browser.

Use cases:

- Payment confirmation.
- Payment failure.
- Refund confirmation.
- Subscription renewal.
- Dispute notifications.
- Settlement updates.

---

# 18. Understanding Webhook Signature Verification

A webhook endpoint must verify that the incoming request actually originated from Razorpay.

Otherwise, an attacker could send a fake request:

```http
POST /api/payments/webhook
```

```json
{
    "event": "payment.captured",
    "payment_id": "fake_payment"
}
```

If the backend trusts this request, an attacker might activate subscriptions without paying.

### Webhook Secret

Razorpay provides a webhook secret configured for your webhook endpoint.

Store it separately:

```env
RAZORPAY_WEBHOOK_SECRET=your_webhook_secret
```

This is not necessarily the same as your API Key Secret.

### Signature Formula

Razorpay webhook signatures are generated using:

```text
HMAC-SHA256(
    raw_request_body,
    webhook_secret
)
```

The signature is sent in the:

```text
X-Razorpay-Signature
```

header.

### Node.js Implementation

```javascript
const crypto = require("crypto");


function verifyWebhookSignature(
    rawBody,
    receivedSignature
) {

    const expectedSignature = crypto

        .createHmac(

            "sha256",

            process.env.RAZORPAY_WEBHOOK_SECRET

        )

        .update(rawBody)

        .digest("hex");


    const expectedBuffer = Buffer.from(
        expectedSignature,
        "hex"
    );


    const receivedBuffer = Buffer.from(
        receivedSignature || "",
        "hex"
    );


    if (
        expectedBuffer.length !== receivedBuffer.length
    ) {

        return false;

    }


    return crypto.timingSafeEqual(

        expectedBuffer,

        receivedBuffer

    );

}


module.exports = verifyWebhookSignature;
```

### Important Difference

Payment signature verification and webhook signature verification use different messages and secrets.

| Verification | Message | Secret |
|---|---|---|
| Checkout payment | `order_id + "|" + payment_id` | Razorpay Key Secret |
| Webhook | Raw HTTP request body | Razorpay Webhook Secret |

Never use one verification formula for both.

# 19. Preserving the Raw Webhook Body

This is one of the most common mistakes when integrating payment webhooks.

Razorpay webhook signature verification requires the original raw request body.

But Express commonly uses:

```javascript
app.use(express.json());
```

This parses the JSON body.

If we stringify the parsed JSON again, we may get a different byte sequence.

For example:

Original body:

```json
{"amount":49900,"currency":"INR"}
```

Re-serialized body:

```json
{
  "amount": 49900,
  "currency": "INR"
}
```

These are semantically equivalent JSON objects, but their byte representations differ.

The HMAC will therefore differ.

### Correct Express Configuration

For the webhook route, preserve the raw body.

```javascript
const express = require("express");

const app = express();


app.post(

    "/api/payments/webhook",

    express.raw({

        type: "application/json"

    }),

    paymentWebhookController

);


app.use(express.json());
```

The webhook route must be registered before the general JSON middleware.

### Why?

The raw middleware provides a Buffer containing the original request body.

This Buffer is used for signature verification.

Create:

```javascript
const verifyWebhookSignature =
    require("./verify-webhook-signature");


async function handleWebhook(req, res, next) {

            req.headers["x-razorpay-signature"];

    }

}

```

# 21. Webhook Idempotency

Payment gateways may send the same webhook more than once.

For example:

```text
payment.captured
       |
       v
Webhook received
       |
       v
Database updated
       |
       v
Server response lost
       |
       v
Webhook delivered again
```

If we process the same event twice, we may accidentally activate the subscription twice.

This is why webhook idempotency is important.

### Create Webhook Events Table

```sql
CREATE TABLE webhook_events (

    id BIGINT PRIMARY KEY AUTO_INCREMENT,

    gateway_event_id VARCHAR(150) NOT NULL UNIQUE,

    event_type VARCHAR(100) NOT NULL,

    processed_at DATETIME NULL,

    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP

);
```

The gateway event ID should be taken from the webhook payload if the gateway provides one.

### Processing Logic

```javascript
await sequelize.transaction(async (transaction) => {

    const existingEvent = await WebhookEvent.findOne({

        where: {

            gatewayEventId: eventId

        },

        transaction,

        lock: transaction.LOCK.UPDATE

    });


    if (existingEvent) {

        return;

    }


    await WebhookEvent.create({

        gatewayEventId: eventId,

        eventType: eventType

    }, {

        transaction

    });


    // Process payment event

    // Update payment status

    // Activate subscription if applicable

});
```

The unique database constraint is essential.

For concurrent duplicate webhook requests, catch unique-constraint violations and treat already-processed events as duplicates.

### Important

Do not acknowledge a webhook as successfully processed before its required database changes have committed.

Otherwise, a failed database operation could result in an event being lost from your processing workflow.

For more complex processing, persist the verified webhook event first and process it through a reliable queue.

# 22. Payment Failure Handling

Payments can fail for different reasons.

Examples:

- Insufficient funds.
- Incorrect payment details.
- Bank rejection.
- Network problems.
- Payment authorization timeout.
- User cancels checkout.

We should store payment failures properly.

### Example

```javascript
await Payment.create({

    paymentOrderId: order.id,

    gatewayPaymentId: payment.id,

    amount: payment.amount / 100,

    currency: payment.currency,

    status: "failed"

});
```

Also store useful diagnostic information:

- Failure code.
- Failure description.
- Payment method.
- Gateway payment ID.
- Timestamp.

Do not store sensitive card information.

### Important

A failed payment attempt does not necessarily mean the entire payment order should be marked permanently failed.

The customer may retry the payment.

Your system should distinguish between:

- Payment attempt status.
- Payment order status.

# 23. Refund Processing

Suppose a user purchased a premium subscription but requests a refund.

We need to initiate a refund through Razorpay.

### Refund API Example

```javascript
const refund = await razorpay.payments.refund(

    paymentId,

    {

        amount: 49900,

        speed: "normal"

    }

);
```

This example requests a refund of ₹499.

### Partial Refund

Suppose the user paid ₹499 but we want to refund ₹200.

```javascript
const refund = await razorpay.payments.refund(

    paymentId,

    {

        amount: 20000,

        speed: "normal"

    }

);
```

### Important

Creating a refund request does not necessarily mean the money has already reached the customer's account.

Refund processing has its own lifecycle.

Typical states include:

| Status | Meaning |
|---|---|
| pending | Refund processing |
| processed | Refund successfully processed |
| failed | Refund failed |

The exact states depend on the gateway.

### Refund Database Table

```sql
CREATE TABLE refunds (

    id BIGINT PRIMARY KEY AUTO_INCREMENT,

    payment_id BIGINT NOT NULL,

    gateway_refund_id VARCHAR(100) NOT NULL UNIQUE,

    amount DECIMAL(12,2) NOT NULL,

    status VARCHAR(30) NOT NULL,

    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,

    updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
        ON UPDATE CURRENT_TIMESTAMP,

    FOREIGN KEY (payment_id)
        REFERENCES payments(id)

);
```

### Important Refund Rules

1. Do not refund more than the captured amount minus previous successful refunds.
2. Prevent duplicate refund requests.
3. Store every refund separately.
4. Verify refund webhook events.
5. Update subscription status according to your refund policy.
6. Do not assume refund completion immediately after creating a refund request.

# 24. Understanding Idempotency in Payments

Idempotency is extremely important in financial systems.

Suppose a user clicks the Pay button twice.

Without protection:

```text
Click 1 → Create Order 1
Click 2 → Create Order 2
```

The user might accidentally make two payments.

### What Is an Idempotency Key?

An idempotency key is a unique identifier associated with a logical operation.

Example:

```text
payment-request-12345
```

If the same request is submitted multiple times with the same idempotency key, the backend should return the existing result rather than creating a new logical operation.

### Example Table

```sql
CREATE TABLE idempotency_keys (

    id BIGINT PRIMARY KEY AUTO_INCREMENT,

    user_id BIGINT NOT NULL,

    idempotency_key VARCHAR(150) NOT NULL,

    request_hash VARCHAR(64) NOT NULL,

    response_json JSON NULL,

    status VARCHAR(30) NOT NULL,

    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,

    UNIQUE KEY unique_user_key (
        user_id,
        idempotency_key
    )

);
```

### Example Request

```http
POST /api/payments/create-order
Idempotency-Key: 7d8c9f-example-key
```

### Backend Logic

1. Read the idempotency key.
2. Check whether the key already exists for the authenticated user.
3. Compare the request hash.
4. If the same request was already completed, return its previous result.
5. If the key is currently being processed, return an appropriate in-progress response.
6. If the key is reused with a different request, reject it.
7. Otherwise, create and store the new operation.

### Important

Idempotency must be enforced with database constraints and transaction-safe logic.

A simple JavaScript check is not sufficient when multiple API instances receive requests simultaneously.

# 25. Payment Security Best Practices

Payment processing requires careful security design.

### 25.1 Never Trust Frontend Amounts

The backend calculates the actual amount from trusted data.

### 25.2 Never Expose API Secrets

The Key Secret must remain on the server.

### 25.3 Verify Payment Signatures

Always verify the checkout signature.

### 25.4 Verify Webhook Signatures

Never trust unsigned webhook requests.

### 25.5 Verify Payment Amount

Compare the gateway payment amount with the internal order amount.

### 25.6 Verify Currency

Do not assume every payment is in INR.

### 25.7 Check Order Ownership

A user must not be able to verify another user's payment order.

### 25.8 Use Database Transactions

Update payment records and subscription records atomically.

### 25.9 Implement Idempotency

Prevent duplicate payment processing.

### 25.10 Protect Sensitive Payment Data

Do not store:

- Card CVV.
- Card PIN.
- Internet banking passwords.
- Raw card credentials.

Use the gateway's hosted checkout and tokenization mechanisms where appropriate.

# 26. What Is PCI DSS?

PCI DSS stands for:

**Payment Card Industry Data Security Standard.**

It is a security standard for organizations that store, process, or transmit payment card data.

It defines security requirements for protecting cardholder data.

Examples of areas covered:

- Access control.
- Network security.
- Data protection.
- Security monitoring.
- Vulnerability management.
- Security policies.

### Why Is It Important?

If an application directly handles sensitive card data, its compliance obligations can become significantly more complex.

Using a hosted payment checkout generally reduces the merchant application's exposure to raw card data, but it does not automatically eliminate all PCI DSS responsibilities.

Your exact obligations depend on the integration and applicable payment rules.

```text
                 +-------+-------+
                 |               |
                 v               v
              RAZORPAY         MYSQL
                 |               |
                 |               |
                 v               |
             CHECKOUT            |
                 |               |
                 v               |
             PAYMENT             |
                 |               |
                 +-------+-------+
                         |
                         v
                   WEBHOOK EVENT
                         |
                         v
                SIGNATURE VALIDATION
                         |
                         v
                 PAYMENT PROCESSING
                         |
                         v
                  DATABASE TXN
                         |
             +-----------+-----------+
             |                       |
             v                       v
       PAYMENT RECORD           SUBSCRIPTION
             |                       |
             +-----------+-----------+
                         |
                         v
                  SUCCESSFUL PAYMENT
```

### Why Use Both Frontend Verification and Webhooks?

They serve complementary purposes.

| Frontend Verification | Webhook |
|---|---|
| Gives the customer immediate feedback | Gives the backend an independent event |
| Depends on the browser completing its callback | Does not depend on the browser remaining open |
| Useful for checkout flow | Useful for reliable backend state updates |
| Can be missed if the browser closes | Can be retried by the gateway |

Your backend should process both through the same idempotent payment-state transition logic.

# 30. Interview Questions and Answers

### Q1. What is a payment gateway?

A service that facilitates online payments between customers, merchants, and payment networks.

### Q2. What is Razorpay?

A payment gateway and financial technology platform that provides payment APIs and related services.

### Q3. What is a payment order?

A gateway-side record representing a request to collect a specific amount from a customer.

### Q4. What is the difference between Order ID and Payment ID?

Order ID identifies a payment order, while Payment ID identifies an individual payment attempt.

### Q5. What is payment authorization?

The stage where a payment is approved by the payment infrastructure, subject to the payment flow.

### Q6. What is payment capture?

The operation that finalizes an authorized payment for collection.

### Q7. What is a webhook?

An HTTP callback sent by one system to another when a particular event occurs.

### Q8. Why are webhooks important?

They allow the backend to receive payment updates independently of the frontend.

### Q9. What is HMAC?

A cryptographic mechanism that uses a secret key and hash function to verify message authenticity and integrity.

### Q10. How do you verify a Razorpay payment signature?

Generate an HMAC-SHA256 signature using the order ID, payment ID, and Razorpay Key Secret, then compare it securely with the received signature.

### Q11. How do you verify a Razorpay webhook?

Generate an HMAC-SHA256 signature using the original raw request body and the configured webhook secret.

### Q12. Why is the raw webhook body important?

Because changing the original request bytes can produce a different HMAC signature.

### Q13. What is idempotency?

A mechanism that prevents duplicate processing of the same logical operation.

### Q14. Why is idempotency important in payment systems?

It prevents duplicate payment orders, subscription activations, refunds, and other financial operations.

### Q15. What is a refund?

A process of returning captured payment funds to a customer.

### Q16. What is PCI DSS?

A security standard for protecting payment card information.

### Q17. Why should the backend calculate payment amounts?

Because frontend values can be manipulated by users.

### Q18. Why do we use database transactions in payment processing?

To ensure related payment and business-state updates happen atomically.

### Q19. Can frontend payment success be trusted?

No. The backend must verify the payment using trusted gateway information.

### Q20. What happens if the user closes the browser after payment?

The backend can still receive the payment event through a webhook.

### Q21. Should a subscription be activated immediately after payment authorization?

Not necessarily. The application should follow the gateway's capture and settlement model and activate the subscription only after the required payment state is confirmed.

### Q22. Why do we need a separate refunds table?

Because one payment can have multiple refund operations, and each refund needs its own status and gateway reference.

### Q23. What is the difference between payment failure and order failure?

A payment attempt can fail while the overall order remains eligible for another payment attempt.

### Q24. Why should we verify payment amount and currency?

To ensure that the gateway payment matches the internal order.

### Q25. Why should we process webhooks idempotently?

Because webhook deliveries can be duplicated or retried.
