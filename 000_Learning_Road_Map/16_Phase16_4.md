# 1. Why Do We Need a Scalable Project Structure?

Imagine you initially create an application with only three features:

1. User registration.
2. User login.
3. Expense management.

Your initial project might look like this:

```text
backend/
│
├── server.js
├── package.json
├── routes.js
├── controllers.js
└── models.js
```

This may work for a small application.

But later, your client requests:

- Category management.
- Income management.
- Budget management.
- Monthly reports.
- Excel exports.
- PDF generation.
- Email notifications.
- Payment integration.
- Admin dashboard.
- Audit logs.

Now your files become large and difficult to maintain.

### Problems with Poor Project Structure

| Problem | Consequence |
|---|---|
| Everything inside controllers | Difficult to maintain business logic |
| Database queries everywhere | Difficult to modify database operations |
| Duplicate code | Difficult to maintain consistency |
| Mixed responsibilities | Difficult to test individual components |
| Hardcoded configuration | Environment-specific issues |
| No module boundaries | Tight coupling between features |
| Inconsistent error handling | Unpredictable API responses |

A scalable structure helps prevent these problems.

# 2. Understanding Different Folder Organization Strategies

There are several ways to organize a backend project.

## 2.1 Layer-Based Structure

Files are grouped by technical responsibility.

```text
src/
│
├── routes/
├── controllers/
├── services/
├── repositories/
├── models/
├── middleware/
└── utils/
```

For example:

```text
controllers/
    user.controller.js
    expense.controller.js
    category.controller.js

services/
    user.service.js
    expense.service.js
    category.service.js
```

**Problem:** As the project grows, files belonging to the same feature become distributed across multiple directories.

## 2.2 Feature-Based Structure

Files are grouped by business functionality.

```text
src/
│
├── modules/
│   │
│   ├── users/
│   ├── expenses/
│   ├── categories/
│   └── budgets/
│
└── config/
```

Example:

```text
modules/
│
└── expenses/
    │
    ├── expense.routes.js
    ├── expense.controller.js
    ├── expense.service.js
    ├── expense.repository.js
    ├── expense.model.js
    └── expense.validation.js
```

**Advantage:** All files related to expense management remain together.

## 2.3 Hybrid Structure

A hybrid structure combines feature-based organization with shared technical infrastructure.

For professional Node.js applications, this is a strong default.

Example:

```text
src/
│
├── modules/
│   ├── users/
│   ├── expenses/
│   ├── categories/
│   └── budgets/
│
├── config/
├── database/
├── middleware/
├── services/
├── utils/
└── app.js
```

We will use this approach.

# 4. Understanding the Config Folder

The `config` folder stores application configuration.

Example:

```text
config/
│
├── env.js
├── database.config.js
├── redis.config.js
├── cors.config.js
└── logger.config.js
```

### 4.1 env.js

Responsible for reading and validating environment variables.

Example `.env`:

```env
NODE_ENV=development

PORT=5000

DB_HOST=localhost
DB_PORT=3306
DB_NAME=expense_tracker
DB_USER=root
DB_PASSWORD=your_password

JWT_SECRET=your_secret
```

Example `env.js`:

```javascript
require("dotenv").config();

const env = {

    NODE_ENV: process.env.NODE_ENV || "development",

    PORT: Number(process.env.PORT || 5000),

    DB_HOST: process.env.DB_HOST,

    DB_PORT: Number(process.env.DB_PORT || 3306),

    DB_NAME: process.env.DB_NAME,

    DB_USER: process.env.DB_USER,

    DB_PASSWORD: process.env.DB_PASSWORD,

    JWT_SECRET: process.env.JWT_SECRET

};

module.exports = env;
```

A stronger production implementation should validate required variables during startup using Zod or another schema validator.

Example:

```javascript
const { z } = require("zod");

const envSchema = z.object({

    NODE_ENV: z.enum([
        "development",
        "test",
        "production"
    ]).default("development"),

    PORT: z.coerce.number().int().positive().default(5000),

    DB_HOST: z.string().min(1),

    DB_NAME: z.string().min(1),

    DB_USER: z.string().min(1),

    DB_PASSWORD: z.string(),

    JWT_SECRET: z.string().min(32)

});

const env = envSchema.parse(process.env);

module.exports = env;
```

If a required variable is missing or invalid, the application fails during startup instead of failing unexpectedly during a request.

### Why Is This Useful?

Without centralized configuration, you may find code like:

```javascript
const PORT = 5000;
```

or:

```javascript
const DB_HOST = "localhost";
```

inside multiple files.

This creates maintenance problems.

Instead, read configuration centrally.

# 5. Understanding the Database Folder

The `database` folder contains database-related components.

```text
database/
│
├── connection.js
├── models/
├── migrations/
├── seeders/
└── associations.js
```

### 5.1 connection.js

Creates the database connection.

Example:

```javascript
const { Sequelize } = require("sequelize");

const env = require("../config/env");

const sequelize = new Sequelize(

    env.DB_NAME,

    env.DB_USER,

    env.DB_PASSWORD,

    {

        host: env.DB_HOST,

        port: env.DB_PORT,

        dialect: "mysql",

        logging: false,

        pool: {

            max: 10,

            min: 0,

            acquire: 30000,

            idle: 10000

        }

    }

);

module.exports = sequelize;
```

### 5.2 models/

Contains database model definitions.

```text
models/
│
├── User.js
├── Expense.js
├── Category.js
├── Income.js
└── Budget.js
```

### 5.3 migrations/

Contains database schema changes.

Example:

```text
migrations/
│
├── 202611250001-create-users.js
├── 202611250002-create-categories.js
└── 202611250003-create-expenses.js
```

A migration records a controlled database schema change.

### 5.4 seeders/

Contains scripts for inserting initial or sample data.

Examples:

- Default categories.
- Admin account.
- Development test data.

### 5.5 associations.js

Defines relationships between Sequelize models.

Example:

```javascript
User.hasMany(Expense, {

    foreignKey: "userId",

    as: "expenses"

});

Expense.belongsTo(User, {

    foreignKey: "userId",

    as: "user"

});
```

### Why Keep Associations Separate?

In a large application, models may reference each other.

Defining all relationships in one initialization module makes model initialization easier to manage.

Be careful to avoid circular imports between model files.

# 6. Understanding the Modules Folder

This is the heart of a feature-based backend application.

```text
modules/
│
├── users/
├── auth/
├── expenses/
├── categories/
├── incomes/
├── budgets/
└── reports/
```

Each folder represents a business module.

For example:

```text
expenses/
│
├── expense.routes.js
├── expense.controller.js
├── expense.service.js
├── expense.repository.js
├── expense.model.js
└── expense.validation.js
```

Let's understand the responsibilities.

| File | Responsibility |
|---|---|
| expense.routes.js | Define expense endpoints |
| expense.controller.js | Handle HTTP requests |
| expense.service.js | Execute business logic |
| expense.repository.js | Perform database operations |
| expense.model.js | Define database model |
| expense.validation.js | Define input validation rules |

### Important Design Rule

A module should own its business logic.

For example:

- Expense creation belongs to the expense module.
- User registration belongs to the auth module.
- Monthly spending analysis belongs to the reports module.

Modules can communicate through clearly defined services or application interfaces.

Avoid directly importing another module's internal repository or model unless that dependency is deliberately part of the architecture.

### Example: Email Service

```javascript

    // Integrate email provider here.

    console.log("Sending email to:", to);

}

module.exports = {

    sendEmail

};
```

Usage:

```javascript

    "john@example.com",

    "Welcome",

    "Welcome to our application"
```

### Business Service vs Infrastructure Service

This distinction is important.

| Business Service | Infrastructure Service |
|---|---|
| ExpenseService | EmailService |
| OrderService | RedisService |
| EnrollmentService | StorageService |
| PaymentApplicationService | SMSProvider |

A business service implements application rules.

An infrastructure service communicates with an external system.

For example, an `ExpenseService` may decide when a notification should be sent, while `EmailService` handles actual email delivery.

# 8. Understanding the Middleware Folder

Middleware contains reusable request-processing functions.

```text
middleware/
│
├── authenticate.js
├── authorize.js
├── validate.js
├── errorHandler.js
├── notFound.js
└── requestLogger.js
```

### 8.1 Authentication Middleware

Verifies the user's identity.

```javascript
function authenticate(req, res, next) {

    // Verify access token.

    next();

}

module.exports = authenticate;
```

### 8.2 Authorization Middleware

Checks whether the authenticated user has permission to access a resource.

```javascript
function authorize(...allowedRoles) {

    return (req, res, next) => {

        if (!allowedRoles.includes(req.user.role)) {

            return res.status(403).json({

                success: false,

                message: "Forbidden"

            });

        }

        next();

    };

}

module.exports = authorize;
```

This is a simplified role check. Sensitive operations may also require permission and resource-ownership checks.

### 8.3 Validation Middleware

Validates incoming request data.

```javascript
function validate(schema) {

    return (req, res, next) => {

        const result = schema.safeParse({

            body: req.body,

            params: req.params,

            query: req.query

        });

        if (!result.success) {

            return res.status(400).json({

                success: false,

                errors: result.error.issues

            });

        }

        req.validated = result.data;

        next();

    };

}

module.exports = validate;
```

### Why Keep Middleware Separate?

Middleware is reusable across multiple routes and modules.

For example:

```javascript
router.post(
    "/",
    authenticate,
    validate(createExpenseSchema),
    expenseController.createExpense
);
```

# 9. Understanding the Utils Folder

The `utils` folder contains generic helper functions and reusable utilities.

Example:

```text
utils/
│
├── ApiError.js
├── ApiResponse.js
├── asyncHandler.js
└── pagination.js
```

### 9.1 ApiError.js

```javascript
class ApiError extends Error {

    constructor(statusCode, message) {

        super(message);

        this.statusCode = statusCode;

        this.name = "ApiError";

    }

}

module.exports = ApiError;
```

Usage:

```javascript
const ApiError = require("./ApiError");

throw new ApiError(404, "User not found");
```

### 9.2 asyncHandler.js

A reusable wrapper for asynchronous Express handlers.

```javascript
const asyncHandler = (handler) => {

    return (req, res, next) => {

        Promise.resolve(handler(req, res, next))
            .catch(next);

    };

};

module.exports = asyncHandler;
```

Usage:

```javascript
router.get(

    "/",

    asyncHandler(async (req, res) => {

        const users = await userService.getUsers();

        res.json(users);

    })

);
```

In Express 5, rejected Promises returned by async handlers are automatically forwarded to error middleware. This wrapper is particularly useful for Express 4 compatibility or consistent explicit handling.

### 9.3 pagination.js

```javascript
function getPagination(page = 1, limit = 10) {

    const safePage = Math.max(1, Number(page) || 1);

    const safeLimit = Math.min(
        100,
        Math.max(1, Number(limit) || 10)
    );

    const offset = (safePage - 1) * safeLimit;

    return {

        page: safePage,

        limit: safeLimit,

        offset

    };

}

module.exports = getPagination;
```

Usage:

```javascript
const pagination = getPagination(
    req.query.page,
    req.query.limit
);
```

Always validate and constrain pagination parameters. For large datasets, cursor-based pagination may be more appropriate.

# 10. Understanding the Routes Folder

The root `routes` folder registers all module routes.

Example:

```text
routes/
│
└── index.js
```

`index.js`:

```javascript
const express = require("express");

const router = express.Router();

const authRoutes = require("../modules/auth/auth.routes");

const userRoutes = require("../modules/users/user.routes");

const expenseRoutes = require("../modules/expenses/expense.routes");

const categoryRoutes = require("../modules/categories/category.routes");

router.use("/auth", authRoutes);

router.use("/users", userRoutes);

router.use("/expenses", expenseRoutes);

router.use("/categories", categoryRoutes);

module.exports = router;
```

### Why Is This Useful?

Instead of registering every route directly inside `app.js`, all API routes are managed through one entry point.

Now `app.js` remains clean.

# 11. Understanding app.js

`app.js` creates and configures the Express application.

Responsibilities:

- Register security middleware.
- Parse request bodies.
- Register routes.
- Handle unknown routes.
- Register error middleware.

Example:

```javascript
const express = require("express");

const helmet = require("helmet");

const cors = require("cors");

const apiRoutes = require("./routes");

const notFound = require("./middleware/notFound");

const errorHandler = require("./middleware/errorHandler");

const app = express();

app.use(helmet());

app.use(cors({

    origin: process.env.FRONTEND_URL

}));

app.use(express.json());

app.use(express.urlencoded({

    extended: true

}));

app.use("/api/v1", apiRoutes);

app.use(notFound);

app.use(errorHandler);

module.exports = app;
```

Middleware ordering matters.

For example, error-handling middleware should be registered after routes and the not-found handler.

# 12. Understanding server.js

`server.js` is responsible for starting the application.

Responsibilities:

- Load configuration.
- Connect to the database.
- Connect to Redis if required.
- Initialize dependencies.
- Start the HTTP server.

Example:

```javascript
require("dotenv").config();

const app = require("./app");

const sequelize = require("./database/connection");

const env = require("./config/env");

async function startServer() {

    try {

        await sequelize.authenticate();

        console.log("Database connected");

        const server = app.listen(env.PORT, () => {

            console.log(
                `Server running on port ${env.PORT}`
            );

        });

        return server;

    } catch (error) {

        console.error("Application startup failed:", error);

        process.exit(1);

    }

}

startServer();
```

This is a basic startup example. A production startup sequence should also initialize model associations and other required dependencies, verify infrastructure readiness, and support graceful shutdown.

# 14. Understanding Environment-Specific Configuration

A professional backend application typically runs in multiple environments.

Common environments:

1. Development.
2. Testing.
3. Staging.
4. Production.

### Example

| Configuration | Development | Testing | Production |
|---|---|---|---|
| Database | Local MySQL | Test database | Production DB |
| Logging | Debug | Controlled | Structured |
| Error details | Detailed locally | Test-friendly | Generic API errors |
| Debugger | Sometimes enabled | Usually disabled | Disabled |
| Email | Sandbox/mock | Mock | Real provider |
| Caching | Optional | Often isolated | Redis |

### Example Environment Files

```text
.env.development

.env.test

.env.staging

.env.production
```

These files should not contain committed secrets.

For production, use environment variables or a dedicated secrets manager.

### Important

Do not automatically load every environment file.

The application should explicitly load the configuration for its current environment.

### Examples

- User profile pictures.
- Generated Excel reports.

### Important Production Consideration

Local disk storage is not always appropriate for production.

If you deploy multiple application instances or use ephemeral containers, local files may not be shared or persistent.

Consider object storage such as:

- AWS S3.
- Cloudinary.
- Other S3-compatible storage services.

Store file metadata and object keys in the database rather than treating the database as a general file-storage system.

# 16. Understanding Jobs and Queues Folders

Large operations should not always execute during an HTTP request.

Example:

A user requests an Excel report containing 100,000 expense records.

Generating it synchronously could make the API request slow or time out.

Instead, use a background job.

### Architecture

```text
CLIENT
  |
  v
API REQUEST
  |
  v
CREATE REPORT JOB
  |
  v
REDIS QUEUE
  |
  v
BACKGROUND WORKER
  |
  v
GENERATE EXCEL
  |
  v
STORE FILE
  |
  v
NOTIFY USER
```

### Folder Structure

```text
jobs/
│
├── report.job.js
└── email.job.js

queues/
│
├── report.queue.js
└── email.queue.js
```

Common technology:

- BullMQ.
- Redis.

A queue processor should be designed to handle retries and duplicate job execution safely.

We will cover this in a later topic.

- Production credentials.
- JWT secrets.
- Database passwords.
- API keys.
- Private certificates.
- User-uploaded private files.

# 19. How Modules Should Communicate

This is one of the most important concepts in scalable architecture.

Suppose the Expense module needs user information.

There are different ways to communicate between modules.

### Bad Approach: Accessing Another Module's Database Directly

```javascript
// Inside expense.service.js

const { User } = require("../users/user.model");

const user = await User.findByPk(userId);
```

This may create unwanted dependencies between modules.

It is not always forbidden to share model access, but it can make module boundaries unclear.

### Better Approach: Use a Public Service Interface

`user.service.js`:

```javascript
exports.getUserById = async (id) => {

    return await userRepository.findById(id);

};
```

`expense.service.js`:

```javascript
const userService = require("../users/user.service");

exports.createExpense = async (userId, expenseData) => {

    const user = await userService.getUserById(userId);

    if (!user) {

        throw new Error("User not found");

    }

    return await expenseRepository.create({

        ...expenseData,

        userId

    });

};
```

For larger systems, use explicit dependency injection and module interfaces to avoid circular dependencies.

### Important

Not every module interaction requires a separate service call.

If the expense table has a foreign key to the user table, the database already maintains the relationship.

Use module services when you need business behavior, not simply to repeat a database lookup.

# 21. Common Project Structure Mistakes

Avoid these mistakes:

### Mistake 1: Putting Everything in One Controller

Controllers should not contain all business logic, database queries, email operations, and file processing.

### Mistake 2: Creating Too Many Abstractions

You do not need a repository, factory, adapter, and interface for every trivial CRUD operation.

Introduce abstractions when they improve maintainability, testing, or replaceability.

### Mistake 3: One Giant Utils Folder

Avoid placing unrelated business logic inside `utils`.

A calculation specific to expense management belongs in the expense module.

### Mistake 4: Circular Dependencies

Example:

```text
UserService → ExpenseService

ExpenseService → UserService
```

This creates circular dependencies.

Redesign module boundaries or introduce a coordinating application service when necessary.

### Mistake 5: Hardcoding Configuration

Use validated environment configuration.

### Mistake 6: Mixing Infrastructure and Business Logic

Email-provider implementation should not be mixed with expense calculation rules.

### Mistake 7: Using Production Database Sync for Schema Changes

Use database migrations for controlled schema evolution.

### Mistake 8: Exposing Internal Module Files

Keep module interfaces clear. Avoid allowing unrelated modules to depend on every internal file.

# 23. Interview Questions and Answers

### Q1. What is a scalable project structure?

A project organization that allows an application to grow while maintaining clear responsibilities and manageable dependencies.

### Q2. What is feature-based organization?

A structure that groups files according to business functionality.

### Q3. What is layer-based organization?

A structure that groups files according to technical responsibilities.

### Q4. What is a hybrid project structure?

A structure combining feature-based modules with shared technical infrastructure.

### Q5. What is the purpose of the config folder?

It centralizes application configuration and environment-specific settings.

### Q6. What is the purpose of the database folder?

It organizes database connections, models, migrations, seeders, and associations.

### Q7. What is the purpose of the middleware folder?

It contains reusable request-processing functions such as authentication, validation, and logging.

### Q8. What is the purpose of the utils folder?

It contains generic reusable helper functions.

### Q9. What is the difference between services and utils?

Services usually perform meaningful operations or integrations, while utilities provide generic helper functionality.

### Q10. Why separate app.js and server.js?

To separate Express application configuration from HTTP server startup.

### Q11. What is a migration?

A version-controlled database schema change.

### Q12. What is a seeder?

A script used to insert predefined or initial data into the database.

### Q13. Why use environment variables?

They allow configuration to differ between environments without changing application source code.

### Q14. What is a background job?

An operation executed outside the normal HTTP request-response lifecycle.

### Q15. Why use queues?

Queues help process asynchronous work reliably and manage workloads independently of HTTP requests.

### Q16. What is a module boundary?

A defined boundary that separates one business module's responsibilities and internal implementation from others.

### Q17. What causes circular dependencies?

Two or more modules importing each other directly or indirectly.

### Q18. Where should business logic be written?

Primarily in the appropriate business or application service, rather than inside route definitions or HTTP controllers.

### Q19. Should every database operation have a repository?

No. Repository abstractions are useful when they improve separation, testing, or maintainability, but they are not mandatory for every simple query.

### Q20. Which project structure is recommended for a large Express application?

A feature-based modular structure with clear internal layers and shared infrastructure.
