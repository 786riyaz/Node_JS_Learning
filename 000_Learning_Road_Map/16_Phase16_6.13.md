## 1. Introduction to Background Jobs

In a typical Node.js application, an HTTP request is received, processed, and answered.

For example, when a user creates an expense:

1. Validate request data.
2. Verify the user's identity.
3. Insert the expense into MySQL.
4. Create an audit log.
5. Send an email.
6. Generate a notification.
7. Return the API response.

Some operations are quick, while others may take several seconds or even minutes.

Consider these tasks:

| Task | Approximate Processing Time |
|---|---|
| Validate request | Milliseconds |
| Insert database record | Milliseconds |
| Send email | Depends on provider |
| Generate PDF report | Seconds |
| Process large Excel file | Seconds or minutes |
| Compress video | Minutes |
| Send bulk notifications | Seconds or minutes |
| Generate monthly financial report | Seconds or minutes |

If we execute every task directly inside an HTTP request, the user may have to wait until everything finishes.

This is where **Background Jobs** become useful.

### What is a Background Job?

A background job is a task that is executed asynchronously, independently of the main HTTP request-response lifecycle.

Instead of performing a time-consuming operation directly inside an API request, the application adds a job to a queue.

A separate worker processes that job.

### Without Background Jobs

```text
Client
  |
  v
POST /expenses
  |
  v
Express API
  |
  v
Create Expense
  |
  v
Send Email
  |
  v
Generate PDF
  |
  v
Send Notification
  |
  v
Return Response
```

The API waits for all operations.

### With Background Jobs

```text
Client
  |
  v
POST /expenses
  |
  v
Express API
  |
  v
Create Expense
  |
  v
Add Background Jobs
  |
  v
Return Response
  |
  |
  v
Background Workers
  |
  +------------------+
  |                  |
  v                  v
Send Email       Generate PDF
  |                  |
  v                  v
Send Notification  Store Report
```

The API can respond without waiting for the background tasks to finish.

# 2. Why Do We Need Background Jobs?

Let's understand the main benefits.

### 2.1 Faster API Responses

Suppose sending an email takes 3 seconds.

Without background processing:

```text
API Response Time = 3 seconds + database processing time
```

With background processing:

```text
API Response Time = database processing time + job enqueue time
```

The email is processed separately.

### 2.2 Better Scalability

Suppose 10,000 users register within a short period.

Sending 10,000 emails directly inside API requests can create significant load.

Instead, we can add 10,000 jobs to a queue and process them at a controlled rate.

### 2.3 Retry Failed Operations

Suppose the email provider is temporarily unavailable.

A background job can retry the operation automatically.

### 2.4 Control Processing Concurrency

We can configure how many jobs workers process simultaneously.

### 2.5 Schedule Tasks

We can execute tasks at specific times.

Examples:

- Generate monthly reports.
- Send daily reminders.
- Clean expired records.
- Process recurring financial summaries.

### 2.6 Separate Responsibilities

The API handles HTTP requests.

The worker handles long-running tasks.

This improves separation of concerns.

# 3. Understanding Job Queue Architecture

A job queue is a system that stores tasks until workers process them.

A typical architecture has four components.

| Component | Responsibility |
|---|---|
| Producer | Creates jobs |
| Queue | Stores pending jobs |
| Worker | Processes jobs |
| Storage | Maintains job state |

### Producer

The producer is the application component that creates jobs.

Example:

```javascript
await emailQueue.add("send-email", {
    to: "user@example.com",
    subject: "Welcome"
});
```

### Queue

The queue stores the job until a worker processes it.

### Worker

The worker retrieves the job and executes the required operation.

Example:

```javascript
const worker = new Worker(
    "email-queue",
    async (job) => {
        console.log(job.data);
    },
    {
        connection
    }
);
```

### Architecture

```text
              PRODUCER
                  |
                  v
             ADD JOB
                  |
                  v
                QUEUE
                  |
                  v
               REDIS
                  |
                  v
               WORKER
                  |
                  v
           PROCESS JOB
                  |
          +-------+-------+
          |               |
          v               v
       SUCCESS          FAILURE
          |               |
          v               v
      COMPLETED         RETRY
```

# 6. Understanding the Job Lifecycle

A job moves through different states during its lifetime.

Important states include:

| State | Meaning |
|---|---|
| waiting | Waiting to be processed |
| active | Currently being processed |
| delayed | Scheduled for future processing |
| completed | Successfully processed |
| failed | Processing failed |
| waiting-children | Waiting for dependent jobs |
| prioritized | Waiting according to priority |

### Job Lifecycle

```text
              ADD JOB
                 |
                 v
               WAITING
                 |
                 v
               ACTIVE
                 |
          +------+------+
          |             |
          v             v
       SUCCESS        FAILURE
          |             |
          v             v
      COMPLETED      RETRY?
                        |
                   +----+----+
                   |         |
                  YES        NO
                   |         |
                   v         v
                WAITING    FAILED
```

A delayed job follows a different path:

```text
ADD JOB
   |
   v
DELAYED
   |
   v
WAITING
   |
   v
ACTIVE
   |
   v
COMPLETED / FAILED
```

# 8. Redis Connection Configuration

We already created a Redis connection in Part 12.

Let's reuse it.

File:

```text
src/config/redis.js
```

```javascript
const Redis = require("ioredis");


const redisConnection = new Redis(
    process.env.REDIS_URL || "redis://127.0.0.1:6379",
    {
        maxRetriesPerRequest: null
    }
);


redisConnection.on("connect", () => {

    console.log("Redis connected");

});


redisConnection.on("error", (error) => {

    console.error("Redis error:", error.message);

});


module.exports = redisConnection;
```

### Why `maxRetriesPerRequest: null`?

BullMQ workers use Redis connections for background processing.

BullMQ's worker connection configuration expects blocking Redis operations to remain available rather than failing after a small number of retries.

This configuration is commonly used for BullMQ connections.

For API-side Redis caching, you may use a separate Redis connection with different retry settings.

# 9. Creating a Queue

Let's create our first queue.

File:

```text
src/queues/email.queue.js
```

```javascript
const {
    Queue
} = require("bullmq");

const redisConnection = require("../config/redis");


const emailQueue = new Queue("email-queue", {

    connection: redisConnection

});


module.exports = emailQueue;
```

### Understanding Queue()

```javascript
new Queue("email-queue", {
    connection: redisConnection
});
```

The first argument is the queue name.

The second argument contains its configuration.

The queue name must match the name used by the worker.

For example:

```javascript
new Worker(
    "email-queue",
    processor,
    {
        connection: redisConnection
    }
);
```

If the queue names are different, the worker will not process jobs from the intended queue.

A producer adds jobs to a queue.

File:

```

const emailQueue = require("../queues/email.queue");


async function addWelcomeEmailJob(user) {

        {

            userId: String(user.id),

            email: user.email,

            name: user.name

        }

module.exports = {
    addWelcomeEmailJob
};
```

### Understanding Queue.add()

```javascript
emailQueue.add(
    "welcome-email",
    jobData
);
```

Arguments:

1. Job name.
2. Job data.
3. Optional job configuration.

### Example Job Data

```json
{
    "userId": "10",
    "email": "john@example.com",
    "name": "John"
}
```

### Important

Only put the data required to process the job into the queue.

Avoid placing:

- Passwords.
- JWT secrets.
- API credentials.
- Full user records.
- Unnecessary personal information.

Prefer passing record IDs and retrieving authoritative information from the database inside the worker.

For example, a better production job might contain only:

```javascript
{
    userId: "10",
    eventId: "500"
}
```

# 11. Creating a Worker

A worker processes jobs from a queue.

File:

```text
src/workers/email.worker.js
```

```javascript
const {
    Worker
} = require("bullmq");

const redisConnection = require("../config/redis");

const emailService = require("../services/email.service");


const emailWorker = new Worker(

    "email-queue",

    async (job) => {

        console.log("Processing job:", job.id);

        console.log("Job name:", job.name);


        if (job.name === "welcome-email") {

            await emailService.sendWelcomeEmail(job.data);

        }

    },

    {

        connection: redisConnection,

        concurrency: 5

    }

);


emailWorker.on("completed", (job) => {

    console.log(`Job ${job.id} completed`);

});


emailWorker.on("failed", (job, error) => {

    console.error(
        `Job ${job?.id} failed:`,
        error.message
    );

});


module.exports = emailWorker;
```

### How does it work?

When a job is added:

```javascript
await emailQueue.add(
    "welcome-email",
    data
);
```

BullMQ makes it available to a worker.

The worker executes:

```javascript
async (job) => {
    // Process job
}
```

The `job` object contains information about the job.

Important properties include:

| Property | Description |
|---|---|
| `job.id` | Unique job identifier |
| `job.name` | Job name |
| `job.data` | Job payload |
| `job.attemptsMade` | Number of attempts already made |
| `job.timestamp` | Job creation timestamp |
| `job.progress` | Current progress information |

# 13. Adding Job Options

BullMQ supports many useful job options.

Example:

```javascript
await emailQueue.add(

    "welcome-email",

    {
        userId: "10"
    },

    {

        attempts: 3,

        backoff: {

            type: "exponential",

            delay: 5000

        },

        removeOnComplete: 100,

        removeOnFail: 500

    }

);
```

Let's understand them.

| Option | Description |
|---|---|
| `attempts` | Maximum processing attempts |
| `backoff` | Retry delay strategy |
| `delay` | Delay before processing |
| `priority` | Job priority |
| `removeOnComplete` | Completed job retention |
| `removeOnFail` | Failed job retention |
| `jobId` | Custom job identifier |
| `timeout` | Not a general BullMQ job option; implement task-specific timeouts where needed |

### Why retain completed jobs?

Keeping some job history helps with debugging and monitoring.

But retaining every completed job forever consumes Redis memory.

Use appropriate retention settings.

# 14. Job Retries

Sometimes jobs fail because of temporary problems.

Examples:

- Email provider unavailable.
- Network timeout.
- Temporary database outage.
- External API rate limit.

Instead of permanently failing immediately, we can retry.

### Example

```javascript
await emailQueue.add(

    "send-email",

    data,

    {

        attempts: 5,

        backoff: {

            type: "fixed",

            delay: 3000

        }

    }

);
```

This allows up to five processing attempts, with a fixed three-second backoff between retries.

### What Is Exponential Backoff?

Exponential backoff increases the delay between attempts.

Example:

```javascript
backoff: {

    type: "exponential",

    delay: 1000

}
```

Approximate retry delays:

| Attempt | Delay |
|---|---:|
| First retry | 1 second |
| Second retry | 2 seconds |
| Third retry | 4 seconds |
| Fourth retry | 8 seconds |

BullMQ's exponential backoff doubles the delay for successive retries, subject to its configuration.

### Why is exponential backoff useful?

Suppose an external email provider is temporarily unavailable.

Retrying every 100 milliseconds may increase the load on an already unhealthy service.

Exponential backoff gives the service time to recover.

### Important

Not every failure should be retried.

For example:

| Error | Retry? |
|---|---|
| Temporary network failure | Usually yes |
| Provider rate limit | Usually yes, respecting retry guidance |
| Temporary server error | Usually yes |
| Invalid recipient address | Usually no |
| Invalid email configuration | Usually no |
| Invalid job payload | Usually no |

Implement error classification so permanent errors do not waste all retry attempts.

# 15. Delayed Jobs

Sometimes we want a job to run after a specific delay.

Example:

Send a reminder email after 10 minutes.

```javascript
await emailQueue.add(

    "reminder-email",

    {

        userId: "10"

    },

    {

        delay: 10 * 60 * 1000

    }

);
```

The job will remain delayed until its scheduled time.

### Use Cases

- Send a reminder after registration.
- Retry a payment-related workflow later.
- Send an inactivity reminder.
- Schedule follow-up notifications.
- Delay an email until a specific point in a workflow.

### Example: Expense Reminder

Suppose a user creates a monthly budget but has not recorded any expenses.

We can schedule a reminder.

```javascript
await notificationQueue.add(

    "budget-reminder",

    {
        userId: "10",
        budgetId: "50"
    },

    {
        delay: 24 * 60 * 60 * 1000
    }

);
```

This schedules the reminder approximately 24 hours later.

Before sending it, the worker should check whether the reminder is still relevant.

# 16. Job Priorities

Sometimes certain jobs are more important than others.

Example:

- Password reset email.
- Welcome email.
- Monthly report generation.

A password reset email should generally be processed before a routine monthly report.

BullMQ supports job priorities.

Example:

```javascript
await emailQueue.add(

    "password-reset",

    {
        userId: "10"
    },

    {
        priority: 1
    }

);


await emailQueue.add(

    "welcome-email",

    {
        userId: "20"
    },

    {
        priority: 5
    }

);
```

In BullMQ, lower numerical priority values represent higher priority.

### Example Priority Scheme

| Job | Priority |
|---|---:|
| Password Reset | 1 |
| Security Alert | 2 |
| Email Verification | 3 |
| Welcome Email | 5 |
| Monthly Report | 10 |

Jobs with higher priority are generally selected before lower-priority jobs that are waiting.

**Important:** Priority is not a substitute for separate queues or dedicated worker capacity. A large number of high-priority jobs can still delay other jobs.

# 17. Job Concurrency

Concurrency determines how many jobs a worker processes simultaneously.

Example:

```javascript
const worker = new Worker(

    "email-queue",

    async (job) => {

        await processEmail(job.data);

    },

    {

        connection: redisConnection,

        concurrency: 10

    }

);
```

This worker can process up to ten jobs concurrently.

### Concurrency = 1

```text
Worker
  |
  v
Job 1
  |
  v
Job 2
  |
  v
Job 3
```

Jobs are processed one at a time.

### Concurrency = 5

```text
Worker
  |
  +---- Job 1
  |
  +---- Job 2
  |
  +---- Job 3
  |
  +---- Job 4
  |
  +---- Job 5
```

Up to five jobs can be active simultaneously.

### Multiple Workers

Suppose:

```text
Worker 1: Concurrency 5

Worker 2: Concurrency 5

Worker 3: Concurrency 5
```

Total theoretical concurrency:

```text
5 + 5 + 5 = 15
```

This is useful when scaling background processing horizontally.

### Important

Higher concurrency does not always mean better performance.

It depends on:

- CPU usage.
- Memory usage.
- Database connection capacity.
- External API limits.
- Network capacity.
- Job processing type.

For CPU-intensive work, increasing asynchronous concurrency may not improve performance. Use separate processes, worker threads, or dedicated processing services where appropriate.

# 18. Rate Limiting Jobs

Suppose your email provider allows only 100 emails per minute.

If you process 1,000 email jobs immediately, the provider may reject many requests.

BullMQ supports rate limiting.

Example:

```javascript
const worker = new Worker(

    "email-queue",

    async (job) => {

        await processEmail(job.data);

    },

    {

        connection: redisConnection,

        limiter: {

            max: 100,

            duration: 60000

        }

    }

);
```

This configures the worker to process up to 100 jobs per 60-second interval.

### Why is rate limiting useful?

- Prevents provider abuse.
- Reduces API rate-limit errors.
- Controls workload.
- Protects external services.
- Helps maintain stable throughput.

For distributed workers, use a shared queue and rate-limiting strategy supported by your BullMQ version.

# 19. Job Progress Tracking

Some jobs take a long time.

For example:

Generating a PDF report for 100,000 transactions.

We may want to track its progress.

BullMQ supports job progress updates.

### Worker Example

```javascript
const worker = new Worker(

    "report-queue",

    async (job) => {

        await job.updateProgress(10);


        // Step 1: Fetch data

        const data = await fetchReportData(job.data);


        await job.updateProgress(40);


        // Step 2: Generate PDF

        const pdf = await generatePDF(data);


        await job.updateProgress(80);


        // Step 3: Store PDF

        await uploadPDF(pdf);


        await job.updateProgress(100);


        return {
            message: "Report generated successfully"
        };

    },

    {
        connection: redisConnection
    }

);
```

### Progress Values

```text
10%  → Fetching data

40%  → Generating PDF

80%  → Uploading PDF

100% → Completed
```

### Why is progress tracking useful?

The frontend can display:

```text
Report Generation: 80%
```

This improves the user experience for long-running operations.

Progress is informational. It does not guarantee that a job will finish successfully.

# 20. Scheduled and Recurring Jobs

Sometimes we need jobs that execute at specific times.

Examples:

- Generate reports every month.
- Send reminders every day.
- Delete expired temporary records.
- Send weekly financial summaries.

BullMQ supports delayed and recurring jobs.

### Example: Daily Reminder

Using BullMQ's Job Scheduler API:

```javascript
await notificationQueue.upsertJobScheduler(

    "daily-reminder",

    {

        pattern: "0 9 * * *"

    },

    {

        name: "daily-reminder",

        data: {
            type: "DAILY_REMINDER"
        }

    }

);
```

The cron expression:

```text
0 9 * * *
```

means 9:00 AM every day.

### Understanding Cron Syntax

A common five-field cron expression:

```text
* * * * *
```

Fields:

```text
┬ ┬ ┬ ┬ ┬
│ │ │ │ │
│ │ │ │ └── Day of week
│ │ │ └──── Month
│ │ └────── Day of month
│ └──────── Hour
└────────── Minute
```

Examples:

| Cron Expression | Meaning |
|---|---|
| `0 9 * * *` | Every day at 9:00 AM |
| `0 0 * * *` | Every day at midnight |
| `0 9 * * 1` | Every Monday at 9:00 AM |
| `0 8 1 * *` | First day of every month at 8:00 AM |
| `*/15 * * * *` | Every 15 minutes |

### Important: Time Zones

Cron scheduling depends on the configured scheduler timezone.

Do not assume that a cron expression automatically follows the user's local timezone.

For example, if the application is deployed on a server using UTC but users expect India Standard Time, configure and test the timezone explicitly.

For user-specific schedules, store the user's timezone and calculate the next execution time appropriately.

### BullMQ Version Note

BullMQ's Job Scheduler API is available in modern versions. Older tutorials may use the previous repeatable-job API.

Use the API matching your installed BullMQ version.

# 21. Handling Failed Jobs

Not every job will succeed.

For example:

```text
Email provider unavailable
```

After all configured retries, the job may enter the failed state.

We should monitor failed jobs.

### Worker Events

```javascript
worker.on("failed", (job, error) => {

    console.error({

        jobId: job?.id,

        jobName: job?.name,

        attemptsMade: job?.attemptsMade,

        error: error.message

    });

});
```

### Retrieving Failed Jobs

BullMQ Queue provides methods for inspecting job states.

Example:

```javascript
const failedJobs = await emailQueue.getFailed(
    0,
    49
);

console.log(failedJobs);
```

This retrieves a range of failed jobs.

### Retry a Failed Job

```javascript
const job = await emailQueue.getJob("123");

if (job) {

    await job.retry();

}
```

The job must be in an appropriate state for retrying.

### Remove a Failed Job

```javascript
const job = await emailQueue.getJob("123");

if (job) {

    await job.remove();

}
```

Be careful when deleting job records because they may be useful for debugging or auditing.

# 22. Dead-Letter Queue (DLQ)

A Dead-Letter Queue is a separate queue or storage mechanism for jobs that cannot be successfully processed after the allowed retries.

For example:

```text
Email Queue
    |
    v
Process Job
    |
    v
Failure
    |
    v
Retry 3 Times
    |
    v
Still Failing
    |
    v
Dead-Letter Queue
```

### Why is a DLQ useful?

It helps us:

- Isolate permanently failed jobs.
- Investigate processing errors.
- Prevent repeated failure loops.
- Reprocess jobs after fixing a problem.
- Maintain operational visibility.

### Important

BullMQ has a failed state, but a separate DLQ is an additional architecture that you implement.

It is not automatically created simply by setting `attempts`.

### Example

```javascript
const {
    Queue
} = require("bullmq");


const deadLetterQueue = new Queue(
    "email-dead-letter-queue",
    {
        connection: redisConnection
    }
);
```

You can move terminally failed jobs into this queue through a carefully designed failure-handling workflow.

Preserve:

- Original job ID.
- Original job name.
- Original payload or safe reference.
- Failure reason.
- Number of attempts.
- Failure timestamp.

Avoid copying secrets or unnecessary personal information into the DLQ.

# 23. Idempotent Job Processing

This is one of the most important concepts in production background processing.

### What is Idempotency?

An operation is idempotent if executing it multiple times produces the same intended result as executing it once.

Example:

```javascript
await User.update(
    {
        emailVerified: true
    },
    {
        where: {
            id: userId
        }
    }
);
```

Setting `emailVerified` to `true` repeatedly produces the same final state.

This operation is naturally idempotent.

### Non-Idempotent Example

```javascript
await Account.increment("balance", {
    by: 1000,
    where: {
        id: accountId
    }
});
```

If this job executes twice, the balance increases by ₹2,000 instead of ₹1,000.

This is dangerous.

### Why do background jobs need idempotency?

A job may be executed again because:

- A worker crashes.
- A network request times out.
- A retry occurs.
- A job is manually reprocessed.
- A queue event is published more than once.

Therefore, we should design job processing to handle duplicate execution safely.

### Example: Process an Event Once

Suppose we have a table:

```sql
CREATE TABLE processed_events (

    id BIGINT PRIMARY KEY AUTO_INCREMENT,

    event_id VARCHAR(100) NOT NULL UNIQUE,

    processed_at DATETIME DEFAULT CURRENT_TIMESTAMP

);
```

Before processing an event, insert its unique event ID.

If the event ID already exists, do not repeat the business operation.

### Sequelize Example

```javascript
async function processExpenseEvent(event) {

    await sequelize.transaction(async (transaction) => {

        const [record, created] =
            await ProcessedEvent.findOrCreate({

                where: {
                    eventId: event.id
                },

                defaults: {
                    eventId: event.id
                },

                transaction

            });


        if (!created) {

            return;

        }


        await createExpenseNotification(
            event.userId,
            event.expenseId,
            transaction
        );

    });

}
```

This example assumes:

- `event_id` has a database unique constraint.
- Notification creation uses the same transaction.
- The notification operation is performed only if the event is newly recorded.

For concurrent processing, the unique database constraint is essential. Application-level checks alone are insufficient.

### Important Email Limitation

Sending an email is an external side effect.

Suppose the provider accepts the email, but the worker crashes before recording success.

A retry may send the same email again.

Exactly-once delivery cannot generally be guaranteed simply by using BullMQ.

Use provider-supported idempotency mechanisms where available, event deduplication, and carefully designed delivery workflows.

# 24. Graceful Worker Shutdown

Suppose your server is being restarted.

What happens if a worker is currently processing a job?

We should shut it down gracefully.

### What is Graceful Shutdown?

Graceful shutdown means allowing active operations to finish or safely release their resources before the process exits.

BullMQ workers provide:

```javascript
await worker.close();
```

### Example

File:

```text
src/workers/start-email-worker.js
```

```javascript
require("dotenv").config();

const emailWorker = require("./email.worker");

const redis = require("../config/redis");


async function shutdown(signal) {

    console.log(`${signal} received`);

    try {

        await emailWorker.close();

        await redis.quit();

        console.log("Worker shutdown completed");

        process.exit(0);

    } catch (error) {

        console.error("Shutdown error:", error);

        process.exit(1);

    }

}


process.on("SIGTERM", () => {
    shutdown("SIGTERM");
});


process.on("SIGINT", () => {
    shutdown("SIGINT");
});
```

### Why is this important?

It helps prevent:

- Abrupt worker termination.
- Unnecessary job failures.
- Connection leaks.
- Incomplete shutdown.

In production, also implement a shutdown timeout so the process does not remain stuck indefinitely.

# 27. Building a Monthly Financial Report Worker

Let's implement a practical use case.

Suppose a user requests a monthly financial report.

Generating the report may take time.

We should process it in the background.

### Step 1: Add Report Job

```javascript
const reportQueue = require("../queues/report.queue");


async function addMonthlyReportJob(userId, month) {

    return await reportQueue.add(

        "monthly-report",

        {

            userId: String(userId),

            month

        },

        {

            attempts: 3,

            backoff: {

                type: "exponential",

                delay: 5000

            },

            removeOnComplete: 100,

            removeOnFail: 500

        }

    );

}


module.exports = {
    addMonthlyReportJob
};
```

### Step 2: Create Report Worker

```javascript
const {
    Worker
} = require("bullmq");

const redisConnection = require("../config/redis");

const reportService = require("../services/report.service");


const reportWorker = new Worker(

    "report-queue",

    async (job) => {

        if (job.name === "monthly-report") {

            await job.updateProgress(10);


            const report =
                await reportService.generateMonthlyReport(

                    job.data.userId,

                    job.data.month

                );


            await job.updateProgress(100);


            return {

                reportId: report.id,

                status: "completed"

            };

        }

    },

    {

        connection: redisConnection,

        concurrency: 2

    }

);


reportWorker.on("completed", (job, result) => {

    console.log("Report completed:", result);

});


reportWorker.on("failed", (job, error) => {

    console.error(
        "Report failed:",
        job?.id,
        error.message
    );

});


module.exports = reportWorker;
```

### Step 3: API Endpoint

Example:

```javascript
router.post(
    "/reports/monthly",
    authenticate,
    reportController.generateMonthlyReport
);
```

Controller:

```javascript
async function generateMonthlyReport(req, res, next) {

    try {

        const userId = req.user.id;

        const { month } = req.body;


        const job = await addMonthlyReportJob(
            userId,
            month
        );


        res.status(202).json({

            message: "Report generation started",

            jobId: job.id,

            status: "queued"

        });

    } catch (error) {

        next(error);

    }

}
```

### Why HTTP 202?

HTTP status `202 Accepted` indicates that the request has been accepted for processing but the processing has not necessarily completed.

### Step 4: Job Status API

The frontend may want to check whether the report is ready.

Example endpoint:

```text
GET /reports/jobs/:jobId
```

Controller logic:

```javascript
const reportQueue = require("../../queues/report.queue");


async function getReportJobStatus(req, res, next) {

    try {

        const job = await reportQueue.getJob(
            req.params.jobId
        );


        if (!job) {

            return res.status(404).json({

                message: "Job not found"

            });

        }


        const state = await job.getState();


        res.json({

            jobId: job.id,

            state,

            progress: job.progress,

            result: job.returnvalue

        });

    } catch (error) {

        next(error);

    }

}
```

### Important Security Rule

A job ID is not an authorization mechanism.

Before returning a report or job result, verify that the authenticated user owns that job or the associated report.

One approach is to store the requesting user ID in the job payload and compare it with `req.user.id`.

For stronger control, store report-job ownership and status in MySQL.

Do not depend on Redis job retention as the only permanent record of generated reports.

# 29. Important Production Considerations

Before deploying background workers, understand these concepts.

### 29.1 Do Not Assume Exactly-Once Processing

Jobs may be retried or processed again after failures.

Design handlers to be idempotent.

### 29.2 Do Not Store Sensitive Data in Job Payloads

Store identifiers and retrieve sensitive data securely when needed.

### 29.3 Use Separate Workers for Different Workloads

Email delivery and PDF generation have different resource requirements.

### 29.4 Configure Retry Policies Carefully

Do not retry permanent errors indefinitely.

### 29.5 Monitor Failed Jobs

A failed queue should not remain unnoticed.

### 29.6 Implement Graceful Shutdown

Allow active jobs to finish or safely return to the queue.

### 29.7 Keep Redis Protected

Use private networking, authentication, TLS where appropriate, and controlled access.

### 29.8 Configure Redis Persistence and Recovery

Redis is the queue's storage layer.

Its persistence, replication, and recovery configuration should match the durability requirements of your jobs.

### 29.9 Keep Job Payloads Small

Store references to database records or files instead of large objects.

### 29.10 Use the Transactional Outbox Pattern

For important business events, make event creation atomic with the underlying database transaction.

# 31. Interview Questions and Answers

### Q1. What is a background job?

A task executed asynchronously outside the main HTTP request-response lifecycle.

### Q2. Why do we need background jobs?

To handle time-consuming operations without unnecessarily delaying API responses.

### Q3. What is a job queue?

A system that stores tasks until workers process them.

### Q4. What is BullMQ?

A Node.js job queue library built on Redis.

### Q5. What is a producer?

A component responsible for adding jobs to a queue.

### Q6. What is a worker?

A component responsible for processing jobs from a queue.

### Q7. What is job concurrency?

The number of jobs a worker can process simultaneously.

### Q8. What is a delayed job?

A job that becomes available for processing after a specified delay.

### Q9. What is job priority?

A mechanism for deciding which waiting jobs should generally be processed first.

### Q10. What is exponential backoff?

A retry strategy where the delay between attempts increases exponentially.

### Q11. What is a failed job?

A job that could not be processed successfully.

### Q12. What is a Dead-Letter Queue?

A separate mechanism for storing jobs that have exhausted their retries or cannot be processed.

### Q13. What is idempotency?

A property where repeating an operation does not produce additional unintended effects.

### Q14. Why is idempotency important in background jobs?

Because jobs can be retried or executed more than once after failures.

### Q15. What is graceful shutdown?

A process of safely stopping workers while handling active jobs and releasing resources.

### Q16. What is horizontal scaling?

Increasing processing capacity by running additional worker instances.

### Q17. What is job progress tracking?

A mechanism for reporting how much of a long-running job has completed.

### Q18. What is a scheduled job?

A job configured to execute at a future or recurring time.

### Q19. What is rate limiting in a queue?

A mechanism that restricts how frequently jobs are processed.

### Q20. What is the difference between an API process and a worker process?

The API process handles HTTP requests, while the worker process handles background tasks.

### Q21. Does BullMQ guarantee exactly-once job execution?

No. Design job handlers to tolerate retries and duplicate execution.

### Q22. Why should different workloads use separate queues?

To isolate workloads and configure their processing capacity, retry behavior, and priorities independently.

### Q23. What is queue latency?

The time a job waits in the queue before processing begins.

### Q24. Why is Redis persistence important for BullMQ?

Redis stores queue state. Appropriate persistence and recovery configuration help protect queued jobs against infrastructure failures.

### Q25. What is the Transactional Outbox Pattern?

It stores a business event in the same database transaction as the business operation, allowing reliable asynchronous publishing afterward.
