# 1. What Is Authentication?

Authentication is the process of verifying the identity of a user.

In simple words:

**Authentication answers: Who are you?**

Suppose a user opens our Expense Tracker application.

The user enters:

```text
Email: john@example.com
Password: ********
```

The backend verifies whether these credentials belong to a registered user.

If they are correct, the user is authenticated.

# 2. What Is Authorization?

Authorization determines what an authenticated user is allowed to do.

In simple words:

**Authorization answers: What are you allowed to access?**

Suppose our application has two roles:

1. Admin.
2. User.

An admin can:

- View all users.
- Manage users.
- View application statistics.
- Manage global categories.

A normal user can:

- Manage their own expenses.
- Manage their own income.
- Manage their own budgets.
- View their own reports.

### Authentication vs Authorization

| Authentication | Authorization |
|---|---|
| Verifies identity | Checks permissions |
| Happens before protected access | Happens after identity is established |
| Answers who you are | Answers what you can do |
| Example: Login | Example: Admin-only endpoint |
| Uses credentials and tokens | Uses roles, permissions, and ownership rules |

### Example

A user successfully logs in.

The backend issues a valid access token.

The user then tries to access:

```http
GET /api/v1/admin/users
```

The token is valid, so authentication succeeds.

But the user has the `user` role, not the `admin` role.

Therefore, authorization fails.

The server returns:

```http
403 Forbidden
```

**Important:** A valid token does not automatically mean the user has permission to access every resource.

# 3. Understand Password Hashing

Before implementing registration and login, we need to understand password security.

Suppose a user registers with:

```text
Password: mypassword123
```

Should we store this password directly in MySQL?

Absolutely not.

If the database is compromised, attackers could obtain users' actual passwords.

Instead, we store a password hash.

## 3.1 What Is Hashing?

Hashing converts input data into a fixed-format output using a one-way algorithm.

Example:

```text
Original Password:
mypassword123

        |
        v

Hashing Algorithm

        |
        v

Stored Hash:
$2b$12$...
```

A secure password hash is designed to be computationally expensive to verify, making large-scale password guessing more difficult.

## 3.2 Hashing vs Encryption

| Hashing | Encryption |
|---|---|
| Designed to be one-way | Designed to be reversible with the correct key |
| No decryption operation | Can be decrypted |
| Used for password verification | Used for protecting recoverable data |
| Example: bcrypt | Example: AES |

Passwords should be hashed, not reversibly encrypted.

## 3.3 What Is bcrypt?

bcrypt is a password-hashing algorithm.

It is designed to make password guessing computationally expensive.

Install it if you haven't already:

```bash
npm install bcrypt
```

### Hash a Password

```javascript
const bcrypt = require("bcrypt");

async function hashPassword(password) {

    const saltRounds = 12;

    const hashedPassword = await bcrypt.hash(
        password,
        saltRounds
    );

    return hashedPassword;

}
```

Usage:

```javascript
const hash = await hashPassword("mypassword123");

console.log(hash);
```

### What Are Salt Rounds?

Salt rounds determine the computational cost of bcrypt hashing.

Higher cost means more computation is required to generate and verify the hash.

Choose a cost factor based on current security recommendations and measured server performance.

### What Is a Salt?

A salt is random data incorporated into password hashing.

bcrypt generates and stores the salt information as part of its encoded hash.

Therefore, you do not need to manually store a separate salt when using the normal bcrypt API.

## 3.4 Compare Passwords

During login, we compare the entered password with the stored hash.

```javascript
const isPasswordValid = await bcrypt.compare(

    "mypassword123",

    storedPasswordHash

);
```

Result:

```javascript
true
```

If the password is incorrect:

```javascript
false
```

### Important

Never compare passwords like this:

```javascript
if (password === user.password) {
    // Incorrect approach
}
```

The stored password is a hash, not the original password.

# 4. Understand JWT Authentication

JWT stands for **JSON Web Token**.

It is a compact token format commonly used to represent claims about an authenticated user.

A server can verify a JWT's signature and validity without looking up a server-side session for every request.

## 4.1 What Does a JWT Look Like?

A JWT usually contains three parts separated by dots.

```text
HEADER.PAYLOAD.SIGNATURE
```

Example:

```text
eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9
.
eyJzdWIiOiIxMjMiLCJyb2xlIjoidXNlciJ9
.
signature
```

The actual token is one continuous string.

## 4.2 JWT Structure

### Part 1: Header

The header describes the token type and signing algorithm.

Example:

```json
{
    "alg": "HS256",
    "typ": "JWT"
}
```

### Part 2: Payload

The payload contains claims.

Example:

```json
{
    "sub": "123",
    "role": "user",
    "iat": 1795600000,
    "exp": 1795600900
}
```

Common claims:

| Claim | Meaning |
|---|---|
| sub | Subject, usually the user ID |
| iat | Issued-at timestamp |
| exp | Expiration timestamp |
| iss | Issuer |
| aud | Audience |

### Part 3: Signature

The signature allows the server to verify that the token has not been modified.

For example, with HMAC SHA-256, the signing process uses the header, payload, and secret key.

**Important:** A signed JWT is not automatically encrypted.

Its payload is generally readable by anyone who possesses the token.

Never store passwords, private information, or secrets inside a JWT payload.

# 5. Access Token vs Refresh Token

Professional authentication systems often use two types of tokens.

## 5.1 Access Token

An access token is used to access protected APIs.

Example:

```text
Access Token Expiration: 15 minutes
```

Usage:

```http
GET /api/v1/expenses
Authorization: Bearer ACCESS_TOKEN
```

The server verifies the token before processing the request.

## 5.2 Refresh Token

A refresh token is used to obtain a new access token when the existing access token expires.

Example:

```text
Refresh Token Expiration: 7 days
```

The refresh token should be handled more carefully because it can be used to obtain new access tokens.

### Why Use Two Tokens?

Suppose the access token expires after 15 minutes.

Without a refresh token, the user would need to log in again every 15 minutes.

With a refresh token, the client can request a new access token without asking the user to enter their password again.

### Access Token vs Refresh Token

| Feature | Access Token | Refresh Token |
|---|---|---|
| Purpose | Access protected APIs | Obtain new access token |
| Lifetime | Short | Longer |
| Used frequently | Yes | Only when refreshing |
| Sent to protected APIs | Yes | No |
| Storage | Client-side, preferably memory | Secure persistent storage |
| Revocation | Usually through short expiry or additional controls | Server-side revocation |

# 13. Create Token Service

Now we will implement JWT generation and verification.

Create:

```text
src/services/token.service.js
```

Code:

```javascript
const jwt = require("jsonwebtoken");

const crypto = require("crypto");

const env = require("../config/env");

class TokenService {

    generateAccessToken(user) {

        return jwt.sign(

            {

                sub: String(user.id),

                role: user.role

            },

            env.JWT_ACCESS_SECRET,

            {

                expiresIn: env.JWT_ACCESS_EXPIRES_IN,

                issuer: "expense-tracker-api",

                audience: "expense-tracker-client"

            }

        );

    }

    generateRefreshToken(user) {

        return jwt.sign(

            {

                sub: String(user.id),

                tokenType: "refresh"

            },

            env.JWT_REFRESH_SECRET,

            {

                expiresIn: env.JWT_REFRESH_EXPIRES_IN,

                issuer: "expense-tracker-api",

                audience: "expense-tracker-client"

            }

        );

    }

    verifyAccessToken(token) {

        return jwt.verify(

            token,

            env.JWT_ACCESS_SECRET,

            {

                issuer: "expense-tracker-api",

                audience: "expense-tracker-client"

            }

        );

    }

    verifyRefreshToken(token) {

        const payload = jwt.verify(

            token,

            env.JWT_REFRESH_SECRET,

            {

                issuer: "expense-tracker-api",

                audience: "expense-tracker-client"

            }

        );

        if (payload.tokenType !== "refresh") {

            throw new Error("Invalid token type");

        }

        return payload;

    }

    hashToken(token) {

        return crypto

            .createHash("sha256")

            .update(token)

            .digest("hex");

    }

}

module.exports = new TokenService();
```

### Understanding the Code

**Generate access token:**

```javascript
generateAccessToken(user)
```

Creates a short-lived token.

**Generate refresh token:**

```javascript
generateRefreshToken(user)
```

Creates a longer-lived token.

**Verify access token:**

```javascript
verifyAccessToken(token)
```

Checks its signature, expiration, issuer, and audience.

**Verify refresh token:**

```javascript
verifyRefreshToken(token)
```

Checks the refresh token and verifies its type.

**Hash token:**

```javascript
hashToken(token)
```

Creates a SHA-256 hash for database storage.

### Important Security Consideration

We use different secrets for access tokens and refresh tokens.

This prevents a token signed with one secret from being accepted by the other verification process.

Never commit these secrets to GitHub.

# 15. Create Authentication Service

This is where the authentication business logic lives.

Create:

```text
src/modules/auth/auth.service.js
```

Code:

```javascript
const bcrypt = require("bcrypt");

const crypto = require("crypto");

const sequelize = require("../../database/connection");

const AuthRepository = require("./auth.repository");

const tokenService = require("../../services/token.service");

const ApiError = require("../../utils/ApiError");

class AuthService {

    constructor() {

        this.authRepository = new AuthRepository();

    }

    async register(data) {

        const existingUser =
            await this.authRepository.findUserByEmail(data.email);

        if (existingUser) {

            throw new ApiError(409, "Email already registered");

        }

        const hashedPassword = await bcrypt.hash(

            data.password,

            12

        );

        const user = await this.authRepository.createUser({

            name: data.name,

            email: data.email,

            password: hashedPassword

        });

        return {

            id: user.id,

            name: user.name,

            email: user.email,

            role: user.role

        };

    }

    async login(email, password) {

        const user =
            await this.authRepository.findUserByEmail(email);

        if (!user) {

            throw new ApiError(401, "Invalid email or password");

        }

        const isPasswordValid = await bcrypt.compare(

            password,

            user.password

        );

        if (!isPasswordValid) {

            throw new ApiError(401, "Invalid email or password");

        }

        const accessToken =
            tokenService.generateAccessToken(user);

        const refreshToken =
            tokenService.generateRefreshToken(user);

        const tokenHash =
            tokenService.hashToken(refreshToken);

        const decoded =
            tokenService.verifyRefreshToken(refreshToken);

        await this.authRepository.createRefreshToken({

            userId: user.id,

            tokenHash,

            expiresAt: new Date(decoded.exp * 1000)

        });

        return {

            user: {

                id: user.id,

                name: user.name,

                email: user.email,

                role: user.role

            },

            accessToken,

            refreshToken

        };

    }

    async refresh(refreshToken) {

        let payload;

        try {

            payload = tokenService.verifyRefreshToken(refreshToken);

        } catch (error) {

            throw new ApiError(401, "Invalid or expired refresh token");

        }

        const tokenHash = tokenService.hashToken(refreshToken);

        const storedToken =
            await this.authRepository.findRefreshToken(tokenHash);

        if (!storedToken) {

            throw new ApiError(401, "Refresh token revoked or invalid");

        }

        const user =
            await this.authRepository.findUserById(payload.sub);

        if (!user) {

            throw new ApiError(401, "User not found");

        }

        const transaction = await sequelize.transaction();

        try {

            await this.authRepository.revokeRefreshToken(

                tokenHash,

                transaction

            );

            const newAccessToken =
                tokenService.generateAccessToken(user);

            const newRefreshToken =
                tokenService.generateRefreshToken(user);

            const newTokenHash =
                tokenService.hashToken(newRefreshToken);

            const newPayload =
                tokenService.verifyRefreshToken(newRefreshToken);

            await this.authRepository.createRefreshToken(

                {

                    userId: user.id,

                    tokenHash: newTokenHash,

                    expiresAt: new Date(newPayload.exp * 1000)

                },

                transaction

            );

            await transaction.commit();

            return {

                accessToken: newAccessToken,

                refreshToken: newRefreshToken

            };

        } catch (error) {

            await transaction.rollback();

            throw error;

        }

    }

    async logout(refreshToken) {

        if (!refreshToken) {

            return;

        }

        const tokenHash = tokenService.hashToken(refreshToken);

        await this.authRepository.revokeRefreshToken(tokenHash);

    }

}

module.exports = AuthService;
```

### Important: What Happens During Login?

1. Find the user by email.
2. Compare the password with the stored hash.
3. Generate an access token.
4. Generate a refresh token.
5. Hash the refresh token.
6. Store the hash in the database.
7. Return the user and tokens.

### Why Return a Generic Login Error?

Consider these two responses:

```text
Email does not exist.
```

```text
Password is incorrect.
```

They reveal whether an account exists.

A generic message reduces account-enumeration risk:

```text
Invalid email or password.
```

# 16. Understand Refresh Token Rotation

Notice what happens inside the refresh method.

Suppose the client has:

```text
Refresh Token A
```

The client requests a new access token.

The backend:

1. Verifies Token A.
2. Checks whether its hash exists in the database.
3. Revokes Token A.
4. Generates Token B.
5. Stores Token B's hash.
6. Returns the new tokens.

```text
REFRESH TOKEN A
       |
       v
   VALIDATE
       |
       v
   REVOKE A
       |
       v
 GENERATE B
       |
       v
   STORE B
       |
       v
 RETURN B
```

This is called **Refresh Token Rotation**.

### Why Is Rotation Important?

If a refresh token is stolen and reused after rotation, the server can identify that the token is no longer active.

Our simplified implementation rejects revoked tokens.

A more advanced production implementation can also track token families and detect refresh-token reuse, revoking the entire affected session family when reuse is detected.

```javascript
            .transform(value => value.toLowerCase()),

        password: z.string()
            .min(8)
            .max(72)

    }).strict()

});

const loginSchema = z.object({

    body: z.object({

        email: z.string()
            .trim()
            .email()
            .transform(value => value.toLowerCase()),

        password: z.string()
            .min(1)
            .max(72)

    }).strict()

});

module.exports = {

    registerSchema,

    loginSchema

};
```

### Why Use `.strict()`?

It rejects unexpected fields.

For example, a user might submit:

```json
{
    "name": "John",
    "email": "john@example.com",
    "password": "password123",
    "role": "admin"
}
```

Our registration schema does not accept `role`.

This prevents users from assigning themselves administrative privileges through the registration endpoint.

### Why Limit Password Length?

bcrypt has a maximum effective input length of 72 bytes.

Our schema limits passwords to 72 characters, but note that some Unicode characters occupy multiple bytes.

For strict byte-length enforcement, validate the UTF-8 byte length explicitly.

Also, use current password-security guidance when deciding minimum and maximum lengths.

# 22. Create Authentication Middleware

Now we need to protect private APIs.

Suppose someone requests:

```http
GET /api/v1/expenses
```

The backend should verify that the request contains a valid access token.

Create:

```text
src/middleware/authenticate.js
```

Code:

```javascript
const tokenService = require("../services/token.service");

const ApiError = require("../utils/ApiError");

function authenticate(req, res, next) {

    try {

        const authHeader = req.headers.authorization;

        if (!authHeader || !authHeader.startsWith("Bearer ")) {

            throw new ApiError(401, "Authentication required");

        }

        const token = authHeader.split(" ")[1];

        if (!token) {

            throw new ApiError(401, "Invalid access token");

        }

        const payload = tokenService.verifyAccessToken(token);

        req.user = {

            id: payload.sub,

            role: payload.role

        };

        next();

    } catch (error) {

        if (error instanceof ApiError) {

            return next(error);

        }

        return next(

            new ApiError(401, "Invalid or expired access token")

        );

    }

}

module.exports = authenticate;
```

### Understand the Bearer Token

A client sends:

```http
Authorization: Bearer eyJhbGciOiJIUzI1NiIs...
```

The backend extracts the token.

```javascript
const token = authHeader.split(" ")[1];
```

Then verifies it.

```javascript
const payload = tokenService.verifyAccessToken(token);
```

If valid, we attach the user information to the request:

```javascript
req.user = {
    id: payload.sub,
    role: payload.role
};
```

Now downstream controllers and services can access the authenticated user's identity.

### Important

`req.user` is populated by trusted server-side middleware.

Never trust a user ID sent in the request body as proof of identity.

# 23. Create Authorization Middleware

Authentication verifies identity.

Authorization checks permissions.

Create:

```text
src/middleware/authorize.js
```

Code:

```javascript
const ApiError = require("../utils/ApiError");

function authorize(...allowedRoles) {

    return (req, res, next) => {

        if (!req.user) {

            return next(

                new ApiError(401, "Authentication required")

            );

        }

        if (!allowedRoles.includes(req.user.role)) {

            return next(

                new ApiError(403, "You do not have permission")

            );

        }

        next();

    };

}

module.exports = authorize;
```

### How Does It Work?

Usage:

```javascript
authorize("admin")
```

Only admins can access the endpoint.

Usage:

```javascript
authorize("admin", "user")
```

Both roles can access it.

### Example

```javascript
router.get(

    "/admin/users",

    authenticate,

    authorize("admin"),

);
```

```text
REQUEST
   |
   v
AUTHENTICATE
   |
   v
TOKEN VALID?
   |
   v
AUTHORIZE
   |
   v
ADMIN ROLE?
   |
   v
CONTROLLER
```

If authentication fails, the response is `401`.

If authorization fails, the response is `403`.

# 24. Understand Resource Ownership Authorization

Role-based authorization is not sufficient for our Expense Tracker.

Consider:

```text
User A:
    Expense ID 1
    Expense ID 2

User B:
    Expense ID 3
    Expense ID 4
```

Suppose User A sends:

```http
GET /api/v1/expenses/3
```

The user has a valid token.

The user also has the correct `user` role.

But Expense ID 3 belongs to User B.

Therefore, the backend must reject the request.

This is called **resource ownership authorization**.

### Correct Sequelize Query

```javascript
const expense = await Expense.findOne({

    where: {

        id: req.params.id,

        userId: req.user.id

    }

});
```

This ensures that the requested expense belongs to the authenticated user.

### Why Is This Important?

A common API security vulnerability is Broken Object Level Authorization (BOLA).

It occurs when an application allows users to access objects they are not authorized to access.

Always validate ownership when accessing user-specific resources.

# 26. Understand Logout and Token Revocation

JWT access tokens are generally stateless.

That means the server does not necessarily store each access token.

Therefore, simply deleting a token from the frontend does not invalidate it on the server.

Our design uses refresh-token revocation.

### Logout Flow

```text
CLIENT
   |
   v
LOGOUT REQUEST
   |
   v
REFRESH TOKEN
   |
   v
HASH TOKEN
   |
   v
FIND STORED TOKEN
   |
   v
SET revoked_at
   |
   v
LOGOUT SUCCESS
```

Our authentication service already implements:

```javascript
async logout(refreshToken) {

    if (!refreshToken) {

        return;

    }

    const tokenHash = tokenService.hashToken(refreshToken);

    await this.authRepository.revokeRefreshToken(tokenHash);

}
```

After logout, the revoked refresh token cannot be used to obtain a new access token.

However, an already-issued access token remains valid until it expires unless you implement additional access-token revocation or session checks.

This is why short access-token lifetimes are important.

# 27. Browser Security: Where Should We Store Tokens?

This is an important production consideration.

There are different ways to store tokens on the client.

| Storage | Characteristics |
|---|---|
| JavaScript memory | Less persistent; lost on page reload |
| localStorage | Persistent but accessible to JavaScript |
| sessionStorage | Session-scoped but accessible to JavaScript |
| HttpOnly cookie | Not directly accessible to JavaScript |

### Why Avoid Storing Sensitive Refresh Tokens in localStorage?

If an attacker executes JavaScript through an XSS vulnerability, they may be able to read tokens stored in localStorage.

For browser applications, a common design is:

- Keep access token in memory.
- Store refresh token in an HttpOnly cookie.
- Use Secure cookies over HTTPS.
- Configure SameSite appropriately.
- Protect cookie-based state-changing requests against CSRF.

### Example Cookie Configuration

```javascript
res.cookie("refreshToken", refreshToken, {

    httpOnly: true,

    secure: process.env.NODE_ENV === "production",

    sameSite: "lax",

    path: "/api/v1/auth",

    maxAge: 7 * 24 * 60 * 60 * 1000

});
```

### What Does HttpOnly Mean?

JavaScript running in the browser cannot directly read the cookie through `document.cookie`.

### What Does Secure Mean?

The browser sends the cookie only over secure HTTPS connections.

### What Does SameSite Mean?

It controls when cookies are included in cross-site requests.

`SameSite=Lax` is a common starting point, but the correct setting depends on your frontend/backend deployment arrangement.

For cross-site frontend and backend deployments, you may need:

```javascript
sameSite: "none",
secure: true
```

In that configuration, implement appropriate CSRF protections.

### Important

Our earlier controller example returned the refresh token in JSON for simplicity.

For a browser application, we should modify the controller to set the refresh token in an HttpOnly cookie rather than exposing it to JavaScript.

For mobile applications or non-browser clients, use an appropriate secure token-storage mechanism.

# 28. Implement Forgot Password Workflow

Now let's understand how password recovery works.

Suppose a user forgets their password.

They should be able to reset it without knowing the old password.

### Forgot Password Flow

```text
USER
  |
  v
FORGOT PASSWORD
  |
  v
ENTER EMAIL
  |
  v
BACKEND
  |
  v
GENERATE RESET TOKEN
  |
  v
STORE TOKEN HASH
  |
  v
SEND RESET EMAIL
  |
  v
USER OPENS RESET LINK
  |
  v
ENTER NEW PASSWORD
  |
  v
VERIFY RESET TOKEN
  |
  v
HASH NEW PASSWORD
  |
  v
UPDATE DATABASE
```

### Important Security Rules

1. Do not reveal whether an email address is registered.
2. Use a cryptographically random reset token.
3. Store only its hash.
4. Set a short expiration time.
5. Make the token single-use.
6. Invalidate existing refresh sessions after a successful password reset.
7. Send the reset link through a trusted email provider.
8. Rate-limit reset requests.

### Example Token Generation

```javascript
const crypto = require("crypto");

const resetToken = crypto.randomBytes(32).toString("hex");
```

Hash it before storing:

```javascript
const tokenHash = crypto

    .createHash("sha256")

    .update(resetToken)

    .digest("hex");
```

The raw token is sent to the user.

The database stores only the hash.

We will implement the complete password-reset workflow in a later part of the project.

# 32. Common Authentication Security Mistakes

These mistakes should be avoided in production applications.

### Mistake 1: Storing Plain-Text Passwords

Always use a password-hashing algorithm such as bcrypt or Argon2id.

### Mistake 2: Using the Same JWT Secret Everywhere

Use separate secrets for access and refresh tokens.

### Mistake 3: Never Expiring Access Tokens

Use short-lived access tokens.

### Mistake 4: Trusting User IDs From Request Bodies

Use the authenticated identity from `req.user`.

### Mistake 5: Not Checking Resource Ownership

Always ensure that the requested resource belongs to the authenticated user or that the user has another valid permission to access it.

### Mistake 6: Storing Refresh Tokens as Plain Text

Store their hashes and support revocation.

### Mistake 7: Returning Password Hashes in API Responses

Never expose password hashes.

### Mistake 8: Allowing Users to Set Their Own Role

Never accept an unrestricted `role` field during public registration.

### Mistake 9: No Login Rate Limiting

Attackers may repeatedly attempt passwords.

Use rate limiting and monitoring on authentication endpoints.

### Mistake 10: Not Validating JWT Claims

Verify:

- Signature.
- Expiration.
- Issuer.
- Audience.
- Token purpose/type.

### Mistake 11: Ignoring CSRF

Cookie-based authentication needs an appropriate CSRF defense for state-changing requests.

### Mistake 12: Ignoring XSS

HttpOnly cookies reduce token theft through JavaScript access, but they do not eliminate XSS risks.

Continue using output encoding, input handling, and a suitable Content Security Policy.

# 34. Interview Questions and Answers

### Q1. What is authentication?

Authentication verifies the identity of a user.

### Q2. What is authorization?

Authorization determines what an authenticated user is allowed to access or perform.

### Q3. What is the difference between 401 and 403?

401 means authentication is missing or invalid. 403 means the identity is known, but access is not permitted.

### Q4. What is password hashing?

Password hashing converts a password into a one-way representation suitable for secure storage.

### Q5. What is bcrypt?

bcrypt is a password-hashing algorithm designed to make password guessing computationally expensive.

### Q6. What is a salt?

A salt is random data incorporated into password hashing to prevent identical passwords from producing identical hashes.

### Q7. What is JWT?

JSON Web Token is a compact format for representing claims that can be digitally signed or encrypted.

### Q8. What are the three parts of a JWT?

Header, payload, and signature.

### Q9. Is JWT payload encrypted?

Not necessarily. A normal signed JWT has a readable payload.

### Q10. What is an access token?

A short-lived token used to access protected resources.

### Q11. What is a refresh token?

A longer-lived credential used to obtain new access tokens.

### Q12. Why use access and refresh tokens?

It allows short access-token lifetimes without forcing users to log in repeatedly.

### Q13. What is JWT middleware?

Middleware that extracts and verifies a JWT before allowing access to protected routes.

### Q14. What is RBAC?

Role-Based Access Control assigns permissions according to user roles.

### Q15. What is resource ownership authorization?

It checks whether the authenticated user owns or otherwise has permission to access a specific resource.

### Q16. What is refresh-token rotation?

It replaces a refresh token with a new token whenever the refresh operation succeeds.

### Q17. Can JWT be revoked?

A self-contained JWT generally remains valid until expiration unless additional server-side revocation or validation mechanisms are implemented.

### Q18. Why hash refresh tokens in the database?

It reduces the damage if the token database is compromised.

### Q19. What is BOLA?

Broken Object Level Authorization is a security vulnerability where users can access objects they are not authorized to access.

### Q20. Why should we not store passwords in JWT payloads?

JWT payloads are generally readable, and passwords are highly sensitive information.

### Q21. What is HttpOnly?

It is a cookie attribute that prevents JavaScript from directly accessing the cookie.

### Q22. What is CSRF?

Cross-Site Request Forgery is an attack that tricks a user's browser into making an unwanted authenticated request.

### Q23. What is XSS?

Cross-Site Scripting is a vulnerability that allows attackers to execute malicious scripts in a user's browser.

### Q24. What is token rotation?

Token rotation replaces an existing token with a newly issued token.

### Q25. Why should registration not accept the role field?

Otherwise, a user could potentially assign themselves an administrative role.
