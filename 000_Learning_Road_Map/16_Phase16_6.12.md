## 1. Introduction to Caching

As applications grow, the number of API requests and database queries increases.

Suppose our Expense Tracker has 10,000 users.

Every time a user opens the dashboard, the backend executes multiple database queries:

1. Calculate total income.
2. Calculate total expenses.
3. Calculate net balance.
4. Calculate category-wise expenses.
5. Calculate monthly spending.
6. Retrieve recent transactions.
7. Calculate budget utilization.

If thousands of users repeatedly request this information, the database has to execute many queries.

This can increase:

- Database CPU usage.
- Query execution time.
- Server load.
- API response time.
- Infrastructure costs.

**Caching** helps reduce repeated computation and database access.

### What is caching?

Caching is the process of temporarily storing frequently accessed data so that future requests can retrieve it faster.

Instead of querying MySQL every time, we can retrieve previously calculated results from a cache.

### Without caching

```text
Client Request
      |
      v
Node.js Backend
      |
      v
    MySQL
      |
      v
Execute SQL Queries
      |
      v
Return Response
```

Every request queries the database.

### With caching

```text
Client Request
      |
      v
Node.js Backend
      |
      v
    Redis
      |
      v
  Cache Exists?
      |
   +--+--+
   |     |
  YES    NO
   |     |
   v     v
Return  Query MySQL
Cache      |
   |       v
   |    Store in Redis
   |       |
   +---+---+
       |
       v
   Return Response
```

This approach can significantly reduce database workload for suitable read-heavy operations.

# 2. What Is Redis?

Redis is an in-memory data store used for caching, queues, real-time data, and other application workloads.

Redis stores data primarily in memory, which allows very fast data access.

Official website: [Redis](https://redis.io/?utm_source=chatgpt.com)

### Why is Redis fast?

Traditional databases such as MySQL commonly store persistent data on disk, using memory and disk together.

Redis primarily operates on data in RAM.

RAM access is significantly faster than accessing persistent storage.

### Redis vs MySQL

| Feature | Redis | MySQL |
|---|---|---|
| Primary purpose | In-memory data store | Relational database |
| Data model | Key-value and data structures | Tables and relationships |
| Storage | Primarily memory | Persistent storage |
| Query language | Redis commands | SQL |
| Relationships | No relational foreign keys | Supports foreign keys |
| Transactions | Redis transactions and scripts | ACID database transactions |
| Typical use | Cache, queues, sessions | Application's primary data |
| Data persistence | Optional/configurable | Persistent by default |

### Important

Redis is not a replacement for MySQL in our Expense Tracker.

We will use:

- MySQL for users, expenses, incomes, budgets, and financial records.
- Redis for caching, frequently accessed data, and selected temporary application data.

# 3. Understanding Cache Hit and Cache Miss

These two terms are fundamental to caching.

## 3.1 Cache Hit

A cache hit occurs when the requested data already exists in the cache.

Example:

```text
Request: GET /dashboard

Redis:
dashboard:user:10

Result: Found
```

The backend returns the cached result.

No MySQL query is needed for that cached response.

## 3.2 Cache Miss

A cache miss occurs when the requested data does not exist in the cache.

Example:

```text
Request: GET /dashboard

Redis:
dashboard:user:10

Result: Not Found
```

The backend retrieves the data from MySQL and may store it in Redis for future requests.

### Comparison

| Cache Hit | Cache Miss |
|---|---|
| Data found in cache | Data not found in cache |
| Usually faster | Requires fetching from another source |
| May avoid database queries | Usually triggers database queries |
| Returns cached data | Can populate cache |

### Cache Hit Ratio

Cache hit ratio measures how often requests are served from the cache.

Formula:

```text
Cache Hit Ratio =
(Cache Hits / Total Cache Requests) × 100
```

Example:

```text
Total Requests = 1,000

Cache Hits = 800

Cache Misses = 200
```

Calculation:

```text
(800 / 1000) × 100 = 80%
```

Cache hit ratio:

```text
80%
```

A higher hit ratio can indicate effective caching, but it does not automatically mean the application is faster. Also measure latency, database load, and cache memory usage.

# 4. Redis Data Types

Redis supports several data structures.

Let's understand the most important ones.

## 4.1 Strings

Strings are the simplest Redis data type.

They can store:

- Text.
- Numbers.
- JSON strings.
- Serialized application data.

Example:

```redis
SET username "John"
```

Retrieve:

```redis
GET username
```

Output:

```text
"John"
```

### Store a number

```redis
SET visits 100
```

Increment:

```redis
INCR visits
```

Output:

```text
(integer) 101
```

Useful for:

- Simple cache values.
- Counters.
- Temporary tokens.
- Feature flags.

## 4.2 Lists

Redis lists are ordered collections of strings.

Example:

```redis
LPUSH notifications "Notification 1"

LPUSH notifications "Notification 2"
```

Retrieve:

```redis
LRANGE notifications 0 -1
```

Useful for:

- Simple queues.
- Recent activity.
- Ordered data collections.

## 4.3 Sets

Sets store unique values.

Example:

```redis
SADD activeUsers 10

SADD activeUsers 20

SADD activeUsers 10
```

The value `10` is not duplicated.

Retrieve:

```redis
SMEMBERS activeUsers
```

Useful for:

- Unique collections.
- Membership checks.
- Tags.
- Unique user IDs.

## 4.4 Sorted Sets

Sorted sets store unique members associated with scores.

Example:

```redis
ZADD leaderboard 100 user1

ZADD leaderboard 200 user2

ZADD leaderboard 150 user3
```

Retrieve:

```redis
ZRANGE leaderboard 0 -1 WITHSCORES
```

Useful for:

- Leaderboards.
- Ranking.
- Time-based ordering.
- Priority systems.

## 4.5 Hashes

Hashes store field-value pairs.

Example:

```redis
HSET user:10 name "John" email "john@example.com"
```

Retrieve one field:

```redis
HGET user:10 name
```

Retrieve all fields:

```redis
HGETALL user:10
```

Useful for:

- User session information.
- Structured objects.
- Counters and metadata.

## 4.6 Streams

Redis Streams provide an append-only data structure for event-oriented data processing.

Example:

```redis
XADD expense-events * userId 10 amount 500
```

Retrieve events:

```redis
XRANGE expense-events - +
```

Useful for:

- Event processing.
- Message streams.
- Consumer groups.
- Event-driven systems.

### Data Type Summary

| Data Type | Purpose |
|---|---|
| String | Simple key-value data |
| List | Ordered collection |
| Set | Unique collection |
| Sorted Set | Ordered by score |
| Hash | Field-value objects |
| Stream | Event stream |

# 7. Understanding TTL

TTL stands for:

**Time To Live.**

It defines how long a key should remain available before automatic expiration.

Example:

```redis
SET dashboard:user:10 '{"totalExpenses":5000}' EX 300
```

This cache entry expires after five minutes.

Check TTL:

```redis
TTL dashboard:user:10
```

Possible results:

| Result | Meaning |
|---|---|
| Positive number | Remaining seconds |
| `-1` | Key exists without expiration |
| `-2` | Key does not exist |

### Why is TTL important?

Suppose a user opens their dashboard.

We cache the dashboard for five minutes.

If the user does not modify any financial records, subsequent requests can use the cached response.

After five minutes, Redis automatically expires the key.

The next request fetches fresh data from MySQL.

### TTL Examples

| Data | Possible TTL |
|---|---|
| Dashboard summary | 1–5 minutes |
| Category list | 30 minutes |
| User profile | 5–15 minutes |
| Frequently accessed configuration | 1 hour |
| OTP | 5 minutes |
| Temporary verification state | Application-dependent |

These are starting points, not universal rules. Choose TTL according to freshness requirements and invalidation strategy.

# 9. Storing JSON Data in Redis

Our Expense Tracker mostly works with structured data.

For example:

```javascript
const dashboard = {

    totalIncome: "50000.00",

    totalExpenses: "15000.00",

    balance: "35000.00",

    savingsRate: 70

};
```

Redis strings can store serialized JSON.

### Store JSON

```javascript
await redis.set(

    "dashboard:user:10",

    JSON.stringify(dashboard)

);
```

### Retrieve JSON

```javascript
const result = await redis.get("dashboard:user:10");

const dashboardData = result
    ? JSON.parse(result)
    : null;
```

### Store JSON with TTL

```javascript
await redis.set(

    "dashboard:user:10",

    JSON.stringify(dashboard),

    "EX",

    300

);
```

Now the key expires after five minutes.

### Important

JSON serialization does not preserve every JavaScript type.

For example:

- `Date` objects become strings.
- `undefined` object properties are omitted.
- `BigInt` cannot be directly serialized with `JSON.stringify()`.
- Class instances lose their prototype behavior.

Convert data into a deliberate JSON-safe DTO before caching.

For financial values, preserve decimal strings instead of converting them to floating-point numbers.

# 10. What Is Cache-Aside Pattern?

Cache-aside is one of the most commonly used caching strategies.

It works like this:

1. Application checks Redis.
2. If the data exists, return it.
3. If the data does not exist, query MySQL.
4. Store the result in Redis.
5. Return the result.

### Architecture

```text
             API REQUEST
                  |
                  v
             CHECK REDIS
                  |
             +----+----+
             |         |
           FOUND     NOT FOUND
             |         |
             v         v
         RETURN     QUERY MYSQL
         CACHE          |
                        v
                    STORE CACHE
                        |
                        v
                    RETURN DATA
```

### Example Without Caching

```javascript
async function getUser(userId) {

    return await User.findByPk(userId);

}
```

Every request queries MySQL.

### Example With Cache-Aside

```javascript
const redis = require("../../config/redis");

const {
    User
} = require("../../database/models");


async function getUser(userId) {

    const cacheKey = `user:${userId}`;


    // Step 1: Check Redis

    const cachedUser = await redis.get(cacheKey);


    if (cachedUser) {

        return JSON.parse(cachedUser);

    }


    // Step 2: Query MySQL

    const user = await User.findByPk(userId, {

        attributes: [
            "id",
            "name",
            "email"
        ]

    });


    if (!user) {

        return null;

    }


    // Step 3: Store in Redis

    await redis.set(

        cacheKey,

        JSON.stringify(user.toJSON()),

        "EX",

        300

    );


    return user;

}
```

### What happens?

First request:

```text
Redis: Cache Miss

MySQL: Query Executed

Redis: Data Stored

Response: Returned
```

Second request:

```text
Redis: Cache Hit

MySQL: No Query

Response: Returned
```

This reduces repeated database reads.

# 11. Implementing a Reusable Cache Service

Instead of writing Redis commands in every service, create a reusable cache service.

### Project Structure

```text
src/
│
├── config/
│   └── redis.js
│
├── services/
│   └── cache.service.js
│
└── modules/
    └── dashboard/
```

### cache.service.js

```javascript
const redis = require("../config/redis");


class CacheService {

    async get(key) {

        const value = await redis.get(key);

        if (!value) {

            return null;

        }

        return JSON.parse(value);

    }


    async set(key, value, ttl = 300) {

        return await redis.set(

            key,

            JSON.stringify(value),

            "EX",

            ttl

        );

    }


    async delete(key) {

        return await redis.del(key);

    }


    async exists(key) {

        return await redis.exists(key);

    }


    async expire(key, seconds) {

        return await redis.expire(key, seconds);

    }


    async getTTL(key) {

        return await redis.ttl(key);

    }

}


module.exports = new CacheService();
```

### Usage

```javascript
const cacheService = require("../../services/cache.service");


await cacheService.set(

    "user:10",

    {
        name: "John",
        email: "john@example.com"
    },

    300

);


const user = await cacheService.get("user:10");
```

Now cache operations are reusable throughout the application.

### Production Improvement

This basic service assumes every cached value is valid JSON.

For production, consider:

- Handling malformed cache entries.
- Adding structured logging.
- Supporting versioned keys.
- Setting sensible TTL limits.
- Handling Redis connection failures.
- Avoiding caching sensitive information.

# 12. Caching Our Expense Tracker Dashboard

Now let's implement something practical.

Our dashboard API calculates:

- Total income.
- Total expenses.
- Net balance.
- Savings rate.
- Category-wise expenses.
- Recent transactions.

These calculations may be expensive if performed repeatedly.

We can cache the dashboard response.

### Dashboard Service

```javascript
const cacheService = require("../../services/cache.service");

const dashboardRepository =
    require("./dashboard.repository");


class DashboardService {

    async getDashboard(userId, startDate, endDate) {

        const cacheKey =
            `dashboard:v1:${userId}:${startDate}:${endDate}`;


        // Check cache

        const cachedData = await cacheService.get(cacheKey);


        if (cachedData) {

            return cachedData;

        }


        // Fetch from MySQL

        const summary =
            await dashboardRepository.getSummary(
                userId,
                startDate,
                endDate
            );


        const categoryTotals =
            await dashboardRepository.getCategoryTotals(
                userId,
                startDate,
                endDate
            );


        const recentTransactions =
            await dashboardRepository.getRecentTransactions(
                userId
            );


        const dashboard = {

            summary,

            categoryTotals,

            recentTransactions

        };


        // Store in Redis

        await cacheService.set(

            cacheKey,

            dashboard,

            300

        );


        return dashboard;

    }

}


module.exports = new DashboardService();
```

### Understanding the Cache Key

```javascript
`dashboard:v1:${userId}:${startDate}:${endDate}`
```

Example:

```text
dashboard:v1:10:2026-11-01:2026-11-30
```

Why include these values?

Because the dashboard data depends on:

- User ID.
- Start date.
- End date.

If we use only:

```text
dashboard
```

different users could receive the same cached data.

That would be a serious data isolation and security bug.

**Rule:** A cache key must include every input that materially changes the cached result, including tenant, authorization scope, filters, and representation where applicable.

# 13. Cache Invalidation

One of the hardest problems in caching is keeping cached data up to date.

Suppose a user opens their dashboard.

Redis stores:

```json
{
    "totalExpenses": "10000.00"
}
```

Now the user creates another expense of ₹2,000.

MySQL now contains:

```json
{
    "totalExpenses": "12000.00"
}
```

But Redis still contains:

```json
{
    "totalExpenses": "10000.00"
}
```

The cached data is stale.

This is called a cache invalidation problem.

### What is cache invalidation?

Cache invalidation is the process of removing or updating cached data when the underlying source data changes.

### Common Strategies

1. TTL-based expiration.
2. Delete-on-write.
3. Update-on-write.
4. Versioned cache keys.
5. Event-driven invalidation.

---

# 14. Delete-on-Write Strategy

This is a common approach.

Whenever the underlying data changes, delete the related cache entry.

Example:

```javascript
await Expense.create(expenseData);

await redis.del(`dashboard:user:${userId}`);
```

But our dashboard cache keys also contain dates.

Therefore, deleting only:

```text
dashboard:user:10
```

will not remove keys such as:

```text
dashboard:v1:10:2026-11-01:2026-11-30
```

We need a better invalidation strategy.

### Option 1: Redis SCAN

We can search for keys matching:

```text
dashboard:v1:10:*
```

Using Redis SCAN and delete matching keys.

However, scanning a large keyspace on every expense creation is inefficient.

Do not build routine request-time invalidation around broad key scans.

### Option 2: Cache Versioning

A better approach for this dashboard is to maintain a per-user cache version.

Example:

```text
dashboard:version:10 = 1
```

Cache key:

```text
dashboard:v1:user:10:version:1:2026-11
```

When the user creates an expense, increment the version:

```redis
INCR dashboard:version:10
```

Now the version becomes:

```text
2
```

The application looks for:

```text
dashboard:v1:user:10:version:2:2026-11
```

The old cached key is no longer used.

It will expire automatically according to its TTL.

### Advantages

- No need to search and delete many keys.
- Simple invalidation.
- Useful for user-specific dashboard caches.

### Important

If you use this approach, initialize the version consistently and handle a missing version as an initial version.

The version increment should be performed after the database write succeeds. For stronger reliability, use an outbox event to invalidate or update the cache after commit.

# 15. Update Cache After Write

Another strategy is to update the cache whenever data changes.

Example:

```javascript
await Expense.create(expenseData);

const updatedTotal =
    await Expense.sum("amount", {
        where: {
            userId
        }
    });

await redis.set(

    `expenses:total:${userId}`,

    String(updatedTotal ?? "0"),

    "EX",

    300

);
```

This ensures the cached total reflects the new database state after the query.

However, this example calculates the total for all expenses, not a specific dashboard date range.

### Advantages

- Cached data can remain fresh.
- Future reads may avoid database queries.

### Disadvantages

- Additional database work during writes.
- More complicated concurrent updates.
- Greater implementation complexity.

For our Expense Tracker, delete-on-write or version-based invalidation is a sensible starting point.

# 16. Cache Stampede Problem

Another important caching problem is cache stampede.

Suppose a popular cache key expires.

At that moment, 1,000 requests arrive.

All 1,000 requests see a cache miss.

All 1,000 requests query MySQL.

This can overload the database.

### Architecture

```text
             CACHE EXPIRES
                   |
                   v
            1,000 REQUESTS
                   |
                   v
              CACHE MISS
                   |
          +--------+--------+
          |        |        |
          v        v        v
        Query    Query    Query
        MySQL    MySQL    MySQL
          |        |        |
          +--------+--------+
                   |
                   v
             DATABASE LOAD
```

This is called a cache stampede.

### How to prevent it?

Common approaches:

1. Distributed locks.
2. Request coalescing.
3. Stale-while-revalidate.
4. Randomized TTL.
5. Prewarming popular cache entries.

### Simple Randomized TTL

Instead of using exactly 300 seconds for every key:

```javascript
const ttl = 300 + Math.floor(Math.random() * 60);
```

This gives a TTL between approximately 300 and 359 seconds.

It reduces the likelihood that many keys expire at exactly the same moment.

It does not, by itself, prevent simultaneous requests for one popular key from causing a stampede.

### Request Coalescing

Request coalescing means multiple requests for the same missing key share one database operation.

A process-local example:

```javascript
const pendingRequests = new Map();


async function getCachedData(key, fetchFunction) {

    const cached = await redis.get(key);

    if (cached) {

        return JSON.parse(cached);

    }


    if (pendingRequests.has(key)) {

        return pendingRequests.get(key);

    }


    const promise = (async () => {

        try {

            const data = await fetchFunction();

            await redis.set(
                key,
                JSON.stringify(data),
                "EX",
                300
            );

            return data;

        } finally {

            pendingRequests.delete(key);

        }

    })();


    pendingRequests.set(key, promise);

    return promise;

}
```

This shares work within one Node.js process.

For multiple application instances, use a distributed coordination strategy if necessary.

# 17. Cache-Aside vs Write-Through vs Write-Behind

These are common caching strategies.

## 17.1 Cache-Aside

Application manages cache reads and writes.

```text
Read:
Redis → MySQL on miss

Write:
MySQL → Invalidate Redis
```

This is the strategy we implemented earlier.

## 17.2 Write-Through

Application writes to the cache and underlying database as part of the same logical write workflow.

Conceptually:

```text
Application
     |
     v
Cache Layer
     |
     v
Database
```

The cache is updated as data is written.

The exact consistency guarantees depend on the implementation. Redis and MySQL do not share a normal atomic transaction.

## 17.3 Write-Behind

Application writes to the cache first, and the database is updated asynchronously later.

```text
Application
     |
     v
Redis
     |
     v
Background Worker
     |
     v
MySQL
```

This can improve write latency, but introduces durability and consistency risks.

For financial records such as expenses and incomes, do not treat Redis as the authoritative write store.

Use MySQL as the source of truth.

### Comparison

| Strategy | Read | Write |
|---|---|---|
| Cache-Aside | Cache, then DB on miss | DB, then invalidate/update cache |
| Write-Through | Usually cache | Cache and DB together logically |
| Write-Behind | Cache | Cache first, DB later |

# 18. Redis Caching in Express Middleware

We can also build reusable Express middleware to cache API responses.

Example:

```javascript
const redis = require("../config/redis");


function cacheMiddleware(ttl = 60) {

    return async (req, res, next) => {

        try {

            const cacheKey =
                `api:${req.originalUrl}`;


            const cachedResponse =
                await redis.get(cacheKey);


            if (cachedResponse) {

                return res.json(
                    JSON.parse(cachedResponse)
                );

            }


            const originalJson = res.json.bind(res);


            res.json = (body) => {

                redis.set(

                    cacheKey,

                    JSON.stringify(body),

                    "EX",

                    ttl

                ).catch(console.error);


                return originalJson(body);

            };


            next();

        } catch (error) {

            next(error);

        }

    };

}


module.exports = cacheMiddleware;
```

### Usage

```javascript
router.get(

    "/categories",

    authenticate,

    cacheMiddleware(300),

    categoryController.getCategories

);
```

### Important Security Problem

The example key:

```javascript
`api:${req.originalUrl}`
```

is insufficient for authenticated and user-specific endpoints.

Two users may request the same URL but should receive different results.

For private APIs, the cache key must include the authenticated user's ID and all relevant query parameters.

Also:

- Do not cache sensitive responses by default.
- Do not cache arbitrary POST/PUT/PATCH/DELETE responses.
- Avoid storing responses containing private information without a clear policy.
- Handle cache write failures without breaking the response.
- Consider `Cache-Control` and HTTP caching semantics.
- Prefer service-level caching when business data and authorization rules are complex.

For our Expense Tracker, service-level caching is preferable for the dashboard.

# 19. Redis Memory Management

Redis uses memory to store data.

If the cache grows without limits, Redis can run out of memory.

Redis supports memory management policies.

### Important Concepts

**maxmemory**

Defines the maximum memory Redis should use for its dataset.

**Eviction Policy**

Defines what Redis does when it reaches its memory limit and needs to store additional data.

### Common Eviction Policies

| Policy | Meaning |
|---|---|
| noeviction | Reject writes that require additional memory |
| allkeys-lru | Evict least recently used keys from all keys |
| volatile-lru | Evict least recently used keys with expiration |
| allkeys-lfu | Evict least frequently used keys from all keys |
| volatile-lfu | Evict least frequently used keys with expiration |
| allkeys-random | Evict random keys |
| volatile-ttl | Evict keys with the shortest remaining TTL |

### What is LRU?

LRU stands for:

**Least Recently Used.**

It removes keys that have not been accessed recently.

### What is LFU?

LFU stands for:

**Least Frequently Used.**

It removes keys that are accessed less frequently.

### Configuration Example

In Redis configuration:

```text
maxmemory 256mb

maxmemory-policy allkeys-lru
```

This is an example, not a universal production configuration.

Choose a policy based on the type of data stored.

For example, a Redis instance used for BullMQ jobs should not casually evict queue data. It may be better to separate queue data from disposable application cache data.

# 20. Cache Consistency

Caching introduces a new challenge: the cache and database can temporarily contain different values.

Example:

MySQL:

```text
Total Expenses = ₹15,000
```

Redis:

```text
Total Expenses = ₹12,000
```

This is called stale or inconsistent cached data.

### Why does this happen?

- Data was modified in MySQL.
- Cache invalidation did not occur.
- Cache expiration has not happened yet.
- An application process failed before invalidating the cache.
- Concurrent requests updated data in an unexpected order.

### Strategies to improve consistency

1. Use appropriate TTLs.
2. Invalidate cache after successful database writes.
3. Use versioned cache keys.
4. Use reliable event delivery.
5. Use the transactional outbox pattern.
6. Avoid caching data that requires immediate consistency.

### Financial Data Recommendation

For our Expense Tracker:

- Expense creation and updates must be committed to MySQL.
- Financial records must never depend on Redis as their only source of truth.
- Dashboard summaries may be cached briefly.
- Cache invalidation should occur after successful database changes.
- Critical financial decisions should use authoritative database data.

For example, do not use a stale cached balance to authorize a financial transfer.

# 21. Redis Caching Best Practices

| Area | Recommendation |
|---|---|
| Cache keys | Use consistent naming conventions |
| TTL | Set expiration for temporary cached data |
| Cache values | Store deliberate JSON-safe DTOs |
| Security | Include user/tenant scope in private cache keys |
| Invalidation | Invalidate after successful writes |
| Large values | Avoid unnecessarily large cache entries |
| Memory | Configure memory limits and eviction |
| Monitoring | Track hit ratio and latency |
| Redis failure | Decide whether the application should fall back to MySQL |
| Financial data | Keep MySQL as the source of truth |
| Deployment | Use private networking and authentication |
| Cache stampede | Consider request coalescing and distributed coordination |

### Naming Convention

Prefer meaningful key names.

Examples:

```text
user:10

user:10:profile

dashboard:v1:10:2026-11

expenses:total:10

notifications:unread:10

categories:global
```

Avoid unclear keys such as:

```text
data1

cache2

temp123
```

### Cache Versioning

When the cached data structure changes, version the key.

Example:

```text
dashboard:v1:10
```

Later:

```text
dashboard:v2:10
```

This prevents newer application code from accidentally reading old cached structures.

# 24. Interview Questions and Answers

### Q1. What is caching?

Caching is the process of storing frequently accessed data temporarily to reduce repeated computation and improve retrieval performance.

### Q2. What is Redis?

Redis is an in-memory data store that supports multiple data structures and is commonly used for caching and queues.

### Q3. Why is Redis fast?

Redis primarily stores and processes data in memory, reducing the need for slower persistent-storage access on common operations.

### Q4. What is a cache hit?

A cache hit occurs when requested data is found in the cache.

### Q5. What is a cache miss?

A cache miss occurs when requested data is not found in the cache.

### Q6. What is TTL?

Time To Live defines how long a cache key remains available before expiration.

### Q7. What is cache invalidation?

Cache invalidation is the process of removing or updating cached data when the original data changes.

### Q8. What is the cache-aside pattern?

An application checks the cache first, fetches data from the database on a miss, and then stores the result in the cache.

### Q9. What is write-through caching?

Write-through caching updates the cache and the underlying database as part of the same logical write workflow.

### Q10. What is write-behind caching?

Write-behind caching stores changes in the cache first and persists them to the database asynchronously.

### Q11. What is a cache stampede?

A cache stampede occurs when many requests simultaneously miss an expired cache entry and overload the underlying database.

### Q12. What is LRU?

Least Recently Used is an eviction strategy that removes less recently accessed keys.

### Q13. What is LFU?

Least Frequently Used is an eviction strategy that removes less frequently accessed keys.

### Q14. What is cache consistency?

Cache consistency refers to keeping cached data sufficiently aligned with the authoritative data source.

### Q15. Why should cache keys contain user IDs?

To prevent different users from accidentally receiving each other's cached private data.

### Q16. Why should financial records not depend on Redis?

Because financial records require durable, authoritative storage and strong consistency guarantees. MySQL should remain the source of truth.

### Q17. What is a cache hit ratio?

It is the percentage of cache requests successfully served from the cache.

### Q18. What is Redis eviction?

Eviction is the process of removing keys when Redis reaches its configured memory limit.

### Q19. What is the difference between Redis and MySQL?

Redis is primarily an in-memory data store, while MySQL is a relational database designed for persistent structured data and relational queries.

### Q20. What is the Transactional Outbox Pattern?

It stores business data changes and corresponding events within one database transaction so that events can be published reliably afterward.
