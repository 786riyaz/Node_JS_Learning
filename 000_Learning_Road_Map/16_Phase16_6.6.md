## 1. Introduction

In the previous part, we implemented the Expense Management Module.

Now we will implement the **Income Management Module**.

An Expense Tracker should manage both money going out and money coming in.

For example:

| Income Source | Amount |
|---|---:|
| Monthly Salary | ₹50,000 |
| Freelancing | ₹15,000 |
| Business | ₹20,000 |
| Investments | ₹5,000 |
| **Total Income** | **₹90,000** |

Our Income Management Module will allow users to:

1. Create income records.
2. Retrieve all income records.
3. Retrieve a specific income record.
4. Update income records.
5. Delete income records.
6. Search income records.
7. Filter by category.
8. Filter by date range.
9. Filter by amount.
10. Sort and paginate results.

### Expense vs Income

| Feature | Expense | Income |
|---|---|---|
| Money movement | Money goes out | Money comes in |
| Example | Shopping | Salary |
| Category type | expense | income |
| Database table | expenses | incomes |
| Create API | POST /expenses | POST /incomes |
| Update API | PATCH /expenses/:id | PATCH /incomes/:id |

The architecture will be almost identical to our Expense Management Module.

The main differences will be:

- We will use the `Income` model.
- We will validate categories with `type: "income"`.
- We will use the `incomes` database table.

# 3. Sequelize Model Associations

We already defined the Expense associations.

Now ensure that Income associations are also registered.

Open your model association initialization file.

```javascript
// User has many incomes

User.hasMany(Income, {
    foreignKey: "userId",
    as: "incomes"
});

Income.belongsTo(User, {
    foreignKey: "userId",
    as: "user"
});


// Category has many incomes

Category.hasMany(Income, {
    foreignKey: "categoryId",
    as: "incomes"
});

Income.belongsTo(Category, {
    foreignKey: "categoryId",
    as: "category"
});
```

### Why do we use aliases?

Consider:

```javascript
Income.belongsTo(Category, {
    foreignKey: "categoryId",
    as: "category"
});
```

The alias is:

```javascript
as: "category"
```

Therefore, when using eager loading, we must use the same alias:

```javascript
const income = await Income.findByPk(1, {
    include: [
        {
            model: Category,
            as: "category"
        }
    ]
});
```

If the aliases do not match, Sequelize can throw an association error.

# 5. Income Validation

We will use Zod.

Create:

```text
src/modules/incomes/income.validation.js
```

### 5.1 Create Income Schema

```javascript
const { z } = require("zod");

const idSchema = z.string().regex(/^[1-9]\d*$/, {
    message: "Invalid ID"
});


const createIncomeSchema = z.object({

    categoryId: idSchema,

    amount: z.string()
        .regex(/^(0|[1-9]\d{0,9})(\.\d{1,2})?$/)
        .refine(value => value !== "0" && value !== "0.00", {
            message: "Amount must be greater than zero"
        }),

    description: z.string()
        .trim()
        .min(2)
        .max(500),

    incomeDate: z.string()
        .date(),

    paymentMethod: z.enum([
        "cash",
        "card",
        "upi",
        "bank_transfer",
        "other"
    ])

}).strict();
```

### Understanding `.strict()`

Suppose a client sends:

```json
{
    "categoryId": "5",
    "amount": "50000",
    "description": "Salary",
    "incomeDate": "2026-11-24",
    "paymentMethod": "bank_transfer",
    "userId": "20"
}
```

The `userId` property is not allowed.

The validation will reject this request.

Why?

Because the income owner must come from the authenticated user:

```javascript
req.user.id
```

We should never trust the client to determine resource ownership.

```javascript
const updateIncomeSchema = createIncomeSchema

    .refine(
        data => Object.keys(data).length > 0,
        {
            message: "At least one field is required"
        }
    );
```

Example:

```json
{
    "amount": "55000.00"
}
```

Only the amount will be updated.

### 5.4 Income Query Schema

We will support pagination, search, filtering, and sorting.

```javascript
const incomeQuerySchema = z.object({

    page: z.coerce.number()
        .int()
        .min(1)
        .default(1),

    limit: z.coerce.number()
        .int()
        .min(1)
        .max(100)
        .default(10),

    search: z.string()
        .trim()
        .max(100)
        .optional(),

    categoryId: idSchema.optional(),

    startDate: z.string()
        .date()
        .optional(),

    endDate: z.string()
        .date()
        .optional(),

    minAmount: z.string()
        .regex(/^(0|[1-9]\d{0,9})(\.\d{1,2})?$/)
        .optional(),

    maxAmount: z.string()
        .regex(/^(0|[1-9]\d{0,9})(\.\d{1,2})?$/)
        .optional(),

    sortBy: z.enum([
        "incomeDate",
        "amount",
        "createdAt"
    ]).default("incomeDate"),

    sortOrder: z.enum([
        "ASC",
        "DESC"
    ]).default("DESC")

})
.strict()
.refine(
    data => {
        if (data.startDate && data.endDate) {
            return data.startDate <= data.endDate;
        }

        return true;
    },
    {
        message: "Start date cannot be after end date"
    }
)
.refine(
    data => {
        if (data.minAmount && data.maxAmount) {
            return Number(data.minAmount) <= Number(data.maxAmount);
        }

        return true;
    },
    {
        message: "Minimum amount cannot exceed maximum amount"
    }
);
```

### Export schemas

```javascript

    createIncomeSchema,

    updateIncomeSchema,

    incomeIdSchema,

    incomeQuerySchema

};
```

**Note:** We are using `Number()` only to compare validated decimal strings in this example. For actual financial calculations, use decimal-safe arithmetic.

# 6. Income Repository

## What is the Repository Layer?

The repository is responsible for database operations.

It does not decide whether an income category is valid or whether the user is authorized to create an income.

Those are business rules and belong in the service layer.

Create:

```text
src/modules/incomes/income.repository.js
```

### Implementation

```javascript
const { Op } = require("sequelize");

const {
    Income,
    Category
} = require("../../database/models");


class IncomeRepository {


    // Create income
    async create(data, transaction = null) {

        return await Income.create(data, {
            transaction
        });

    }


    // Find income by ID and owner
    async findById(id, userId) {

        return await Income.findOne({

            where: {
                id,
                userId
            },

            include: [
                {
                    model: Category,

                    as: "category",

                    attributes: [
                        "id",
                        "name",
                        "type"
                    ]
                }
            ]

        });

    }


    // Find all incomes
    async findAll(userId, filters) {

        const {

            page,
            limit,
            search,
            categoryId,
            startDate,
            endDate,
            minAmount,
            maxAmount,
            sortBy,
            sortOrder

        } = filters;


        const where = {
            userId
        };


        // Search by description
        if (search) {

            const escapedSearch = search.replace(
                /[\\%_]/g,
                "\\$&"
            );

            where.description = {
                [Op.like]: `%${escapedSearch}%`
            };

        }


        // Category filter
        if (categoryId) {

            where.categoryId = categoryId;

        }


        // Date range filter
        if (startDate || endDate) {

            where.incomeDate = {};

            if (startDate) {

                where.incomeDate[Op.gte] = startDate;

            }

            if (endDate) {

                where.incomeDate[Op.lte] = endDate;

            }

        }


        // Amount filter
        if (minAmount || maxAmount) {

            where.amount = {};

            if (minAmount) {

                where.amount[Op.gte] = minAmount;

            }

            if (maxAmount) {

                where.amount[Op.lte] = maxAmount;

            }

        }


        const offset = (page - 1) * limit;


        const result = await Income.findAndCountAll({

            where,

            include: [
                {
                    model: Category,

                    as: "category",

                    attributes: [
                        "id",
                        "name",
                        "type"
                    ]
                }
            ],

            limit,

            offset,

            order: [
                [sortBy, sortOrder],
                ["id", "DESC"]
            ]

        });


        return result;

    }


    // Update income
    async update(id, userId, data, transaction = null) {

        const [updatedRows] = await Income.update(data, {

            where: {
                id,
                userId
            },

            transaction

        });

        return updatedRows;

    }


    // Delete income
    async delete(id, userId, transaction = null) {

        return await Income.destroy({

            where: {
                id,
                userId
            },

            transaction

        });

    }

}


module.exports = new IncomeRepository();
```

## Important Repository Concepts

### 6.1 Why use `findOne()` instead of `findByPk()`?

Consider:

```javascript
await Income.findByPk(incomeId);
```

This retrieves an income based only on its ID.

It does not check ownership.

Instead:

```javascript
await Income.findOne({

    where: {
        id: incomeId,
        userId
    }

});
```

Now the query checks both conditions.

This prevents users from retrieving another user's income records.

### 6.2 Why use `findAndCountAll()`?

It returns two things:

```javascript
const result = await Income.findAndCountAll({
    limit: 10,
    offset: 0
});
```

The result contains:

```javascript
result.rows;
result.count;
```

- `rows`: Retrieved income records.
- `count`: Total number of matching records.

We use these values to implement pagination.

# 7. Income Service

The service layer contains the business logic.

The most important validation is checking the income category.

A user must not be able to select:

- Another user's private category.
- An expense category.

### Example categories

| ID | User ID | Name | Type |
|---|---:|---|---|
| 1 | NULL | Salary | income |
| 2 | NULL | Freelancing | income |
| 3 | NULL | Food | expense |
| 4 | 10 | Business | income |
| 5 | 20 | Investments | income |

User 10 can use categories 1, 2, and 4.

User 10 cannot use categories 3 and 5.

Create:

```text
src/modules/incomes/income.service.js
```

### Implementation

```javascript
const { Op } = require("sequelize");

const incomeRepository = require("./income.repository");

const {
    Category
} = require("../../database/models");

const ApiError = require("../../utils/ApiError");


class IncomeService {


    // Validate income category
    async validateCategory(categoryId, userId) {

        const category = await Category.findOne({

            where: {

                id: categoryId,

                type: "income",

                [Op.or]: [
                    { userId },
                    { userId: null }
                ]

            }

        });


        if (!category) {

            throw new ApiError(
                400,
                "Invalid income category"
            );

        }


        return category;

    }


    // Create income
    async createIncome(userId, data) {

        await this.validateCategory(
            data.categoryId,
            userId
        );


        const income = await incomeRepository.create({

            userId,

            categoryId: data.categoryId,

            amount: data.amount,

            description: data.description,

            incomeDate: data.incomeDate,

            paymentMethod: data.paymentMethod

        });


        return await incomeRepository.findById(
            income.id,
            userId
        );

    }


    // Get all incomes
    async getAllIncomes(userId, filters) {

        const result = await incomeRepository.findAll(
            userId,
            filters
        );


        const totalPages = Math.ceil(
            result.count / filters.limit
        );


        return {

            incomes: result.rows,

            pagination: {

                totalRecords: result.count,

                currentPage: filters.page,

                limit: filters.limit,

                totalPages

            }

        };

    }


    // Get income by ID
    async getIncomeById(incomeId, userId) {

        const income = await incomeRepository.findById(
            incomeId,
            userId
        );


        if (!income) {

            throw new ApiError(
                404,
                "Income not found"
            );

        }


        return income;

    }


    // Update income
    async updateIncome(incomeId, userId, data) {

        const existingIncome =
            await incomeRepository.findById(
                incomeId,
                userId
            );


        if (!existingIncome) {

            throw new ApiError(
                404,
                "Income not found"
            );

        }


        // Validate category if it is being changed
        if (data.categoryId !== undefined) {

            await this.validateCategory(
                data.categoryId,
                userId
            );

        }


        const updatedRows = await incomeRepository.update(
            incomeId,
            userId,
            data
        );


        if (updatedRows === 0) {

            throw new ApiError(
                404,
                "Income not found"
            );

        }


        return await incomeRepository.findById(
            incomeId,
            userId
        );

    }


    // Delete income
    async deleteIncome(incomeId, userId) {

        const deletedRows = await incomeRepository.delete(
            incomeId,
            userId
        );


        if (deletedRows === 0) {

            throw new ApiError(
                404,
                "Income not found"
            );

        }


        return {

            message: "Income deleted successfully"

        };

    }

}


module.exports = new IncomeService();
```

## Understanding the Business Logic

### 7.1 Category validation

This condition is particularly important:

```javascript
{
    id: categoryId,
    type: "income",
    [Op.or]: [
        { userId },
        { userId: null }
    ]
}
```

It means:

```sql
WHERE id = categoryId
AND type = 'income'
AND (
    user_id = authenticatedUserId
    OR user_id IS NULL
)
```

A category is valid only when all these conditions are satisfied.

### 7.2 Why do we check `updatedRows`?

Consider:

```javascript
const updatedRows = await Income.update(data, {
    where: {
        id: incomeId,
        userId
    }
});
```

If no matching record exists, Sequelize returns zero affected rows.

This can happen when:

- The income ID does not exist.
- The income belongs to another user.
- The record was deleted before the update.

Checking affected rows prevents us from reporting a successful update when nothing was updated.

```javascript
    "/:id",

    validate(incomeIdSchema, "params"),

    asyncHandler(incomeController.deleteIncome)

);


module.exports = router;
```

# 13. Reusing Code Between Expense and Income Modules

Now we have two modules:

```text
expenses/
    expense.routes.js
    expense.controller.js
    expense.service.js
    expense.repository.js
    expense.validation.js

incomes/
    income.routes.js
    income.controller.js
    income.service.js
    income.repository.js
    income.validation.js
```

You may notice that a large amount of code is similar.

For example:

| Operation | Expense Module | Income Module |
|---|---|---|
| Create | createExpense() | createIncome() |
| Retrieve all | getAllExpenses() | getAllIncomes() |
| Retrieve one | getExpenseById() | getIncomeById() |
| Update | updateExpense() | updateIncome() |
| Delete | deleteExpense() | deleteIncome() |
| Category validation | type = expense | type = income |
| Database model | Expense | Income |
| Date field | expenseDate | incomeDate |

This raises an important software engineering question:

**Should we duplicate similar code or create reusable components?**

The answer depends on the complexity and how likely the behavior is to change.

### Option 1: Separate Modules

Keep Expense and Income implementations separate.

Advantages:

- Easy to understand.
- Independent business rules.
- Easier to modify each module.
- Less abstraction.

Disadvantages:

- Some duplicated code.
- Fixes may need to be applied in multiple places.

### Option 2: Shared Utilities

Extract genuinely common operations into shared utilities.

For example:

```text
src/
│
├── modules/
```

### Option 3: Generic Transaction Module

A more advanced architecture could use a common transaction model.

```text
transactions/
    transaction.routes.js
    transaction.controller.js
    transaction.service.js
    transaction.repository.js
```

The transaction model might contain:

```javascript
{
    id: 1,
    userId: 10,
    type: "income",
    categoryId: 5,
    amount: "50000.00",
    description: "Monthly salary"
}
```

Then:

```javascript
type: "income"
```

represents income, and:

```javascript
type: "expense"
```

represents expense.

This can reduce duplication, but it also changes the database design and business logic.

**For our current learning project, keep separate Expense and Income modules.** We can explore a unified transaction architecture later.

# 14. Important Production Considerations

Before deploying this module, consider the following.

| Area | Recommendation |
|---|---|
| Financial amounts | Use DECIMAL and decimal-safe calculations |
| Category validation | Check ownership and category type |
| Authorization | Always scope queries by authenticated user |
| Search | Escape wildcard characters when literal matching is needed |
| Pagination | Enforce a maximum page size |
| Sorting | Allow only predefined columns |
| Database indexes | Index frequently queried columns |
| Deletion | Consider soft deletion |
| Validation | Reject unknown request properties |
| Logging | Record important financial operations |

### Recommended indexes

```sql
CREATE INDEX idx_incomes_user_date
ON incomes(user_id, income_date);

CREATE INDEX idx_incomes_user_category
ON incomes(user_id, category_id);

CREATE INDEX idx_incomes_user_amount
ON incomes(user_id, amount);
```

Use `EXPLAIN` to verify whether these indexes improve your actual queries.

### Important: Avoid unnecessary abstractions

Do not create a generic repository or service just because two modules look similar.

A good architecture balances:

- Reusability.
- Maintainability.
- Readability.
- Separation of concerns.
- Business requirements.

# 15. Interview Questions and Answers

### Q1. What is the difference between Expense and Income modules?

Expense tracks outgoing money, while Income tracks incoming money.

### Q2. Why do we use separate database tables?

Separate tables provide clear data ownership, constraints, and business rules for each type of financial record. A unified transaction table is another valid design.

### Q3. What is Sequelize eager loading?

Eager loading retrieves associated records using the `include` option.

### Q4. Why do we validate category type?

To prevent an income record from using an expense category.

### Q5. Why should we validate category ownership?

To prevent users from assigning records to categories owned by other users.

### Q6. What is the purpose of the service layer?

It implements business rules and coordinates operations between repositories and other components.

### Q7. What is the purpose of the repository layer?

It encapsulates database queries and persistence operations.

### Q8. What is the difference between `findByPk()` and `findOne()`?

`findByPk()` searches using the primary key. `findOne()` supports arbitrary conditions.

### Q9. What is `Op.gte`?

It represents the greater-than-or-equal-to SQL comparison operator.

### Q10. What is the purpose of `findAndCountAll()`?

It retrieves matching records and the total number of matching records, which is useful for pagination.

### Q11. What is the purpose of database indexing?

Indexes improve the efficiency of certain database queries.

### Q12. Why should we use DECIMAL for money?

DECIMAL provides exact decimal representation suitable for financial values, unlike binary floating-point types.

### Q13. What is the difference between filtering and sorting?

Filtering selects matching records. Sorting controls their order.

### Q14. Why should userId come from authentication middleware?

It prevents clients from specifying another user's identity when creating or accessing records.

### Q15. What is code duplication?

Code duplication occurs when similar logic is repeated in multiple places, making maintenance more difficult.
