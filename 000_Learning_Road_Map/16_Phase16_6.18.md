## 1. Introduction to CI/CD

Until now, we have learned how to:

- Develop a Node.js backend.
- Connect MySQL and Redis.
- Build REST APIs.
- Write automated tests.
- Dockerize our application.
- Run multiple services using Docker Compose.

Now imagine you have completed a new feature in your Expense Tracker application.

You need to deploy it to production.

Traditionally, you might perform these steps manually:

1. Push code to GitHub.
2. Connect to the production server.
3. Pull the latest code.
4. Install dependencies.
5. Run tests.
6. Build the application.
7. Restart the server.
8. Verify that everything works.

This process becomes repetitive and error-prone.

**CI/CD automates much of this software delivery process.**

### What Is CI/CD?

CI/CD stands for:

- CI — Continuous Integration.
- CD — Continuous Delivery or Continuous Deployment.

CI/CD is a software engineering practice that automates the process of integrating, testing, building, and delivering application changes.

### Without CI/CD

```text
Developer
    |
    v
Write Code
    |
    v

    v
Connect to Server
    |
    v
Pull Latest Code

    v

Deploy Manually
```

### With CI/CD

```text
Developer
    |
    v
Write Code
    |
    v

CI/CD Pipeline
    |
    +------------------+
    |                  |

             |

             |
             v
       Build Docker Image
             |
             v
       Deploy Application
             |
             v
       Production Server
```

The objective is to make software delivery repeatable, reliable, and efficient.

# 2. What Is Continuous Integration (CI)?

Continuous Integration is a development practice in which developers frequently integrate their code changes into a shared repository.

Whenever code is pushed or a pull request is created, automated processes can:

- Install dependencies.
- Run linting.
- Execute tests.
- Check code quality.
- Build the application.

### Example

Suppose three developers are working on an Expense Tracker.

```text
Developer A
    |
    v
Authentication Feature
    |
    v
GitHub
    |
    +------------------+
    |                  |
    v                  v
Developer B         Developer C
    |                  |
    v                  v
Expense Module      Budget Module
    |                  |
    +--------+---------+
             |
             v
       Shared Repository
             |
             v
       Automated CI
             |
       +-----+------+
       |            |
       v            v
      Tests       Build
```

Whenever code is integrated, automated checks help identify problems early.

### Benefits of CI

1. Detect bugs earlier.
2. Reduce integration problems.
3. Maintain code quality.
4. Automate testing.
5. Reduce manual work.
6. Improve collaboration.

### Example CI Workflow

```text
Code Push
    |
    v
Install Dependencies
    |
    v
Run ESLint
    |
    v
Run Unit Tests
    |
    v
Run Integration Tests
    |
    v
Build Application
    |
    v
CI Successful
```

If a test fails, the pipeline reports failure.

The team can fix the issue before merging or releasing the code.

# 3. What Is Continuous Delivery?

Continuous Delivery is a software delivery practice in which application changes are automatically built, tested, and prepared for release.

The application is kept in a deployable state.

However, production deployment generally requires manual approval or an explicit release decision.

### Example

```text
Developer Push
      |
      v
Automated Tests
      |
      v
Application Build
      |
      v
Docker Image Build
      |
      v
Staging Deployment
      |
      v
Manual Approval
      |
      v
Production Deployment
```

### Key Point

Continuous Delivery automates the delivery process, but production release is generally controlled by a person or approval step.

# 4. What Is Continuous Deployment?

Continuous Deployment takes automation further.

Every change that successfully passes the required pipeline checks can be automatically deployed to production.

### Example

```text
Developer Push
      |
      v
Automated Tests
      |
      v
Application Build
      |
      v
Docker Image Build
      |
      v
Security Checks
      |
      v
Automatic Deployment
      |
      v
Production
```

There is no mandatory manual production approval in the normal deployment path.

### Continuous Delivery vs Continuous Deployment

| Feature | Continuous Delivery | Continuous Deployment |
|---|---|---|
| Automated testing | Yes | Yes |
| Automated build | Yes | Yes |
| Deployment preparation | Yes | Yes |
| Production deployment | Usually approval-based | Automatically triggered |
| Manual approval | Generally required for production release | Not required in the normal path |
| Automation Level | High | Higher |

### Important

Continuous Deployment does not mean deploying untested code.

Automated quality checks, security controls, and deployment safeguards are essential.

# 5. CI vs CD: Complete Comparison

| Feature | CI | Continuous Delivery | Continuous Deployment |
|---|---|---|---|
| Code integration | Yes | Yes | Yes |
| Automated testing | Yes | Yes | Yes |
| Automated build | Yes | Yes | Yes |
| Deployment preparation | Not necessarily | Yes | Yes |
| Production deployment | Not necessarily | Approval-based | Automatic |
| Main objective | Validate code changes | Keep software ready to release | Automatically release validated changes |

### Easy Way to Remember

- **CI:** Is the code working?
- **Continuous Delivery:** Is the code ready to deploy?
- **Continuous Deployment:** Can the code be deployed automatically?

# 6. Understanding a CI/CD Pipeline

# 9. Understanding GitHub Actions Architecture

A GitHub Actions workflow contains several important components:

1. Workflow.
2. Events.
3. Jobs.
4. Steps.
5. Actions.
6. Runners.

Let's understand each one.

## 9.1 Workflow

A workflow is an automated process defined in a YAML file.

Example:

```text
.github/workflows/ci.yml
```

A repository can have multiple workflows.

For example:

```text
ci.yml
deploy.yml
security.yml
release.yml
```

## 9.2 Events

Events determine when a workflow should execute.

Examples:

- Push.
- Pull request.
- Release.
- Schedule.
- Manual trigger.

## 9.3 Jobs

A job is a collection of steps executed on a runner.

Example:

```yaml
jobs:

  test:

    runs-on: ubuntu-latest

    steps:
      - name: Checkout Code
        uses: actions/checkout@v4
```

## 9.4 Steps

Steps are individual tasks inside a job.

Examples:

- Checkout code.
- Install Node.js.
- Install dependencies.
- Run tests.

## 9.5 Actions

Actions are reusable automation components.

Example:

```yaml
uses: actions/checkout@v4
```

This action checks out your repository code.

## 9.6 Runners

A runner is the machine that executes your workflow.

GitHub provides hosted runners, and you can also configure self-hosted runners.

Examples:

```yaml
runs-on: ubuntu-latest
```

Other options include:

```yaml
runs-on: windows-latest
```

```yaml
runs-on: macos-latest
```

### Architecture

```text
          GITHUB REPOSITORY
                  |
                  v
               EVENT
                  |
                  v
              WORKFLOW
                  |
                  v
                 JOB
                  |
                  v
                RUNNER
                  |
          +-------+-------+
          |       |       |
          v       v       v
        STEP 1  STEP 2  STEP 3
          |       |       |
          v       v       v
        ACTION  COMMAND  TESTS
```

# 11. Understanding GitHub Actions Triggers

Triggers determine when workflows execute.

### 11.1 Push Event

```yaml
on:
  push:
    branches:
      - main
```

Runs whenever code is pushed to `main`.

### 11.2 Pull Request Event

```yaml
on:
  pull_request:
    branches:
      - main
```

Runs when a pull request targets `main`.

### 11.3 Multiple Branches

```yaml
on:
  push:
    branches:
      - main
      - develop
      - staging
```

### 11.4 Manual Trigger

```yaml
on:
  workflow_dispatch:
```

This allows you to manually execute a workflow from GitHub.

You can also define manual input parameters.

Example:

```yaml
name: Manual Deployment

on:
  workflow_dispatch:
    inputs:
      environment:
        description: Deployment environment
        required: true
        type: choice
        options:
          - staging
          - production

jobs:

  deploy:

    runs-on: ubuntu-latest

    steps:

      - name: Show Selected Environment
        run: echo "Deploying to ${{ inputs.environment }}"
```

### 11.5 Scheduled Workflow

```yaml
on:
  schedule:
    - cron: "0 0 * * *"
```

This schedules the workflow to run daily at midnight UTC.

GitHub scheduled workflows use UTC.

They may be delayed during periods of high load, so they should not be treated as precise real-time schedulers.

### 11.6 Multiple Triggers

```yaml
on:

  push:
    branches:
      - main

  pull_request:
    branches:
      - main

  workflow_dispatch:
```

This workflow supports all three events.

# 12. Understanding Jobs and Steps

A workflow can contain multiple jobs.

Example:

```yaml
name: Backend CI

on:
  push:
    branches:
      - main

jobs:

  lint:

    runs-on: ubuntu-latest

    steps:

      - uses: actions/checkout@v4

      - uses: actions/setup-node@v4
        with:
          node-version: 22

      - run: npm ci

      - run: npm run lint


  test:

    runs-on: ubuntu-latest

    steps:

      - uses: actions/checkout@v4

      - uses: actions/setup-node@v4
        with:
          node-version: 22

      - run: npm ci

      - run: npm test


  build:

    needs:
      - lint
      - test

    runs-on: ubuntu-latest

    steps:

      - uses: actions/checkout@v4

      - uses: actions/setup-node@v4
        with:
          node-version: 22

      - run: npm ci

      - run: npm run build
```

### Understanding `needs`

```yaml
needs:
  - lint
  - test
```

This means the `build` job waits for both `lint` and `test` to complete successfully.

### Parallel vs Sequential Jobs

Without `needs`, independent jobs can run in parallel.

```text
          WORKFLOW
              |
       +------+------+
       |             |
       v             v
      LINT          TEST
       |             |
       +------+------+
              |
              v
             BUILD
```

In this example, build runs after lint and test.

### Important

Jobs run on separate runners by default.

Files created in one job are not automatically available in another job.

If you need to transfer build artifacts between jobs, use artifact upload and download actions.

# 14. Understanding GitHub Repository Secrets

Suppose our deployment requires:

```text
DOCKERHUB_USERNAME

DOCKERHUB_TOKEN

SERVER_HOST

SERVER_USER

SERVER_SSH_KEY
```

We should store these values in GitHub Secrets.

### Where to Add Secrets?

Open your GitHub repository.

Navigate to:

```text
Settings
   |
   v
Secrets and variables
   |
   v
Actions
   |
   v
New repository secret
```

Add the required secrets.

Official documentation:

[GitHub Actions Secrets Documentation](https://docs.github.com/en/actions/how-tos/write-workflows/choose-what-workflows-do/use-secrets?utm_source=chatgpt.com)

### Use a Secret in Workflow

```yaml
steps:

  - name: Login to Docker Hub
    run: |
      echo "${{ secrets.DOCKERHUB_TOKEN }}" |
      docker login \
        -u "${{ secrets.DOCKERHUB_USERNAME }}" \
        --password-stdin
```

This avoids directly writing the token into your workflow.

### Security Considerations

- Never print secrets in logs.
- Never commit `.env` files.
- Avoid passing secrets through command-line arguments when a safer method is available.
- Use least-privilege tokens.
- Prefer short-lived credentials or OIDC-based authentication where supported.
- Restrict production secrets to trusted branches and deployment environments.

# 15. Creating a Complete Node.js CI Workflow

Now let's create a proper CI workflow for our Expense Tracker.

Our project has:

- Node.js.
- Express.
- Sequelize.
- MySQL.
- Jest.
- Supertest.

We need to run automated tests.

### Step 1: Configure package.json

Make sure your `package.json` contains appropriate scripts.

Example:

```json
{
  "scripts": {
    "start": "node src/server.js",
    "dev": "nodemon src/server.js",
    "test": "jest --runInBand",
    "test:coverage": "jest --coverage --runInBand",
    "lint": "eslint src"
  }
}
```

These commands must match the tools and files actually configured in your project.

### Step 2: Create CI Workflow

Create:

```text
.github/workflows/ci.yml
```

```yaml
name: Expense Tracker CI

on:

  push:
    branches:
      - main
      - develop

  pull_request:
    branches:
      - main
      - develop


permissions:
  contents: read


jobs:

  test:

    runs-on: ubuntu-latest

    services:

      mysql:

        image: mysql:8

        env:
          MYSQL_ROOT_PASSWORD: root
          MYSQL_DATABASE: expense_tracker_test

        ports:
          - 3306:3306

        options: >-
          --health-cmd="mysqladmin ping -h 127.0.0.1 -proot"
          --health-interval=10s
          --health-timeout=5s
          --health-retries=10


      redis:

        image: redis:7

        ports:
          - 6379:6379

        options: >-
          --health-cmd="redis-cli ping"
          --health-interval=10s
          --health-timeout=5s
          --health-retries=5


    steps:

      - name: Checkout Repository
        uses: actions/checkout@v4


      - name: Setup Node.js
        uses: actions/setup-node@v4
        with:
          node-version: 22
          cache: npm


      - name: Install Dependencies
        run: npm ci


      - name: Run Lint
        run: npm run lint


      - name: Run Database Migrations
        run: npx sequelize-cli db:migrate
        env:
          NODE_ENV: test
          DB_HOST: 127.0.0.1
          DB_PORT: 3306
          DB_NAME: expense_tracker_test
          DB_USER: root
          DB_PASSWORD: root


      - name: Run Tests
        run: npm test
        env:
          NODE_ENV: test
          DB_HOST: 127.0.0.1
          DB_PORT: 3306
          DB_NAME: expense_tracker_test
          DB_USER: root
          DB_PASSWORD: root
          REDIS_HOST: 127.0.0.1
          REDIS_PORT: 6379
          JWT_ACCESS_SECRET: test-access-secret
          JWT_REFRESH_SECRET: test-refresh-secret
```

### Important Explanation

We are using GitHub Actions service containers.

```yaml
services:
  mysql:
    image: mysql:8

  redis:
    image: redis:7
```

GitHub Actions starts these dependencies for the job.

The test job can connect to them.

Because the workflow runs directly on the GitHub-hosted runner, the service ports are accessed using:

```text
127.0.0.1:3306

127.0.0.1:6379
```

If the job itself runs inside a container, networking configuration is different and service names are generally used as hostnames.

### Important Test Database Considerations

- Use a dedicated test database.
- Never point CI tests at production.
- Run migrations against the test database.
- Use isolated test data.
- Do not use production credentials.
- Ensure tests clean up after themselves.

# 19. Automating Docker Image Publishing with GitHub Actions

We can automate the entire process.

Whenever code is pushed to `main`:

1. Run tests.
2. Build Docker image.
3. Log in to Docker Hub.
4. Push image to Docker Hub.

Create:

```text
.github/workflows/docker-publish.yml
```

Example:

```yaml
name: Build and Publish Docker Image

on:

  push:
    branches:
      - main


permissions:
  contents: read


jobs:

  publish:

    runs-on: ubuntu-latest

    steps:

      - name: Checkout Repository
        uses: actions/checkout@v4


      - name: Setup Docker Buildx
        uses: docker/setup-buildx-action@v3


      - name: Login to Docker Hub
        uses: docker/login-action@v3
        with:
          username: ${{ secrets.DOCKERHUB_USERNAME }}
          password: ${{ secrets.DOCKERHUB_TOKEN }}


      - name: Extract Metadata
        id: meta
        uses: docker/metadata-action@v5
        with:
          images: ${{ secrets.DOCKERHUB_USERNAME }}/expense-tracker-api


      - name: Build and Push
        uses: docker/build-push-action@v6
        with:
          context: .
          push: true
          tags: |
            ${{ secrets.DOCKERHUB_USERNAME }}/expense-tracker-api:latest
            ${{ secrets.DOCKERHUB_USERNAME }}/expense-tracker-api:${{ github.sha }}
```

### Understanding Important Actions

**docker/setup-buildx-action**

Sets up Docker Buildx for advanced image building.

**docker/login-action**

Authenticates with Docker Hub.

**docker/metadata-action**

Generates image metadata and tags.

**docker/build-push-action**

Builds and optionally pushes Docker images.

### Why Use `github.sha`?

Every Git commit has a unique SHA.

Example:

```text
expense-tracker-api:8a4f2c1...
```

This helps identify exactly which commit produced an image.

For production, the immutable image digest is an even stronger deployment reference.

**Important:** This workflow demonstrates image publishing. In a production pipeline, make sure the image is published only after required tests and security checks have passed.

### Deployment Workflow

```text
       GITHUB PUSH

             |

             |

             v
       CONNECT TO VPS
             |
             v
       PULL NEW IMAGE
             |
             v
       RESTART CONTAINERS
             |
             v
       VERIFY DEPLOYMENT
```

### GitHub Secrets Required

Create these secrets:

```text
DOCKERHUB_USERNAME

DOCKERHUB_TOKEN

SERVER_HOST

SERVER_USER

SERVER_SSH_KEY
```

### Example Deployment Workflow

Create:

```text
.github/workflows/deploy.yml
```

```yaml
name: Deploy Expense Tracker

on:

  workflow_dispatch:


permissions:
  contents: read


jobs:

  deploy:

    runs-on: ubuntu-latest

    steps:

      - name: Checkout Repository
        uses: actions/checkout@v4


      - name: Login to Docker Hub
        uses: docker/login-action@v3
        with:
          username: ${{ secrets.DOCKERHUB_USERNAME }}
          password: ${{ secrets.DOCKERHUB_TOKEN }}


      - name: Build and Push Image
        uses: docker/build-push-action@v6
        with:
          context: .
          push: true
          tags: |
            ${{ secrets.DOCKERHUB_USERNAME }}/expense-tracker-api:${{ github.sha }}


      - name: Deploy to VPS
        uses: appleboy/ssh-action@v1
        with:
          host: ${{ secrets.SERVER_HOST }}
          username: ${{ secrets.SERVER_USER }}
          key: ${{ secrets.SERVER_SSH_KEY }}
          script: |
            cd /opt/expense-tracker

            export IMAGE_TAG=${{ github.sha }}

            docker compose pull api

            docker compose up -d --no-deps api

            docker image prune -f
```

### Important Explanation

The deployment workflow:

- Builds an image.
- Pushes it to Docker Hub.
- Connects to the VPS.
- Updates the image tag.
- Pulls the image.
- Recreates the API container.

However, this example requires the server's Compose file to reference the image through an `IMAGE_TAG` variable.

For example:

```yaml
services:

  api:

    image: YOUR_USERNAME/expense-tracker-api:${IMAGE_TAG}
```

The deployment script must also ensure that the new image tag is passed to Docker Compose.

A robust implementation should store the deployment tag in a controlled environment file or use a carefully managed deployment script.

**Security note:** Pin third-party GitHub Actions to verified full commit SHAs in sensitive production workflows. Also validate SSH host keys rather than disabling host-key verification.

# 23. Understanding Deployment Strategies

Deploying a new application version can introduce downtime or unexpected bugs.

Different deployment strategies help reduce these risks.

## 23.1 Recreate Deployment

The existing application is stopped and replaced with the new version.

```text
VERSION 1
    |
    v
STOP OLD VERSION
    |
    v
START NEW VERSION
    |
    v
VERSION 2
```

### Advantages

- Simple.
- Easy to implement.
- Requires fewer resources.

### Disadvantages

- Can cause downtime.
- New version may fail after old version is stopped.

Suitable for simple applications where brief downtime is acceptable.

## 23.2 Rolling Deployment

The application is updated gradually.

```text
OLD VERSION
OLD VERSION
OLD VERSION
    |
    v
UPDATE ONE INSTANCE
    |
    v
NEW VERSION
OLD VERSION
OLD VERSION
    |
    v
UPDATE NEXT INSTANCE
    |
    v
NEW VERSION
NEW VERSION
NEW VERSION
```

### Advantages

- Reduces downtime.
- Gradual replacement.
- Useful for multiple instances.

### Disadvantages

- Requires compatible application versions.
- More complex.
- Old and new versions may run simultaneously.

## 23.3 Blue-Green Deployment

Two separate environments are maintained.

- Blue: Current production.
- Green: New version.

### Architecture

```text
              USERS
                |
                v
          LOAD BALANCER
                |
         +------+------+
         |             |
         v             v
       BLUE          GREEN
      VERSION 1     VERSION 2
```

Initially, traffic goes to Blue.

After Green is deployed and verified, traffic is switched to Green.

### Advantages

- Fast traffic switching.
- Easier rollback.
- New version can be tested before receiving traffic.

### Disadvantages

- Requires additional resources.
- Database compatibility needs careful planning.
- More complex infrastructure.

## 23.4 Canary Deployment

A new version is released to a small percentage of users first.

Example:

```text
             USERS
               |
               v
         TRAFFIC ROUTER
               |
       +-------+-------+
       |               |
       v               v
   VERSION 1       VERSION 2
      95%              5%
```

If the new version performs well, gradually increase its traffic.

### Advantages

- Limits the impact of new bugs.
- Enables production validation.
- Supports gradual rollout.

### Disadvantages

- Requires traffic routing.
- Requires monitoring.
- More complicated implementation.

### Deployment Strategy Comparison

| Strategy | Downtime | Complexity | Rollback |
|---|---|---|---|
| Recreate | Possible | Low | Manual |
| Rolling | Usually minimal | Medium | More complex |
| Blue-Green | Usually minimal | High | Fast traffic switch |
| Canary | Usually minimal | High | Gradual traffic rollback |

# 24. Understanding Rollback Strategies

Sometimes a deployment introduces problems.

For example:

- API starts returning HTTP 500.
- Database queries fail.
- Authentication breaks.
- Performance decreases.
- Application crashes.

We need to restore the previous stable version.

### What Is Rollback?

Rollback is the process of reverting an application deployment to a previously working version.

### Example

```text
VERSION 1.0
    |
    v
DEPLOY VERSION 1.1
    |
    v
APPLICATION FAILURE
    |
    v
ROLLBACK
    |
    v
VERSION 1.0
```

### Docker Rollback Example

Suppose the previous image was:

```text
expense-tracker-api:1.0.0
```

And the new image is:

```text
expense-tracker-api:1.1.0
```

To roll back:

1. Change the Compose image tag to `1.0.0`.
2. Pull the old image if necessary.
3. Recreate the application container.
4. Verify application health.

Example:

```bash
docker compose pull api
docker compose up -d --no-deps api
```

This assumes the Compose configuration has already been updated to reference the old image tag.

### Important Database Warning

Rolling back application code does not automatically roll back database migrations.

For example:

```text
Version 1.0
    |
    v
Database Schema A
    |
    v
Version 1.1
    |
    v
Database Schema B
```

If version 1.1 changes or removes database columns, version 1.0 may no longer work.

This is why backward-compatible database migrations are important.

# 25. Understanding Database Migrations in CI/CD

Our Expense Tracker uses Sequelize migrations.

Example:

```bash
npx sequelize-cli db:migrate
```

Should we run migrations automatically during every API container startup?

Usually, this is not the best approach.

### Why?

Suppose we run five API instances:

```text
API 1
API 2
API 3
API 4
API 5
```

If all instances attempt to execute migrations simultaneously, we can encounter:

- Migration conflicts.
- Locking problems.
- Startup failures.
- Unpredictable deployment behavior.

### Better Approach

Run migrations as a separate deployment step.

```text
BUILD IMAGE
     |
     v
PUSH IMAGE
     |
     v
BACKUP DATABASE
     |
     v
RUN MIGRATIONS ONCE
     |
     v
DEPLOY API
     |
     v
VERIFY APPLICATION
```

### Migration Best Practices

1. Run migrations in a controlled deployment job.
2. Take database backups before risky changes.
3. Use backward-compatible schema changes where possible.
4. Avoid destructive migrations in the same release that first depends on them.
5. Test migrations before production.
6. Monitor migration execution.
7. Maintain a rollback or recovery plan.

### Example: Expand-and-Contract Migration

Suppose we want to rename:

```text
full_name
```

to:

```text
display_name
```

A risky approach is to immediately delete `full_name`.

A safer approach:

**Release 1: Expand**

- Add `display_name`.
- Write to both columns if necessary.
- Keep reading from the old column.

**Release 2: Migrate**

- Backfill existing values.
- Switch application reads to `display_name`.

**Release 3: Contract**

- Stop writing to `full_name`.
- Remove the old column after all dependent versions are gone.

This supports deployments where old and new application versions may temporarily coexist.

The actual environment used by customers.


Characteristics:

- Production credentials.
- Monitoring.
- Logging.
- Security controls.
- Backup and recovery.

| Feature | Development | Testing | Staging | Production |

| Stability | Flexible | Isolated | High | Critical |

**Important:** Do not use production data casually in development or testing environments. Sensitive data should be protected, anonymized, or replaced with synthetic data.

# 28. Understanding CI/CD Security

CI/CD pipelines often have access to important systems.

For example:

- GitHub repository.
- Docker Hub.
- Production server.
- Cloud infrastructure.
- Database credentials.

If a pipeline is compromised, an attacker may gain access to these resources.

Therefore, pipeline security is essential.

### Important Security Practices

**1. Never hardcode credentials.**

Use GitHub Secrets or an appropriate secrets manager.

**2. Use least privilege.**

Give workflows only the permissions they need.

Example:

```yaml
permissions:
  contents: read
```

**3. Protect production branches.**

Use pull requests, branch protection rules, and required checks.

**4. Protect deployment environments.**

Use required reviewers and deployment restrictions where appropriate.

**5. Pin third-party actions.**

For sensitive workflows, use verified full commit SHAs rather than relying only on mutable version tags.

**6. Scan dependencies.**

Check for known vulnerable packages.

**7. Scan Docker images.**

Identify vulnerable operating system packages and application dependencies.

**8. Avoid exposing secrets in logs.**

Do not print environment variables or credentials.

**9. Secure SSH deployment.**

Validate server host keys and restrict SSH credentials.

**10. Use OIDC where supported.**

OpenID Connect can allow GitHub Actions to obtain short-lived cloud credentials without storing long-lived cloud access keys.

# 33. Interview Questions and Answers

### Q1. What is CI/CD?

CI/CD is a software engineering practice that automates code integration, testing, building, and software delivery.

### Q2. What is Continuous Integration?

Continuous Integration is the practice of frequently integrating code changes into a shared repository and validating them using automated checks.

### Q3. What is Continuous Delivery?

Continuous Delivery ensures that software changes are automatically built, tested, and prepared for release, generally with manual production approval.

### Q4. What is Continuous Deployment?

Continuous Deployment automatically releases successfully validated changes to production.

### Q5. What is a CI/CD pipeline?

A CI/CD pipeline is an automated sequence of stages used to test, build, package, and deploy software.

### Q6. What is GitHub Actions?

GitHub Actions is a GitHub automation platform used to implement workflows such as testing, building, and deployment.

### Q7. What is a GitHub Actions workflow?

A workflow is an automated process defined in a YAML file inside `.github/workflows/`.

### Q8. What is a GitHub Actions runner?

A runner is the machine that executes workflow jobs.

### Q9. What is a job?

A job is a collection of steps executed on a runner.

### Q10. What is a step?

A step is an individual task inside a job.

### Q11. What is the difference between `uses` and `run`?

`uses` invokes a reusable action, while `run` executes a shell command.

### Q12. What is a GitHub Actions secret?

A secret is a protected value used to store sensitive information such as API keys, passwords, and deployment credentials.

### Q13. What is Docker Hub?

Docker Hub is a registry used to store and distribute Docker images.

### Q14. What is a deployment artifact?

A deployment artifact is a packaged output produced by a build process that can be used for deployment.

### Q15. Why should we use Docker images in CI/CD?

Docker images package the application and its runtime dependencies into a consistent deployment artifact.

### Q16. What is a rolling deployment?

A rolling deployment gradually replaces old application instances with new ones.

### Q17. What is blue-green deployment?

Blue-green deployment maintains two environments and switches traffic from the old environment to the new one after verification.

### Q18. What is canary deployment?

Canary deployment gradually releases a new version to a small percentage of users before increasing its traffic.

### Q19. What is rollback?

Rollback is the process of reverting an application to a previously working version.

### Q20. Why should database migrations run separately from API startup?

Running migrations from every application instance can cause concurrent migration execution and deployment conflicts. A controlled migration step is safer.

### Q21. What is staging?

Staging is a production-like environment used to verify application releases before production deployment.

### Q22. What is a smoke test?

A smoke test is a basic test that verifies whether the most important application functionality works after deployment.

### Q23. What is the difference between a build and a deployment?

A build creates a deployable artifact, while deployment releases that artifact into an environment.

### Q24. What is OIDC in CI/CD?

OpenID Connect allows workflows to obtain short-lived identity-based credentials from supported cloud providers without storing long-lived credentials.

### Q25. Why is monitoring important after deployment?

Monitoring helps identify application failures, performance degradation, and infrastructure problems after a release.
