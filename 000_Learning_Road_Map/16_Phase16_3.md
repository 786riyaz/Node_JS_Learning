# 1. What Is Backend Architecture?

Backend architecture describes how the different components of a backend application are organized, how they communicate, and how responsibilities are distributed.

It defines:

- Project structure.
- Modules.
- Layers.
- Business logic.
- Database access.
- Middleware.
- Authentication.
- Error handling.
- External integrations.
- Communication between components.

### Example

Consider an e-commerce application.

```text
                 CLIENT
                   |
                   v
               API SERVER
                   |
       +-----------+-----------+
       |           |           |
       v           v           v
      AUTH       PRODUCT      ORDER
     MODULE      MODULE      MODULE
       |           |           |
       +-----------+-----------+
                   |
                   v
                DATABASE
                   |
          +--------+--------+
          |                 |
          v                 v
         REDIS          EXTERNAL APIs
```

Each module has a particular responsibility.

This separation makes the application easier to maintain and extend.

# 3. Monolithic Architecture

A monolithic application is developed and deployed as one application.

All business modules are part of the same application.

### Architecture

```text
           E-COMMERCE APPLICATION
                      |
          +-----------+-----------+
          |           |           |
          v           v           v
         AUTH       PRODUCT      ORDER
        MODULE      MODULE      MODULE
          |           |           |
          +-----------+-----------+
                      |
                      v
                   DATABASE
```

### Example Structure

```text
backend/
│
├── routes/
├── controllers/
├── models/
├── middleware/
├── config/
├── utils/
└── server.js
```

### Advantages

- Simple initial development.
- Easy local setup.
- Simple deployment.
- Easy in-process communication.
- Straightforward debugging.

### Disadvantages

- Can become difficult to maintain if poorly organized.
- Individual modules cannot always be scaled independently.
- Entire application is often deployed together.
- Large codebases can become difficult to manage.

### When to Use?

- Small applications.
- MVPs.
- Internal business applications.
- Applications with a small development team.

**Important:** Monolithic architecture does not mean putting everything into one file. A monolith can have a highly organized internal structure.

# 4. Modular Monolithic Architecture

A modular monolith is a single deployable application divided into independent, logically organized modules.

Each module handles a particular business domain.

### Example

```text
              E-COMMERCE APPLICATION
                         |
       +-----------------+-----------------+
       |                 |                 |
       v                 v                 v
    AUTH MODULE      PRODUCT MODULE    ORDER MODULE
       |                 |                 |
       v                 v                 v
  AUTH LOGIC         PRODUCT LOGIC     ORDER LOGIC
       |                 |                 |
       +-----------------+-----------------+
                         |
                         v
                      DATABASE
```

### Project Structure

```text
backend/
│
├── src/
│   │
│   ├── modules/
│   │   ├── auth/
│   │   ├── users/
│   │   ├── products/
│   │   ├── categories/
│   │   ├── orders/
│   │   └── payments/
│   │
│   ├── config/
│   ├── middleware/
│   ├── database/
│   ├── utils/
│   ├── app.js
│   └── server.js
│
└── package.json
```

### Benefits

1. Better separation of business logic.
2. Easier maintenance.
3. Clear ownership of functionality.
4. Easier testing.
5. Simpler deployment than microservices.
6. Can evolve into independently deployed services if justified.

### Monolith vs Modular Monolith

| Monolith | Modular Monolith |
|---|---|
| Single application | Single application |
| May have weak internal boundaries | Has explicit module boundaries |
| Code can become tightly coupled | Encourages lower coupling |
| Responsibilities may be mixed | Responsibilities are organized by domain |

### Recommendation

For many Node.js applications, a modular monolith is an excellent starting architecture.

# 5. What Is MVC Architecture?

MVC stands for:

- Model.
- View.
- Controller.

It is a software architectural pattern that separates an application's data, presentation, and request-handling responsibilities.

### MVC Diagram

```text
              USER
                |
                v
            CONTROLLER
                |
         +------+------+
         |             |
         v             v
       MODEL          VIEW
         |             |
         v             v
      DATABASE      RESPONSE
```

### 5.1 Model

Responsible for representing and interacting with application data.

Example:

```javascript
const { DataTypes } = require("sequelize");

module.exports = (sequelize) => {

    return sequelize.define("User", {

        name: {

            type: DataTypes.STRING,

            allowNull: false

        },

        email: {

            type: DataTypes.STRING,

            unique: true

        }

    });

};
```

### 5.2 View

Responsible for presenting data.

In a traditional server-rendered application, this could be:

- EJS.
- Pug.
- Handlebars.

In a React or Next.js application, the frontend commonly acts as the presentation layer.

### 5.3 Controller

Handles incoming requests and returns responses.

```javascript
exports.getUsers = async (req, res, next) => {

    try {

        const users = await User.findAll();

        res.status(200).json({

            success: true,

            data: users

        });

    } catch (error) {

        next(error);

    }

};
```

### MVC in Express

Express does not enforce MVC, but you can organize an application using this pattern.

```text
backend/
│
├── models/
├── views/
├── controllers/
├── routes/
└── app.js
```

### Is MVC Enough for Large Applications?

MVC provides useful separation, but complex applications often benefit from additional layers such as:

- Services.
- Repositories.
- Validators.
- Domain logic.
- External integrations.

That brings us to layered architecture.

# 6. Layered Architecture

Layered architecture divides an application into layers according to their responsibilities.

A common Node.js backend uses:

1. Presentation Layer.
2. Controller Layer.
3. Service Layer.
4. Repository Layer.
5. Database Layer.

### Architecture

```text
              CLIENT
                 |
                 v
            ROUTE LAYER
                 |
                 v
          MIDDLEWARE LAYER
                 |
                 v
          CONTROLLER LAYER
                 |
                 v
            SERVICE LAYER
                 |
                 v
          REPOSITORY LAYER
                 |
                 v
            DATABASE
```

Let's understand each layer.

## 6.1 Route Layer

Defines API endpoints and associates them with middleware and controllers.

```javascript
const express = require("express");

const router = express.Router();

const userController = require("./user.controller");

router.get("/", userController.getUsers);

router.post("/", userController.createUser);

module.exports = router;
```

Responsibilities:

- Define endpoints.
- Attach middleware.
- Connect requests to controllers.

## 6.2 Middleware Layer

Handles operations that run during the request lifecycle.

Examples:

- Authentication.
- Authorization.
- Validation.
- Logging.
- Rate limiting.

Example:

```javascript
function authenticate(req, res, next) {

    // Verify access token.

    next();

}
```

## 6.3 Controller Layer

Handles HTTP-specific responsibilities.

```javascript
const userService = require("./user.service");

exports.getUsers = async (req, res, next) => {

    try {

        const users = await userService.getUsers();

        res.status(200).json({

            success: true,

            data: users

        });

    } catch (error) {

        next(error);

    }

};
```

Responsibilities:

- Read request parameters.
- Call services.
- Return HTTP responses.
- Forward errors.

## 6.4 Service Layer

Contains business logic.

```javascript
const userRepository = require("./user.repository");

exports.getUsers = async () => {

    return await userRepository.findAll();

};
```

Responsibilities:

- Business rules.
- Business validations.
- Coordinate operations.
- Manage application transactions when required.

## 6.5 Repository Layer

Handles database access.

```javascript
const { User } = require("../../database/models");

exports.findAll = async () => {

    return await User.findAll();

};

exports.findById = async (id) => {

    return await User.findByPk(id);

};

exports.create = async (data) => {

    return await User.create(data);

};
```

Responsibilities:

- Database queries.
- Data persistence.
- Query organization.
- Database-specific operations.

### Why Separate These Layers?

Suppose your application has 100 API endpoints.

If database queries are directly written inside every controller, maintaining them becomes difficult.

Separating the layers makes the code easier to understand and test.

# 7. Feature-Based vs Layer-Based Project Structure

This is an important architectural decision.

There are two common ways to organize backend projects.

## 7.1 Layer-Based Structure

Files are grouped by technical responsibility.

```text
src/
│
├── routes/
│   ├── user.routes.js
│   ├── product.routes.js
│   └── order.routes.js
│
├── controllers/
│   ├── user.controller.js
│   ├── product.controller.js
│   └── order.controller.js
│
├── services/
│   ├── user.service.js
│   ├── product.service.js
│   └── order.service.js
│
├── repositories/
│   ├── user.repository.js
│   ├── product.repository.js
│   └── order.repository.js
│
└── models/
```

### Advantages

- Easy to understand initially.
- Responsibilities are grouped.
- Suitable for smaller applications.

### Disadvantages

As the project grows, related files become distributed across many folders.

For example, to modify the product module, you may need to visit:

```text
routes/product.routes.js

controllers/product.controller.js

services/product.service.js

repositories/product.repository.js

models/product.model.js
```

## 7.2 Feature-Based Structure

Files are grouped according to business functionality.

```text
src/
│
├── modules/
│   │
│   ├── users/
│   │   ├── user.routes.js
│   │   ├── user.controller.js
│   │   ├── user.service.js
│   │   ├── user.repository.js
│   │   ├── user.model.js
│   │   └── user.validation.js
│   │
│   ├── products/
│   │   ├── product.routes.js
│   │   ├── product.controller.js
│   │   ├── product.service.js
│   │   ├── product.repository.js
│   │   ├── product.model.js
│   │   └── product.validation.js
│   │
│   └── orders/
│       ├── order.routes.js
│       ├── order.controller.js
│       ├── order.service.js
│       ├── order.repository.js
│       ├── order.model.js
│       └── order.validation.js
│
├── config/
├── middleware/
└── app.js
```

### Advantages

- Related files stay together.
- Easier feature development.
- Easier module ownership.
- Better organization for growing applications.

### Comparison

| Layer-Based | Feature-Based |
|---|---|
| Groups by technical responsibility | Groups by business functionality |
| Easier for small projects | Often easier for larger projects |
| Related files are distributed | Related files stay together |
| Simple initial structure | Clearer business boundaries |

### Which Is Better?

For a growing backend application, I recommend feature-based organization with internal layers.

This gives you both:

- Business module separation.
- Technical responsibility separation.

# 8. Controller-Service-Repository Pattern

This pattern is commonly used in professional Node.js applications.

Let's understand it through a complete example.

Suppose we need an API:

```http
GET /api/users/10
```

Its responsibility is to retrieve a user.

### Request Flow

```text
CLIENT
  |
  v
ROUTE
  |
  v
CONTROLLER
  |
  v
SERVICE
  |
  v
REPOSITORY
  |
  v
DATABASE
```

### 8.1 Route

`user.routes.js`

```javascript
const express = require("express");

const router = express.Router();

const userController = require("./user.controller");

router.get("/:id", userController.getUserById);

module.exports = router;
```

### 8.2 Controller

`user.controller.js`

```javascript
const userService = require("./user.service");

exports.getUserById = async (req, res, next) => {

    try {

        const user = await userService.getUserById(
            req.params.id
        );

        res.status(200).json({

            success: true,

            data: user

        });

    } catch (error) {

        next(error);

    }

};
```

### 8.3 Service

`user.service.js`

```javascript
const userRepository = require("./user.repository");

exports.getUserById = async (id) => {

    const user = await userRepository.findById(id);

    if (!user) {

        const error = new Error("User not found");

        error.statusCode = 404;

        throw error;

    }

    return user;

};
```

### 8.4 Repository

`user.repository.js`

```javascript
const { User } = require("../../database/models");

exports.findById = async (id) => {

    return await User.findByPk(id);

};
```

### Why Is This Architecture Useful?

Imagine you want to replace Sequelize with another database access approach.

With repository separation, you can isolate many changes within the repository implementation.

The controller and service can continue using the same repository contract.

However, database-specific differences may still require changes elsewhere.

# 9. What Is Separation of Concerns?

Separation of Concerns (SoC) is a software design principle that means different parts of an application should handle different responsibilities.

Example:

Bad design:

```javascript
app.post("/users", async (req, res) => {

    // Validate input

    // Hash password

    // Connect to database

    // Insert user

    // Send email

    // Generate JWT

    // Return response

});
```

This route handles too many responsibilities.

Better design:

```text
ROUTE
  |
  v
VALIDATION MIDDLEWARE
  |
  v
CONTROLLER
  |
  v
USER SERVICE
  |
  +---- PASSWORD SERVICE
  |
  +---- USER REPOSITORY
  |
  +---- EMAIL SERVICE
  |
  +---- TOKEN SERVICE
```

Each component has a focused responsibility.

### Benefits

- Easier testing.
- Better maintainability.
- Lower coupling.
- Improved readability.
- Easier debugging.

# 10. What Is Coupling?

Coupling describes how strongly one component depends on another component.

### Tight Coupling

```javascript
class OrderService {

    constructor() {

        this.paymentService = new StripePaymentService();

    }

}
```

The order service is directly tied to a specific payment implementation.

### Loose Coupling

```javascript
class OrderService {

    constructor(paymentService) {

        this.paymentService = paymentService;

    }

}
```

Now the payment dependency is supplied externally.

### Tight vs Loose Coupling

| Tight Coupling | Loose Coupling |
|---|---|
| Strong dependency | Reduced dependency |
| Harder to replace components | Easier to replace components |
| More difficult unit testing | Easier mocking and testing |
| Less flexible | More flexible |

### Important

Low coupling is desirable, but some dependencies are natural and necessary. The goal is to avoid unnecessary dependency between unrelated components.

# 11. What Is Cohesion?

Cohesion describes how closely related the responsibilities inside a component are.

### Low Cohesion

```javascript
class ApplicationService {

    createUser() {}

    sendEmail() {}

    generateInvoice() {}

    processPayment() {}

    generateReport() {}

}
```

This class handles unrelated operations.

### High Cohesion

```text
UserService
  - createUser()
  - updateUser()
  - deleteUser()

EmailService
  - sendEmail()
  - sendWelcomeEmail()

PaymentService
  - processPayment()
  - refundPayment()

InvoiceService
  - generateInvoice()
  - downloadInvoice()
```

Each service has a focused responsibility.

### Important Design Goal

```text
LOW COUPLING
     +
HIGH COHESION
     =
BETTER MODULAR DESIGN
```

# 12. What Is Dependency Injection?

Dependency Injection is a technique in which a component receives its dependencies externally rather than creating them internally.

### Without Dependency Injection

```javascript
const database = require("./database");

class UserService {

    constructor() {

        this.database = database;

    }

}
```

This directly imports a specific implementation.

### With Dependency Injection

```javascript
class UserService {

    constructor(userRepository) {

        this.userRepository = userRepository;

    }

    async getUsers() {

        return await this.userRepository.findAll();

    }

}
```

Usage:

```javascript
const userRepository = require("./user.repository");

const UserService = require("./user.service");

const userService = new UserService(userRepository);
```

### Benefits

- Easier unit testing.
- Lower coupling.
- Replaceable implementations.
- Better architecture.

### Testing Example

```javascript
const mockRepository = {

    async findAll() {

        return [

            { id: 1, name: "John" },

            { id: 2, name: "Alex" }

        ];

    }

};

const service = new UserService(mockRepository);
```

Now you can test the service without connecting to the actual database.

# 13. What Is the Composition Root?

A composition root is the place where application dependencies are created and connected.

In a Node.js application, this is commonly done during application startup.

Example:

```javascript
const userRepository = require("./modules/users/user.repository");

const UserService = require("./modules/users/user.service");

const userControllerFactory = require("./modules/users/user.controller");

const userService = new UserService(userRepository);

const userController = userControllerFactory(userService);
```

The composition root creates the dependencies and passes them to the relevant components.

### Why Is It Useful?

Instead of allowing every module to create its own dependencies, the application has one clear place where components are assembled.

This improves testability and makes the dependency graph easier to understand.

# 14. SOLID Principles in Practical Node.js Applications

You learned SOLID in Phase 15.

Now let's understand how these principles apply to actual backend architecture.

| Principle | Node.js Example |
|---|---|
| SRP | Separate UserService and EmailService |
| OCP | Add new payment providers without rewriting order logic |
| LSP | Implementations honor the same expected service contract |
| ISP | Use small, focused interfaces or contracts |
| DIP | Inject repositories instead of directly creating database dependencies |

### Example: Payment Provider

```javascript
class PaymentService {

    constructor(paymentProvider) {

        this.paymentProvider = paymentProvider;

    }

    async processPayment(amount) {

        return await this.paymentProvider.pay(amount);

    }

}
```

Different providers:

```javascript
class StripeProvider {

    async pay(amount) {

        console.log("Processing Stripe payment:", amount);

    }

}

class RazorpayProvider {

    async pay(amount) {

        console.log("Processing Razorpay payment:", amount);

    }

}
```

Usage:

```javascript
const paymentService = new PaymentService(
    new RazorpayProvider()
);
```

You can replace the provider without rewriting the payment service.

# 15. What Is Clean Architecture?

Clean Architecture organizes software so that business rules remain independent of external infrastructure.

Its central principle is:

**Dependencies should point inward, toward business rules.**

### Architecture

```text
        FRAMEWORKS & DRIVERS
        +----------------------+
        | Express              |
        | MySQL                |
        | Redis                |
        | External APIs        |
        +----------------------+
                   |
                   v
          INTERFACE ADAPTERS
        +----------------------+
        | Controllers          |
        | Repository Adapters  |
        | Presenters           |
        +----------------------+
                   |
                   v
          APPLICATION LAYER
        +----------------------+
        | Use Cases            |
        | Application Services |
        +----------------------+
                   |
                   v
              DOMAIN LAYER
        +----------------------+
        | Entities             |
        | Business Rules       |
        +----------------------+
```

### Domain Layer

Contains core business rules.

Example:

```javascript
class Expense {

    constructor(amount, categoryId) {

        if (amount <= 0) {

            throw new Error("Expense amount must be positive");

        }

        this.amount = amount;

        this.categoryId = categoryId;

    }

}
```

This logic does not depend on Express or Sequelize.

### Application Layer

Contains use cases.

Example:

```javascript
class CreateExpenseUseCase {

    constructor(expenseRepository) {

        this.expenseRepository = expenseRepository;

    }

    async execute(expenseData) {

        const expense = new Expense(
            expenseData.amount,
            expenseData.categoryId
        );

        return await this.expenseRepository.create(expense);

    }

}
```

### Interface Adapters

Convert external requests into application inputs.

Examples:

- Controllers.
- Repository implementations.
- Request mappers.

### Infrastructure Layer

Contains external technology integrations.

Examples:

- Sequelize.
- MySQL.
- Redis.
- Express.
- Email providers.

### When to Use Clean Architecture?

Useful when:

- Business rules are complex.
- Application is expected to grow.
- Multiple infrastructure integrations exist.
- Extensive unit testing is required.
- Business logic should remain independent of frameworks.

For a small CRUD application, a simpler layered architecture may be sufficient.

# 16. What Is Hexagonal Architecture?

Hexagonal Architecture is also known as Ports and Adapters Architecture.

It aims to isolate business logic from external systems.

### Main Concepts

**Ports:** Contracts that define how the application communicates with external components.

**Adapters:** Implementations that connect external systems to those contracts.

### Architecture

```text
             EXTERNAL SYSTEMS
       +----------+----------+
       |          |          |
       v          v          v
    EXPRESS     MYSQL      REDIS
       |          |          |
       v          v          v
    ADAPTER     ADAPTER    ADAPTER
       |          |          |
       +----------+----------+
                  |
                  v
             APPLICATION
                  |
                  v
               DOMAIN
```

### Example

Your application needs to store users.

Define a repository contract:

```javascript
class UserRepository {

    async findById(id) {

        throw new Error("Method not implemented");

    }

    async create(userData) {

        throw new Error("Method not implemented");

    }

}
```

MySQL implementation:

```javascript
class MySQLUserRepository {

    async findById(id) {

        return await User.findByPk(id);

    }

    async create(userData) {

        return await User.create(userData);

    }

}
```

The application uses the repository contract instead of directly depending on MySQL.

### Benefits

- Database independence at the application boundary.
- Easier testing.
- Replaceable external integrations.
- Better isolation of business logic.

# 17. MVC vs Layered vs Clean vs Hexagonal Architecture

These approaches are related but not identical.

| Architecture | Main Focus |
|---|---|
| MVC | Separates model, view, and controller |
| Layered | Separates technical responsibilities into layers |
| Clean Architecture | Keeps business rules independent of infrastructure |
| Hexagonal Architecture | Uses ports and adapters to isolate external systems |
| Modular Monolith | Organizes a single deployment into business modules |
| Microservices | Splits an application into independently deployable services |

### Important

These architectures can be combined.

For example, you can build:

- A modular monolith.
- With feature-based modules.
- Using layered architecture internally.
- Applying Clean Architecture principles to complex business modules.

Architecture is not about choosing one fashionable pattern. It is about selecting an organization that fits the problem.

# 19. Understanding app.js vs server.js

This is an important professional Node.js practice.

Many beginner applications place everything inside `server.js`.

A cleaner approach separates Express application configuration from server startup.

### app.js

Responsible for:

- Creating the Express application.
- Registering middleware.
- Registering routes.
- Registering error handlers.

```javascript
const express = require("express");

const app = express();

app.use(express.json());

app.get("/health", (req, res) => {

    res.status(200).json({

        success: true,

        message: "Application is running"

    });

});

module.exports = app;
```

### server.js

Responsible for:

- Connecting infrastructure.
- Starting the HTTP server.
- Listening on a port.

```javascript
const app = require("./app");

const PORT = process.env.PORT || 5000;

const server = app.listen(PORT, () => {

    console.log(`Server running on port ${PORT}`);

});
```

### Why Separate Them?

It allows you to import the Express app into tests without automatically opening a network port.

For example:

```javascript
const request = require("supertest");

const app = require("../src/app");

describe("Health API", () => {

    test("should return 200", async () => {

        const response = await request(app).get("/health");

        expect(response.status).toBe(200);

    });

});
```

This improves testability.

# 20. Understanding the Complete Request Lifecycle

Let's understand what happens when a request enters an Express backend.

Example:

```http
POST /api/v1/expenses
```

### Request Lifecycle

```text
             CLIENT REQUEST
                    |
                    v
             EXPRESS SERVER
                    |
                    v
              REQUEST LOGGER
                    |
                    v
            SECURITY MIDDLEWARE
                    |
                    v
           AUTHENTICATION MIDDLEWARE
                    |
                    v
             VALIDATION MIDDLEWARE
                    |
                    v
                ROUTE
                    |
                    v
              CONTROLLER
                    |
                    v
                SERVICE
                    |
                    v
              REPOSITORY
                    |
                    v
                DATABASE
                    |
                    v
               RESPONSE
                    |
                    v
                 CLIENT
```

### Detailed Explanation

**Step 1: Client sends request**

React or Next.js sends an HTTP request.

**Step 2: Express receives request**

The Express server receives it.

**Step 3: Request logging**

The application records request metadata.

**Step 4: Security middleware**

Security headers, CORS policy, and other middleware are applied as configured.

**Step 5: Authentication**

The application verifies the user's credentials.

**Step 6: Validation**

The request body, parameters, and query strings are validated.

**Step 7: Controller**

The controller extracts request data.

**Step 8: Service**

Business rules are executed.

**Step 9: Repository**

Database operations are performed.

**Step 10: Response**

The controller returns an appropriate HTTP response.

### Step 5: Create User Repository

`user.repository.js`

```javascript
const users = [

    {
        id: 1,
        name: "John",
        email: "john@example.com"
    },

    {
        id: 2,
        name: "Alex",
        email: "alex@example.com"

};

    return users.find(user => user.id === Number(id));
```

This is an in-memory repository for learning. Data will disappear when the application restarts.

### Step 6: Create User Service

`user.service.js`

```javascript
const userRepository = require("./user.repository");

exports.getUsers = async () => {

    return await userRepository.findAll();

};

exports.getUserById = async (id) => {

    const user = await userRepository.findById(id);

    if (!user) {

        const error = new Error("User not found");

        error.statusCode = 404;

        throw error;

    }

    return user;

};
```

### Step 7: Create User Controller

`user.controller.js`

```javascript
const userService = require("./user.service");

exports.getUsers = async (req, res, next) => {

    try {

        const users = await userService.getUsers();

        res.status(200).json({

            success: true,

            data: users

        });

    } catch (error) {

        next(error);

    }

};

exports.getUserById = async (req, res, next) => {

    try {

        const user = await userService.getUserById(req.params.id);

        res.status(200).json({

            success: true,

            data: user

        });

    } catch (error) {

        next(error);

    }

};
```

### Step 8: Create User Routes

`user.routes.js`

```javascript
const express = require("express");

router.get("/:id", userController.getUserById);
```

### Step 9: Create app.js

```javascript
const express = require("express");

const helmet = require("helmet");

const cors = require("cors");

const userRoutes = require("./modules/users/user.routes");

const app = express();

app.use(helmet());

app.use(cors({

    origin: "http://localhost:3000"

}));

app.use(express.json());

app.use("/api/v1/users", userRoutes);

app.use((req, res) => {

    res.status(404).json({

        success: false,

        message: "Route not found"

    });

});

app.use((err, req, res, next) => {

    const statusCode = err.statusCode || 500;

    res.status(statusCode).json({

        success: false,

        message: statusCode === 500
            ? "Internal server error"
            : err.message

    });

});

module.exports = app;
```

# 22. Architecture Design Best Practices

1. Choose architecture based on application complexity.
2. Prefer modular monoliths for many new applications.
3. Keep business modules separate.
4. Separate HTTP handling from business logic.
5. Avoid putting database queries directly in controllers.
6. Use dependency injection where it provides value.
7. Keep business logic independent of Express where practical.
8. Avoid unnecessary abstractions.
9. Keep modules highly cohesive.
10. Minimize unnecessary coupling.
11. Centralize configuration.
12. Centralize error handling.
13. Keep application startup separate from Express configuration.
14. Write automated tests.
15. Document important architecture decisions.

# 23. Interview Questions and Answers

### Q1. What is backend architecture?

It defines how backend components are organized and how they communicate.

### Q2. What is monolithic architecture?

An architecture where multiple application functionalities are developed and deployed as one application.

### Q3. What is modular monolithic architecture?

A single deployable application organized into separate business modules.

### Q4. What is MVC?

MVC stands for Model-View-Controller. It separates data handling, presentation, and request handling.

### Q5. What is layered architecture?

An architecture that separates application responsibilities into layers such as controllers, services, repositories, and databases.

### Q6. What is the repository pattern?

A pattern that encapsulates data-access operations behind a consistent interface.

### Q7. What is the service layer?

A layer responsible for application business logic and coordinating operations.

### Q8. What is separation of concerns?

The principle of dividing an application into components with distinct responsibilities.

### Q9. What is coupling?

The degree of dependency between components.

### Q10. What is cohesion?

The degree to which the responsibilities inside a component are related.

### Q11. What is dependency injection?

A technique where dependencies are supplied to a component externally.

### Q12. What is Clean Architecture?

An architectural approach that separates business rules from external infrastructure and frameworks.

### Q13. What is Hexagonal Architecture?

An architecture that uses ports and adapters to isolate application logic from external systems.

### Q14. What is a composition root?

A centralized location where application dependencies are created and connected.

### Q15. What is the difference between feature-based and layer-based structures?

Feature-based structures group files by business functionality, whereas layer-based structures group files by technical responsibility.

### Q16. Why separate app.js and server.js?

To separate Express configuration from server startup, improving testability and application organization.

### Q17. Can MVC and layered architecture be used together?

Yes. MVC can be used inside a layered backend architecture.

### Q18. What is the dependency inversion principle?

High-level modules should depend on abstractions rather than concrete low-level implementations.

### Q19. What is high cohesion and low coupling?

A design where components have focused responsibilities and minimal unnecessary dependencies.

### Q20. Which architecture is best for a new Node.js project?

There is no universally best architecture. A modular monolith with feature-based organization and appropriate internal layers is a strong default for many applications.
