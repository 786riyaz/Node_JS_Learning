## 1. Introduction to Software Testing

Testing is an essential part of professional software development.

When we build a Node.js backend, we need to ensure that:

- APIs return correct responses.
- Business logic works as expected.
- Database operations are correct.
- Authentication is secure.
- Invalid requests are rejected.
- Errors are handled properly.
- External services work correctly with our application.
- Existing functionality does not break when new features are added.

Consider our Expense Tracker application.

We have implemented:

- User registration and login.
- Expense management.
- Income management.
- Budget management.
- Financial analytics.
- File uploads.
- Email notifications.
- Redis caching.
- Background jobs.
- Socket.IO.
- Payment integration.

Manually testing every feature after every code change would be time-consuming.

This is why we use automated testing.

### What Is Software Testing?

Software testing is the process of evaluating an application to identify defects and verify that it behaves according to its requirements.

### Manual Testing vs Automated Testing

| Manual Testing | Automated Testing |
|---|---|
| Performed manually by a person | Performed using test code and tools |
| Usually requires repetitive effort | Tests can be executed repeatedly |
| Useful for exploratory testing | Useful for regression testing |
| Can be time-consuming | Faster for repeated test scenarios |
| Depends on human execution | Execution is consistent and repeatable |

**Example:**

Suppose we have a login API.

Instead of manually testing it through Postman every time, we can write automated tests that verify:

1. Login succeeds with valid credentials.
2. Login fails with an incorrect password.
3. Login fails when the email is missing.
4. Login fails when the user does not exist.
5. Login returns the expected response structure.

We can execute all these tests with a single command.

# 2. Types of Software Testing

There are several types of software testing.

The most important ones for Node.js backend development are:

1. Unit Testing.
2. Integration Testing.
3. End-to-End Testing.
4. Regression Testing.
5. Smoke Testing.
6. Performance Testing.
7. Security Testing.

Let's understand each one.

## 2.1 Unit Testing

Unit testing verifies individual units of code independently.

A unit can be:

- A function.
- A method.
- A service.
- A utility.
- A validation function.

Example:

```javascript
function calculateTotal(price, quantity) {

    return price * quantity;

}

module.exports = calculateTotal;
```

Unit test:

```javascript
const calculateTotal = require("./calculateTotal");


test("calculates total correctly", () => {

    const result = calculateTotal(100, 5);

    expect(result).toBe(500);

});
```

We are testing only the `calculateTotal()` function.

We are not testing Express, MySQL, or any external service.

### When to Use Unit Testing?

Use it for:

- Business logic.
- Utility functions.
- Calculations.
- Data transformation.
- Validation logic.
- Service methods.

---

## 2.2 Integration Testing

Integration testing verifies whether multiple components work correctly together.

For example:

```text
Controller
    |
    v
Service
    |
    v
Repository
    |
    v
MySQL
```

An integration test may verify that:

1. An API receives an expense request.
2. The controller calls the service.
3. The service validates the business rules.
4. The repository inserts the record.
5. MySQL stores the expense.
6. The API returns the expected response.

Unlike unit tests, integration tests involve multiple components.

### When to Use Integration Testing?

Use it for:

- Express API endpoints.
- Database queries.
- Sequelize associations.
- Authentication middleware.
- Transactions.
- File upload integrations.
- Redis integrations.

---

## 2.3 End-to-End Testing (E2E)

End-to-end testing verifies an entire application workflow from the user's perspective.

Example:

```text
User Opens Application
        |
        v
User Registers
        |
        v
User Logs In
        |
        v
Creates Expense
        |
        v
Creates Budget
        |
        v
Views Dashboard
        |
        v
Logs Out
```

An E2E test verifies that the entire workflow works correctly.

E2E tests may involve:

- Frontend.
- Backend.
- Database.
- Browser.
- External integrations or test doubles.

Tools such as Playwright are commonly used for browser-based E2E testing.

### When to Use E2E Testing?

Use it for critical user journeys:

- Registration and login.
- Subscription purchase.
- Expense creation.
- Report generation.
- Password reset.

---

## 2.4 Regression Testing

Regression testing ensures that new code changes have not broken existing functionality.

Example:

You update the expense module.

After the update, you should verify that:

- Expense creation still works.
- Expense listing still works.
- Dashboard calculations are still correct.
- Budget calculations are still correct.

The purpose is to catch unintended side effects.

Automated test suites are especially useful for regression testing.

---

## 2.5 Smoke Testing

Smoke testing is a basic test performed to verify that the important parts of an application are working.

Example:

After deployment, check:

```text
GET /health
POST /api/auth/login
GET /api/users/me
GET /api/expenses
```

If these critical operations work, the application has passed its initial smoke test.

Smoke tests do not replace comprehensive testing.

---

## 2.6 Performance Testing

Performance testing evaluates how an application behaves under different workloads.

Examples:

- How many requests can the server handle?
- How long does an API take to respond?
- How does the database perform with 100,000 records?
- What happens when 1,000 users access the dashboard simultaneously?

Common tools:

- k6.
- Apache JMeter.
- Artillery.

---

## 2.7 Security Testing

Security testing evaluates whether the application is vulnerable to attacks or unauthorized access.

Examples:

- SQL injection.
- Broken authentication.
- Broken access control.
- IDOR/BOLA.
- Cross-site scripting.
- Rate-limit bypass.
- Sensitive data exposure.

Security testing should be part of the development process, not just a final activity.

# 3. Understanding the Testing Pyramid

The testing pyramid is a model that helps us decide how many tests of each type to write.

```text
              /\
             /  \
            / E2E\
           /------\
          /        \
         / INTEGR.  \
        /------------\
       /              \
      /   UNIT TESTS   \
     /__________________\
```

### Explanation

| Test Type | Quantity | Execution Speed |
|---|---:|---|
| Unit Testing | High | Fast |
| Integration Testing | Medium | Moderate |
| E2E Testing | Low | Usually slower |

### Why More Unit Tests?

Unit tests:

- Execute quickly.
- Are easier to debug.
- Isolate problems.
- Require fewer external dependencies.

### Why Fewer E2E Tests?

E2E tests:

- Require more setup.
- May involve multiple services.
- Are slower.
- Can fail due to environmental issues.

### Recommended Approach

For our Expense Tracker:

| Testing Type | Example |
|---|---|
| Unit | Calculate monthly expense total |
| Integration | Create expense API with MySQL |
| E2E | Register, log in, create expense, view dashboard |

The testing pyramid is a guideline, not a strict numerical rule.

# 7. Understanding Jest Test Syntax

Let's understand the basic structure of a Jest test.

```javascript
describe("Test Group", () => {

    test("Test Case", () => {

    });

```

### `describe()`

Groups related tests.

```javascript

});
```

### `test()`

Defines an individual test case.

```javascript
test("should create an expense", () => {

});
```

`it()` is an alias for `test()`.

### `expect()`

Defines an expectation about the result.

```javascript
expect(10).toBe(10);
```

| Matcher | Purpose |
|---|---|
| `toBe()` | Strict equality |
| `toEqual()` | Deep equality |

| `toBeUndefined()` | Checks undefined |

| `toHaveLength()` | Checks length |
| `toHaveProperty()` | Checks object property |
| `toThrow()` | Checks thrown error |
| `toHaveBeenCalled()` | Checks whether mock was called |

### Example

```javascript
test("checks object values", () => {

        name: "John",

        age: 25

        name: "John",
```

# 8. Writing Your First Unit Test

Let's test a utility function.

Create:

```text
src/utils/calculateExpense.js
```

```javascript
function calculateExpense(amount, quantity) {

    if (
        typeof amount !== "number" ||
        typeof quantity !== "number"
    ) {

        throw new Error("Invalid input");

    }


    if (amount < 0 || quantity < 0) {

        throw new Error("Values cannot be negative");

    }


    return amount * quantity;

}


module.exports = calculateExpense;
```

### Create Test File

```text
src/utils/calculateExpense.test.js
```

```javascript
const calculateExpense = require("./calculateExpense");


describe("calculateExpense", () => {

    test("calculates expense correctly", () => {

        const result = calculateExpense(100, 5);

        expect(result).toBe(500);

    });


    test("throws error for negative amount", () => {

        expect(() => {

            calculateExpense(-100, 5);

        }).toThrow("Values cannot be negative");

    });


    test("throws error for invalid input", () => {

        expect(() => {

            calculateExpense("100", 5);

        }).toThrow("Invalid input");

    });

});
```

Run:

```bash
npm test
```

### Example Output

```text
PASS src/utils/calculateExpense.test.js

✓ calculates expense correctly
✓ throws error for negative amount
✓ throws error for invalid input

Test Suites: 1 passed
Tests:       3 passed
```

### Important Financial Note

This function is only an illustration of Jest testing.

For actual financial calculations, avoid ordinary JavaScript floating-point arithmetic.

Use integer minor units or a decimal arithmetic library such as `decimal.js`.

# 9. Understanding Synchronous and Asynchronous Tests

Node.js applications frequently use asynchronous operations.

Examples:

- Database queries.
- API calls.
- File operations.
- Redis operations.
- Email services.

Jest supports asynchronous testing.

### Promise-Based Testing

```javascript
function getUser() {

    return Promise.resolve({

        id: 1,

        name: "John"

    });

}
```

Test:

```javascript
test("fetches user", async () => {

    const user = await getUser();

    expect(user.name).toBe("John");

});
```

### Testing Rejected Promises

```javascript
function getUser() {

    return Promise.reject(
        new Error("User not found")
    );

}
```

Test:

```javascript
test("handles user not found", async () => {

    await expect(
        getUser()
    ).rejects.toThrow("User not found");

});
```

### Important

Always return or await asynchronous operations.

Incorrect:

```javascript
test("fetches user", () => {

    getUser().then((user) => {

        expect(user.name).toBe("John");

    });

});
```

The test may finish before the assertion executes.

Correct:

```javascript
test("fetches user", async () => {

    const user = await getUser();

    expect(user.name).toBe("John");

});
```

# 10. Understanding Mocking

Mocking is a technique used to replace real dependencies with controlled test implementations.

Suppose our expense service calls a repository.

```text
Expense Service
       |
       v
Expense Repository
       |
       v
MySQL
```

When unit testing the service, we may not want to connect to MySQL.

Instead, we can mock the repository.

### What Is a Mock?

A mock is a test replacement that simulates a dependency and can track how it is used.

Example:

```javascript
const mockRepository = {

    create: jest.fn(),

    findById: jest.fn()

};
```

### `jest.fn()`

Creates a mock function.

```javascript
const mockFunction = jest.fn();

mockFunction();

expect(mockFunction).toHaveBeenCalled();
```

### Mock Return Values

```javascript
const mockFunction = jest.fn();

mockFunction.mockReturnValue(100);

console.log(mockFunction());
```

Output:

```text
100
```

### Mock Resolved Promise

```javascript
const mockFunction = jest.fn();

mockFunction.mockResolvedValue({

    id: 1,

    name: "John"

});
```

### Mock Rejected Promise

```javascript
const mockFunction = jest.fn();

mockFunction.mockRejectedValue(
    new Error("Database error")
);
```

# 11. Unit Testing an Expense Service

Let's create a simplified expense service.

```text
src/modules/expenses/expense.service.js
```

```javascript
const expenseRepository =
    require("./expense.repository");


async function createExpense(userId, data) {

    if (data.amount <= 0) {

        throw new Error("Amount must be greater than zero");

    }


    const expense = await expenseRepository.create({

        userId,

        amount: data.amount,

        description: data.description

    });


    return expense;

}


module.exports = {
    createExpense
};
```

### Test File

```text
src/modules/expenses/expense.service.test.js
```

```javascript
jest.mock("./expense.repository");


const expenseRepository =
    require("./expense.repository");

const expenseService =
    require("./expense.service");


describe("Expense Service", () => {

    beforeEach(() => {

        jest.clearAllMocks();

    });


    test("creates expense successfully", async () => {

        const mockExpense = {

            id: 1,

            userId: 10,

            amount: 500,

            description: "Food"

        };


        expenseRepository.create.mockResolvedValue(
            mockExpense
        );


        const result = await expenseService.createExpense(

            10,

            {

                amount: 500,

                description: "Food"

            }

        );


        expect(result).toEqual(mockExpense);


        expect(
            expenseRepository.create
        ).toHaveBeenCalledWith({

            userId: 10,

            amount: 500,

            description: "Food"

        });

    });


    test("rejects invalid expense amount", async () => {

        await expect(

            expenseService.createExpense(

                10,

                {

                    amount: 0,

                    description: "Food"

                }

            )

        ).rejects.toThrow(
            "Amount must be greater than zero"
        );


        expect(
            expenseRepository.create
        ).not.toHaveBeenCalled();

    });

});
```

### What Are We Testing?

1. Whether the service validates the amount.
2. Whether the repository is called correctly.
3. Whether the service returns the expected result.
4. Whether invalid data is rejected.

We are not testing MySQL here.

This is a unit test.

# 12. Understanding Jest Lifecycle Hooks

Jest provides lifecycle hooks that execute before or after tests.

| Hook | Purpose |
|---|---|
| `beforeAll()` | Runs once before all tests in its scope |
| `afterAll()` | Runs once after all tests in its scope |
| `beforeEach()` | Runs before each test |
| `afterEach()` | Runs after each test |

### Example

```javascript
describe("User Tests", () => {

    beforeAll(() => {

        console.log("Before all tests");

    });


    beforeEach(() => {

        console.log("Before each test");

    });


    afterEach(() => {

        console.log("After each test");

    });


    afterAll(() => {

        console.log("After all tests");

    });


    test("Test 1", () => {

        expect(1).toBe(1);

    });


    test("Test 2", () => {

        expect(2).toBe(2);

    });

});
```

### Execution Order

```text
beforeAll()

    beforeEach()
        Test 1
    afterEach()

    beforeEach()
        Test 2
    afterEach()

afterAll()
```

### Use Cases

`beforeAll()`:

- Connect to test database.
- Initialize test environment.

`afterAll()`:

- Close database connections.
- Close Redis connections.

`beforeEach()`:

- Reset test data.
- Clear mocks.

`afterEach()`:

- Clean temporary files.
- Restore mocked functions.

# 13. Understanding Spies

A spy is used to observe how a function is called.

Jest provides:

```javascript
jest.spyOn()
```

Example:

```javascript
const userService = {

    getUser() {

        return "John";

    }

};


const spy = jest.spyOn(
    userService,
    "getUser"
);


userService.getUser();


expect(spy).toHaveBeenCalled();
```

### Mock Implementation with Spy

```javascript
jest.spyOn(
    userService,
    "getUser"
).mockReturnValue("Test User");
```

Now the function returns the mocked value.

### Difference Between Mock and Spy

| Mock | Spy |
|---|---|
| Creates a replacement function | Observes an existing function |
| Can simulate behavior | Can track calls and arguments |
| Commonly used to isolate dependencies | Commonly used to verify interactions |

Jest spies can also replace the original implementation.

# 17. Integration Testing with MySQL and Sequelize

So far, we have tested functions and HTTP endpoints.

Now let's test actual database operations.

For integration tests, use a dedicated test database.

For example:

```env
NODE_ENV=test

DB_HOST=127.0.0.1

DB_PORT=3306

DB_NAME=expense_tracker_test

DB_USER=root

DB_PASSWORD=password
```

**Never run destructive test cleanup against your development or production database.**

### Test Database Configuration

Your Sequelize configuration should select the test database when:

```javascript
process.env.NODE_ENV === "test"
```

A common approach is to use a separate Sequelize instance for tests.

### Example Test Setup

```javascript
const {
    sequelize,
    User,
    Expense
} = require("../src/models");


beforeAll(async () => {

    await sequelize.authenticate();

});


beforeEach(async () => {

    await Expense.destroy({

        where: {},

        truncate: true,

        cascade: true

    });


    await User.destroy({

        where: {},

        truncate: true,

        cascade: true

    });

});


afterAll(async () => {

    await sequelize.close();

});
```

### Important

This is a simplified example.

MySQL foreign-key constraints and `TRUNCATE` behavior require careful ordering. `TRUNCATE` may not work while other tables reference the table being truncated.

A safer approach is often:

- Use a fresh test database.
- Apply migrations.
- Clean records in dependency order.
- Use transactions or isolated schemas where appropriate.

Do not use `sequelize.sync({ force: true })` as a production schema management strategy.

# 18. Testing Database Transactions

We previously learned about database transactions.

Now let's test them.

Suppose creating an expense requires:

1. Creating the expense.
2. Creating an audit log.

Both operations should succeed or fail together.

### Business Logic

```javascript
async function createExpenseWithAudit(data) {

    return await sequelize.transaction(async (transaction) => {

        const expense = await Expense.create({

            userId: data.userId,

            amount: data.amount

        }, {

            transaction

        });


        await AuditLog.create({

            userId: data.userId,

            action: "EXPENSE_CREATED",

            resourceId: expense.id

        }, {

            transaction

        });


        return expense;

    });

}
```

### Test Case 1: Successful Transaction

Verify:

- Expense exists.
- Audit log exists.

### Test Case 2: Audit Log Failure

Simulate an audit log failure.

Expected:

- Expense is rolled back.
- Audit log is not created.

### Example

```javascript
test("rolls back expense when audit creation fails", async () => {

    jest.spyOn(

        AuditLog,

        "create"

    ).mockRejectedValueOnce(

        new Error("Audit database failure")

    );


    await expect(

        createExpenseWithAudit({

            userId: "10",

            amount: "500.00"

        })

    ).rejects.toThrow("Audit database failure");


    const expenses = await Expense.findAll({

        where: {

            userId: "10"

        }

    });


    expect(expenses).toHaveLength(0);

});
```

This is an integration-style test because it exercises the real database transaction while replacing one dependency to force a failure.

### Example Server

Suppose the server has:

### Integration Test

```javascript
const http = require("http");

const { io: Client } = require("socket.io-client");

const { Server } = require("socket.io");


let httpServer;

let io;

let clientSocket;


beforeAll((done) => {

    httpServer = http.createServer();


    io = new Server(httpServer);


    io.on("connection", (socket) => {

        socket.on("ping", () => {

            socket.emit("pong", {

                message: "Pong"

            });

        });

    });


    httpServer.listen(() => {

        const port = httpServer.address().port;


        clientSocket = Client(
            `http://localhost:${port}`
        );


        clientSocket.on("connect", done);

    });

});


afterAll(() => {

    clientSocket.close();

    io.close();

});


test("responds to ping event", (done) => {

    clientSocket.on("pong", (data) => {

        expect(data.message).toBe("Pong");

        done();

    });


    clientSocket.emit("ping");

});
```

### What Are We Testing?

- Client connection.
- Server event listener.
- Event emission.
- Event response.

### Important

- Invalid JWT rejection.
- Room authorization.
- Private message delivery.
- Disconnection handling.
- Duplicate event handling.
- Multi-instance communication when using the Redis adapter.

# 24. Test Fixtures and Factories

As your test suite grows, creating test data manually becomes repetitive.

This is where fixtures and factories help.

### What Is a Fixture?

A fixture is predefined test data.

Example:

```javascript
const testUser = {

    name: "John",

    email: "john@example.com",

    password: "TestPassword123!"

};
```

### What Is a Factory?

A factory is a function that generates test data.

Example:

```javascript
function createUserData(overrides = {}) {

    return {

        name: "John",

        email: `user-${Date.now()}@example.com`,

        password: "TestPassword123!",

        ...overrides

    };

}
```

Usage:

```javascript
const user1 = createUserData();

const user2 = createUserData({

    name: "David"

});
```

### Why Use Factories?

They help us:

- Reduce repeated code.
- Generate unique data.
- Create different test scenarios.
- Keep tests readable.
- Maintain consistent test data.

For parallel test execution, prefer a robust unique-ID generator rather than relying only on timestamps.

### Types of Coverage

|---|---|

| Function Coverage | Percentage of executed functions |

### Example


Not always.

- Important business rules.
- Financial calculations.
- Authorization.
- Payment processing.
- Error handling.
- Critical workflows.

Coverage is a useful measurement, not proof of correctness.

# 26. Testing Performance

Functional tests verify whether an API works.

Performance tests evaluate how it behaves under load.

Suppose our API is:

```text
GET /api/expenses
```

We want to know:

- How many requests can it handle?
- What is its average response time?
- What happens with 500 concurrent users?
- Does response time increase significantly?
- Does the database become overloaded?

### Common Performance Metrics

| Metric | Meaning |
|---|---|
| Throughput | Requests processed per unit of time |
| Latency | Time taken to process a request |
| P95 | 95th percentile response time |
| P99 | 99th percentile response time |
| Error Rate | Percentage of failed requests |
| CPU Usage | Processor utilization |
| Memory Usage | RAM consumption |

### What Is P95?

Suppose we execute 1,000 API requests.

If P95 latency is 500 ms, approximately 95% of requests completed within 500 ms.

The remaining 5% took longer.

P95 and P99 are useful because averages can hide slow requests.

### Example Using k6

k6 is a performance testing tool.

Official documentation: [Grafana k6 Documentation](https://grafana.com/docs/k6/latest/?utm_source=chatgpt.com)

Install k6 according to its official installation instructions.

Create:

```text
load-test.js
```

```javascript
import http from "k6/http";

import { check, sleep } from "k6";


export const options = {

    vus: 50,

    duration: "30s"

};


export default function () {

    const response = http.get(
        "http://localhost:5000/api/health"
    );


    check(response, {

        "status is 200": (r) => r.status === 200

    });


    sleep(1);

}
```

Run:

```bash
k6 run load-test.js
```

### What Does This Test Do?

- Creates 50 virtual users.
- Runs the test for 30 seconds.
- Sends requests to the health endpoint.
- Checks whether responses return HTTP 200.

This is a basic load-test example. A real API performance test should use representative requests, realistic user behavior, and appropriate test data.

# 28. Test Database Management

One of the biggest challenges in backend testing is managing test data.

A good test database strategy should ensure:

1. Tests do not modify production data.
2. Tests are repeatable.
3. Test data is cleaned up.
4. Parallel tests do not interfere with one another.
5. Migrations are applied consistently.

### Recommended Test Database Workflow

```text
Start Test Database
        |
        v
Run Migrations
        |
        v
Create Test Data
        |
        v
Execute Tests
        |
        v
Clean Test Data
        |
        v
Close Connections
```

### Recommended Practices

- Use a dedicated database such as `expense_tracker_test`.
- Use migrations to create the schema.
- Use fixtures and factories.
- Reset data between tests.
- Close all database connections.
- Avoid shared mutable test records.
- Use isolated databases or schemas for parallel execution.

### Should We Use SQLite Instead of MySQL?

SQLite can be useful for fast tests, but it is not always a suitable replacement for MySQL integration tests.

Differences may exist in:

- SQL syntax.
- Data types.
- Index behavior.
- Foreign-key behavior.
- Transactions.
- JSON support.
- Query execution.

For our project, use MySQL integration tests to verify MySQL-specific behavior.

# 29. Continuous Integration (CI)

So far, we have been running tests manually.

But professional development teams generally automate test execution.

This is where Continuous Integration comes in.

### What Is Continuous Integration?

Continuous Integration is a development practice where code changes are automatically built and tested when developers push code or create pull requests.

Example workflow:

```text
Developer Writes Code
        |
        v
Git Commit
        |
        v
Push to GitHub
        |
        v
GitHub Actions
        |
        v
Install Dependencies
        |
        v
Run Tests
        |
        v
Generate Test Results
        |
        +----------+
        |          |
        v          v
      PASS       FAIL
        |          |
        v          v
   Build/Deploy  Fix Code
```

### What Is GitHub Actions?

GitHub Actions is a platform for automating development workflows.

Official documentation: [GitHub Actions Documentation](https://docs.github.com/en/actions?utm_source=chatgpt.com)

### Create Workflow File

```text
.github/
└── workflows/
    └── tests.yml
```

### Example Configuration

```yaml
name: Node.js Tests

on:
  push:
    branches:
      - main
      - develop

  pull_request:
    branches:
      - main

jobs:

  test:

    runs-on: ubuntu-latest

    steps:

      - name: Checkout Repository

        uses: actions/checkout@v4


      - name: Setup Node.js

        uses: actions/setup-node@v4

        with:

          node-version: 22

          cache: npm


      - name: Install Dependencies

        run: npm ci


      - name: Run Tests

        run: npm test
```

This example assumes that the test suite does not require a database or Redis service.

If tests require MySQL or Redis, configure those services in the workflow or use Testcontainers.

### Why Use `npm ci` Instead of `npm install`?

`npm ci`:

- Uses the lockfile.
- Installs the dependency versions specified by the lockfile.
- Provides reproducible CI installations.
- Removes an existing `node_modules` directory before installation.

It is generally preferred for automated CI environments.

# 30. Testing Best Practices

Follow these principles when writing tests.

### 1. Write Independent Tests

One test should not depend on another test's execution order.

### 2. Use Descriptive Test Names

Good:

```javascript
test("rejects expense creation when amount is negative", () => {

});
```

Poor:

```javascript
test("test1", () => {

});
```

### 3. Test Edge Cases

Examples:

- Empty values.
- Null values.
- Invalid IDs.
- Duplicate records.
- Large values.
- Unauthorized requests.

### 4. Avoid Testing Implementation Details

Test the behavior of the application rather than relying on private internal implementation.

### 5. Mock External Services

Avoid sending real emails or payments during ordinary unit tests.

### 6. Use Real Dependencies for Important Integration Tests

Mocking everything will not verify that MySQL, Redis, or BullMQ actually work together.

### 7. Keep Tests Readable

Follow the Arrange-Act-Assert pattern.

### 8. Test Failure Scenarios

Do not test only successful requests.

### 9. Clean Up Resources

Close:

- Database connections.
- Redis connections.
- Socket.IO servers.
- HTTP servers.
- Temporary files.

### 10. Run Tests Before Merging Code

Use CI to prevent untested changes from being merged.

# 31. Arrange-Act-Assert Pattern

This is a common structure for writing readable tests.

AAA stands for:

1. Arrange.
2. Act.
3. Assert.

### Example

```javascript
test("calculates total expense", () => {

    // Arrange

    const amount = 100;

    const quantity = 5;


    // Act

    const result = amount * quantity;


    // Assert

    expect(result).toBe(500);

});
```

### Explanation

**Arrange:** Prepare the test data and dependencies.

**Act:** Execute the function or operation.

**Assert:** Verify the expected result.

This structure makes tests easier to understand and maintain.

# 33. Interview Questions and Answers

### Q1. What is software testing?

The process of evaluating software to verify its correctness and identify defects.

### Q2. What is unit testing?

Testing individual functions or components independently.

### Q3. What is integration testing?

Testing whether multiple components work correctly together.

### Q4. What is end-to-end testing?

Testing complete application workflows from the user's perspective.

### Q5. What is regression testing?

Testing existing functionality after code changes to identify unintended breakages.

### Q6. What is smoke testing?

A basic test that checks whether the critical parts of an application are working.

### Q7. What is Jest?

A JavaScript testing framework used to execute tests, make assertions, and mock dependencies.

### Q8. What is Supertest?

A Node.js library used to test HTTP servers and APIs.

### Q9. What is mocking?

Replacing a real dependency with a controlled test implementation.

### Q10. What is a spy?

A mechanism for observing function calls, arguments, and interactions.

### Q11. What is test coverage?

A measurement of how much of the code is executed by tests.

### Q12. What is statement coverage?

The percentage of executable statements that are executed during testing.

### Q13. What is branch coverage?

The percentage of conditional branches that are executed during testing.

### Q14. What is the testing pyramid?

A testing strategy that generally emphasizes many unit tests, fewer integration tests, and a smaller number of E2E tests.

### Q15. What is the AAA pattern?

Arrange, Act, Assert—a structure for organizing test cases.

### Q16. What is a test fixture?

Predefined data used by tests.

### Q17. What is a test factory?

A function that generates test data.

### Q18. Why should we use a separate test database?

To prevent tests from modifying development or production data and to make test execution repeatable.

### Q19. What is CI?

Continuous Integration is the practice of automatically building and testing code changes.

### Q20. What is GitHub Actions?

A GitHub platform for automating workflows such as testing, building, and deployment.

### Q21. What is P95 latency?

The response-time threshold within which approximately 95% of measured requests complete.

### Q22. What is load testing?

Testing how an application performs under a specified workload.

### Q23. Why should we mock payment gateways?

To test business logic without creating real financial transactions.

### Q24. Should every test use mocks?

No. Important integration tests should also verify real interactions with databases, Redis, and other dependencies.

### Q25. Does 100% code coverage guarantee bug-free software?

No. Coverage measures code execution, not the quality or completeness of assertions.
