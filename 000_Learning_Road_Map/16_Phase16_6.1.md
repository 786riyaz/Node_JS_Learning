# 1. Project Overview

First, understand the application we are going to build.

## 1.1 Application Architecture

Our application will follow a modular layered architecture.

```text
                 CLIENT
                   |
                   |
                   v
              EXPRESS API
                   |
                   v
              MIDDLEWARE
                   |
                   v
                ROUTES
                   |
                   v
              CONTROLLERS
                   |
                   v
                SERVICES
                   |
                   v
              REPOSITORIES
                   |
                   v
                 MYSQL
```

### Responsibility of Each Layer

| Layer | Responsibility |
|---|---|
| Client | Sends HTTP requests |
| Express | Handles incoming requests |
| Middleware | Authentication, validation, logging |
| Routes | Defines API endpoints |
| Controllers | Handles HTTP request and response |
| Services | Implements business logic |
| Repositories | Handles database operations |
| MySQL | Stores application data |

### Example

Suppose a user wants to create an expense.

```http
POST /api/v1/expenses
```

Request body:

```json
{
    "categoryId": 2,
    "amount": 500,
    "description": "Food",
    "expenseDate": "2026-11-25"
}
```

The request will pass through:

1. Authentication middleware.
2. Validation middleware.
3. Expense controller.
4. Expense service.
5. Expense repository.
6. MySQL database.

Each component has a separate responsibility.

Non-functional requirements define how the application should operate.

| Requirement | Implementation |
|---|---|
| Security | JWT, password hashing, validation |
| Performance | Database indexes and pagination |
| Maintainability | Modular architecture |
| Reliability | Centralized error handling |

| Data Integrity | Foreign keys and transactions |
| Testability | Unit and integration tests |
| Configuration | Environment variables |
| Logging | Structured application logs |

### Important Security Requirement

Users must only access their own private records.

For example:

```text
User A:
    Expense 1
    Expense 2

User B:
    Expense 3
    Expense 4
```

User A must never be able to access or modify User B's expenses simply by changing an ID in the request.

This is called **resource ownership authorization**.

We will implement this in the relevant modules.

```env
JWT_REFRESH_SECRET=replace_with_another_long_random_secret

```

Replace the database credentials with your actual MySQL configuration.

### Why Use Environment Variables?

Consider this:

```javascript
const DB_PASSWORD = "mypassword123";
```

If you commit this code to GitHub, the password becomes exposed.

Instead:

```javascript
const DB_PASSWORD = process.env.DB_PASSWORD;
```

Now the secret can be configured separately from application source code.

### Important

Never commit `.env` to GitHub.

Create `.env.example` containing the variable names and safe placeholder values.

```env
NODE_ENV=development

PORT=5000

FRONTEND_URL=http://localhost:3000

DB_HOST=localhost
DB_PORT=3306
DB_NAME=expense_tracker
DB_USER=root
```

# 11. Create Environment Configuration

We should not access `process.env` throughout the entire application.

Instead, create a centralized configuration file.

Create:

```text
src/config/env.js
```

Code:

```javascript
require("dotenv").config();

const { z } = require("zod");

const envSchema = z.object({

    NODE_ENV: z.enum([
        "development",
        "test",
        "production"
    ]).default("development"),

    PORT: z.coerce.number().int().positive().default(5000),

    FRONTEND_URL: z.string().url(),

    DB_HOST: z.string().min(1),

    DB_PORT: z.coerce.number().int().positive().default(3306),

    DB_NAME: z.string().min(1),

    DB_USER: z.string().min(1),

    DB_PASSWORD: z.string(),

    JWT_ACCESS_SECRET: z.string().min(32),

    JWT_ACCESS_EXPIRES_IN: z.string().default("15m"),

    JWT_REFRESH_SECRET: z.string().min(32),

    JWT_REFRESH_EXPIRES_IN: z.string().default("7d")

});

const env = envSchema.parse(process.env);

module.exports = env;
```

### What Is Happening Here?

First:

```javascript
require("dotenv").config();
```

Loads variables from `.env` into `process.env`.

Next:

```javascript
const envSchema = z.object({});
```

Defines the expected configuration structure.

Then:

```javascript
const env = envSchema.parse(process.env);
```

Validates the environment variables.

If something is invalid, Zod throws an error during startup.

### Why Is This Better?

Suppose `DB_HOST` is missing.

Without validation, your application may start and fail later when it tries to connect to MySQL.

With validation, the application fails immediately.

This is called **Fail Fast**.

# 12. Create Database Connection

Now we will connect MySQL using Sequelize.

First, create the database manually in MySQL.

```sql
CREATE DATABASE expense_tracker;
```

You can also create it using MySQL Workbench.

Now create:

```text
src/database/connection.js
```

Code:

```javascript
const { Sequelize } = require("sequelize");

const env = require("../config/env");

const sequelize = new Sequelize(

    env.DB_NAME,

    env.DB_USER,

    env.DB_PASSWORD,

    {

        host: env.DB_HOST,

        port: env.DB_PORT,

        dialect: "mysql",

        logging: false,

        pool: {

            max: 10,

            min: 0,

            acquire: 30000,

            idle: 10000

        }

    }

);

module.exports = sequelize;
```

### Understanding Sequelize Configuration

**dialect:**

```javascript
dialect: "mysql"
```

Specifies which database Sequelize should use.

**logging:**

```javascript
logging: false
```

Disables SQL query logging.

During development, you can enable SQL logging:

```javascript
logging: console.log
```

**pool:**

Connection pooling controls how Sequelize manages database connections.

| Property | Meaning |
|---|---|
| max | Maximum number of connections |
| min | Minimum number of connections |
| acquire | Maximum time to wait for a connection |
| idle | Time before an unused connection can be released |

These values are starting examples, not universal production settings. Configure them according to your database capacity and application workload.

# 14. Create Express Application

Now we will configure Express.

Create:

```text
src/app.js
```

Code:

```javascript
const express = require("express");

const helmet = require("helmet");

const cors = require("cors");

const morgan = require("morgan");

const env = require("./config/env");

const app = express();


// Security Middleware

app.use(helmet());


// CORS Configuration

app.use(cors({

    origin: env.FRONTEND_URL,

    credentials: true

}));


// Request Body Parsing

app.use(express.json({

    limit: "1mb"

}));

app.use(express.urlencoded({

    extended: true,

    limit: "1mb"

}));


// HTTP Request Logging

if (env.NODE_ENV !== "test") {

    app.use(morgan("dev"));

}


// Health Check

app.get("/health", (req, res) => {

    res.status(200).json({

        success: true,

        message: "Expense Tracker API is running"

    });

});

module.exports = app;
```

### Understanding Middleware Ordering

The order is important.

```text
Request
   |
   v
Helmet
   |
   v
CORS
   |
   v
Body Parser
   |
   v
Morgan
   |
   v
Routes
```

For example, body parsing should happen before routes that need to access `req.body`.

# 15. Create server.js

Now create:

```text
src/server.js
```

Code:

```javascript
const app = require("./app");

const sequelize = require("./database/connection");

const env = require("./config/env");

async function startServer() {

    try {

        // Verify Database Connection

        await sequelize.authenticate();

        console.log("Database connected successfully");


        // Start HTTP Server

        const server = app.listen(env.PORT, () => {

            console.log(
                `Server running on http://localhost:${env.PORT}`
            );

        });

        return server;

    } catch (error) {

        console.error("Application startup failed:");

        console.error(error);

        process.exit(1);

    }

}

startServer();
```

### Why Separate app.js and server.js?

`app.js`:

- Creates the Express application.
- Configures middleware.
- Registers routes.

`server.js`:

- Initializes infrastructure.
- Connects to the database.
- Starts the HTTP server.

This separation makes it easier to test the Express application without opening a real network port.

# 18. Common Errors and Troubleshooting

### Error 1: Access Denied for User

```text
Access denied for user 'root'@'localhost'
```

**Possible reason:**

Incorrect MySQL username or password.

**Solution:**

Check:

```env
DB_USER=root
DB_PASSWORD=your_actual_password
```

### Error 2: Unknown Database

```text
Unknown database 'expense_tracker'
```

**Solution:**

Create the database:

```sql
CREATE DATABASE expense_tracker;
```

### Error 3: Cannot Find Module

```text
Error: Cannot find module 'express'
```

**Solution:**

Install dependencies:

```bash
npm install
```

### Error 4: Invalid Environment Variable

```text
ZodError
```

**Possible reason:**

A required environment variable is missing or invalid.

**Solution:**

Check your `.env` file.

### Error 5: Port Already in Use

```text
EADDRINUSE: address already in use :::5000
```

**Possible reason:**

Another application is already using port 5000.

**Solution:**

Change the port:

```env
PORT=5001
```

Or stop the process using port 5000.
