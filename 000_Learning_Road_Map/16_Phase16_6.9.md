# 2. What Is a Database Transaction?

A database transaction is a group of database operations treated as one logical unit of work.

Either all required operations succeed, or the transaction is rolled back.

### Example

Suppose we want to transfer ₹5,000 from Account A to Account B.

Initial balances:

| Account | Balance |
|---|---:|
| Account A | ₹10,000 |
| Account B | ₹2,000 |

Operations:

1. Deduct ₹5,000 from Account A.
2. Add ₹5,000 to Account B.

Expected result:

| Account | Balance |
|---|---:|
| Account A | ₹5,000 |
| Account B | ₹7,000 |

But imagine this happens:

- Account A is debited successfully.
- Account B update fails.

Without a transaction:

| Account | Balance |
|---|---:|
| Account A | ₹5,000 |
| Account B | ₹2,000 |

₹5,000 has effectively disappeared from the two account balances.

A transaction prevents this partial update.

If the second operation fails, the first operation is rolled back.

### Transaction flow

```text
BEGIN TRANSACTION
       |
       v
Deduct ₹5,000 from Account A
       |
       v
Add ₹5,000 to Account B
       |
       v
All operations successful?
       |
   +---+---+
   |       |
  YES      NO
   |       |
   v       v
 COMMIT  ROLLBACK
   |       |
   v       v
 Save    Undo changes
 changes
```

# 3. ACID Properties

Database transactions follow four important properties known as **ACID**.

ACID stands for:

- Atomicity
- Consistency
- Isolation
- Durability

These properties help ensure reliable database operations.

## 3.1 Atomicity

Atomicity means that a transaction is treated as one indivisible unit.

Either all operations succeed or none of them are committed.

Example:

```text
Transaction:
    1. Deduct money from Account A.
    2. Add money to Account B.
```

If operation 2 fails, operation 1 must also be rolled back.

**Remember:** All or nothing.

## 3.2 Consistency

Consistency means that a transaction must preserve database rules and constraints.

For example:

Suppose an account must never have a negative balance.

Initial balance:

```text
₹10,000
```

Withdrawal:

```text
₹12,000
```

The application must reject this operation.

A database constraint can also enforce certain rules.

Example:

```sql
ALTER TABLE accounts
ADD CONSTRAINT chk_balance_nonnegative
CHECK (balance >= 0);
```

MySQL enforces `CHECK` constraints in modern versions, including MySQL 8.0.16 and later.

**Remember:** A transaction must move the database from one valid state to another valid state.

## 3.3 Isolation

Isolation means that concurrent transactions should not interfere with each other's intermediate operations in ways that violate the selected isolation level.

Example:

Two users attempt to purchase the last available product simultaneously.

Initial stock:

```text
Available Stock = 1
```

Both transactions read:

```text
Available Stock = 1
```

Both attempt to purchase the product.

Without appropriate concurrency control, the application might sell two units despite having only one.

Isolation and locking mechanisms help prevent this problem.

## 3.4 Durability

Durability means that once a transaction is successfully committed, its changes are persisted according to the database's durability guarantees.

Example:

```text
BEGIN
UPDATE accounts SET balance = 5000;
COMMIT
```

After a successful commit, the database is responsible for preserving the committed change through normal failures and recovery scenarios, subject to its storage and configuration guarantees.

### ACID Summary

| Property | Meaning |
|---|---|
| Atomicity | All operations succeed or none are committed |
| Consistency | Database rules remain valid |
| Isolation | Concurrent transactions are controlled |
| Durability | Committed changes are persisted |

# 4. COMMIT and ROLLBACK

These are two fundamental transaction operations.

## 4.1 COMMIT

`COMMIT` permanently applies the changes made by a transaction.

Example:

```sql
START TRANSACTION;

UPDATE accounts
SET balance = balance - 5000
WHERE id = 1;

UPDATE accounts
SET balance = balance + 5000
WHERE id = 2;

COMMIT;
```

Both updates are committed.

## 4.2 ROLLBACK

`ROLLBACK` cancels the changes made by the current transaction.

Example:

```sql
START TRANSACTION;

UPDATE accounts
SET balance = balance - 5000
WHERE id = 1;

ROLLBACK;
```

The balance update is undone.

### Difference

| COMMIT | ROLLBACK |
|---|---|
| Saves transaction changes | Cancels transaction changes |
| Ends the transaction | Ends the transaction |
| Makes changes persistent | Restores the previous transactional state |

**Important:** These operations apply to transactional storage engines such as InnoDB. Operations involving nontransactional tables cannot necessarily be rolled back.

# 5. Transactions in Sequelize

Sequelize supports two main approaches:

1. Managed Transactions.
2. Unmanaged Transactions.

Let's understand both.

## 5.1 Managed Transactions

In managed transactions, Sequelize automatically commits or rolls back the transaction.

Syntax:

```javascript
await sequelize.transaction(async (transaction) => {

    // Database operations

});
```

Behavior:

- If the callback completes successfully, Sequelize commits.
- If the callback throws an error or rejects, Sequelize rolls back.

You do not manually call `commit()` or `rollback()`.

### Example: Account Transfer

```javascript
const sequelize = require("../../database/connection");

const { Account } = require("../../database/models");


async function transferMoney(fromId, toId, amount) {

    return await sequelize.transaction(async (transaction) => {

        const fromAccount = await Account.findByPk(fromId, {
            transaction
        });

        const toAccount = await Account.findByPk(toId, {
            transaction
        });


        if (!fromAccount || !toAccount) {
            throw new Error("Account not found");
        }


        if (Number(fromAccount.balance) < amount) {
            throw new Error("Insufficient balance");
        }


        await fromAccount.decrement("balance", {
            by: amount,
            transaction
        });


        await toAccount.increment("balance", {
            by: amount,
            transaction
        });


        return {
            message: "Transfer completed successfully"
        };

    });

}
```

This example demonstrates the transaction structure, but it is not yet safe against concurrent withdrawals. We will fix that using row-level locking later.

### Important

Every query that must participate in the transaction must receive the transaction object:

```javascript
{
    transaction
}
```

If you forget to pass it, that query may execute outside the transaction.

---

## 5.2 Unmanaged Transactions

In unmanaged transactions, you manually control commit and rollback.

Example:

```javascript
const sequelize = require("../../database/connection");

async function performOperation() {

    const transaction = await sequelize.transaction();

    try {

        await Account.update(
            {
                balance: 5000
            },
            {
                where: {
                    id: 1
                },
                transaction
            }
        );


        await transaction.commit();

        return {
            message: "Transaction completed"
        };

    } catch (error) {

        await transaction.rollback();

        throw error;

    }

}
```

Here, we explicitly control:

```javascript
await transaction.commit();
```

and:

```javascript
await transaction.rollback();
```

### Managed vs Unmanaged Transactions

| Managed | Unmanaged |
|---|---|
| Sequelize controls commit and rollback | Developer controls commit and rollback |
| Uses callback | Uses transaction object |
| Less boilerplate | More control |
| Easier to maintain | Useful for complex workflows |

**Recommendation:** Prefer managed transactions for most ordinary service-layer operations.

# 6. Implementing Transactions in Our Expense Tracker

Let's apply this concept to our Expense Management Module.

Suppose creating an expense requires:

1. Creating the expense.
2. Creating an audit log.

Both operations should succeed together.

### Example database table

```sql
CREATE TABLE audit_logs (

    id BIGINT PRIMARY KEY AUTO_INCREMENT,

    user_id BIGINT NOT NULL,

    description VARCHAR(500),

    created_at DATETIME DEFAULT CURRENT_TIMESTAMP

```

### Repository example

```javascript
const {
    Expense,
    AuditLog
} = require("../../database/models");


class ExpenseRepository {

    async create(data, transaction) {

        return await Expense.create(data, {
            transaction
        });

    }


    async createAuditLog(data, transaction) {

        return await AuditLog.create(data, {
            transaction
        });

    }

}

module.exports = new ExpenseRepository();
```

### Service example

```javascript
const sequelize = require("../../database/connection");

const expenseRepository = require("./expense.repository");


class ExpenseService {

    async createExpense(userId, data) {

        return await sequelize.transaction(async (transaction) => {

            const expense = await expenseRepository.create({

                userId,

                categoryId: data.categoryId,

                amount: data.amount,

                description: data.description,

                expenseDate: data.expenseDate,

                paymentMethod: data.paymentMethod

            }, transaction);


            await expenseRepository.createAuditLog({

                userId,

                action: "EXPENSE_CREATED",

                description: `Expense created with ID ${expense.id}`

            }, transaction);


            return expense;

        });

    }

}

module.exports = new ExpenseService();
```

### What happens if audit log creation fails?

Suppose:

```javascript
await expenseRepository.createAuditLog(...);
```

throws an error.

Because we are using a managed transaction:

1. The transaction callback fails.
2. Sequelize rolls back the transaction.
3. The expense insertion is also undone.

This maintains consistency.

### Important architectural note

A database transaction can only atomically control operations participating in that database transaction.

For example, sending an email inside the transaction cannot be rolled back.

For reliable external side effects, we will later study the **Transactional Outbox Pattern** and background job processing.

# 7. Transaction Isolation Levels

Now let's understand one of the most important database concurrency concepts.

Isolation levels determine how transactions interact when multiple transactions execute simultaneously.

SQL databases commonly provide four isolation levels:

1. READ UNCOMMITTED
2. READ COMMITTED
3. REPEATABLE READ
4. SERIALIZABLE

Before studying them, understand three common concurrency problems.

## 7.1 Dirty Read

A dirty read occurs when one transaction reads data written by another transaction that has not yet committed.

Example:

Initial balance:

```text
₹10,000
```

Transaction A:

```sql
START TRANSACTION;

UPDATE accounts
SET balance = 5000
WHERE id = 1;
```

Transaction A has not committed yet.

Transaction B:

```sql
SELECT balance
FROM accounts
WHERE id = 1;
```

If Transaction B sees ₹5,000 before Transaction A commits, it has read uncommitted data.

Now suppose Transaction A executes:

```sql
ROLLBACK;
```

The actual balance returns to ₹10,000.

Transaction B had read a value that never became committed data.

That is a dirty read.

## 7.2 Non-Repeatable Read

A non-repeatable read occurs when the same row is read twice within one transaction and produces different committed values.

Example:

Transaction A:

```sql
START TRANSACTION;

SELECT balance
FROM accounts
WHERE id = 1;
```

Result:

```text
₹10,000
```

Transaction B:

```sql
UPDATE accounts
SET balance = 8000
WHERE id = 1;

COMMIT;
```

Transaction A executes the same query again.

```sql
SELECT balance
FROM accounts
WHERE id = 1;
```

Result under an isolation level that allows non-repeatable reads:

```text
₹8,000
```

The same transaction has read two different committed values for the same row.

## 7.3 Phantom Read

A phantom read occurs when a transaction repeats a query using a condition and finds a different set of rows because another transaction inserted or deleted matching records.

Example:

Transaction A:

```sql
START TRANSACTION;

SELECT *
FROM expenses
WHERE amount > 5000;
```

It finds:

```text
2 records
```

Transaction B inserts another matching record and commits.

Transaction A repeats:

```sql
SELECT *
FROM expenses
WHERE amount > 5000;
```

It may now find:

```text
3 records
```

The additional matching row is called a phantom row.

### Summary

| Problem | Meaning |
|---|---|
| Dirty Read | Reading uncommitted data |
| Non-Repeatable Read | Same row returns different committed values |
| Phantom Read | Repeated range query returns a different set of rows |

---

# 8. Understanding Isolation Levels

Let's compare the four standard isolation levels.

| Isolation Level | Dirty Read | Non-Repeatable Read | Phantom Read |
|---|---|---|---|
| READ UNCOMMITTED | Possible | Possible | Possible |
| READ COMMITTED | Prevented | Possible | Possible |
| REPEATABLE READ | Prevented | Prevented for ordinary consistent reads | Possible in the SQL standard |
| SERIALIZABLE | Prevented | Prevented | Prevented |

**Important MySQL detail:** InnoDB's default isolation level is generally `REPEATABLE READ`.

InnoDB uses MVCC (Multi-Version Concurrency Control) for consistent reads. Its locking behavior also prevents many anomalies that might be possible in other implementations of the same isolation level.

### What is MVCC?

MVCC stands for:

**Multi-Version Concurrency Control.**

It allows database readers to access consistent versions of records without always blocking writers.

Instead of making every read wait for every write, the database can use row versions and transaction snapshots.

This improves concurrency.

### When should we use each isolation level?

| Isolation Level | Typical Use |
|---|---|
| READ UNCOMMITTED | Rarely appropriate for application transactions |
| READ COMMITTED | Applications that prefer seeing newly committed data on each read |
| REPEATABLE READ | General-purpose transactional workloads |
| SERIALIZABLE | Operations requiring stronger serialization guarantees |

Higher isolation can reduce concurrency and increase locking or retry requirements.

Do not automatically choose SERIALIZABLE for every operation.

# 10. Pessimistic Locking

Now let's solve the concurrent withdrawal problem.

Suppose Account A has ₹10,000.

Two requests arrive simultaneously:

- Request A withdraws ₹7,000.
- Request B withdraws ₹6,000.

Both requests might read the original balance of ₹10,000.

Both might conclude that sufficient money is available.

But together they attempt to withdraw ₹13,000.

This is a race condition.

### What is pessimistic locking?

Pessimistic locking locks a database row so that competing transactions cannot modify it in conflicting ways until the lock is released.

A common SQL statement is:

```sql
SELECT *
FROM accounts
WHERE id = 1
FOR UPDATE;
```

`FOR UPDATE` obtains an exclusive lock on the selected rows in InnoDB.

### Sequelize implementation

```javascript
const {
    Transaction
} = require("sequelize");

async function withdrawMoney(accountId, amount) {

    return await sequelize.transaction(async (transaction) => {

        const account = await Account.findByPk(accountId, {

            transaction,

            lock: transaction.LOCK.UPDATE

        });


        if (!account) {
            throw new Error("Account not found");
        }


        if (Number(account.balance) < amount) {
            throw new Error("Insufficient balance");
        }


        await account.decrement("balance", {

            by: amount,

            transaction

        });


        return {
            message: "Withdrawal successful"
        };

    });

}
```

### How does it work?

Suppose Request A acquires the lock first.

```text
Request A:
    Lock Account A
    Read ₹10,000
    Withdraw ₹7,000
    Commit
    Release lock
```

Request B must wait for the conflicting lock.

After Request A commits, Request B continues and sees the updated balance:

```text
₹3,000
```

It then rejects the ₹6,000 withdrawal.

This prevents the overspending problem.

**Important:** The example's `Number()` comparison is for illustration. Financial balances should use decimal-safe comparisons, or an atomic conditional SQL update.

# 11. Optimistic Locking

Pessimistic locking locks records before modification.

Optimistic locking works differently.

It assumes conflicts are relatively uncommon and checks whether another transaction modified the record before saving the current transaction's changes.

### Example

Suppose a user opens a budget record.

Initial budget:

```text
₹10,000
```

Two browser tabs open the same record.

Tab A changes it to:

```text
₹12,000
```

Tab B changes it to:

```text
₹15,000
```

Without concurrency protection, the last update might overwrite the first update.

This is called a lost update.

### What is optimistic locking?

Optimistic locking uses a version number.

Example database record:

| ID | Amount | Version |
|---:|---:|---:|
| 1 | 10,000 | 0 |

Tab A updates the record.

The version becomes:

| ID | Amount | Version |
|---:|---:|---:|
| 1 | 12,000 | 1 |

Tab B attempts to update using the old version number `0`.

The database detects that the record has changed and rejects the update.

### Sequelize implementation

In your model:

```javascript
const Budget = sequelize.define("Budget", {

    id: {
        type: DataTypes.BIGINT,
        primaryKey: true,
        autoIncrement: true
    },

    amount: {
        type: DataTypes.DECIMAL(12, 2),
        allowNull: false
    }

}, {

    version: true

});
```

Sequelize will maintain a version field.

Example:

```javascript
const budget = await Budget.findByPk(1);

budget.amount = "12000.00";

await budget.save();
```

If another request modifies the same instance's underlying database record first, Sequelize can throw an `OptimisticLockError`.

Handle it:

```javascript
const {
    OptimisticLockError
} = require("sequelize");

try {

    await budget.save();

} catch (error) {

    if (error instanceof OptimisticLockError) {

        throw new Error(
            "Budget was modified by another request. Please reload."
        );

    }

    throw error;

}
```

### Pessimistic vs Optimistic Locking

| Pessimistic Locking | Optimistic Locking |
|---|---|
| Locks the record | Tracks record version |
| Other conflicting transactions may wait | Conflicting update is rejected |
| Useful for high-contention operations | Useful when conflicts are relatively rare |
| Uses row locks | Uses version checking |

# 12. Database Deadlocks

A deadlock occurs when two or more transactions wait for resources locked by each other.

Example:

Transaction A:

```text
Locks Row 1
Waits for Row 2
```

Transaction B:

```text
Locks Row 2
Waits for Row 1
```

Neither transaction can continue.

### Visual representation

```text
Transaction A
     |
     v
Locks Row 1
     |
     v
Waits for Row 2
     |
     +------------------+
                        |
                        v
                    Deadlock
                        ^
                        |
     +------------------+
     |
     v
Waits for Row 1
     |
     v
Locks Row 2
     |
Transaction B
```

MySQL InnoDB detects deadlocks and normally rolls back one of the transactions to allow the other to proceed.

### How can we prevent deadlocks?

**1. Access records in a consistent order.**

Bad:

```text
Transaction A: Lock Row 1 → Row 2
Transaction B: Lock Row 2 → Row 1
```

Better:

```text
Transaction A: Lock Row 1 → Row 2
Transaction B: Lock Row 1 → Row 2
```

**2. Keep transactions short.**

Do not perform unnecessary operations while holding database locks.

**3. Avoid external API calls inside transactions.**

For example, do not wait for an email provider while holding a database transaction open.

**4. Add appropriate indexes.**

Indexes can reduce the number of records scanned and help reduce unnecessary locking.

**5. Implement retry logic for retryable database errors.**

### Sequelize retry example

```javascript
await sequelize.transaction({

    retry: {
        max: 3,
        match: [
            /Deadlock found/
        ]
    }

}, async (transaction) => {

    // Database operations

});
```

The exact retry configuration should be verified against your installed Sequelize version and database driver.

A retry is safe only when the transaction's operations can be repeated without duplicating external side effects.

# 13. What Is a Database Index?

A database index is a data structure that helps the database locate records more efficiently.

Think of a book.

Without an index:

You must search every page to find a particular topic.

With an index:

You can directly locate the relevant page.

A database index works similarly.

### Example

Suppose we have 1 million expense records.

We frequently execute:

```sql
SELECT *
FROM expenses
WHERE user_id = 10;
```

Without an index, the database may need to scan many rows.

We can create:

```sql
CREATE INDEX idx_expenses_user_id
ON expenses(user_id);
```

Now the database can use the index to locate matching records more efficiently.

### Advantages of indexes

- Faster data retrieval.
- Faster filtering.
- Faster joins in suitable cases.
- Faster sorting in suitable cases.
- Better performance for frequently executed queries.

### Disadvantages of indexes

- Consume additional storage.
- Increase INSERT overhead.
- Increase UPDATE overhead when indexed columns change.
- Increase DELETE overhead.
- Require maintenance.

**Important:** More indexes do not automatically mean better performance.

Indexes should be designed around actual query patterns.

# 14. Types of Database Indexes

## 14.1 Primary Key Index

A primary key uniquely identifies each record.

Example:

```sql
CREATE TABLE users (

    id BIGINT PRIMARY KEY AUTO_INCREMENT,

    name VARCHAR(100)

);
```

In InnoDB, the primary key is the clustered index.

The table's rows are organized around the primary key.

## 14.2 Unique Index

A unique index prevents duplicate indexed values.

Example:

```sql
CREATE UNIQUE INDEX unique_user_email
ON users(email);
```

Two users cannot have the same email value.

Remember that MySQL unique indexes can permit multiple NULL values.

## 14.3 Single-Column Index

An index on one column.

```sql
CREATE INDEX idx_expenses_amount
ON expenses(amount);
```

Useful for queries that filter or sort by amount.

## 14.4 Composite Index

An index containing multiple columns.

Example:

```sql
CREATE INDEX idx_expenses_user_date
ON expenses(user_id, expense_date);
```

This is useful for queries such as:

```sql
SELECT *
FROM expenses
WHERE user_id = 10
AND expense_date >= '2026-11-01'
AND expense_date <= '2026-11-30';
```

### Important: Column order matters

Consider:

```sql
CREATE INDEX idx_user_date
ON expenses(user_id, expense_date);
```

This index is most useful for:

```sql
WHERE user_id = 10
```

and:

```sql
WHERE user_id = 10
AND expense_date = '2026-11-24'
```

But it is generally not as useful for a query filtering only by `expense_date`.

This is related to the **leftmost prefix principle** of composite indexes.

### Example

Index:

```text
(user_id, expense_date, amount)
```

Can support lookups using:

```text
user_id
user_id + expense_date
user_id + expense_date + amount
```

But not necessarily an efficient lookup using only:

```text
expense_date
```

# 15. Creating Indexes Using Sequelize Migrations

In our Expense Tracker, we can create indexes through migrations.

Example:

```javascript
module.exports = {

    async up(queryInterface, Sequelize) {

        await queryInterface.addIndex(
            "expenses",
            ["user_id", "expense_date"],
            {
                name: "idx_expenses_user_date"
            }
        );


        await queryInterface.addIndex(
            "expenses",
            ["user_id", "category_id"],
            {
                name: "idx_expenses_user_category"
            }
        );


        await queryInterface.addIndex(
            "incomes",
            ["user_id", "income_date"],
            {
                name: "idx_incomes_user_date"
            }
        );

    },


    async down(queryInterface) {

        await queryInterface.removeIndex(
            "expenses",
            "idx_expenses_user_date"
        );


        await queryInterface.removeIndex(
            "expenses",
            "idx_expenses_user_category"
        );


        await queryInterface.removeIndex(
            "incomes",
            "idx_incomes_user_date"
        );

    }

};
```

This makes index creation and removal part of your database migration history.

# 16. Query Optimization

Query optimization means improving SQL queries so they execute more efficiently.

Let's understand common problems.

## 16.1 Avoid SELECT *

Bad:

```sql
SELECT *
FROM expenses
WHERE user_id = 10;
```

This retrieves every column.

Better:

```sql
SELECT
    id,
    amount,
    description,
    expense_date
FROM expenses
WHERE user_id = 10;
```

Only retrieve the columns you need.

Sequelize:

```javascript
const expenses = await Expense.findAll({

    attributes: [
        "id",
        "amount",
        "description",
        "expenseDate"
    ],

    where: {
        userId
    }

});
```

## 16.2 Avoid unnecessary queries

Bad:

```javascript
const expenses = await Expense.findAll({
    where: { userId }
});

const total = await Expense.count({
    where: { userId }
});
```

If you only need the total amount, use:

```javascript
const total = await Expense.sum("amount", {
    where: { userId }
});
```

This avoids retrieving all expense records just to calculate a total.

## 16.3 Use LIMIT

Bad:

```sql
SELECT *
FROM expenses;
```

Better:

```sql
SELECT *
FROM expenses
LIMIT 20;
```

For large datasets, use pagination rather than returning every record.

## 16.4 Avoid unnecessary wildcard searches

A query such as:

```sql
WHERE description LIKE '%food%'
```

may require scanning many rows.

A normal B-tree index generally cannot efficiently support a leading-wildcard search.

For larger applications, consider:

- Full-text indexes.
- Dedicated search systems.
- More selective search filters.

## 16.5 Avoid unnecessary functions on indexed columns

Consider:

```sql
SELECT *
FROM expenses
WHERE YEAR(expense_date) = 2026;
```

Applying a function to an indexed column can prevent ordinary index range access.

Prefer:

```sql
SELECT *
FROM expenses
WHERE expense_date >= '2026-01-01'
AND expense_date < '2027-01-01';
```

This range condition can make better use of a suitable index.

# 17. Understanding the N+1 Query Problem

This is a very common problem in backend development.

Suppose we want to retrieve 100 expenses with their categories.

### Incorrect approach

```javascript
const expenses = await Expense.findAll({

    where: { userId }

});


for (const expense of expenses) {

    const category = await Category.findByPk(
        expense.categoryId
    );

    console.log(category.name);

}
```

How many database queries are executed?

1 query to retrieve expenses.

100 additional queries to retrieve categories.

Total:

```text
101 database queries
```

This is called the **N+1 Query Problem**.

### Better approach: Eager Loading

```javascript
const expenses = await Expense.findAll({

    where: { userId },

    include: [

        {
            model: Category,
            as: "category"
        }

    ]

});
```

Now Sequelize retrieves the associated category data using a joined query in the usual `belongsTo` case.

The query count is significantly reduced.

### Comparison

| Approach | Queries |
|---|---:|
| N+1 implementation | 101 |
| Eager loading | Usually 1 joined query |

Actual query behavior can vary depending on associations and Sequelize options.

**Remember:** N+1 is not limited to Sequelize. It can occur with any ORM or database access layer.

# 18. Database Connection Pooling

Every database connection consumes resources.

Creating a new database connection for every HTTP request is inefficient.

Instead, applications use connection pooling.

### What is connection pooling?

A connection pool maintains a collection of reusable database connections.

When an API request needs the database:

1. It requests a connection from the pool.
2. The pool provides an available connection.
3. The query executes.
4. The connection is returned to the pool.

### Without connection pooling

```text
Request 1 → Create connection → Query → Close
Request 2 → Create connection → Query → Close
Request 3 → Create connection → Query → Close
```

### With connection pooling

```text
        Connection Pool
        /      |      \
       /       |       \
  Connection  Connection  Connection
       \       |       /
        \      |      /
         API Requests
```

### Sequelize configuration

In our database connection file:

```javascript
const sequelize = new Sequelize(
    DB_NAME,
    DB_USER,
    DB_PASSWORD,
    {

        host: DB_HOST,

        dialect: "mysql",

        pool: {

            max: 10,

            min: 0,

            acquire: 30000,

            idle: 10000

        }

    }
);
```

### Pool configuration

| Option | Meaning |
|---|---|
| max | Maximum connections in the pool |
| min | Minimum maintained connections |
| acquire | Maximum time to wait for a connection |
| idle | Time an unused connection can remain before being released |

### Important production consideration

Suppose you run:

```text
3 application instances

Pool max per instance = 10
```

Potential maximum connections:

```text
3 × 10 = 30 connections
```

If you have multiple services, workers, or background processes, their pools must also be included in the database connection budget.

Do not blindly set `max: 100` on every application instance.

The database has a finite connection capacity.

# 19. Understanding EXPLAIN

`EXPLAIN` helps us understand how MySQL plans to execute a query.

Example:

```sql
EXPLAIN
SELECT *
FROM expenses
WHERE user_id = 10;
```

It can show:

- Which table is accessed.
- Which indexes are considered.
- Which index is selected.
- The access type.
- Estimated rows examined.
- Additional execution details.

### Important EXPLAIN columns

| Column | Meaning |
|---|---|
| id | Query execution identifier |
| select_type | Type of SELECT operation |
| table | Table being accessed |
| type | Access method |
| possible_keys | Potential indexes |
| key | Selected index |
| rows | Estimated rows examined |
| Extra | Additional execution information |

### Understanding the `type` column

Common access types include:

| Type | General Meaning |
|---|---|
| system | Special case of a one-row table |
| const | At most one matching row |
| eq_ref | One matching row per preceding row |
| ref | Nonunique index lookup |
| range | Index range scan |
| index | Full index scan |
| ALL | Full table scan |

Generally, a full table scan can be expensive on large tables.

However, it is not always bad. For small tables or queries returning a large proportion of records, a table scan may be the optimal plan.

### Example

Without an index:

```sql
EXPLAIN
SELECT *
FROM expenses
WHERE user_id = 10;
```

The optimizer may choose:

```text
type: ALL
key: NULL
```

After creating an index:

```sql
CREATE INDEX idx_expenses_user
ON expenses(user_id);
```

Run EXPLAIN again.

The optimizer may choose:

```text
type: ref
key: idx_expenses_user
```

This indicates indexed access.

The exact result depends on table size, data distribution, statistics, and query structure.

# 20. Understanding EXPLAIN ANALYZE

`EXPLAIN` generally provides the optimizer's estimated execution plan.

MySQL's `EXPLAIN ANALYZE` actually executes the query and reports runtime information.

Example:

```sql
EXPLAIN ANALYZE
SELECT *
FROM expenses
WHERE user_id = 10;
```

It can provide:

- Actual execution time.
- Estimated execution cost.
- Actual rows returned.
- Number of loops.
- Execution time for individual plan operations.

This helps us compare estimated behavior with actual performance.

**Important:** `EXPLAIN ANALYZE` executes the query. Use caution with statements that modify data.

# 21. Practical Optimization of Our Expense Tracker

Let's review some queries from our project.

### Query 1: Get all expenses for a user

```sql
SELECT *
FROM expenses
WHERE user_id = 10;
```

Recommended index:

```sql
CREATE INDEX idx_expenses_user
ON expenses(user_id);
```

### Query 2: Get monthly expenses

```sql
SELECT SUM(amount)
FROM expenses
WHERE user_id = 10
AND expense_date >= '2026-11-01'
AND expense_date < '2026-12-01';
```

Recommended index:

```sql
CREATE INDEX idx_expenses_user_date
ON expenses(user_id, expense_date);
```

### Query 3: Get category-wise expenses

```sql
SELECT
    category_id,
    SUM(amount)
FROM expenses
WHERE user_id = 10
AND expense_date >= '2026-11-01'
AND expense_date < '2026-12-01'
GROUP BY category_id;
```

A possible index:

```sql
CREATE INDEX idx_expenses_user_date_category
ON expenses(user_id, expense_date, category_id);
```

The best index depends on the actual query workload and execution plan.

Do not create all possible indexes without testing.

### Query 4: Get recent expenses

```sql
SELECT *
FROM expenses
WHERE user_id = 10
ORDER BY expense_date DESC, id DESC
LIMIT 10;
```

A possible index:

```sql
CREATE INDEX idx_expenses_user_date_id
ON expenses(user_id, expense_date, id);
```

Check the actual query plan to determine whether this index helps.

# 22. Important Production Concepts

## 22.1 Keep Transactions Short

Avoid:

```javascript
await sequelize.transaction(async (transaction) => {

    await Expense.create(data, { transaction });

    // Slow external API request
    await sendEmail();

    await AuditLog.create(log, { transaction });

});
```

The external request may take several seconds.

During that time, database locks may remain held.

Better:

- Perform database operations inside the transaction.
- Commit the transaction.
- Send notifications afterward.

For reliable delivery, use an outbox pattern or background queue.

## 22.2 Use Atomic Database Updates

Consider:

```javascript
const account = await Account.findByPk(id);

account.balance -= amount;

await account.save();
```

This can cause a lost update when multiple requests modify the same record.

For simple operations, a conditional atomic update can be safer.

Example:

```sql
UPDATE accounts
SET balance = balance - 1000
WHERE id = 1
AND balance >= 1000;
```

Then check the affected-row count.

If zero rows were updated, either the account does not exist or the balance was insufficient.

For financial applications, also use decimal-safe arithmetic and appropriate locking or isolation controls.

## 22.3 Avoid Long Transactions

Long transactions can:

- Hold locks longer.
- Increase contention.
- Increase deadlock probability.
- Delay other transactions.
- Increase resource usage.

## 22.4 Monitor Slow Queries

Enable MySQL slow query logging in appropriate environments.

Analyze frequently executed expensive queries.

Optimize based on measurements rather than assumptions.

# 24. Interview Questions and Answers

### Q1. What is a database transaction?

A transaction is a group of database operations treated as one logical unit of work.

### Q2. What are ACID properties?

Atomicity, Consistency, Isolation, and Durability.

### Q3. What is the difference between COMMIT and ROLLBACK?

COMMIT saves transaction changes, while ROLLBACK cancels uncommitted changes.

### Q4. What is a managed transaction in Sequelize?

A transaction where Sequelize automatically commits when the callback succeeds and rolls back when it fails.

### Q5. What is an unmanaged transaction?

A transaction where the developer manually controls commit and rollback.

### Q6. What is a dirty read?

Reading uncommitted data from another transaction.

### Q7. What is a non-repeatable read?

Reading the same row multiple times within a transaction and receiving different committed values.

### Q8. What is a phantom read?

A repeated query returns a different set of matching rows because another transaction changed the matching dataset.

### Q9. What is MVCC?

Multi-Version Concurrency Control is a database technique that allows transactions to access consistent versions of records while improving concurrency.

### Q10. What is pessimistic locking?

A concurrency-control technique that locks records to prevent conflicting modifications.

### Q11. What is optimistic locking?

A technique that detects conflicting updates using a version number or similar mechanism.

### Q12. What is a deadlock?

A situation where transactions wait for resources held by each other, preventing progress until the database resolves the deadlock.

### Q13. How can deadlocks be reduced?

Use consistent lock ordering, short transactions, appropriate indexes, and retry handling.

### Q14. What is a database index?

A data structure that helps the database locate records efficiently.

### Q15. What is a composite index?

An index containing multiple columns.

### Q16. What is the leftmost prefix principle?

A composite index can generally support lookups using its leading columns and their prefixes.

### Q17. What is the N+1 query problem?

A performance issue where an application executes one query to retrieve records and then an additional query for each record to retrieve related data.

### Q18. How can Sequelize eager loading solve N+1?

By retrieving associated records using the `include` option instead of querying each association individually.

### Q19. What is connection pooling?

Maintaining reusable database connections instead of creating a new connection for every request.

### Q20. What is EXPLAIN?

A MySQL command that shows the execution plan selected for a query.

### Q21. What is EXPLAIN ANALYZE?

A command that executes a query and reports actual execution details alongside its plan.

### Q22. Why are too many indexes harmful?

They consume storage and increase the cost of insert, update, and delete operations.

### Q23. What is a race condition?

A problem where the result of concurrent operations depends on their execution timing.

### Q24. What is a lost update?

A concurrency problem where one update overwrites another update without properly accounting for it.

### Q25. What is the difference between optimistic and pessimistic locking?

Pessimistic locking prevents conflicting operations by acquiring locks. Optimistic locking detects conflicts when changes are saved.
