# 1. What Are Software Design Principles?

Software design principles are guidelines that help developers write better software.

Consider two developers building the same Expense Tracker API.

### Developer A

```javascript
app.post("/expenses", async (req, res) => {

    const user = await User.findByPk(req.body.userId);

    const expense = await Expense.create(req.body);

    await sendEmail(user.email, "Expense Created");

    res.json(expense);

});
```

Everything is inside one route handler:

- User lookup.
- Database operation.
- Email notification.
- HTTP response.

This works, but it becomes difficult to maintain when requirements increase.

### Developer B

```javascript
app.post(
    "/expenses",
    expenseController.createExpense
);
```

The controller delegates the operation to a service.

The service handles business rules and communicates with repositories and other services.

Each component has a clearly defined responsibility.

**The goal of software design principles is to make code easier to understand, modify, test, and extend.**

Two important concepts are:

1. SOLID principles.
2. Design patterns.

# 2. What Are SOLID Principles?

SOLID is an acronym representing five object-oriented design principles.

| Letter | Principle | Main Idea |
|---|---|---|
| S | Single Responsibility Principle | One responsibility per module or class |
| O | Open/Closed Principle | Open for extension, closed for modification |
| L | Liskov Substitution Principle | Subtypes should be replaceable for their base types |
| I | Interface Segregation Principle | Prefer smaller, focused interfaces |
| D | Dependency Inversion Principle | Depend on abstractions, not concrete implementations |

These principles originated in object-oriented software design, but they can also be applied to JavaScript and Node.js applications.

Let's understand each principle with practical examples.

# 3. S — Single Responsibility Principle (SRP)

## 3.1 What Is SRP?

The Single Responsibility Principle states:

> A module should have one reason to change.

In simple words, a class, function, or module should have one clearly defined responsibility.

It does not mean that a function can only contain one line of code.

It means that unrelated responsibilities should not be combined into one component.

## 3.2 Example: Violating SRP

Imagine an application that generates expense reports.

```javascript
class ExpenseReport {

    async getExpenses(userId) {

        return await Expense.findAll({

            where: {
                userId
            }

        });

    }

    generatePDF(expenses) {

        // Generate PDF

    }

    async sendEmail(email, pdf) {

        // Send email

    }

}
```

What responsibilities does this class have?

1. Fetching expenses.
2. Generating PDF files.
3. Sending emails.

These are three different responsibilities.

If we change the email provider, we need to modify this class.

If we change the PDF generation library, we also need to modify this class.

This violates SRP.

## 3.3 Applying SRP

Separate the responsibilities.

### expense.repository.js

```javascript
class ExpenseRepository {

    async findByUserId(userId) {

        return await Expense.findAll({

            where: {
                userId
            }

        });

    }

}

module.exports = ExpenseRepository;
```

### pdf.service.js

```javascript
class PDFService {

    async generateExpenseReport(expenses) {

        // Generate PDF

        return "report.pdf";

    }

}

module.exports = PDFService;
```

### email.service.js

```javascript
class EmailService {

    async sendEmail(email, attachment) {

        // Send email

        console.log("Email sent to:", email);

    }

}

module.exports = EmailService;
```

### report.service.js

```javascript
class ReportService {

    constructor(
        expenseRepository,
        pdfService,
        emailService
    ) {

        this.expenseRepository = expenseRepository;

        this.pdfService = pdfService;

        this.emailService = emailService;

    }

    async generateAndSendReport(userId, email) {

        const expenses =
            await this.expenseRepository.findByUserId(userId);

        const pdf =
            await this.pdfService.generateExpenseReport(expenses);

        await this.emailService.sendEmail(email, pdf);

    }

}

module.exports = ReportService;
```

Now every component has a focused responsibility.

The `ReportService` coordinates the report-generation workflow, while the other components handle their respective operations.

## 3.4 Benefits of SRP

- Easier maintenance.
- Better code organization.
- Easier unit testing.
- Less dependency between components.
- Easier replacement of individual components.

## 3.5 When Should You Apply SRP?

Apply SRP when:

- A class handles unrelated operations.
- A service becomes too large.
- A module changes for multiple unrelated reasons.
- Testing one operation requires setting up many unrelated dependencies.

**Interview Question: What is the Single Responsibility Principle?**

Answer: SRP states that a module or class should have one reason to change. It encourages separating unrelated responsibilities into independent components.

# 4. O — Open/Closed Principle (OCP)

## 4.1 What Is OCP?

The Open/Closed Principle states:

> Software entities should be open for extension but closed for modification.

In simple words:

You should be able to add new functionality without repeatedly modifying existing, stable code.

Let's understand this with a payment example.

## 4.2 Example: Violating OCP

Suppose an application supports three payment methods:

- Credit Card.
- PayPal.
- Stripe.

A developer might write:

```javascript
class PaymentService {

    processPayment(type, amount) {

        if (type === "credit-card") {

            console.log("Processing Credit Card:", amount);

        }

        else if (type === "paypal") {

            console.log("Processing PayPal:", amount);

        }

        else if (type === "stripe") {

            console.log("Processing Stripe:", amount);

        }

    }

}
```

Now imagine the client requests another payment method.

You must modify the existing `PaymentService` class.

As more payment methods are added, the class becomes increasingly complicated.

## 4.3 Applying OCP Using the Strategy Pattern

First, create separate payment implementations.

### creditCardPayment.js

```javascript
class CreditCardPayment {

    pay(amount) {

        console.log("Credit Card Payment:", amount);

    }

}

module.exports = CreditCardPayment;
```

### paypalPayment.js

```javascript
class PayPalPayment {

    pay(amount) {

        console.log("PayPal Payment:", amount);

    }

}

module.exports = PayPalPayment;
```

### stripePayment.js

```javascript
class StripePayment {

    pay(amount) {

        console.log("Stripe Payment:", amount);

    }

}

module.exports = StripePayment;
```

### paymentService.js

```javascript
class PaymentService {

    constructor(paymentProvider) {

        this.paymentProvider = paymentProvider;

    }

    processPayment(amount) {

        return this.paymentProvider.pay(amount);

    }

}

module.exports = PaymentService;
```

### Usage

```javascript
const PaymentService = require("./paymentService");

const CreditCardPayment = require("./creditCardPayment");

const creditCard = new CreditCardPayment();

const paymentService = new PaymentService(creditCard);

paymentService.processPayment(1000);
```

Now, if you want to introduce another payment provider, create another implementation.

You don't need to change the existing `PaymentService`.

This is an example of OCP.

## 4.4 Important Note

JavaScript does not enforce interfaces in the same way as languages such as Java.

However, you can define a common contract through conventions, TypeScript interfaces, abstract classes, or runtime validation.

In the above example, every payment provider is expected to implement:

```javascript
pay(amount)
```

## 4.5 Benefits of OCP

- Easier feature extension.
- Less modification of existing code.
- Better separation of concerns.
- Easier integration of new providers.
- Reduced regression risk.

**Interview Question: What is the Open/Closed Principle?**

Answer: OCP states that software should be open for extension but closed for modification. New functionality should ideally be added through new implementations rather than repeatedly changing stable existing code.

# 5. L — Liskov Substitution Principle (LSP)

## 5.1 What Is LSP?

The Liskov Substitution Principle states:

> Objects of a subtype should be replaceable for objects of their base type without changing the correctness of the program.

In simple words:

If a component promises certain behavior, its alternative implementation should respect that behavior.

Let's understand this through an example.

## 5.2 Example: Violating LSP

Imagine we have a general payment provider.

```javascript
class PaymentProvider {

    pay(amount) {

        console.log("Payment processed:", amount);

    }

    refund(amount) {

        console.log("Refund processed:", amount);

    }

}
```

Now create two implementations.

```javascript
class CreditCardProvider extends PaymentProvider {

    pay(amount) {

        console.log("Credit Card Payment:", amount);

    }

    refund(amount) {

        console.log("Credit Card Refund:", amount);

    }

}
```

```javascript
class CashOnDeliveryProvider extends PaymentProvider {

    pay(amount) {

        console.log("Cash collected:", amount);

    }

    refund(amount) {

        throw new Error("Refund not supported");

    }

}
```

The problem is that the parent class promises that every provider supports refunds.

But `CashOnDeliveryProvider` cannot fulfill that contract.

Any code expecting a fully functional `PaymentProvider` may fail when given the cash-on-delivery implementation.

This violates LSP.

## 5.3 Applying LSP

Separate payment processing and refund capabilities.

```javascript
class CreditCardProvider {

    pay(amount) {

        console.log("Credit Card Payment:", amount);

    }

    refund(amount) {

        console.log("Credit Card Refund:", amount);

    }

}
```

```javascript
class CashOnDeliveryProvider {

    pay(amount) {

        console.log("Cash collected:", amount);

    }

}
```

Now we have separate capabilities.

A component that only requires payment processing can accept either provider.

A refund service should only accept providers that actually support refunds.

In TypeScript, we could express this more explicitly:

```typescript
interface PaymentProvider {

    pay(amount: number): Promise<void>;

}

interface RefundablePaymentProvider extends PaymentProvider {

    refund(amount: number): Promise<void>;

}
```

This makes the contracts clearer.

## 5.4 LSP Is Not Just About Inheritance

This is important.

LSP is often explained through inheritance, but the underlying principle applies to any interchangeable implementation.

For example:

- MySQL repository.
- MongoDB repository.
- Mock repository for testing.

If all three are expected to implement the same repository contract, they should behave consistently with that contract.

## 5.5 Benefits of LSP

- Reliable interchangeable implementations.
- Fewer unexpected runtime errors.
- Better abstraction design.
- More predictable behavior.
- Easier testing.

**Interview Question: What is the Liskov Substitution Principle?**

Answer: LSP states that an implementation should be replaceable by another implementation of the same abstraction without breaking expected behavior.

# 6. I — Interface Segregation Principle (ISP)

## 6.1 What Is ISP?

The Interface Segregation Principle states:

> Clients should not be forced to depend on interfaces they do not use.

In simple words:

Prefer multiple small, focused contracts over one large contract containing unrelated methods.

## 6.2 Example: Violating ISP

Imagine a system with the following interface:

```javascript
class Employee {

    work() {}

    eat() {}

    attendMeeting() {}

    writeCode() {}

    manageTeam() {}

}
```

Now consider different employee types.

A software developer needs:

- Work.
- Eat.
- Attend meetings.
- Write code.

A manager needs:

- Work.
- Eat.
- Attend meetings.
- Manage team.

But not every employee needs every operation.

A single large interface forces implementations to support irrelevant methods.

## 6.3 Applying ISP

Separate responsibilities into smaller interfaces.

In JavaScript, we can represent these contracts through focused classes or conventions.

```javascript
class Workable {

    work() {

        throw new Error("work() must be implemented");

    }

}
```

```javascript
class Eatable {

    eat() {

        throw new Error("eat() must be implemented");

    }

}
```

```javascript
class Codeable {

    writeCode() {

        throw new Error("writeCode() must be implemented");

    }

}
```

```javascript
class Manageable {

    manageTeam() {

        throw new Error("manageTeam() must be implemented");

    }

}
```

Now different classes can implement only the capabilities they need.

```javascript
class Developer {

    work() {

        console.log("Developer is working");

    }

    eat() {

        console.log("Developer is eating");

    }

    writeCode() {

        console.log("Developer is writing code");

    }

}
```

```javascript
class Manager {

    work() {

        console.log("Manager is working");

    }

    eat() {

        console.log("Manager is eating");

    }

    manageTeam() {

        console.log("Manager is managing the team");

    }

}
```

**Note:** These JavaScript classes illustrate the idea of separate contracts. They are not formal TypeScript interfaces.

## 6.4 Practical Node.js Example

Suppose you have a notification system.

Instead of requiring every notification provider to implement:

```javascript
sendEmail()

sendSMS()

sendPushNotification()

sendWhatsApp()
```

Create focused capabilities:

```text
EmailNotificationProvider
SMSNotificationProvider
PushNotificationProvider
WhatsAppNotificationProvider
```

A service that sends emails should not depend on an implementation's SMS functionality.

## 6.5 Benefits of ISP

- Smaller contracts.
- Less unnecessary dependency.
- Easier testing.
- Easier implementation replacement.
- Better modularity.

**Interview Question: What is the Interface Segregation Principle?**

Answer: ISP states that clients should not depend on methods they do not use. It encourages smaller and more focused interfaces.

# 7. D — Dependency Inversion Principle (DIP)

## 7.1 What Is DIP?

The Dependency Inversion Principle states:

1. High-level modules should not depend directly on low-level modules. Both should depend on abstractions.
2. Abstractions should not depend on details. Details should depend on abstractions.

Let's simplify this.

A high-level business service should not be tightly coupled to a specific database, email provider, or payment provider.

Instead, it should depend on an expected contract.

## 7.2 Example: Violating DIP

Suppose we have an expense service.

```javascript
const mysql = require("mysql2/promise");

class ExpenseService {

    async createExpense(data) {

        const connection = await mysql.createConnection({

            host: "localhost",

            user: "root",

            database: "expense_tracker"

        });

        await connection.execute(

            "INSERT INTO expenses (amount) VALUES (?)",

            [data.amount]

        );

    }

}
```

What is the problem?

The business service directly depends on MySQL.

If you switch to MongoDB, you need to modify the business service.

Testing also becomes difficult because the service directly creates a database connection.

## 7.3 Applying DIP

Create a repository abstraction.

The service will depend on the repository contract rather than the database implementation.

### expense.service.js

```javascript
class ExpenseService {

    constructor(expenseRepository) {

        this.expenseRepository = expenseRepository;

    }

    async createExpense(data) {

        if (data.amount <= 0) {

            throw new Error("Invalid expense amount");

        }

        return await this.expenseRepository.create(data);

    }

}

module.exports = ExpenseService;
```

### mysqlExpenseRepository.js

```javascript
class MySQLExpenseRepository {

    async create(data) {

        return await Expense.create(data);

    }

}

module.exports = MySQLExpenseRepository;
```

### Application Composition

```javascript
const ExpenseService = require("./expense.service");

const MySQLExpenseRepository =
    require("./mysqlExpenseRepository");

const expenseRepository = new MySQLExpenseRepository();

const expenseService =
    new ExpenseService(expenseRepository);

module.exports = expenseService;
```

Now the service doesn't need to know whether the repository uses MySQL, MongoDB, or an in-memory test implementation.

### Important

JavaScript does not automatically enforce that a repository implements a particular interface.

You can use TypeScript interfaces or tests to enforce the expected contract.

## 7.4 Benefits of DIP

- Reduced coupling.
- Easier unit testing.
- Easier infrastructure replacement.
- Better modular architecture.
- Better separation between business rules and technical details.

**Interview Question: What is Dependency Inversion?**

Answer: DIP means high-level business modules should depend on abstractions rather than directly depending on low-level implementation details.

# 8. SOLID Principles: Complete Summary

| Principle | Main Idea | Example |
|---|---|---|
| SRP | One responsibility per module | Separate PDF generation from email delivery |
| OCP | Extend without repeatedly modifying stable code | Add new payment providers |
| LSP | Implementations should be interchangeable | Payment providers must respect their contracts |
| ISP | Small, focused interfaces | Separate email and SMS capabilities |
| DIP | Depend on abstractions | ExpenseService depends on a repository contract |

### Important Observation

SOLID principles are guidelines, not rigid rules.

Overengineering can be just as harmful as poorly structured code.

Use these principles when they improve clarity, flexibility, or testability.

# 9. What Are Design Patterns?

A design pattern is a reusable solution to a commonly occurring software design problem.

It is not a ready-made piece of code.

It is a proven approach that developers can adapt to their applications.

For example:

Imagine you need to support multiple payment gateways.

You could write a large collection of `if-else` conditions.

Or you could use the Strategy Pattern to make payment providers interchangeable.

That is a design pattern.

## 9.1 Three Main Categories of Design Patterns

Design patterns are commonly divided into three categories.

| Category | Purpose | Examples |
|---|---|---|
| Creational | Object creation | Factory, Singleton, Builder |
| Structural | Organizing relationships between objects | Adapter, Decorator, Facade |
| Behavioral | Communication and behavior between objects | Strategy, Observer, Command |

We will study the most useful patterns for Node.js backend development.

# 10. Factory Pattern

## 10.1 What Is the Factory Pattern?

The Factory Pattern centralizes object creation.

Instead of creating objects directly throughout the application, a factory decides which object should be created.

### Example Without Factory

```javascript
const provider = new StripePayment();

const paymentService = new PaymentService(provider);
```

Another part of the application:

```javascript
const provider = new PayPalPayment();

const paymentService = new PaymentService(provider);
```

As object creation logic spreads, managing it becomes difficult.

### Applying Factory Pattern

Create:

`paymentFactory.js`

```javascript
const StripePayment = require("./stripePayment");

const PayPalPayment = require("./paypalPayment");

const CreditCardPayment = require("./creditCardPayment");

function createPaymentProvider(type) {

    switch (type) {

        case "stripe":

            return new StripePayment();

        case "paypal":

            return new PayPalPayment();

        case "credit-card":

            return new CreditCardPayment();

        default:

            throw new Error("Unsupported payment provider");

    }

}

module.exports = createPaymentProvider;
```

### Usage

```javascript
const createPaymentProvider =
    require("./paymentFactory");

const PaymentService =
    require("./paymentService");

const provider = createPaymentProvider("stripe");

const paymentService = new PaymentService(provider);

paymentService.processPayment(1000);
```

Now the application does not need to know how each provider is constructed.

### When to Use Factory Pattern?

- Payment gateway selection.
- Database connection creation.
- Notification provider creation.
- File format generators.
- Different authentication strategies.

# 11. Strategy Pattern

## 11.1 What Is the Strategy Pattern?

The Strategy Pattern allows you to define multiple interchangeable algorithms and select one at runtime.

In simple words:

Different implementations perform the same general task in different ways.

### Example: Discount Calculation

Suppose an e-commerce application has three discount types:

1. Regular customer: 5%.
2. Premium customer: 10%.
3. VIP customer: 20%.

### Without Strategy Pattern

```javascript
function calculateDiscount(type, amount) {

    if (type === "regular") {

        return amount * 0.05;

    }

    if (type === "premium") {

        return amount * 0.10;

    }

    if (type === "vip") {

        return amount * 0.20;

    }

    return 0;

}
```

As new discount strategies are added, this function keeps changing.

### Applying Strategy Pattern

`regularDiscount.js`

```javascript
class RegularDiscount {

    calculate(amount) {

        return amount * 0.05;

    }

}

module.exports = RegularDiscount;
```

`premiumDiscount.js`

```javascript
class PremiumDiscount {

    calculate(amount) {

        return amount * 0.10;

    }

}

module.exports = PremiumDiscount;
```

`vipDiscount.js`

```javascript
class VIPDiscount {

    calculate(amount) {

        return amount * 0.20;

    }

}

module.exports = VIPDiscount;
```

`discountService.js`

```javascript
class DiscountService {

    constructor(strategy) {

        this.strategy = strategy;

    }

    calculate(amount) {

        return this.strategy.calculate(amount);

    }

}

module.exports = DiscountService;
```

### Usage

```javascript
const VIPDiscount = require("./vipDiscount");

const DiscountService = require("./discountService");

const strategy = new VIPDiscount();

const discountService = new DiscountService(strategy);

const discount = discountService.calculate(1000);

console.log(discount); // 200
```

### When to Use Strategy Pattern?

- Payment methods.
- Discount calculations.
- Shipping cost calculations.
- Tax calculations.
- Authentication strategies.
- File compression algorithms.

**Remember:** OCP is a design principle, while Strategy is one pattern that can help implement OCP.

# 12. Adapter Pattern

## 12.1 What Is the Adapter Pattern?

The Adapter Pattern allows two incompatible interfaces to work together.

In simple words:

An adapter converts one interface into another interface expected by your application.

### Real-World Example

Suppose your application expects every email provider to expose:

```javascript
sendEmail(to, subject, message)
```

But an external provider exposes:

```javascript
send(to, content)
```

Their interfaces are different.

Instead of modifying your application to accommodate every provider, create an adapter.

### External Provider

```javascript
class ThirdPartyEmailProvider {

    async send(to, content) {

        console.log("Sending email:", to, content);

    }

}

module.exports = ThirdPartyEmailProvider;
```

### Adapter

```javascript
class EmailAdapter {

    constructor(provider) {

        this.provider = provider;

    }

    async sendEmail(to, subject, message) {

        const content = {

            subject,

            body: message

        };

        return await this.provider.send(to, content);

    }

}

module.exports = EmailAdapter;
```

### Usage

```javascript
const ThirdPartyEmailProvider =
    require("./thirdPartyEmailProvider");

const EmailAdapter =
    require("./emailAdapter");

const provider = new ThirdPartyEmailProvider();

const emailService = new EmailAdapter(provider);

emailService.sendEmail(

    "john@example.com",

    "Welcome",

    "Welcome to our application"

);
```

Your application uses a consistent interface even though the external provider has a different API.

### When to Use Adapter Pattern?

- Integrating third-party APIs.
- Replacing email providers.
- Integrating payment gateways.
- Supporting different storage providers.
- Migrating between libraries.

# 13. Repository Pattern

## 13.1 What Is the Repository Pattern?

The Repository Pattern separates data-access logic from business logic.

It provides a consistent interface for accessing and managing data.

For example:

Your application should not need to know whether expenses are stored using:

- MySQL.
- PostgreSQL.
- MongoDB.
- An in-memory collection.

It should communicate with a repository interface.

### Without Repository Pattern

```javascript
class ExpenseService {

    async getExpenses(userId) {

        return await Expense.findAll({

            where: {
                userId
            }

        });

    }

}
```

Here, the service directly uses Sequelize.

### With Repository Pattern

`expense.repository.js`

```javascript
class ExpenseRepository {

    async findByUserId(userId) {

        return await Expense.findAll({

            where: {
                userId
            }

        });

    }

    async create(data) {

        return await Expense.create(data);

    }

}

module.exports = ExpenseRepository;
```

`expense.service.js`

```javascript
class ExpenseService {

    constructor(expenseRepository) {

        this.expenseRepository = expenseRepository;

    }

    async getExpenses(userId) {

        return await this.expenseRepository.findByUserId(userId);

    }

    async createExpense(data) {

        if (data.amount <= 0) {

            throw new Error("Amount must be greater than zero");

        }

        return await this.expenseRepository.create(data);

    }

}

module.exports = ExpenseService;
```

### Benefits

- Separates database operations from business rules.
- Makes service testing easier.
- Provides a consistent data-access interface.
- Helps isolate database-specific implementation details.

### When to Use Repository Pattern?

Especially useful when:

- The application has complex database operations.
- Multiple services share data-access logic.
- You need isolated unit tests.
- Database implementation may change.
- Query logic is becoming difficult to maintain.

**Important:** Don't create repositories merely to wrap every simple Sequelize method without adding any architectural value.

# 14. Singleton Pattern

## 14.1 What Is the Singleton Pattern?

The Singleton Pattern ensures that a particular object has one shared instance within a defined application scope.

In Node.js, modules are cached after being loaded.

This means that repeated `require()` calls for the same resolved module generally receive the same exported object.

### Example: Database Connection

`database.js`

```javascript
const { Sequelize } = require("sequelize");

const sequelize = new Sequelize(

    "expense_tracker",

    "root",

    "password",

    {

        host: "localhost",

        dialect: "mysql",

        logging: false

    }

);

module.exports = sequelize;
```

Now use it in different files.

```javascript
const sequelize = require("./database");
```

Another file:

```javascript
const sequelize = require("./database");
```

Both receive the same cached module export.

This avoids unnecessarily creating multiple Sequelize instances throughout the application.

### Important Distinction

Node.js module caching provides shared module instances, but it does not automatically guarantee one instance across:

- Multiple Node.js processes.
- Cluster workers.
- Separate containers.
- Different application deployments.

Each process normally has its own memory and module cache.

### When to Use Singleton Pattern?

- Application-level database clients.
- Configuration objects.
- Logger instances.
- Shared connection managers.

Avoid turning every class into a singleton. Shared mutable state can create testing and concurrency problems.

# 15. Observer Pattern

## 15.1 What Is the Observer Pattern?

The Observer Pattern allows one object to notify multiple interested objects when an event occurs.

In simple words:

One component publishes an event, and multiple listeners react to it.

### Example: Expense Created

Suppose a user creates an expense.

The application needs to:

1. Save the expense.
2. Update spending analytics.
3. Send a notification.
4. Write an audit log.

Without the Observer Pattern, the expense service may become responsible for coordinating every operation directly.

### Applying Observer Pattern in Node.js

Node.js provides the built-in `events` module.

```javascript
const EventEmitter = require("events");

const eventEmitter = new EventEmitter();

module.exports = eventEmitter;
```

### Register Listeners

`expense.listeners.js`

```javascript
const eventEmitter = require("./eventEmitter");

eventEmitter.on("expense.created", (expense) => {

    console.log("Update analytics:", expense.id);

});

eventEmitter.on("expense.created", (expense) => {

    console.log("Send notification:", expense.id);

});

eventEmitter.on("expense.created", (expense) => {

    console.log("Create audit log:", expense.id);

});
```

### Publish Event

`expense.service.js`

```javascript
const eventEmitter = require("./eventEmitter");

class ExpenseService {

    async createExpense(data) {

        const expense = await Expense.create(data);

        eventEmitter.emit("expense.created", expense);

        return expense;

    }

}

module.exports = ExpenseService;
```

Now multiple listeners can react to the same event.

### When to Use Observer Pattern?

- Notifications.
- Audit logging.
- Analytics.
- User registration events.
- Order creation events.
- Internal application events.

### Important Production Consideration

Node.js `EventEmitter` is an in-memory event mechanism.

It does not provide durable delivery.

If the process crashes, events that were only held in memory may be lost.

For reliable background processing, use a message queue or durable event infrastructure.

We will study BullMQ and Redis later.

# 16. Facade Pattern

## 16.1 What Is the Facade Pattern?

The Facade Pattern provides a simplified interface to a complex subsystem.

Imagine generating a complete expense report requires:

1. Fetching expenses.
2. Fetching categories.
3. Calculating totals.
4. Generating a PDF.
5. Storing the PDF.
6. Sending an email.

A controller should not need to coordinate all these components.

Create a facade.

### reportFacade.js

```javascript
class ReportFacade {

    constructor(
        expenseService,
        categoryService,
        pdfService,
        storageService,
        emailService
    ) {

        this.expenseService = expenseService;

        this.categoryService = categoryService;

        this.pdfService = pdfService;

        this.storageService = storageService;

        this.emailService = emailService;

    }

    async generateReport(userId, email) {

        const expenses =
            await this.expenseService.getExpenses(userId);

        const categories =
            await this.categoryService.getCategories(userId);

        const pdf = await this.pdfService.generate({

            expenses,

            categories

        });

        const fileUrl =
            await this.storageService.upload(pdf);

        await this.emailService.sendEmail(

            email,

            "Your Expense Report",

            fileUrl

        );

        return fileUrl;

    }

}

module.exports = ReportFacade;
```

### Usage

```javascript
const fileUrl = await reportFacade.generateReport(

    userId,

    email

);
```

The caller interacts with one simplified interface.

### When to Use Facade Pattern?

- Complex report generation.
- Checkout workflows.
- User onboarding.
- File processing pipelines.
- Multiple external service integrations.

# 17. Decorator Pattern

## 17.1 What Is the Decorator Pattern?

The Decorator Pattern adds functionality to an existing object without changing its original implementation.

### Example: Logging an Expense Repository

Suppose your repository already works correctly.

You want to log how long database queries take.

Instead of modifying the repository itself, wrap it with a decorator.

```javascript
class LoggingExpenseRepository {

    constructor(expenseRepository) {

        this.expenseRepository = expenseRepository;

    }

    async findByUserId(userId) {

        const start = Date.now();

        try {

            return await this.expenseRepository.findByUserId(userId);

        } finally {

            const duration = Date.now() - start;

            console.log(`Query completed in ${duration}ms`);

        }

    }

}

module.exports = LoggingExpenseRepository;
```

### Usage

```javascript
const repository = new ExpenseRepository();

const loggingRepository =
    new LoggingExpenseRepository(repository);
```

The original repository remains unchanged.

### When to Use Decorator Pattern?

- Logging.
- Performance monitoring.
- Caching.
- Retry behavior.
- Authorization wrappers.

# 18. Command Pattern

## 18.1 What Is the Command Pattern?

The Command Pattern represents an operation as a separate object.

Instead of directly executing business logic everywhere, the application creates a command that represents the requested action.

### Example: Create Expense

```javascript
class CreateExpenseCommand {

    constructor(expenseData, userId) {

        this.expenseData = expenseData;

        this.userId = userId;

    }

}
```

Create a handler:

```javascript
class CreateExpenseHandler {

    constructor(expenseService) {

        this.expenseService = expenseService;

    }

    async execute(command) {

        return await this.expenseService.createExpense({

            ...command.expenseData,

            userId: command.userId

        });

    }

}
```

Usage:

```javascript
const command = new CreateExpenseCommand(

    {

        amount: 500,

        description: "Food"

    },

    10

);

const result = await handler.execute(command);
```

### When to Use Command Pattern?

- Complex business operations.
- Background job processing.
- Undo/redo operations.
- Audit-friendly workflows.
- CQRS-style applications.

For a simple CRUD API, this pattern may be unnecessary.

# 19. Dependency Injection (DI)

We briefly introduced Dependency Injection in Topic 3.

Now let's understand it in more depth because it is closely related to DIP.

## 19.1 What Is Dependency Injection?

Dependency Injection is a technique where an object receives the dependencies it needs from outside rather than creating them internally.

### Without Dependency Injection

```javascript
class ExpenseService {

    constructor() {

        this.repository = new ExpenseRepository();

    }

}
```

The service creates its own repository.

This tightly couples the service to that specific implementation.

### With Dependency Injection

```javascript
class ExpenseService {

    constructor(repository) {

        this.repository = repository;

    }

}
```

Now the repository is supplied from outside.

### Example: Production Implementation

```javascript
const repository = new MySQLExpenseRepository();

const expenseService = new ExpenseService(repository);
```

### Example: Testing Implementation

```javascript
const mockRepository = {

    async create(data) {

        return {

            id: 1,

            ...data

        };

    }

};

const expenseService = new ExpenseService(mockRepository);
```

The same service can work with different repository implementations.

## 19.2 Types of Dependency Injection

### A. Constructor Injection

Dependencies are passed through the constructor.

```javascript
class UserService {

    constructor(userRepository) {

        this.userRepository = userRepository;

    }

}
```

### B. Setter Injection

Dependencies are assigned through a setter method.

```javascript
class UserService {

    setRepository(repository) {

        this.repository = repository;

    }

}
```

### C. Method Injection

Dependencies are passed directly into a method.

```javascript
class ReportService {

    async generateReport(userId, storageService) {

        // Use storageService here.

    }

}
```

### Which Is Most Common?

Constructor injection is commonly preferred when a dependency is required for the object to function.

# 20. Understanding Composition Root

The Composition Root is the place where application dependencies are created and connected.

In our Expense Tracker project, it might look like this:

```text
src/
│
├── modules/
│   └── expenses/
│       ├── expense.repository.js
│       ├── expense.service.js
│       ├── expense.controller.js
│       └── expense.routes.js
│
├── container/
│   └── index.js
│
├── app.js
└── server.js
```

### container/index.js

```javascript
const ExpenseRepository =
    require("../modules/expenses/expense.repository");

const ExpenseService =
    require("../modules/expenses/expense.service");

const ExpenseController =
    require("../modules/expenses/expense.controller");

const expenseRepository = new ExpenseRepository();

const expenseService =
    new ExpenseService(expenseRepository);

const expenseController =
    new ExpenseController(expenseService);

module.exports = {

    expenseRepository,

    expenseService,

    expenseController

};
```

The container constructs and connects the dependencies.

### Why Is This Useful?

Without a composition root, object creation may be scattered across many files.

A centralized composition root makes dependencies easier to understand and replace.

For a small application, manual dependency injection is usually sufficient. A dedicated DI container library is optional.

# 21. Important Differences Between Design Patterns

These patterns are related, but they solve different problems.

| Pattern | Main Purpose | Example |
|---|---|---|
| Factory | Create objects | Select payment provider |
| Strategy | Switch algorithms | Calculate different discounts |
| Adapter | Convert interfaces | Integrate an external email provider |
| Repository | Separate data access | Expense database operations |
| Singleton | Share one instance within a scope | Database client |
| Observer | Notify listeners | Expense-created event |
| Facade | Simplify complex operations | Generate complete report |
| Decorator | Add behavior without modifying original object | Logging repository |
| Command | Represent an operation as an object | Create expense command |

# 22. How SOLID and Design Patterns Work Together

Consider an e-commerce application.

You need to implement a payment system.

### Requirements

- Support Stripe.
- Support PayPal.
- Support Razorpay.
- Allow new payment providers later.
- Log every payment.
- Keep business logic independent of payment provider details.

We can combine several concepts.

| Requirement | Principle or Pattern |
|---|---|
| Each provider has separate implementation | SRP |
| Add providers without modifying core payment logic | OCP |
| All providers follow the same payment contract | LSP |
| Refund capability is separate from payment capability | ISP |
| Payment service depends on a contract | DIP |
| Select provider dynamically | Strategy |
| Construct provider based on configuration | Factory |
| Integrate provider-specific APIs | Adapter |
| Add payment logging | Decorator |
| Inject payment provider into service | Dependency Injection |

This is how software architecture concepts work together in real projects.

# 24. Best Practices

1. Follow SRP when a component has unrelated responsibilities.
2. Use OCP to make frequently extended functionality easier to expand.
3. Ensure interchangeable implementations respect their contracts.
4. Keep interfaces small and focused.
5. Depend on abstractions where infrastructure flexibility matters.
6. Use Strategy for interchangeable algorithms.
7. Use Factory when object creation becomes complex.
8. Use Adapter for incompatible third-party interfaces.
9. Use Repository when separating data access adds value.
10. Use Observer for event-driven communication.
11. Use Facade to simplify complex subsystems.
12. Use Dependency Injection to improve testability.
13. Avoid unnecessary inheritance.
14. Avoid creating patterns just to make code look sophisticated.
15. Prefer readable, straightforward code over excessive abstraction.

# 25. Interview Questions and Answers

### Q1. What is SOLID?

SOLID is a set of five object-oriented design principles that improve maintainability, extensibility, and flexibility.

### Q2. What is SRP?

A module should have one reason to change.

### Q3. What is OCP?

Software should be open for extension but closed for modification.

### Q4. What is LSP?

An implementation should be replaceable by another implementation of the same abstraction without breaking expected behavior.

### Q5. What is ISP?

Clients should not depend on interfaces or capabilities they do not use.

### Q6. What is DIP?

High-level modules should depend on abstractions rather than low-level implementation details.

### Q7. What is a design pattern?

A reusable approach to a commonly occurring software design problem.

### Q8. What are the three categories of design patterns?

Creational, structural, and behavioral.

### Q9. What is the Factory Pattern?

A pattern that centralizes object creation.

### Q10. What is the Strategy Pattern?

A pattern that allows interchangeable algorithms or behaviors to be selected at runtime.

### Q11. What is the Adapter Pattern?

A pattern that makes incompatible interfaces work together.

### Q12. What is the Repository Pattern?

A pattern that separates data-access logic from business logic.

### Q13. What is the Singleton Pattern?

A pattern that provides one shared instance within a defined scope.

### Q14. What is the Observer Pattern?

A pattern where an object notifies registered listeners when an event occurs.

### Q15. What is the Facade Pattern?

A pattern that provides a simplified interface to a complex subsystem.

### Q16. What is the Decorator Pattern?

A pattern that adds behavior to an existing object without modifying its original implementation.

### Q17. What is Dependency Injection?

A technique where dependencies are supplied to a component externally.

### Q18. What is the difference between DIP and DI?

DIP is a design principle. DI is a technique for supplying dependencies that can help implement DIP.

### Q19. What is the difference between Factory and Strategy?

Factory focuses on creating objects. Strategy focuses on selecting interchangeable behavior or algorithms.

### Q20. What is the difference between Adapter and Facade?

Adapter makes incompatible interfaces compatible. Facade simplifies access to a complex subsystem.

### Q21. Is Repository Pattern mandatory in every Node.js project?

No. It is useful when it improves separation of concerns, testability, or maintainability.

### Q22. Does Node.js support Singleton Pattern?

Node.js module caching can provide a shared module instance within a process, which is commonly used for singleton-like behavior.

### Q23. Can SOLID principles be applied to functional programming?

Yes. Their underlying design ideas, such as separation of responsibilities and dependency inversion, can also be applied to functional code.

### Q24. Why is Dependency Injection useful in unit testing?

It allows tests to replace real dependencies with mock or fake implementations.

### Q25. Should developers always use design patterns?

No. Patterns should solve real design problems. Unnecessary patterns increase complexity.
