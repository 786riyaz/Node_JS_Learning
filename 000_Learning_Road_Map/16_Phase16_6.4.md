# 3. User Repository

## What is a Repository?

A repository is responsible for database operations.

It separates database queries from business logic.

For example:

Without a repository:

```javascript
// user.service.js

const user = await User.findByPk(userId);
```

With a repository:

```javascript
// user.service.js

const user = await userRepository.findById(userId);
```

The second approach makes the service independent of the database implementation.

### 3.1 Implement user.repository.js

```javascript
const { Op } = require("sequelize");

const { User } = require("../../database/models");

class UserRepository {

    async findById(id, transaction = null) {

        return await User.findByPk(id, {
            attributes: [
                "id",
                "name",
                "email",
                "role",
                "createdAt",
                "updatedAt"
            ],
            transaction
        });

    }

    async findByEmail(email) {

        return await User.findOne({
            where: { email }
        });

    }

    async findAll({
        page = 1,
        limit = 10,
        search = "",
        role = ""
    }) {

        const where = {};

        if (search) {

            where[Op.or] = [
                { name: { [Op.like]: `%${search}%` } },
                { email: { [Op.like]: `%${search}%` } }
            ];

        }

        if (role) {
            where.role = role;
        }

        const offset = (page - 1) * limit;

        const result = await User.findAndCountAll({

            where,

            attributes: [
                "id",
                "name",
                "email",
                "role",
                "createdAt",
                "updatedAt"
            ],

            limit,
            offset,

            order: [["createdAt", "DESC"]]

        });

        return result;

    }

    async updateById(id, data, transaction = null) {

        const [updatedRows] = await User.update(data, {

            where: { id },

            transaction

        });

        return updatedRows;

    }

    async deleteById(id, transaction = null) {

        return await User.destroy({

            where: { id },

            transaction

        });

    }

}

module.exports = new UserRepository();
```

### Important concepts

**1. findByPk()**

Finds a record using its primary key.

```javascript
const user = await User.findByPk(10);
```

**2. findAndCountAll()**

Returns records and the total matching record count.

```javascript
const result = await User.findAndCountAll({
    limit: 10,
    offset: 0
});

console.log(result.rows);
console.log(result.count);
```

**3. Op.or**

Used to apply OR conditions.

```javascript
where: {
    [Op.or]: [
        { name: "Riyaz" },
        { email: "riyaz@example.com" }
    ]
}
```

This is equivalent to:

```sql
SELECT *
FROM users
WHERE name = 'Riyaz'
   OR email = 'riyaz@example.com';
```

**4. attributes**

Controls which columns Sequelize returns.

This is particularly important for security.

Never expose sensitive fields such as:

- password
- password reset tokens
- internal security fields

# 4. User Validation

## Why do we need validation?

Never trust data received from the client.

For example, suppose the frontend sends:

```json
{
    "name": "Riyaz",
    "email": "riyaz@example.com",
    "role": "admin"
}
```

If our backend directly updates the user using this object, an ordinary user might be able to change their own role.

This is a serious security vulnerability.

Therefore, we must explicitly define which fields are allowed.

We will use **Zod** for validation.

### 4.1 user.validation.js

```javascript
const { z } = require("zod");

const userIdSchema = z.object({

    id: z.string().regex(/^[1-9]\d*$/, {
        message: "Invalid user ID"
    })

});

const updateProfileSchema = z.object({

    name: z.string()
        .trim()
        .min(2)
        .max(100)
        .optional(),

    email: z.string()
        .trim()
        .email()
        .max(255)
        .optional()

})
.strict()
.refine(
    data => Object.keys(data).length > 0,
    {
        message: "At least one field is required"
    }
);

const changePasswordSchema = z.object({

    currentPassword: z.string()
        .min(1),

    newPassword: z.string()
        .min(8)
        .max(72)

})
.strict();

const userListSchema = z.object({

    page: z.coerce.number()
        .int()
        .min(1)
        .default(1),

    limit: z.coerce.number()
        .int()
        .min(1)
        .max(100)
        .default(10),

    search: z.string()
        .trim()
        .max(100)
        .optional(),

    role: z.enum(["user", "admin"])
        .optional()

});

const updateRoleSchema = z.object({

    role: z.enum(["user", "admin"])

})
.strict();

module.exports = {

    userIdSchema,
    updateProfileSchema,
    changePasswordSchema,
    userListSchema,
    updateRoleSchema

};
```

### Important: Why use string IDs?

Our database uses MySQL `BIGINT` IDs.

JavaScript numbers cannot safely represent every possible `BIGINT` value.

Therefore, accepting IDs as digit strings avoids potential precision loss.

Example:

```javascript
const userId = "9223372036854775807";
```

We preserve it as a string when passing it to Sequelize.

### Important: Why use `.strict()`?

Consider:

```javascript
const data = {
    name: "Riyaz",
    role: "admin"
};
```

Our profile validation schema does not allow `role`.

Using `.strict()` ensures that unexpected properties are rejected instead of silently accepted or ignored.

# 5. User Service

## What is the Service Layer?

The service layer contains business logic.

For example, updating an email requires more than executing an SQL query.

We need to:

1. Check whether the user exists.
2. Normalize the email.
3. Check whether another account already uses that email.
4. Update the record.
5. Return the updated user.

These operations belong in the service layer.

### 5.1 Create user.service.js

```javascript
const bcrypt = require("bcrypt");
const { UniqueConstraintError } = require("sequelize");

const userRepository = require("./user.repository");

const ApiError = require("../../utils/ApiError");

const sequelize = require("../../database/connection");

const { RefreshToken } = require("../../database/models");


class UserService {

    // Get logged-in user's profile
    async getMyProfile(userId) {

        const user = await userRepository.findById(userId);

        if (!user) {
            throw new ApiError(404, "User not found");
        }

        return user;

    }


    // Update logged-in user's profile
    async updateMyProfile(userId, data) {

        const user = await userRepository.findById(userId);

        if (!user) {
            throw new ApiError(404, "User not found");
        }

        const updateData = {};

        if (data.name !== undefined) {
            updateData.name = data.name;
        }

        if (data.email !== undefined) {

            const normalizedEmail = data.email.toLowerCase();

            const existingUser =
                await userRepository.findByEmail(normalizedEmail);

            if (existingUser && String(existingUser.id) !== String(userId)) {
                throw new ApiError(409, "Email already exists");
            }

            updateData.email = normalizedEmail;

        }

        try {

            await userRepository.updateById(userId, updateData);

        } catch (error) {

            if (error instanceof UniqueConstraintError) {
                throw new ApiError(409, "Email already exists");
            }

            throw error;

        }

        return await userRepository.findById(userId);

    }


    // Change password
    async changePassword(userId, data) {

        const user = await userRepository.findByEmail(
            data.email
        );

        // The current user is identified by authenticated ID.
        // Fetch the actual account using that ID.
        const account = await userRepository.findById(userId);

        if (!account) {
            throw new ApiError(404, "User not found");
        }

        const accountWithPassword = await require(
            "../../database/models"
        ).User.findByPk(userId);

        const isPasswordValid = await bcrypt.compare(
            data.currentPassword,
            accountWithPassword.password
        );

        if (!isPasswordValid) {
            throw new ApiError(400, "Current password is incorrect");
        }

        if (data.currentPassword === data.newPassword) {
            throw new ApiError(
                400,
                "New password must be different"
            );
        }

        const hashedPassword = await bcrypt.hash(
            data.newPassword,
            12
        );

        await sequelize.transaction(async transaction => {

            await accountWithPassword.update(
                { password: hashedPassword },
                { transaction }
            );

            // Revoke all refresh tokens.
            await RefreshToken.destroy({

                where: {
                    userId
                },

                transaction

            });

        });

        return {
            message: "Password changed successfully"
        };

    }


    // Get all users (admin)
    async getAllUsers(filters) {

        const result = await userRepository.findAll(filters);

        const totalPages = Math.ceil(
            result.count / filters.limit
        );

        return {

            users: result.rows,

            pagination: {

                totalRecords: result.count,

                currentPage: filters.page,

                limit: filters.limit,

                totalPages

            }

        };

    }


    // Get user by ID (admin)
    async getUserById(userId) {

        const user = await userRepository.findById(userId);

        if (!user) {
            throw new ApiError(404, "User not found");
        }

        return user;

    }


    // Update user role (admin)
    async updateUserRole(userId, role) {

        const user = await userRepository.findById(userId);

        if (!user) {
            throw new ApiError(404, "User not found");
        }

        await userRepository.updateById(userId, { role });

        return await userRepository.findById(userId);

    }


    // Delete logged-in user's account
    async deleteMyAccount(userId, currentPassword) {

        const User = require("../../database/models").User;

        const user = await User.findByPk(userId);

        if (!user) {
            throw new ApiError(404, "User not found");
        }

        const isPasswordValid = await bcrypt.compare(
            currentPassword,
            user.password
        );

        if (!isPasswordValid) {
            throw new ApiError(400, "Password is incorrect");
        }

        await sequelize.transaction(async transaction => {

            await RefreshToken.destroy({

                where: { userId },

                transaction

            });

            await user.destroy({ transaction });

        });

        return {
            message: "Account deleted successfully"
        };

    }

}

module.exports = new UserService();
```

### Important correction to understand

The `changePassword()` example above includes an unnecessary email lookup:

```javascript
const user = await userRepository.findByEmail(data.email);
```

Our password-change request does not contain an email. Remove that line.

Also, for cleaner code, import `User` directly at the top:

```javascript
const {
    User,
    RefreshToken
} = require("../../database/models");
```

Then retrieve the account using:

```javascript
const account = await User.findByPk(userId);
```

And use `account.password` for password verification.

This is the cleaner implementation. The final `changePassword()` method should use that approach.

### Important security considerations

**1. Why verify the current password?**

If someone gains access to an already authenticated session, they should not automatically be able to replace the account password.

**2. Why revoke refresh tokens?**

After changing the password, existing sessions should be invalidated.

Our example deletes all refresh tokens for the user.

**3. Why handle UniqueConstraintError?**

Checking whether an email exists before updating is not enough.

Two requests could attempt to register or update to the same email simultaneously.

The database unique constraint is the final protection.

**4. Why should users not update their own roles?**

Role changes must be handled by a separate admin-only endpoint.

# 6. User Controller

## What is a Controller?

The controller handles HTTP requests and responses.

It should not contain database queries or complex business logic.

### user.controller.js

```javascript
const userService = require("./user.service");

class UserController {

    async getMyProfile(req, res) {

        const user = await userService.getMyProfile(
            req.user.id
        );

        res.status(200).json({

            success: true,

            data: user

        });

    }


    async updateMyProfile(req, res) {

        const user = await userService.updateMyProfile(
            req.user.id,
            req.body
        );

        res.status(200).json({

            success: true,

            message: "Profile updated successfully",

            data: user

        });

    }


    async changePassword(req, res) {

        const result = await userService.changePassword(
            req.user.id,
            req.body
        );

        res.status(200).json({

            success: true,

            ...result

        });

    }


    async deleteMyAccount(req, res) {

        const result = await userService.deleteMyAccount(
            req.user.id,
            req.body.currentPassword
        );

        res.status(200).json({

            success: true,

            ...result

        });

    }


    async getAllUsers(req, res) {

        const result = await userService.getAllUsers(
            req.query
        );

        res.status(200).json({

            success: true,

            data: result

        });

    }


    async getUserById(req, res) {

        const user = await userService.getUserById(
            req.params.id
        );

        res.status(200).json({

            success: true,

            data: user

        });

    }


    async updateUserRole(req, res) {

        const user = await userService.updateUserRole(
            req.params.id,
            req.body.role
        );

        res.status(200).json({

            success: true,

            message: "User role updated successfully",

            data: user

        });

    }

}

module.exports = new UserController();
```

We are assuming that your `asyncHandler` middleware automatically catches rejected promises from asynchronous controllers.

# 7. User Routes

Now we will define the API endpoints.

### user.routes.js

```javascript
const express = require("express");

const router = express.Router();

const userController = require("./user.controller");

const authenticate = require("../../middlewares/authenticate");

const authorize = require("../../middlewares/authorize");

const validate = require("../../middlewares/validate");

const {
    userIdSchema,
    updateProfileSchema,
    changePasswordSchema,
    userListSchema,
    updateRoleSchema
} = require("./user.validation");

const { asyncHandler } = require("../../utils/asyncHandler");


// Current user's profile
router.get(
    "/me",
    authenticate,
    asyncHandler(userController.getMyProfile)
);


// Update current user's profile
router.patch(
    "/me",
    authenticate,
    validate(updateProfileSchema),
    asyncHandler(userController.updateMyProfile)
);


// Change password
router.patch(
    "/me/password",
    authenticate,
    validate(changePasswordSchema),
    asyncHandler(userController.changePassword)
);


// Delete current user's account
router.delete(
    "/me",
    authenticate,
    validate(changePasswordSchema),
    asyncHandler(userController.deleteMyAccount)
);


// Admin: Get all users
router.get(
    "/",
    authenticate,
    authorize("admin"),
    validate(userListSchema, "query"),
    asyncHandler(userController.getAllUsers)
);


// Admin: Get user by ID
router.get(
    "/:id",
    authenticate,
    authorize("admin"),
    validate(userIdSchema, "params"),
    asyncHandler(userController.getUserById)
);


// Admin: Update user role
router.patch(
    "/:id/role",
    authenticate,
    authorize("admin"),
    validate(userIdSchema, "params"),
    validate(updateRoleSchema),
    asyncHandler(userController.updateUserRole)
);


module.exports = router;
```

**Note:** The `validate()` middleware must support selecting the request property being validated (`body`, `query`, or `params`). The delete route should use a dedicated schema containing `currentPassword`, rather than reusing the password-change schema.

### Why `/me` should come before `/:id`

Consider these routes:

```javascript
router.get("/:id", controller.getUserById);

router.get("/me", controller.getMyProfile);
```

Depending on the router matching order, `/me` could be interpreted as an ID parameter.

Therefore, define specific routes before parameterized routes.

# 9. Important: API Response Design

A good backend should return consistent API responses.

### Successful response

```json
{
    "success": true,
    "message": "Profile retrieved successfully",
    "data": {
        "id": "1",
        "name": "Riyaz",
        "email": "riyaz@example.com",
        "role": "user"
    }
}
```

### Error response

```json
{
    "success": false,
    "message": "User not found"
}
```

### Paginated response

```json
{
    "success": true,
    "data": {
        "users": [
            {
                "id": "1",
                "name": "Riyaz",
                "email": "riyaz@example.com",
                "role": "user"
            }
        ],
        "pagination": {
            "totalRecords": 100,
            "currentPage": 1,
            "limit": 10,
            "totalPages": 10
        }
    }
}
```

### What is Pagination?

Pagination divides a large dataset into smaller groups.

Suppose we have 1,000 users.

Instead of returning all 1,000 users, we return 10 users per request.

Request:

```http
GET /api/v1/users?page=1&limit=10
```

Second page:

```http
GET /api/v1/users?page=2&limit=10
```

Formula:

```javascript
const offset = (page - 1) * limit;
```

| Page | Limit | Offset |
|---|---:|---:|
| 1 | 10 | 0 |
| 2 | 10 | 10 |
| 3 | 10 | 20 |
| 4 | 10 | 30 |

Pagination is particularly important for applications with large datasets.

For very large datasets or frequently changing data, cursor-based pagination can be more efficient and consistent than offset pagination.

# 11. Important Security Concepts

These concepts are especially important when building production APIs.

## 11.1 IDOR — Insecure Direct Object Reference

Suppose a user has ID 10.

They send:

```http
GET /users/20
```

If the API returns user 20's information without checking authorization, this creates an access-control vulnerability.

This is commonly discussed as IDOR and is part of the broader Broken Object Level Authorization (BOLA) category.

**Solution:**

- Verify authentication.
- Check resource ownership or appropriate permissions.
- Restrict administrative endpoints to administrators.
- Never assume that hiding an ID in the frontend provides security.

Our `GET /users/:id` endpoint is administrator-only.

## 11.2 Mass Assignment

Suppose the frontend sends:

```json
{
    "name": "Riyaz",
    "role": "admin",
    "isVerified": true
}
```

And the backend executes:

```javascript
await User.update(req.body, {
    where: { id: req.user.id }
});
```

This is dangerous.

A user could modify fields they should not control.

**Solution:**

Explicitly select allowed fields:

```javascript
const updateData = {
    name: req.body.name,
    email: req.body.email
};
```

Never blindly update database records using `req.body`.

## 11.3 Sensitive Data Exposure

Never return:

```json
{
    "password": "$2b$12$...",
    "refreshToken": "..."
}
```

Even hashed passwords must remain private.

Use explicit attributes or a dedicated user serializer.

## 11.4 Admin Privilege Escalation

A regular user must never be able to execute:

```json
{
    "role": "admin"
}
```

through the profile update endpoint.

Role management must have a separate authorization policy.

For production, also consider:
- Preventing administrators from demoting the last active administrator.
- Recording role changes in an audit log.
- Requiring stronger authentication for sensitive administrative actions.

# 12. Important Production Considerations

Our educational implementation demonstrates the architecture, but some areas require additional work before production.

| Area | Production Consideration |
|---|---|
| Email updates | Require email verification |
| Password changes | Validate password byte length for bcrypt |
| Password changes | Revoke all sessions |
| Account deletion | Apply data retention and anonymization policies |
| User search | Escape SQL LIKE wildcard characters where literal matching is intended |
| Admin roles | Audit every role change |
| User listing | Add rate limiting and maximum page size |
| Email uniqueness | Enforce a database unique constraint |
| User deletion | Consider financial record retention |
| Admin safety | Prevent accidental removal of the last administrator |

**Important:** In an Expense Tracker, deleting a user with cascading foreign keys could delete their financial records. Real financial applications should have a deliberate retention policy. Soft deletion or anonymization may be more appropriate.

Also, our role-update example should be strengthened with transaction-safe safeguards before production use.

# 13. Interview Questions and Answers

### Q1. What is the difference between authentication and user management?

Authentication verifies user identity. User management handles account-related operations such as profile updates, password changes, and account deletion.

### Q2. What is the Repository Pattern?

It abstracts database operations behind a dedicated interface, separating persistence logic from business logic.

### Q3. Why should controllers not contain business logic?

Controllers should focus on HTTP request and response handling. Business logic belongs in services, improving maintainability and testability.

### Q4. What is mass assignment?

Mass assignment occurs when user-provided properties are directly assigned to database models without restricting allowed fields.

### Q5. What is IDOR?

IDOR is an access-control vulnerability where users can access another user's resources by manipulating identifiers.

### Q6. Why should we never return a password hash?

Password hashes are sensitive authentication data. Exposing them increases the consequences of database or API data leaks.

### Q7. What is pagination?

Pagination divides large datasets into smaller chunks to reduce response size and improve API performance.

### Q8. What is the difference between offset and cursor pagination?

Offset pagination uses page numbers and offsets. Cursor pagination uses a reference to the last retrieved record and is often more efficient for large datasets.

### Q9. Why do we use database unique constraints?

They guarantee uniqueness even when concurrent requests attempt to create or update records with the same value.

### Q10. Why should password changes invalidate refresh tokens?

To prevent previously authenticated sessions from continuing to obtain new access tokens after a password change.

### Q11. What is soft deletion?

Soft deletion marks a record as deleted without physically removing it from the database.

### Q12. Why should role updates have separate endpoints?

Role changes are sensitive administrative operations and require stronger authorization than ordinary profile updates.

### Q13. What is BOLA?

Broken Object Level Authorization occurs when an API fails to verify whether the requesting user is authorized to access a particular object.

### Q14. What is a DTO?

A Data Transfer Object defines the structure of data transferred between application layers or returned by an API.

### Q15. What is the purpose of a service layer?

It contains business rules and coordinates operations between repositories and other application components.
