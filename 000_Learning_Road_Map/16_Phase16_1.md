**Topic 1: Project Planning and Requirement Analysis**

**Level:** Professional  
**Objective:** Learn how to plan, analyze, design, and organize a real-world backend project before writing code.

In previous phases, you learned how to write Node.js code, build APIs, integrate databases, implement authentication, and deploy applications.

Now we will learn something equally important:

# 1. What Is Project Planning?

Project planning is the process of defining what needs to be developed, how it will be developed, and what resources are required.

Suppose a client approaches you with this requirement:

> I want an expense management application where users can register, log in, add their expenses, manage categories, and view monthly reports.

A beginner might immediately start writing:

```text
server.js
routes/
controllers/
models/
```

A professional developer first asks:

- Who will use the application?
- What features are required?
- What are the user roles?
- What information needs to be stored?
- What database relationships are required?
- Which APIs are needed?
- What security requirements exist?
- What is the expected traffic?
- Where will the application be deployed?

These questions help prevent architectural problems later.

## 1.1 Software Development Life Cycle (SDLC)

SDLC is a structured process used to develop software.

Typical stages:

```text
       REQUIREMENT ANALYSIS
                |
                v
          PLANNING
                |
                v
             DESIGN
                |
                v
           DEVELOPMENT
                |
                v
             TESTING
                |
                v
           DEPLOYMENT
                |
                v
          MAINTENANCE
```

### Explanation

| Stage | Description |
|---|---|
| Requirement Analysis | Understand what the client needs |
| Planning | Define scope, resources, and timeline |
| Design | Design architecture, database, and APIs |
| Development | Write application code |
| Testing | Verify functionality and quality |
| Deployment | Release the application |
| Maintenance | Fix issues and improve the application |

### Common SDLC Models

**1. Waterfall Model**

Development proceeds through predefined stages.

```text
Requirements → Design → Development → Testing → Deployment
```

Useful when requirements are stable and clearly defined.

**2. Agile Model**

Development happens in smaller iterations.

Example:

```text
SPRINT 1 → Authentication

SPRINT 2 → Expense Management

SPRINT 3 → Reports

SPRINT 4 → Deployment
```

Useful when requirements evolve and frequent feedback is important.

**3. Iterative Development**

The application is improved through repeated development cycles.

**4. Spiral Model**

Combines iterative development with explicit risk analysis.

### Waterfall vs Agile

| Waterfall | Agile |
|---|---|
| Sequential development | Iterative development |
| Requirements defined early | Requirements can evolve |
| Changes can be expensive | Changes are handled incrementally |
| Feedback often comes later | Frequent feedback |
| Suitable for stable requirements | Suitable for evolving requirements |

# 2. What Is Requirement Analysis?

Requirement analysis is the process of understanding and documenting what a software application must do.

Requirements generally fall into two categories:

1. Functional Requirements.
2. Non-Functional Requirements.

## 2.1 Functional Requirements

Functional requirements describe **what the application should do**.

Example: Expense Tracker.

| ID | Requirement |
|---|---|
| FR-01 | Users can register |
| FR-02 | Users can log in |
| FR-03 | Users can add expenses |
| FR-04 | Users can edit expenses |
| FR-05 | Users can delete expenses |
| FR-06 | Users can create categories |
| FR-07 | Users can view monthly reports |
| FR-08 | Users can filter expenses by date |
| FR-09 | Users can export reports to Excel |
| FR-10 | Users can manage their profiles |

These are functional requirements because they describe application functionality.

## 2.2 Non-Functional Requirements

Non-functional requirements describe **how well the application should work** and the constraints under which it operates.

Examples:

| ID | Requirement |
|---|---|
| NFR-01 | Passwords must be securely hashed |
| NFR-02 | API responses should generally complete within an agreed latency target |
| NFR-03 | The application must support HTTPS |
| NFR-04 | The database must be backed up regularly |
| NFR-05 | The application must support concurrent users |
| NFR-06 | APIs must validate incoming data |
| NFR-07 | Sensitive information must not appear in logs |
| NFR-08 | The application must support automated testing |

### Functional vs Non-Functional Requirements

| Functional | Non-Functional |
|---|---|
| What the system does | How the system behaves |
| Add expense | Response-time target |
| Login user | Authentication security |
| Generate report | Report-generation performance |
| Upload file | Maximum file size and permitted file types |

**Interview Question: What is the difference between functional and non-functional requirements?**

Answer:

Functional requirements define the features and operations a system must provide, whereas non-functional requirements define quality attributes and constraints such as performance, security, reliability, and scalability.

# 3. Understanding Stakeholders

A stakeholder is a person or organization that has an interest in the software project.

Common stakeholders:

| Stakeholder | Responsibility |
|---|---|
| Client | Defines business requirements |
| Product Owner | Prioritizes product requirements |
| Project Manager | Manages project delivery |
| Business Analyst | Analyzes and documents requirements |
| UI/UX Designer | Designs user experience |
| Frontend Developer | Develops frontend |
| Backend Developer | Develops backend |
| QA Engineer | Tests application |
| DevOps Engineer | Manages deployment and infrastructure |

### Why Is This Important?

Suppose a client says:

> Users should be able to manage expenses.

This requirement is ambiguous.

You need to clarify:

- Can users create expenses?
- Can they edit expenses?
- Can they delete expenses?
- Can they upload receipts?
- Can they add recurring expenses?
- Can they export expense data?

Requirement clarification prevents misunderstandings during development.

# 4. Understanding User Roles

Before designing APIs, identify who will use the application and what each user can do.

Consider an expense management application.

Possible roles:

```text
             APPLICATION
                  |
          +-------+-------+
          |               |
          v               v
        ADMIN           USER
          |               |
          v               v
     Manage Users    Manage Expenses
     View Analytics  Manage Categories
     System Config   View Reports
```

### Example Role Permissions

| Feature | Admin | User |
|---|---|---|
| Register | No | Yes |
| Login | Yes | Yes |
| View own expenses | Yes | Yes |
| Create expense | No | Yes |
| Edit own expense | No | Yes |
| Delete own expense | No | Yes |
| Manage users | Yes | No |
| View system analytics | Yes | No |

Remember that roles and resource ownership are different authorization checks.

For example, a normal user may edit their own expense but must not edit another user's expense.

# 5. What Is a Software Requirements Specification (SRS)?

An SRS is a document that describes the requirements, functionality, constraints, and expected behavior of a software application.

It acts as a reference for:

- Developers.
- Designers.
- Testers.
- Project managers.
- Clients.

### Typical SRS Structure

```text
SOFTWARE REQUIREMENTS SPECIFICATION
│
├── 1. Introduction
│
├── 2. Project Overview
│
├── 3. Project Objectives
│
├── 4. Scope
│
├── 5. User Roles
│
├── 6. Functional Requirements
│
├── 7. Non-Functional Requirements
│
├── 8. Technology Stack
│
├── 9. Database Requirements
│
├── 10. API Requirements
│
├── 11. Security Requirements
│
├── 12. Deployment Requirements
│
└── 13. Assumptions and Constraints
```

## Example: Expense Tracker SRS

### 5.1 Project Overview

The Expense Tracker is a web-based application that allows users to record, categorize, manage, and analyze their personal expenses.

### 5.2 Project Objectives

- Track daily expenses.
- Organize expenses by category.
- Monitor monthly spending.
- Generate financial reports.
- Export expense records.

### 5.3 Scope

Included:

- User registration.
- Login and logout.
- Expense CRUD.
- Category management.
- Dashboard.
- Monthly reports.
- Excel export.

Not included in the initial version:

- Bank account integration.
- Automatic bank transaction imports.
- Payment processing.
- Multi-currency conversion.

### 5.4 User Roles

- Admin.
- Registered User.

### 5.5 Functional Requirements

```text
FR-01: User Registration

The system must allow users to create an account
using their name, email, and password.

FR-02: User Login

The system must authenticate registered users.

FR-03: Add Expense

Users must be able to add expenses with
amount, date, category, and description.

FR-04: Edit Expense

Users must be able to update their own expenses.

FR-05: Delete Expense

Users must be able to delete their own expenses.

FR-06: Expense Reports

Users must be able to view monthly expense summaries.
```

### 5.6 Non-Functional Requirements

```text
NFR-01: Passwords must be securely hashed.

NFR-02: All production communication must use HTTPS.

NFR-03: APIs must validate request data.

NFR-04: The application must support pagination.

NFR-05: The application must provide centralized error handling.

NFR-06: Database backups must be maintained.
```

# 6. What Is Project Scope?

Project scope defines what is included and excluded from a project.

Suppose a client wants an expense tracker.

Without a defined scope, they may later request:

- Expense management.
- Bank integration.
- AI expense categorization.
- Invoice generation.
- Subscription billing.
- Mobile applications.
- Multi-company management.

These features can significantly change development time and cost.

### Example Scope Definition

**Version 1.0**

Included:

- Authentication.
- Expense management.
- Categories.
- Dashboard.
- Reports.
- Excel export.

Excluded:

- AI integration.
- Bank integration.
- Mobile app.
- Subscription system.

### Why Scope Matters

- Prevents scope creep.
- Helps estimate development time.
- Helps estimate cost.
- Establishes clear expectations.
- Makes project delivery measurable.

# 7. What Is a User Story?

A user story describes a feature from the perspective of the person who will use it.

Common format:

```text
As a [user],
I want [functionality],
so that [benefit].
```

### Examples

**User Registration**

As a visitor, I want to register an account so that I can manage my expenses.

**Add Expense**

As a registered user, I want to add expenses so that I can track my spending.

**Monthly Report**

As a registered user, I want to view monthly reports so that I can understand my spending habits.

### Acceptance Criteria

Acceptance criteria define the conditions that must be satisfied for a user story to be considered complete.

Example:

**User Story:** Add Expense.

Acceptance criteria:

1. User must be authenticated.
2. Amount must be greater than zero.
3. Category must exist.
4. Expense date must be valid.
5. User must not be able to create an expense for another user's account.
6. The expense must be saved successfully.
7. The API must return an appropriate response.

### User Story vs Requirement

| User Story | Requirement |
|---|---|
| Written from the user's perspective | Describes system behavior |
| Focuses on user value | Can describe technical or business constraints |
| Commonly used in Agile | Used across development methodologies |

# 8. What Is a Use Case?

A use case describes how an actor interacts with a system to achieve a particular goal.

Example:

**Use Case:** Add Expense.

| Field | Description |
|---|---|
| Use Case ID | UC-01 |
| Name | Add Expense |
| Actor | Registered User |
| Precondition | User must be authenticated |
| Main Flow | User submits expense details |
| System Action | Validates and saves expense |
| Postcondition | Expense is stored |
| Alternative Flow | Invalid data returns validation error |

### Use Case Flow

```text
USER
  |
  v
LOGIN
  |
  v
OPEN EXPENSE FORM
  |
  v
ENTER EXPENSE DETAILS
  |
  v
SUBMIT REQUEST
  |
  v
VALIDATE DATA
  |
  +------ INVALID ------> RETURN ERROR
  |
  v
SAVE EXPENSE
  |
  v
RETURN SUCCESS
```

# 9. What Is an MVP?

MVP stands for Minimum Viable Product.

It is the smallest version of a product that provides enough value to be tested with real users.

Suppose you are developing an expense tracker.

### MVP Features

- Register.
- Login.
- Add expense.
- View expenses.
- Edit expense.
- Delete expense.

### Future Features

- Analytics dashboard.
- Excel export.
- PDF reports.
- Recurring expenses.
- AI expense categorization.
- Bank integration.

### MVP vs Full Product

| MVP | Full Product |
|---|---|
| Minimum essential functionality | Complete planned functionality |
| Faster initial delivery | Longer development |
| Used to validate assumptions | Used to serve broader requirements |
| Limited feature set | Expanded feature set |

**Important:** MVP does not mean poor-quality software. Security, data integrity, and core functionality must still be implemented correctly.

# 10. What Is a Project Milestone?

A milestone is an important checkpoint in a project's timeline.

Example:

| Milestone | Deliverable |
|---|---|
| M1 | Requirements finalized |
| M2 | Database design completed |
| M3 | Authentication completed |
| M4 | Expense APIs completed |
| M5 | Reports completed |
| M6 | Testing completed |
| M7 | Production deployment |

### Milestone vs Task

A task is an individual activity.

A milestone represents a significant completion point.

Example:

```text
MILESTONE: Authentication Completed

    TASK 1: Registration API

    TASK 2: Login API

    TASK 3: Password Hashing

    TASK 4: JWT Authentication

    TASK 5: Refresh Token

    TASK 6: Authentication Testing
```

# 11. What Is Risk Analysis?

Risk analysis identifies potential problems that could affect project delivery or application quality.

### Example: Expense Tracker

| Risk | Impact | Mitigation |
|---|---|---|
| Database failure | High | Backups and recovery |
| Unauthorized access | High | Authentication and authorization |
| Slow reports | Medium | Indexing and query optimization |
| Data loss | High | Backup and restore strategy |
| Scope changes | Medium | Scope approval process |
| Server downtime | High | Monitoring and recovery |

### Risk Categories

- Technical risks.
- Security risks.
- Business risks.
- Financial risks.
- Operational risks.
- Schedule risks.

### Risk Assessment

A simple risk score can be calculated as:

```text
Risk Score = Probability × Impact
```

For example:

```text
Probability = 4

Impact = 5

Risk Score = 20
```

Higher scores indicate risks that need greater attention.

This is a prioritization technique, not a universal risk standard.

# 12. What Is a Technical Feasibility Study?

A technical feasibility study determines whether a proposed application can realistically be built with the available technology, skills, infrastructure, time, and budget.

Example:

Client requirement:

> The application must process 100,000 uploaded PDF documents every day.

Before agreeing, investigate:

- Expected file sizes.
- Available server resources.
- Processing time per file.
- Whether processing can be parallelized.
- Queue requirements.
- Storage requirements.
- Database workload.
- Expected peak traffic.
- Cost of infrastructure.

A technical feasibility study helps avoid unrealistic commitments.

# 13. Estimating Project Development Time

After understanding requirements, divide the project into smaller tasks.

Example:

| Task | Estimated Time |
|---|---:|
| Requirement Analysis | 1 day |
| Project Setup | 0.5 day |
| Database Design | 1 day |
| Authentication | 2 days |
| Expense CRUD | 2 days |
| Category Management | 1 day |
| Dashboard APIs | 1 day |
| Reports | 2 days |
| Testing | 2 days |
| Deployment | 1 day |
| **Total** | **13.5 days** |

These are illustrative estimates. Actual estimates depend on complexity, developer experience, integrations, and testing requirements.

### Important Estimation Techniques

**1. Expert Judgment**

Estimate based on previous experience.

**2. Analogous Estimation**

Compare the task with similar completed projects.

**3. Three-Point Estimation**

Use three estimates:

- Optimistic (O).
- Most Likely (M).
- Pessimistic (P).

PERT estimate:

```text
Expected Time = (O + 4M + P) / 6
```

Example:

```text
O = 2 days

M = 4 days

P = 8 days

Expected Time = (2 + 16 + 8) / 6

Expected Time = 4.33 days
```

# 14. What Is a Technical Design Document (TDD)?

A Technical Design Document explains how the application will be implemented technically.

Do not confuse this with Test-Driven Development, which is also abbreviated as TDD.

An architecture or technical design document commonly includes:

```text
TECHNICAL DESIGN DOCUMENT
│
├── Architecture Overview
│
├── Technology Stack
│
├── Project Structure
│
├── Database Design
│
├── API Design
│
├── Authentication Design
│
├── Authorization Design
│
├── Error Handling
│
├── Security Design
│
├── Deployment Architecture
│
└── Testing Strategy
```

### SRS vs Technical Design Document

| SRS | Technical Design Document |
|---|---|
| Describes what the application must do | Describes how it will be implemented |
| Business and system requirements | Architecture and technical decisions |
| Focuses on expected behavior | Focuses on implementation |
| Usually prepared during analysis | Usually prepared during design |

# 16. Interview Questions and Answers

### Q1. What is SDLC?

SDLC is a structured process used to plan, develop, test, deploy, and maintain software applications.

### Q2. What is requirement analysis?

It is the process of understanding, evaluating, and documenting what a software system must do.

### Q3. What are functional requirements?

Requirements that describe the features and operations a system must provide.

### Q4. What are non-functional requirements?

Requirements that define quality attributes and constraints such as performance, security, scalability, and reliability.

### Q5. What is an SRS document?

A Software Requirements Specification document describes the functional and non-functional requirements of an application.

### Q6. What is project scope?

Project scope defines the work, features, deliverables, and boundaries included in a project.

### Q7. What is scope creep?

Scope creep is the uncontrolled expansion of project requirements after the original scope has been agreed upon.

An MVP is the smallest usable version of a product that provides core value and helps validate assumptions.

A user story describes a feature from the perspective of a user and explains the value it provides.

Acceptance criteria define the conditions a feature must satisfy to be considered complete.

A use case describes how an actor interacts with a system to achieve a particular goal.
