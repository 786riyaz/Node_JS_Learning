```javascript
const { z } = require("zod");

const envSchema = z.object({

    NODE_ENV: z.enum([
        "development",
        "test",
        "production"
    ]),

    PORT: z.coerce.number().int().positive(),

    DB_HOST: z.string().min(1),

    DB_PORT: z.coerce.number().int().positive(),

    DB_NAME: z.string().min(1),

    DB_USER: z.string().min(1),

    DB_PASSWORD: z.string(),

    JWT_ACCESS_SECRET: z.string().min(32),

    JWT_REFRESH_SECRET: z.string().min(32)

});

const result = envSchema.safeParse(process.env);

if (!result.success) {

    console.error(
        "Invalid environment configuration",
        result.error.flatten()
    );

    process.exit(1);

}

module.exports = result.data;
```

The application should fail fast if critical configuration is missing or invalid.

**Important:** A minimum string length is not a complete security check for cryptographic secrets. Use securely generated, high-entropy secrets.

# 4. Production Security Checklist

Security is one of the most important parts of production readiness.

A backend application may contain:

- User information.
- Email addresses.
- Password hashes.
- Financial transactions.
- Payment records.
- Authentication tokens.
- Uploaded documents.

A security vulnerability can expose this information.

Let's review the important security areas.

## 4.1 Authentication Security

Authentication verifies user identity.

Production checklist:

- Passwords must be hashed using a suitable password-hashing algorithm.
- Use Argon2id or appropriately configured bcrypt.
- Never store plaintext passwords.
- Implement secure login.
- Implement refresh token rotation where appropriate.
- Support token revocation.
- Expire access tokens.
- Implement password reset securely.
- Rate-limit login attempts.
- Avoid revealing whether an account exists during password recovery.

### Password Hashing Example

```javascript
const argon2 = require("argon2");

const hashedPassword = await argon2.hash(password);

const isValid = await argon2.verify(
    hashedPassword,
    password
);
```

Argon2id is a strong general-purpose choice for password hashing.

## 4.2 Authorization Security

Authentication alone is not sufficient.

You must also verify what a user is allowed to access.

Example:

User A must not be able to access User B's expenses.

Incorrect:

```javascript
const expense = await Expense.findByPk(expenseId);
```

This retrieves an expense without checking ownership.

Better:

```javascript
const expense = await Expense.findOne({

    where: {

        id: expenseId,

        userId: req.user.id

    }

});
```

This prevents users from accessing another user's expense through an unscoped lookup.

### Important Security Concepts

| Concept | Meaning |
|---|---|
| Authentication | Verifies identity |
| Authorization | Verifies permissions |
| RBAC | Role-Based Access Control |
| ABAC | Attribute-Based Access Control |
| BOLA | Broken Object Level Authorization |
| IDOR | Insecure Direct Object Reference |

Always enforce authorization on the server, not only in the frontend.

## 4.3 Input Validation

Never trust incoming client data.

Validate:

- Request body.
- Query parameters.
- URL parameters.
- File uploads.
- Pagination values.
- Date ranges.
- Numeric values.

Example:

```javascript
const expenseSchema = z.object({

    amount: z
        .string()
        .regex(/^\d+(\.\d{1,2})?$/),

    description: z
        .string()
        .trim()
        .min(1)
        .max(500),

    categoryId: z
        .string()
        .min(1)

});
```

Validation rules should also reflect database constraints and business rules.

## 4.4 SQL Injection Prevention

Avoid building SQL queries using untrusted string concatenation.

Incorrect:

```javascript
const query = `
    SELECT * FROM users
    WHERE email = '${email}'
`;
```

Better:

```javascript
const users = await User.findAll({

    where: {

        email

    }

});
```

Use ORM parameterization or parameterized SQL queries.

## 4.5 XSS Protection

Cross-Site Scripting occurs when untrusted content is executed as code in a browser.

Prevent it by:

- Escaping untrusted output.
- Avoiding unsafe HTML insertion.
- Using Content Security Policy.
- Sanitizing HTML when rich-text input is required.
- Keeping frontend dependencies updated.

## 4.6 CSRF Protection

Cross-Site Request Forgery can occur when a browser sends authenticated requests without the user's intention.

Protection depends on the authentication model.

For cookie-based authentication, consider:

- `HttpOnly`.
- `Secure`.
- Appropriate `SameSite` settings.
- CSRF tokens or another suitable CSRF defense.
- Origin validation where appropriate.

## 4.7 Rate Limiting

Limit repeated requests to sensitive endpoints.

Examples:

- Login.
- Registration.
- Forgot password.
- OTP verification.
- Payment operations.

We will implement this later in this lesson.

## 4.8 Security Headers

Use Helmet:

```javascript
const helmet = require("helmet");

app.use(helmet());
```

Configure Content Security Policy and other headers according to your application requirements.

## 4.9 File Upload Security

Validate:

- File size.
- File type.
- File content.
- File extension.
- Storage path.

Do not trust the MIME type supplied by the client.

For images, consider decoding and re-encoding them with a trusted image-processing library.

Never allow users to upload executable files that can be served and executed from your application directory.

## 4.10 Secrets Management

Never expose:

- Database passwords.
- JWT secrets.
- Payment gateway secrets.
- AWS access keys.
- SMTP credentials.
- Private SSH keys.

Use appropriate secret storage and access controls.

# 6. Production Database Integrity

Our Expense Tracker stores financial information.

Therefore, database correctness is critical.

### Database Responsibilities

MySQL should remain the authoritative storage system for:

- Users.
- Expenses.
- Incomes.
- Categories.
- Budgets.
- Payments.
- Subscriptions.
- Financial audit records.

### Important Database Constraints

Use:

- Primary keys.
- Foreign keys.
- Unique constraints.
- NOT NULL constraints.
- CHECK constraints where supported and appropriate.
- Appropriate indexes.

### Example

```sql
CREATE TABLE expenses (

    id BIGINT PRIMARY KEY AUTO_INCREMENT,

    user_id BIGINT NOT NULL,

    category_id BIGINT NOT NULL,

    amount DECIMAL(12,2) NOT NULL,

    description VARCHAR(500),

    expense_date DATE NOT NULL,

    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,

    FOREIGN KEY (user_id)
        REFERENCES users(id),

    FOREIGN KEY (category_id)
        REFERENCES categories(id)

);
```

This is an illustrative schema. The full production design must also enforce category ownership and category type through application logic or additional database constraints.

### Why Use DECIMAL for Money?

Financial values should not use ordinary floating-point arithmetic.

Incorrect:

```javascript
const total = 0.1 + 0.2;

console.log(total);
```

Output:

```text
0.30000000000000004
```

Better approaches include:

- MySQL `DECIMAL`.
- Integer minor units, such as paise.
- Decimal arithmetic libraries such as `decimal.js`.

Example:

```javascript
const Decimal = require("decimal.js");

const total = new Decimal("0.10")
    .plus("0.20");

console.log(total.toFixed(2));
```

Output:

```text
0.30
```

### Important Database Rules

1. Use transactions for related financial operations.
2. Validate ownership before modifying records.
3. Use appropriate foreign keys.
4. Avoid unnecessary indexes.
5. Monitor slow queries.
6. Use migrations.
7. Do not modify production schemas manually without a controlled process.
8. Keep database backups.
9. Test recovery procedures.
10. Define data-retention requirements.

# 7. Production Backup and Recovery Strategy

A database backup is essential for protecting application data.

Imagine:

- The server crashes.
- A developer accidentally deletes records.
- A database migration fails.
- The storage device becomes corrupted.
- An attacker modifies or deletes data.

Without backups, recovery may be impossible.

### What Is a Database Backup?

A database backup is a copy of database information that can be used to restore data after failure or loss.

### Common Backup Types

#### 1. Full Backup

Copies the entire database.

Advantages:

- Simple restoration.
- Complete snapshot.

Disadvantages:

- Requires more storage.
- May take longer for large databases.

#### 2. Incremental Backup

Stores changes made since the previous backup.

Advantages:

- Uses less storage.
- Can reduce backup time.

Disadvantages:

- Restoration may require multiple backup sets.

#### 3. Differential Backup

Stores changes made since the last full backup.

Advantages:

- Restoration is often simpler than a long incremental chain.

Disadvantages:

- Backup size grows until the next full backup.

#### 4. Binary Log Backup

MySQL binary logs record database changes and can support point-in-time recovery when configured appropriately.

### Backup Strategy Example

```text
FULL BACKUP
    |
    v
DAILY INCREMENTAL BACKUPS
    |
    v
BINARY LOG ARCHIVING
    |
    v
OFFSITE BACKUP STORAGE
```

The exact strategy depends on database size, recovery requirements, and available infrastructure.

### What Is RPO?

RPO stands for Recovery Point Objective.

It describes the maximum acceptable amount of data loss measured in time.

Example:

```text
RPO = 15 minutes
```

This means the recovery strategy should aim to limit data loss to no more than 15 minutes.

### What Is RTO?

RTO stands for Recovery Time Objective.

It describes the maximum acceptable time required to restore service.

Example:

```text
RTO = 2 hours
```

This means the service should be restored within two hours of a qualifying incident.

### RPO vs RTO

| Concept | Meaning |
|---|---|
| RPO | How much recent data can be lost |
| RTO | How long service can remain unavailable |

### Example MySQL Backup

Using `mysqldump`:

```bash
mysqldump \
  -u root \
  -p \
  --single-transaction \
  expense_tracker \
  > expense_tracker_backup.sql
```

For an InnoDB database, `--single-transaction` can provide a consistent snapshot without locking ordinary transactional tables for the duration of the dump.

### Restore Backup

```bash
mysql \
  -u root \
  -p \
  expense_tracker \
  < expense_tracker_backup.sql
```

### Backup Best Practices

1. Automate backups.
2. Store backups outside the production server.
3. Encrypt sensitive backups.
4. Restrict backup access.
5. Define retention periods.
6. Monitor backup failures.
7. Test restoration regularly.
8. Document recovery procedures.

**Important:** A backup that has never been restored and verified should not be assumed to be recoverable.

# 8. Understanding High Availability

Production applications should ideally remain available even when some components fail.

This is where High Availability becomes important.

### What Is High Availability?

High Availability (HA) is the ability of a system to remain operational with minimal downtime despite component failures.

### Single-Server Architecture

```text
          USERS
            |
            v
        ONE SERVER
            |
     +------+------+
     |      |      |
     v      v      v
    API   MYSQL  REDIS
```

If the server fails, the entire application becomes unavailable.

### High-Availability Architecture

```text
                  USERS
                    |
                    v
              LOAD BALANCER
                    |
           +--------+--------+
           |                 |
           v                 v
        API 1              API 2
           |                 |
           +--------+--------+
                    |
                    v
              DATABASE LAYER
                    |
          +---------+---------+
          |                   |
          v                   v
      PRIMARY DB           REPLICA
```

This architecture provides more resilience, depending on the database failover configuration.

### Common HA Techniques

- Multiple application instances.
- Load balancing.
- Database replication.
- Automatic failover.
- Redundant infrastructure.
- Health checks.
- Shared session storage.
- Distributed caching.
- Backup and recovery.

### Important

Multiple application servers do not automatically provide high availability.

You must also consider shared dependencies such as:

- Database.
- Redis.
- File storage.
- Message queues.
- External APIs.
- Network infrastructure.

These dependencies can still become single points of failure.

# 9. Understanding Load Balancing

A load balancer distributes incoming requests across multiple application instances.

### Without Load Balancing

```text
          USERS
            |
            v
          API 1
```

All requests go to one application instance.

### With Load Balancing

```text
              USERS
                |
                v
          LOAD BALANCER
                |
        +-------+-------+
        |       |       |
        v       v       v
      API 1   API 2   API 3
```

### Why Use Load Balancing?

1. Distribute traffic.
2. Improve capacity.
3. Reduce load on individual instances.
4. Support multiple application replicas.
5. Improve availability when configured with health checks.

### Common Load Balancing Algorithms

| Algorithm | Description |
|---|---|
| Round Robin | Distributes requests sequentially |
| Weighted Round Robin | Distributes according to configured weights |
| Least Connections | Sends traffic to the instance with fewer active connections |
| IP Hash | Selects an instance using client IP information |

### Important Node.js Consideration

When running multiple API instances:

- Avoid storing critical shared state only in process memory.
- Use Redis or a database for shared state.
- Use centralized logging.
- Ensure workers are safe to run concurrently.
- Configure Socket.IO scaling appropriately.
- Handle graceful shutdown.

# 10. Production Rate Limiting and Abuse Prevention

An API can become overloaded due to:

- Excessive user requests.
- Automated bots.
- Brute-force login attempts.
- API abuse.
- Unexpected traffic spikes.

Rate limiting helps control the number of requests a client can make within a period.

### What Is Rate Limiting?

Rate limiting restricts the number of requests allowed from a client or identity during a defined time window.

### Example

```text
Maximum Requests: 100

Time Window: 15 Minutes
```

If a client exceeds the limit, the server can return:

```http
HTTP/1.1 429 Too Many Requests
```

### Install express-rate-limit

```bash
npm install express-rate-limit
```

### Basic Implementation

```javascript
const rateLimit = require("express-rate-limit");

const apiLimiter = rateLimit({

    windowMs: 15 * 60 * 1000,

    limit: 100,

    standardHeaders: "draft-8",

    legacyHeaders: false,

    message: {

        success: false,

        message: "Too many requests. Please try again later."

    }

});

app.use("/api", apiLimiter);
```

This example uses the current-style `limit` option. Check the installed package version when implementing it.

### Different Rate Limits for Different Routes

General API:

```javascript
const generalLimiter = rateLimit({

    windowMs: 15 * 60 * 1000,

    limit: 100

});
```

Login:

```javascript
const loginLimiter = rateLimit({

    windowMs: 15 * 60 * 1000,

    limit: 5

});
```

Register:

```javascript
const registerLimiter = rateLimit({

    windowMs: 60 * 60 * 1000,

    limit: 10

});
```

Apply the stricter limits to the relevant authentication routes.

### Important Production Consideration

The default in-memory rate-limit store is not shared between multiple Node.js instances.

If your application runs on multiple servers, use a shared store such as Redis.

Also configure Express proxy trust carefully when operating behind a reverse proxy. Incorrect proxy configuration can cause client IP identification and rate limiting to behave incorrectly.

# 11. Graceful Shutdown

This is one of the most important production topics.

### What Is Graceful Shutdown?

Graceful shutdown is the process of stopping an application without abruptly interrupting active operations.

Suppose your Node.js server is processing requests.

You execute:

```bash
Ctrl + C
```

A poorly designed application may terminate immediately.

This can interrupt:

- Active HTTP requests.
- Database operations.
- Background jobs.
- Socket.IO connections.
- Queue workers.

A graceful shutdown gives the application time to finish or safely terminate ongoing work.

### Shutdown Process

```text
       SHUTDOWN SIGNAL
              |
              v
       STOP ACCEPTING
        NEW REQUESTS
              |
              v
       FINISH ACTIVE REQUESTS
              |
              v
        CLOSE SOCKET.IO
              |
              v
        CLOSE WORKERS
              |
              v
        CLOSE REDIS
              |
              v
        CLOSE DATABASE
              |
              v
          EXIT PROCESS
```

### Example Node.js Implementation

Assume your application has:

- Express HTTP server.
- Sequelize.
- Redis client.
- BullMQ worker.

```javascript
const http = require("node:http");

const app = require("./app");

const sequelize = require("./config/database");

const redis = require("./config/redis");

const worker = require("./workers/expense.worker");

const logger = require("./config/logger");

const PORT = process.env.PORT || 5000;

const server = http.createServer(app);

server.listen(PORT, "0.0.0.0", () => {

    logger.info(`Server running on port ${PORT}`);

});


let isShuttingDown = false;


const shutdown = async (signal) => {

    if (isShuttingDown) {
        return;
    }

    isShuttingDown = true;

    logger.info(`Received ${signal}. Starting shutdown.`);

    const forceExitTimer = setTimeout(() => {

        logger.error("Graceful shutdown timed out.");

        process.exit(1);

    }, 30000);

    forceExitTimer.unref();

    try {

        // Stop accepting new connections.
        await new Promise((resolve, reject) => {

            server.close((error) => {

                if (error) {
                    reject(error);
                } else {
                    resolve();
                }

            });

        });

        // Stop background worker.
        await worker.close();

        // Close Redis.
        await redis.quit();

        // Close database connections.
        await sequelize.close();

        logger.info("Application shutdown completed.");

        clearTimeout(forceExitTimer);

        process.exitCode = 0;

    } catch (error) {

        logger.error("Shutdown failed", {

            error: error.message

        });

        clearTimeout(forceExitTimer);

        process.exitCode = 1;

    }

};


process.on("SIGTERM", () => {

    shutdown("SIGTERM");

});


process.on("SIGINT", () => {

    shutdown("SIGINT");

});
```

This is a simplified reference implementation.

For a real application, also consider:

- Socket.IO server shutdown.
- BullMQ producer queues.
- Queue event listeners.
- WebSocket connections.
- In-flight request draining.
- Redis client ownership.
- Shutdown ordering.
- Worker-specific shutdown behavior.

Do not close a shared Redis connection before all services using it have shut down.

### Important Signals

| Signal | Meaning |
|---|---|
| SIGINT | Interrupt signal, commonly Ctrl+C |
| SIGTERM | Termination request |
| SIGKILL | Forceful termination; cannot be handled by the application |

**Important:** Graceful shutdown cannot protect against every failure. A process may be killed abruptly, the machine may lose power, or the operating system may terminate it. Database transactions, durable queues, and recovery mechanisms are still necessary.

# 12. Production Error Handling

An application should have a centralized error-handling strategy.

### Why Centralized Error Handling?

Without centralized handling, different controllers may return inconsistent errors.

Incorrect:

```javascript
res.status(500).json({

    message: error.message

});
```

Another controller might return:

```javascript
res.status(400).json({

    error: error

});
```

This creates inconsistent API responses.

### Centralized Error Middleware

```javascript
const logger = require("../config/logger");

const errorHandler = (err, req, res, next) => {

    if (res.headersSent) {

        return next(err);

    }

    const statusCode = err.statusCode || 500;

    logger.error("Request failed", {

        requestId: req.requestId,

        statusCode,

        error: err.message,

        stack: process.env.NODE_ENV !== "production"
            ? err.stack
            : undefined

    });

    const response = {

        success: false,

        message: statusCode >= 500
            ? "Internal Server Error"
            : err.message,

        requestId: req.requestId

    };

    if (err.code) {

        response.error = {

            code: err.code

        };

    }

    res.status(statusCode).json(response);

};

module.exports = errorHandler;
```

Register it after all routes:

```javascript
app.use(errorHandler);
```

### Production Error-Handling Rules

1. Never expose stack traces to ordinary production API clients.
2. Log unexpected errors.
3. Return consistent error responses.
4. Use appropriate HTTP status codes.
5. Preserve request IDs.
6. Do not silently ignore important errors.
7. Distinguish expected business errors from unexpected system failures.

# 13. Production File Storage Strategy

Our Expense Tracker supports file uploads.

For example:

- Expense receipts.
- Invoice images.
- Supporting documents.

Should we store these files inside the Node.js application directory?

For small local projects, local storage may be acceptable.

For scalable production systems, object storage is often a better choice.

### Local Storage

```text
NODE.JS SERVER
      |
      v
UPLOAD DIRECTORY
      |
      v
FILES
```

Problems:

- Files may be lost when a container is recreated.
- Multiple application instances may not share files.
- Disk space may become exhausted.
- Backups become more complicated.

### Object Storage

```text
          NODE.JS API
               |
               v
          OBJECT STORAGE
               |
       +-------+-------+
       |       |       |
       v       v       v
    FILE 1  FILE 2  FILE 3
```

Examples:

- Amazon S3.
- Cloudinary.
- Google Cloud Storage.
- Azure Blob Storage.

### Recommended Approach

Store file metadata in MySQL:

```text
id
user_id
file_name
storage_key
mime_type
file_size
created_at
```

Store the actual file in object storage.

### Important

- Use private buckets for private documents.
- Generate short-lived access URLs where appropriate.
- Validate file content.
- Restrict file size.
- Avoid exposing storage credentials.
- Delete files through controlled cleanup workflows.
- Include files in backup and retention planning.

1. Never trust frontend payment status.
2. Verify gateway signatures.

# 15. Production Performance Optimization

Production performance is not only about writing fast code.

It requires optimizing the entire request lifecycle.

### Important Areas

| Area | Optimization |
|---|---|
| Node.js | Avoid blocking event loop |
| Express | Efficient middleware |
| Database | Indexes and query optimization |
| Redis | Effective caching |
| API | Pagination and filtering |
| Files | Streaming and object storage |
| Background jobs | Queue processing |
| Network | Compression and connection reuse |
| Infrastructure | Scaling and resource allocation |

### 15.1 Avoid Blocking Operations

Avoid unnecessary synchronous operations:

```javascript
fs.readFileSync("large-file.txt");
```

Prefer asynchronous APIs:

```javascript
const fs = require("node:fs/promises");

const data = await fs.readFile("large-file.txt");
```

For very large files, consider streams rather than reading the entire file into memory.

### 15.2 Database Optimization

Use:

- Appropriate indexes.
- Efficient queries.
- Query pagination.
- Connection pooling.
- Transactions where necessary.
- Query-plan analysis.

### 15.3 Redis Caching

Cache frequently requested data when appropriate.

Examples:

- Dashboard summaries.
- Category lists.
- User preferences.

Do not cache data indiscriminately.

### 15.4 Compression

Use compression where it benefits your application.

For example:

```bash
npm install compression
```

```javascript
const compression = require("compression");

app.use(compression());
```

Compression can reduce response size, but it consumes CPU. Configure it according to response types and workload.

### 15.5 Horizontal Scaling

Instead of increasing the resources of one server, you can add more application instances.

```text
          LOAD BALANCER
                |
       +--------+--------+
       |        |        |
       v        v        v
     API 1    API 2    API 3
```

This is horizontal scaling.

### Vertical vs Horizontal Scaling

| Vertical Scaling | Horizontal Scaling |
|---|---|
| Increase resources of one machine | Add more machines or instances |
| More CPU and RAM | More application replicas |
| Easier initially | Requires distributed-system considerations |
| Has hardware limits | Can scale across multiple machines |
