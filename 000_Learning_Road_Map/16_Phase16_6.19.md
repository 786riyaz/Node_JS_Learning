# 2. Logging vs Monitoring vs Observability

These three terms are related but have different meanings.

## 2.1 Logging

Logging is the process of recording events that occur inside an application.

Examples:

```text
User registered successfully.

User login failed.

Expense created successfully.

Database connection established.

Payment verification failed.
```

Logs help us understand what happened.

Example:

```javascript
console.log("User registered successfully");
```

However, production applications should generally use a structured logging library instead of relying entirely on `console.log()`.

## 2.2 Monitoring

Monitoring involves continuously tracking predefined metrics and conditions.

Examples:

- CPU usage is above 90%.
- Memory usage is above 85%.
- API error rate exceeds 5%.
- Average response time exceeds 2 seconds.
- Database connections are exhausted.

Monitoring helps answer:

**Is something wrong with the application?**

## 2.3 Observability

Observability is the ability to understand the internal state of a system by analyzing the data it produces.

It helps investigate problems that were not necessarily anticipated in advance.

For example:

A user reports that the dashboard API takes 8 seconds.

With observability, we can investigate:

1. Which API request was slow?
2. Which database query took the most time?
3. Was Redis unavailable?
4. Did the request call another service?
5. Which part of the request lifecycle caused the delay?

### Comparison

| Feature | Logging | Monitoring | Observability |
|---|---|---|---|
| Main purpose | Record events | Track system health | Understand system behavior |
| Data | Log messages | Metrics and thresholds | Logs, metrics, traces |
| Main question | What happened? | Is something wrong? | Why did it happen? |
| Example | Login failed | Error rate increased | Trace identifies failing database query |

### Easy Way to Remember

- Logging tells you what happened.
- Monitoring tells you when something is wrong.
- Observability helps you understand why it happened.

# 3. Three Pillars of Observability

Observability is commonly discussed using three pillars:

1. Logs.
2. Metrics.
3. Traces.

These provide different perspectives on application behavior.

## 3.1 Logs

Logs are timestamped records of application events.

Example:

```json
{
  "level": "error",
  "message": "Database connection failed",
  "timestamp": "2026-11-25T10:30:00.000Z"
}
```

Logs provide detailed event information.

## 3.2 Metrics

Metrics are numerical measurements collected over time.

Examples:

```text
HTTP Requests: 1200

HTTP Errors: 45

CPU Usage: 72%

Memory Usage: 68%

Average Response Time: 250ms
```

Metrics are useful for identifying trends and detecting unusual behavior.

## 3.3 Traces

A trace represents the journey of a request through different components of a distributed application.

Suppose a dashboard request performs:

1. Authentication.
2. Redis lookup.
3. MySQL query.
4. Business logic.
5. Response serialization.

A trace can show how much time each operation consumed.

### Comparison

| Pillar | Data Type | Example |
|---|---|---|

# 4. What Is Structured Logging?

In earlier examples, we used:

```javascript
console.log("User registered successfully");
```

This is called plain-text logging.

It is easy to read, but it becomes difficult to search and analyze at scale.

### Plain-Text Logs

```text
User registered successfully
Payment failed
Database connection error
User logged in
```

A logging system must interpret these messages to extract useful information.

### Structured Logs

Structured logging stores log information in a consistent format, commonly JSON.

Example:

```json
{
  "level": "info",
  "message": "User registered successfully",
  "userId": "101",
  "timestamp": "2026-11-25T10:30:00.000Z"
}
```

Another example:

```json
{
  "level": "error",
  "message": "Payment verification failed",
  "userId": "101",
  "orderId": "order_123",
  "timestamp": "2026-11-25T10:35:00.000Z"
}
```

### Advantages of Structured Logging

1. Easier searching.
2. Easier filtering.
3. Better integration with log-management systems.
4. Consistent log formats.
5. Easier debugging.
6. Better automated analysis.

### Recommended Log Fields

| Field | Purpose |
|---|---|
| `timestamp` | When the event occurred |
| `level` | Severity of the event |
| `message` | Human-readable description |
| `service` | Application or service name |
| `environment` | Development, staging, production |
| `requestId` | Request identification |
| `userId` | Relevant user identifier, when appropriate |
| `error` | Error details |
| `durationMs` | Operation duration |

**Important:** Never log passwords, access tokens, refresh tokens, payment credentials, or sensitive personal information.

# 5. Understanding Log Levels

Logging libraries provide different severity levels.

Common log levels include:

| Level | Purpose | Example |
|---|---|---|
| `fatal` | Critical failure that prevents operation | Application cannot initialize |
| `error` | Error requiring attention | Database query failed |
| `warn` | Unexpected condition | Retry attempt required |
| `info` | Important application event | User registered |
| `http` | HTTP request information | API request received |
| `verbose` | Detailed operational information | Detailed service activity |
| `debug` | Debugging information | Cache key generated |
| `silly` | Extremely detailed diagnostic information | Internal execution details |

Different logging libraries use different level names and priorities.

For example, Winston supports custom levels and commonly includes levels such as `error`, `warn`, `info`, `http`, `verbose`, `debug`, and `silly`.

### Example

```javascript
logger.error("Database connection failed");

logger.warn("Redis connection is slow");

logger.info("User registered");

logger.debug("Generated cache key");
```

### Why Are Log Levels Important?

In production, you may want:

```text
ERROR
WARN
INFO
```

During development, you may also want:

```text
DEBUG
```

You can control which messages are recorded through configuration.

# 6. What Is Winston?

Winston is a popular logging library for Node.js.

It provides:

- Multiple log levels.
- Structured logging.
- JSON formatting.
- Console transports.
- File transports.
- Custom formats.
- Exception handling.

Official repository:

[Winston GitHub Repository](https://github.com/winstonjs/winston?utm_source=chatgpt.com)

### Install Winston

```bash
npm install winston
```

### Create Logger Structure

```text
src/
│
├── config/
│   └── logger.js
│
├── services/
│
├── controllers/
│
└── server.js
```

### Create `logger.js`

```javascript
const winston = require("winston");

const logger = winston.createLogger({

    level: process.env.LOG_LEVEL || "info",

    format: winston.format.combine(

        winston.format.timestamp(),

        winston.format.errors({
            stack: true
        }),

        winston.format.json()

    ),

    defaultMeta: {

        service: "expense-tracker-api"

    },

    transports: [

        new winston.transports.Console()

    ]

});

module.exports = logger;
```

### Understanding the Configuration

**`createLogger()`**

Creates a logger instance.

**`level`**

Defines the minimum log level.

```javascript
level: "info"
```

**`timestamp()`**

Adds a timestamp to each log.

**`errors({ stack: true })`**

Includes stack information when logging an Error object.

**`json()`**

Formats logs as JSON.

**`defaultMeta`**

Adds common metadata to logs.

**`transports`**

Defines where logs should be written.

### Use Logger

```javascript
const logger = require("./config/logger");

logger.info("Application started");

logger.error("Database connection failed");

logger.warn("Redis connection is slow");
```

Example output:

```json
{
  "level": "info",
  "message": "Application started",
  "service": "expense-tracker-api",
  "timestamp": "2026-11-25T10:30:00.000Z"
}
```

# 7. Understanding Winston Transports

A transport defines where logs are sent.

Winston supports multiple transports.

### Console Transport

```javascript
new winston.transports.Console()
```

Writes logs to standard output or standard error.

Useful for:

- Local development.
- Docker containers.
- Cloud platforms that collect container output.

### File Transport

```javascript
new winston.transports.File({

    filename: "logs/error.log",

    level: "error"

})
```

Stores error-level logs in a file.

### Multiple Transports

```javascript
const logger = winston.createLogger({

    level: "debug",

    format: winston.format.combine(

        winston.format.timestamp(),

        winston.format.json()

    ),

    transports: [

        new winston.transports.Console(),

        new winston.transports.File({

            filename: "logs/error.log",

            level: "error"

        }),

        new winston.transports.File({

            filename: "logs/combined.log"

        })

    ]

});
```

Now:

- All configured log levels are written to `combined.log`.
- Error-level logs are written to `error.log`.
- Logs are also written to the console.

### Important Production Consideration

When running applications inside Docker or Kubernetes, writing logs to standard output and standard error is generally preferred.

The container platform can collect these logs centrally.

If you write logs to files inside a container, you must also consider:

- Persistent storage.
- Log rotation.
- Disk usage.
- File permissions.
- Log collection.

Do not allow log files to grow indefinitely.

# 11. Understanding Request IDs and Correlation IDs

Suppose a user reports:

"My dashboard API failed."

Your application has thousands of requests.

How do you identify the logs related to that specific request?

This is where request IDs become useful.

### What Is a Request ID?

A request ID is a unique identifier assigned to an individual HTTP request.

Example:

```text
Request ID: req-12345
```

Every log generated during that request can include the same ID.

### Without Request IDs

```text
User authentication successful

Database query started

Redis lookup failed

Dashboard service failed
```

It is difficult to determine which events belong to the same request when many requests execute concurrently.

### With Request IDs

```text
requestId=req-12345 Authentication successful

requestId=req-12345 Database query started

requestId=req-12345 Redis lookup failed

requestId=req-12345 Dashboard service failed
```

Now the related events are easier to find.

### What Is a Correlation ID?

A correlation ID is an identifier used to connect related operations across multiple services or components.

For example:

```text
API Gateway
    |
    v
Node.js API
    |
    v
Payment Service
    |
    v
Notification Service
```

The same correlation ID can help connect events generated across the request's lifecycle.

A request ID often identifies one request, while a correlation ID may connect a larger business operation involving multiple requests and services.

# 12. Implementing Request IDs in Express

Node.js provides `AsyncLocalStorage` through the `async_hooks` module.

It allows us to maintain request-specific context across many asynchronous operations.

This is useful for adding request IDs to logs without manually passing the ID through every function.

### Step 1: Create Request Context

Create:

```text
src/utils/requestContext.js
```

```javascript
const {
    AsyncLocalStorage
} = require("node:async_hooks");

const requestContext = new AsyncLocalStorage();

module.exports = requestContext;
```

### Step 2: Create Middleware

```javascript
const crypto = require("node:crypto");

const requestContext = require("../utils/requestContext");

const requestIdMiddleware = (req, res, next) => {

    const requestId = crypto.randomUUID();

    requestContext.run(

        {
            requestId
        },

        () => {

            req.requestId = requestId;

            res.setHeader(
                "X-Request-ID",
                requestId
            );

            next();

        }

    );

};

module.exports = requestIdMiddleware;
```

### Step 3: Register Middleware

```javascript
app.use(requestIdMiddleware);
```

Register it early, before the routes and other middleware whose logs should include the request ID.

### Step 4: Update Winston Logger

```javascript
const winston = require("winston");

const requestContext = require("../utils/requestContext");

const logger = winston.createLogger({

    level: "info",

    format: winston.format.combine(

        winston.format.timestamp(),

        winston.format.errors({
            stack: true
        }),

        winston.format.printf((info) => {

            const requestId =
                requestContext.getStore()?.requestId;

            return JSON.stringify({

                timestamp: info.timestamp,

                level: info.level,

                message: info.message,

                requestId,

                ...info

            });

        })

    ),

    transports: [

        new winston.transports.Console()

    ]

});

module.exports = logger;
```

This is an educational example. A production formatter should carefully construct the output object to avoid duplicated fields or leaking sensitive metadata.

### Step 5: Log Normally

```javascript
logger.info("Expense service started");

logger.error("Expense database query failed");
```

The request ID is automatically included when the log is created inside the request's asynchronous context.

**Important:** Background jobs do not automatically inherit the originating HTTP request context. If you need correlation across a queued job, include a safe correlation ID in the job data and restore that context inside the worker.

# 13. Understanding Application Metrics

Logs explain events.

Metrics measure application behavior.

Metrics are numerical values collected over time.

Examples:

```text
Total HTTP Requests: 10000

Failed Requests: 250

CPU Usage: 65%

Memory Usage: 72%

Average Response Time: 180ms

Active Database Connections: 15
```

Metrics help identify performance trends.

### Common Metric Categories

#### 1. Traffic

Measures how much activity the application receives.

Examples:

- Requests per second.
- Total requests.
- Active users.
- Incoming network traffic.

#### 2. Errors

Measures application failures.

Examples:

- HTTP 500 responses.
- Failed payment attempts.
- Database errors.
- Background job failures.

#### 3. Latency

Measures how long operations take.

Examples:

- API response time.
- Database query duration.
- Redis response time.

#### 4. Saturation

Measures how close resources are to their limits.

Examples:

- CPU utilization.
- Memory usage.
- Database connection pool usage.
- Queue backlog.

### The Four Golden Signals

Google's SRE practices commonly describe four important monitoring signals:

1. Latency.
2. Traffic.
3. Errors.
4. Saturation.

These are useful starting points for monitoring services.

# 14. Understanding Prometheus

Prometheus is an open-source monitoring and alerting system.

It collects and stores numerical metrics over time.

Official documentation:

[Prometheus Documentation](https://prometheus.io/docs/introduction/overview/?utm_source=chatgpt.com)

### What Does Prometheus Do?

Prometheus can:

- Collect application metrics.
- Store time-series data.
- Query metrics.
- Evaluate alerting rules.
- Monitor infrastructure.
- Monitor application performance.

### What Is a Time Series?

A time series is a sequence of data points associated with a metric and its labels, recorded over time.

Example:

```text
http_requests_total{method="GET"} 100

http_requests_total{method="POST"} 45

http_requests_total{method="DELETE"} 10
```

These measurements can be collected repeatedly.

### Prometheus Architecture

```text
          NODE.JS APPLICATION
                   |
                   v
             /metrics
                   |
                   v
               PROMETHEUS
                   |
          +--------+--------+
          |                 |
          v                 v
      TIME SERIES       ALERT RULES
          |                 |
          v                 v
       QUERIES            ALERTS
          |
          v
        GRAFANA
```

### Important Concept: Pull-Based Monitoring

Prometheus commonly collects metrics by scraping HTTP endpoints exposed by monitored applications.

For example:

```text
http://localhost:5000/metrics
```

Prometheus periodically requests this endpoint and collects metrics.

# 15. Integrating Prometheus with Node.js

We can expose metrics from our Express application.

Install:

```bash
npm install prom-client
```

`prom-client` is a Prometheus client library for Node.js.

Official repository:

[prom-client GitHub Repository](https://github.com/siimon/prom-client?utm_source=chatgpt.com)

### Step 1: Create Metrics Configuration

Create:

```text
src/config/metrics.js
```

```javascript
const client = require("prom-client");

const register = new client.Registry();

client.collectDefaultMetrics({

    register

});

const httpRequestsTotal = new client.Counter({

    name: "http_requests_total",

    help: "Total number of HTTP requests",

    labelNames: [

        "method",

        "route",

        "status_code"

    ]

});

const httpRequestDuration = new client.Histogram({

    name: "http_request_duration_seconds",

    help: "HTTP request duration in seconds",

    labelNames: [

        "method",

        "route",

        "status_code"

    ],

    buckets: [

        0.05,
        0.1,
        0.2,
        0.5,
        1,
        2,
        5

    ]

});

register.registerMetric(httpRequestsTotal);

register.registerMetric(httpRequestDuration);

module.exports = {

    register,

    httpRequestsTotal,

    httpRequestDuration

};
```

### Step 2: Create Metrics Middleware

Create:

```text
src/middlewares/metrics.middleware.js
```

```javascript
const {

    httpRequestsTotal,

    httpRequestDuration

} = require("../config/metrics");


const metricsMiddleware = (req, res, next) => {

    const startTime = process.hrtime.bigint();

    res.on("finish", () => {

        const duration = Number(

            process.hrtime.bigint() - startTime

        ) / 1e9;

        const route = req.route?.path
            ? `${req.baseUrl || ""}${req.route.path}`
            : "unmatched";

        const labels = {

            method: req.method,

            route,

            status_code: String(res.statusCode)

        };

        httpRequestsTotal.inc(labels);

        httpRequestDuration.observe(

            labels,

            duration

        );

    });

    next();

};

module.exports = metricsMiddleware;
```

### Why Use `process.hrtime.bigint()`?

It provides high-resolution timing.

It is useful for measuring elapsed time.

### Why Use Route Templates?

Consider these requests:

```text
/api/v1/expenses/101

/api/v1/expenses/102

/api/v1/expenses/103
```

If we use the full URL as a metric label, every expense ID may create a new time series.

This creates high cardinality.

Instead, use a route template:

```text
/api/v1/expenses/:id
```

This groups requests under a consistent label.

**Important:** Avoid high-cardinality metric labels such as user IDs, request IDs, email addresses, or arbitrary URLs. They can create excessive time-series data and increase monitoring costs.

### Step 3: Register Middleware

In `app.js`:

```javascript
const metricsMiddleware =
    require("./middlewares/metrics.middleware");

app.use(metricsMiddleware);
```

Register it before the routes you want to monitor.

### Step 4: Create Metrics Endpoint

```javascript
const {

    register

} = require("./config/metrics");


app.get("/metrics", async (req, res) => {

    res.set("Content-Type", register.contentType);

    res.end(await register.metrics());

});
```

Now open:

```text
http://localhost:5000/metrics
```

You should see Prometheus metrics.

### Important Production Consideration

Do not expose the `/metrics` endpoint publicly without access controls.

It can reveal internal application information.

In production, restrict it to your monitoring network or monitoring service.

# 16. Understanding Metric Types

Prometheus provides several metric types.

The most commonly used are:

1. Counter.
2. Gauge.
3. Histogram.
4. Summary.

## 16.1 Counter

A counter is a cumulative value that increases over time.

Example:

```javascript
const requests = new client.Counter({

    name: "total_requests",

    help: "Total HTTP requests"

});
```

Increment:

```javascript
requests.inc();
```

Use cases:

- Total requests.
- Total errors.
- Total successful payments.
- Total completed jobs.

Counters generally reset when the process restarts.

## 16.2 Gauge

A gauge represents a value that can increase or decrease.

Example:

```javascript
const activeUsers = new client.Gauge({

    name: "active_users",

    help: "Current active users"

});
```

Update:

```javascript
activeUsers.set(50);
```

Increase:

```javascript
activeUsers.inc();
```

Decrease:

```javascript
activeUsers.dec();
```

Use cases:

- Active connections.
- Current queue size.
- Memory usage.
- Active users.

## 16.3 Histogram

A histogram records observations in configurable buckets.

Example:

```javascript
const responseTime = new client.Histogram({

    name: "response_time_seconds",

    help: "HTTP response duration"

});
```

Record:

```javascript
responseTime.observe(0.25);
```

Use cases:

- API response duration.
- Database query duration.
- Request payload sizes.

Histograms are useful for calculating latency percentiles using Prometheus queries.

## 16.4 Summary

A summary calculates statistical observations, including quantiles when configured.

Example:

```javascript
const processingTime = new client.Summary({

    name: "job_processing_seconds",

    help: "Background job processing duration"

});
```

Record:

```javascript
processingTime.observe(0.5);
```

### Comparison

| Metric | Behavior | Example |
|---|---|---|
| Counter | Only increases | Total API requests |
| Gauge | Increases or decreases | Active connections |
| Histogram | Observations grouped into buckets | API latency |
| Summary | Observations with calculated quantiles | Job duration |

# 18. Understanding PromQL

PromQL stands for Prometheus Query Language.

It is used to query and analyze metrics stored in Prometheus.

### Example 1: Total Requests

```promql
http_requests_total
```

Returns the request counter series.

### Example 2: Requests Per Second

```promql
rate(http_requests_total[5m])
```

Calculates the average per-second increase over five minutes.

### Example 3: HTTP 500 Errors

```promql
http_requests_total{status_code="500"}
```

Returns the HTTP 500 request counter series.

### Example 4: Error Rate

```promql
sum(rate(http_requests_total{status_code=~"5.."}[5m]))
/
sum(rate(http_requests_total[5m]))
```

Calculates the proportion of HTTP 5xx responses over the total request rate.

### Example 5: 95th Percentile Latency

```promql
histogram_quantile(
  0.95,
  sum by (le) (
    rate(http_request_duration_seconds_bucket[5m])
  )
)
```

This estimates the 95th percentile latency from histogram buckets.

### What Is P95?

P95 means the 95th percentile.

Suppose your API response times are:

```text
100ms
120ms
150ms
200ms
300ms
500ms
```

P95 represents a latency threshold below which approximately 95% of observations fall.

It is useful for understanding slower requests that averages may hide.

# 20. Understanding CPU and Memory Monitoring

A Node.js application runs inside a process.

We need to monitor its resource consumption.

### CPU Monitoring

CPU usage indicates how much processing capacity the application consumes.

High CPU usage may result from:

- Infinite loops.
- Expensive calculations.
- Inefficient algorithms.
- Excessive JSON processing.
- Synchronous blocking operations.
- CPU-intensive background jobs.

### Memory Monitoring

Memory usage indicates how much RAM the application consumes.

High memory usage may result from:

- Memory leaks.
- Large objects retained in memory.
- Unbounded caches.
- Uncontrolled event listeners.
- Large file buffers.
- Unbounded request payloads.

### Get Process Memory Usage

Node.js provides:

```javascript
const memory = process.memoryUsage();

console.log(memory);
```

Example output:

```javascript
{
    rss: 85000000,
    heapTotal: 40000000,
    heapUsed: 25000000,
    external: 5000000,
    arrayBuffers: 1000000
}
```

Let's understand these fields.

| Field | Meaning |
|---|---|
| `rss` | Total resident memory used by the process |
| `heapTotal` | Total allocated V8 heap |
| `heapUsed` | Currently used V8 heap |
| `external` | Memory used by C++ objects bound to JavaScript |
| `arrayBuffers` | Memory used by ArrayBuffers and related buffers |

### Convert Bytes to MB

```javascript
const memory = process.memoryUsage();

const toMB = (bytes) => {

    return (bytes / 1024 / 1024).toFixed(2);

};

console.log({

    rss: toMB(memory.rss),

    heapUsed: toMB(memory.heapUsed),

    heapTotal: toMB(memory.heapTotal)

});
```

### CPU Usage

Node.js provides:

```javascript
const cpu = process.cpuUsage();

console.log(cpu);
```

This returns cumulative user and system CPU time in microseconds for the process.

To measure CPU consumption over an interval, compare two readings and account for elapsed wall-clock time and the number of CPU cores.

### Important

A single memory measurement does not prove a memory leak.

A memory leak is better investigated by observing memory trends over time and examining heap snapshots.

# 21. Understanding Node.js Event Loop Monitoring

We previously studied the Node.js event loop.

Now let's connect it to monitoring.

The event loop is responsible for coordinating asynchronous callbacks and other work in Node.js.

If the event loop becomes blocked, requests may become slow even when the server has available CPU capacity.

### Example of Blocking Code

```javascript
function blockEventLoop() {

    const start = Date.now();

    while (Date.now() - start < 5000) {

        // Blocks the event loop for approximately 5 seconds

    }

}
```

During this operation, the event loop cannot process normal callbacks.

### What Problems Can This Cause?

- Slow API responses.
- Delayed timers.
- Delayed background operations.
- Poor application responsiveness.

### Monitoring Event Loop Delay

Node.js provides `monitorEventLoopDelay()` through `node:perf_hooks`.

Example:

```javascript
const {

    monitorEventLoopDelay

} = require("node:perf_hooks");

const histogram = monitorEventLoopDelay({

    resolution: 20

});

histogram.enable();

setInterval(() => {

    console.log({

        meanMs: histogram.mean / 1e6,

        maxMs: histogram.max / 1e6,

        p95Ms: histogram.percentile(95) / 1e6

    });

    histogram.reset();

}, 10000);
```

### Why Is This Useful?

Suppose:

```text
Average Event Loop Delay: 15ms

Maximum Event Loop Delay: 1200ms
```

A large delay may indicate that the event loop is being blocked or heavily delayed.

Investigate:

- CPU-heavy operations.
- Synchronous file operations.
- Large JSON parsing.
- Expensive regular expressions.
- Long-running JavaScript callbacks.

### Cache Hit Ratio

A cache hit occurs when requested data is found in Redis.

A cache miss occurs when the requested data is not found.

Formula:

\[
\text{Cache Hit Ratio} =
\frac{\text{Cache Hits}}{\text{Cache Hits + Cache Misses}}
\times 100
\]

Example:

```text
Cache Hits: 800

Cache Misses: 200
```

\[
\frac{800}{800+200}\times100 = 80\%
\]

Your cache hit ratio is 80%.

A high hit ratio can indicate effective caching, but the ideal value depends on the workload.

# 25. Understanding Health Checks

A monitoring system needs a way to determine whether an application is healthy.

This is where health-check endpoints are useful.

We introduced health checks during Docker learning.

Now let's understand them more deeply.

There are two important concepts:

1. Liveness.
2. Readiness.

## 25.1 Liveness Check

A liveness check answers:

**Is the application process alive and functioning enough to continue running?**

Example:

```text
GET /health/live
```

Response:

```json
{
  "status": "ok"
}
```

If the application is completely stuck or unhealthy, an orchestrator may restart it.

## 25.2 Readiness Check

A readiness check answers:

**Is the application ready to accept requests?**

It may verify that important dependencies are available.

Example:

```text
GET /health/ready
```

Response:

```json
{
  "status": "ready",
  "dependencies": {
    "database": "connected",
    "redis": "connected"
  }
}
```

### Comparison

| Liveness | Readiness |
|---|---|
| Checks whether the application is alive | Checks whether it can serve requests |
| Used to detect stuck processes | Used to control traffic |
| Failure may trigger restart | Failure generally removes instance from service |

### Example Implementation

```javascript
app.get("/health/live", (req, res) => {

    res.status(200).json({

        status: "ok"

    });

});
```

Readiness check:

```javascript
app.get("/health/ready", async (req, res) => {

    try {

        await sequelize.authenticate();

        await redis.ping();

        return res.status(200).json({

            status: "ready",

            dependencies: {

                database: "connected",

                redis: "connected"

            }

        });

    } catch (error) {

        return res.status(503).json({

            status: "not_ready"

        });

    }

});
```

This is a simplified example. In production, use appropriate timeouts and avoid creating excessive dependency-check traffic.

### Important

Do not expose detailed database errors, credentials, or internal infrastructure information through public health endpoints.

# 26. Understanding Alerting

Monitoring is useful only if someone can respond when something goes wrong.

Alerting sends notifications when predefined conditions are met.

### Example

Suppose:

```text
CPU Usage > 90%
```

Your monitoring system can trigger an alert.

Other examples:

- API error rate exceeds 5%.
- P95 latency exceeds 2 seconds.
- Database connections exceed 90% of capacity.
- Queue backlog grows continuously.
- Disk usage exceeds 85%.
- Application health check fails.

### Alerting Flow

```text
       APPLICATION
            |
            v
        METRICS
            |
            v
       MONITORING
            |
            v
       ALERT RULE
            |
            v
       CONDITION MET?
            |
       +----+----+
       |         |
       v         v
      NO        YES
       |         |
       v         v
    CONTINUE   SEND ALERT
                 |
                 v
          EMAIL / SLACK
                 |
                 v
             DEVELOPER
```

### Example Prometheus Alert Rule

```yaml
groups:

  - name: expense-tracker-alerts

    rules:

      - alert: HighErrorRate

        expr: |
          (
            sum(rate(http_requests_total{status_code=~"5.."}[5m]))
            /
            sum(rate(http_requests_total[5m]))
          ) > 0.05

        for: 5m

        labels:

          severity: critical

        annotations:

          summary: High API error rate

          description: API 5xx error rate has exceeded 5% for 5 minutes.
```

This alert triggers when the 5xx error rate exceeds 5% continuously for five minutes.

In a real system, also handle the case where there are no requests, so that an empty metric series does not produce misleading alert behavior.

### Alerting Best Practices

1. Avoid unnecessary alerts.
2. Define meaningful thresholds.
3. Include relevant context.
4. Avoid duplicate notifications.
5. Prioritize critical alerts.
6. Assign ownership.
7. Document response procedures.

# 27. Understanding Distributed Tracing

Now let's explore the third pillar of observability in more detail.

### What Is Distributed Tracing?

Distributed tracing is a technique used to track a request as it travels through multiple services.

Suppose our application uses:

```text
Frontend
   |
   v
API Gateway
   |
   v
Node.js API
   |
   +----------+
   |          |
   v          v
 MySQL      Redis
   |
   v
Payment Service
   |
   v
Notification Service
```

A single business operation may involve several components.

Distributed tracing helps identify where time is spent and where failures occur.

### What Is a Trace?

A trace represents the complete journey of an operation.

### What Is a Span?

A span represents one individual operation inside a trace.

Example:

```text
TRACE: Create Expense

    |
    +-- Authentication Span
    |       10ms
    |
    +-- Expense Service Span
    |       20ms
    |
    +-- MySQL Query Span
    |       150ms
    |
    +-- Notification Job Span
    |       5ms
    |
    +-- Response Span
            10ms
```

### Important Trace Concepts

| Concept | Meaning |
|---|---|
| Trace | Complete operation journey |
| Span | Individual operation |
| Trace ID | Identifier for the entire trace |
| Span ID | Identifier for an individual span |
| Parent Span | Span that initiated another span |
| Attributes | Additional metadata |
| Events | Events associated with a span |

### What Is OpenTelemetry?

OpenTelemetry is an open-source observability framework.

It provides APIs, SDKs, and instrumentation for collecting:

You find:

```text

Response: 50ms
```

The database query is the main bottleneck.

### Step 4: Investigate MySQL

You discover that the query is performing a full table scan.

### Step 5: Check Query Plan

Execute:

```sql
EXPLAIN
SELECT *
FROM expenses
WHERE user_id = 101
ORDER BY expense_date DESC;
```

You discover that the query needs an appropriate index.

### Step 6: Optimize Query

Create an index based on the actual query pattern.

For example:

```sql
CREATE INDEX idx_expenses_user_date
ON expenses(user_id, expense_date);
```

The exact index should be selected after examining the schema, existing indexes, and query plan.

### Step 7: Verify

After optimization:

```text
Previous Query Time: 7600ms

New Query Time: 120ms
```

The dashboard response time improves significantly.

# 32. Monitoring Best Practices

Follow these practices in production.

### 1. Use Structured Logs

Prefer JSON logs with consistent fields.

### 2. Add Request IDs

Make it easier to correlate logs from the same request.

### 3. Monitor Important Metrics

At minimum, monitor:

- Request rate.
- Error rate.
- Latency.
- CPU.
- Memory.
- Database connections.
- Queue backlog.

### 4. Monitor Dependencies

Do not monitor only the Node.js application.

Also monitor:

- MySQL.
- Redis.
- External APIs.
- Background workers.

### 5. Use Centralized Logging

Avoid manually checking logs across multiple servers.

### 6. Avoid Sensitive Data

Never log:

- Passwords.
- JWTs.
- Refresh tokens.
- Payment credentials.
- Private keys.
- Sensitive personal information.

### 7. Configure Alerts

Define alerts for important failures.

### 8. Use Distributed Tracing

Especially useful when an application communicates with multiple services.

### 9. Monitor Resource Consumption

Watch CPU, memory, disk, and network usage.

### 10. Control Monitoring Costs

Avoid excessive log volume, unnecessary metric labels, and capturing every trace at full sampling rates.

### 11. Configure Log Retention

Logs should have a defined retention period.

### 12. Test Monitoring

Verify that alerts, dashboards, and error reporting actually work.

# 34. Interview Questions and Answers

### Q1. What is application monitoring?

Application monitoring is the continuous tracking of application health, performance, availability, and resource usage.

### Q2. What is logging?

Logging is the process of recording application events for debugging, auditing, and analysis.

### Q3. What is observability?

Observability is the ability to understand the internal state of a system using its emitted telemetry data.

### Q4. What are the three pillars of observability?

Logs, metrics, and traces.

### Q5. What is structured logging?

Structured logging records information in a consistent machine-readable format, commonly JSON.

### Q6. What is Winston?

Winston is a flexible logging library for Node.js.

### Q7. What is Pino?

Pino is a performance-oriented structured logging library for Node.js.

### Q8. What is Morgan?

Morgan is HTTP request logging middleware for Node.js.

### Q9. What is a request ID?

A request ID is a unique identifier assigned to an individual HTTP request.

### Q10. What is a correlation ID?

A correlation ID connects related operations across multiple components or services.

### Q11. What is AsyncLocalStorage?

AsyncLocalStorage is a Node.js API that maintains context across asynchronous operations.

### Q12. What is Prometheus?

Prometheus is an open-source monitoring and alerting system used to collect and query time-series metrics.

### Q13. What is Grafana?

Grafana is a visualization and observability platform used to build dashboards from different data sources.

### Q14. What is PromQL?

PromQL is the query language used by Prometheus.

### Q15. What is Sentry?

Sentry is an error-monitoring platform used to capture and investigate application exceptions.

### Q16. What is OpenTelemetry?

OpenTelemetry is an open-source framework for generating, collecting, and exporting telemetry data.

### Q17. What is distributed tracing?

Distributed tracing tracks the journey of a request through multiple services.

### Q18. What is a span?

A span represents an individual operation within a trace.

### Q19. What is the difference between a trace and a span?

A trace represents the complete operation journey, while a span represents one part of that journey.

### Q20. What is P95 latency?

P95 latency is the response-time threshold below which approximately 95% of measured requests complete.

### Q21. What is a health check?

A health check determines whether an application or service is functioning correctly.

### Q22. What is the difference between liveness and readiness?

Liveness checks whether an application is alive, while readiness checks whether it is ready to receive traffic.

### Q23. What is centralized logging?

Centralized logging collects logs from multiple application instances into a common system.

### Q24. What is a cache hit ratio?

It is the percentage of cache requests successfully served from the cache.

### Q25. What is event loop delay?

Event loop delay measures how late the Node.js event loop executes scheduled work compared with its expected timing.

### Q26. What is a memory leak?

A memory leak occurs when an application retains memory that it no longer needs, preventing that memory from being reclaimed.

### Q27. Why should we monitor database connections?

Because connection exhaustion can cause requests to wait or fail when the application cannot acquire a database connection.

### Q28. Why is monitoring BullMQ important?

It helps identify queue backlogs, failed jobs, worker problems, and processing delays.

### Q29. What is alerting?

Alerting notifies responsible people or systems when monitored conditions exceed defined thresholds.

### Q30. Why is monitoring important after deployment?

It helps detect failures, investigate incidents, and maintain application reliability.
