# 1. What Is Database Schema Design?

Database schema design is the process of defining how data will be organized, stored, related, and accessed in a database.

It includes:

- Tables.
- Columns.
- Data types.
- Primary keys.
- Foreign keys.
- Relationships.
- Constraints.
- Indexes.
- Database normalization.

### Example

Suppose an Expense Tracker application needs to store users and their expenses.

A simple database design might look like:

```text
USERS
----------------
id
name
email
password

EXPENSES
----------------
id
user_id
amount
description
date
```

Here:

- `users` stores user information.
- `expenses` stores expense information.
- `user_id` connects an expense to its owner.

This is the basic idea of database schema design.

# 3. What Is an Entity?

An entity is a real-world object or concept about which the application needs to store information.

Examples in an Expense Tracker:

- User.
- Expense.
- Category.
- Income.
- Budget.
- Account.

Each entity generally becomes a database table in a relational database.

### Entity Identification

Suppose the requirements say:

1. Users can register.
2. Users can create expenses.
3. Expenses belong to categories.
4. Users can create monthly budgets.
5. Users can record income.

We can identify these entities:

```text
USERS
EXPENSES
CATEGORIES
BUDGETS
INCOMES
```

### Important

An entity is a conceptual business object.

A table is its database representation.

They are related concepts, but they are not necessarily identical in every database design.

Attributes are the properties or characteristics of an entity.

For example, a User entity may have:

```text

----------------

password
```

Here:

- `id` identifies the user.
- `name` stores the user's name.

# 5. Understanding Database Data Types

A database column must have an appropriate data type.

MySQL provides several data types.

## 5.1 Numeric Data Types

| Data Type | Description | Example |
|---|---|---|
| TINYINT | Very small integer | 1 |
| SMALLINT | Small integer | 100 |
| INT | Standard integer | 10000 |
| BIGINT | Large integer | 9000000000 |
| DECIMAL | Exact decimal value | 1250.50 |
| FLOAT | Approximate floating-point value | 12.5 |
| DOUBLE | Higher-precision approximate floating-point value | 123.456 |

### DECIMAL vs FLOAT

For financial values, prefer `DECIMAL`.

Example:

```sql
amount DECIMAL(12, 2)
```

This supports up to 12 total digits, with 2 digits after the decimal point.

Example values:

```text
100.50
12500.75
9999999999.99
```

Avoid using floating-point types for financial calculations where exact decimal representation matters.

## 5.2 String Data Types

| Data Type | Description |
|---|---|
| CHAR(n) | Fixed-length string |
| VARCHAR(n) | Variable-length string |
| TEXT | Long text |
| TINYTEXT | Very short text |
| MEDIUMTEXT | Medium-length text |
| LONGTEXT | Large text |

Example:

```sql
name VARCHAR(100)
email VARCHAR(255)
description TEXT
```

### CHAR vs VARCHAR

**CHAR**

Fixed-length string.

```sql
country_code CHAR(2)
```

Example:

```text
IN
US
UK
```

**VARCHAR**

Variable-length string.

```sql
name VARCHAR(100)
```

Useful for names, email addresses, titles, and other variable-length values.

## 5.3 Date and Time Types

| Data Type | Description |
|---|---|
| DATE | Date only |
| TIME | Time only |
| DATETIME | Date and time |
| TIMESTAMP | Date and time with MySQL timestamp conversion behavior |
| YEAR | Year value |

Example:

```sql
birth_date DATE

created_at DATETIME

updated_at TIMESTAMP
```

### DATE vs DATETIME vs TIMESTAMP

**DATE**

```text
2026-11-25
```

**DATETIME**

```text
2026-11-25 14:30:00
```

**TIMESTAMP**

Stores a timestamp value with MySQL-specific time-zone conversion behavior between the session time zone and UTC.

For applications serving users across time zones, define a consistent time-zone strategy.

A common approach is to store event timestamps in UTC and convert them to the user's local time when displaying them.

## 5.4 Boolean Values

MySQL supports:

```sql
BOOLEAN
```

However, `BOOLEAN` is an alias for `TINYINT(1)`.

Example:

```sql
is_active BOOLEAN DEFAULT TRUE
```

Values are commonly represented as:

```text
1 = TRUE
0 = FALSE
```

## 5.5 JSON Data Type

MySQL supports JSON columns.

Example:

```sql
settings JSON
```

Stored value:

```json
{
    "theme": "dark",
    "notifications": true,
    "language": "en"
}
```

Useful for flexible data structures.

However, do not store every relationship in JSON. Frequently queried relational data should generally be modeled using proper columns and tables.

# 6. What Is a Primary Key?

A primary key uniquely identifies every record in a table.

Example:

```sql
CREATE TABLE users (

    id INT PRIMARY KEY,

    name VARCHAR(100),

    email VARCHAR(255)

);
```

Example records:

| id | name | email |
|---:|---|---|
| 1 | John | john@example.com |
| 2 | Alex | alex@example.com |
| 3 | David | david@example.com |

The `id` column uniquely identifies each user.

### Primary Key Rules

1. Must be unique.
2. Cannot contain NULL.
3. Each table has one primary key constraint.
4. It can contain multiple columns (composite primary key).

### Auto Increment

Instead of manually assigning IDs:

```sql
CREATE TABLE users (

    id INT AUTO_INCREMENT PRIMARY KEY,

    name VARCHAR(100)

);
```

MySQL automatically generates new integer IDs.

### Composite Primary Key

A composite primary key uses multiple columns together.

Example:

```sql
CREATE TABLE user_roles (

    user_id INT,

    role_id INT,

    PRIMARY KEY (user_id, role_id)

);
```

The combination of `user_id` and `role_id` must be unique.

# 7. What Is a Foreign Key?

A foreign key is a column or combination of columns that references a candidate key, usually the primary key, in another table.

It establishes a relationship between tables and helps maintain referential integrity.

Example:

```sql
CREATE TABLE users (

    id INT AUTO_INCREMENT PRIMARY KEY,

    name VARCHAR(100)

);
```

```sql
CREATE TABLE expenses (

    id INT AUTO_INCREMENT PRIMARY KEY,

    user_id INT,

    amount DECIMAL(12, 2),

    FOREIGN KEY (user_id)
    REFERENCES users(id)

);
```

Here:

`expenses.user_id` references `users.id`.

### Example

**users**

| id | name |
|---:|---|
| 1 | John |
| 2 | Alex |

**expenses**

| id | user_id | amount |
|---:|---:|---:|
| 101 | 1 | 500 |
| 102 | 1 | 300 |
| 103 | 2 | 700 |

User 1 owns expenses 101 and 102.

User 2 owns expense 103.

### Why Foreign Keys Matter

They help prevent invalid references.

For example, you cannot insert an expense for a nonexistent user when the foreign key constraint is enforced.

### ON DELETE Behavior

MySQL supports different foreign key actions.

**1. CASCADE**

```sql
FOREIGN KEY (user_id)
REFERENCES users(id)
ON DELETE CASCADE
```

Deleting the referenced user automatically deletes related expense records.

**2. SET NULL**

```sql
FOREIGN KEY (user_id)
REFERENCES users(id)
ON DELETE SET NULL
```

The foreign key becomes NULL when the referenced record is deleted, provided the column permits NULL.

**3. RESTRICT**

Prevents deleting a referenced record while dependent records exist.

**4. NO ACTION**

For InnoDB, this generally behaves like RESTRICT.

### Important

Choose delete behavior according to business requirements.

For financial records, automatic cascading deletion is often inappropriate. You may need to preserve records for auditing, accounting, or legal retention.

# 8. Understanding Database Relationships

Relational databases support three fundamental relationship types.

1. One-to-One.
2. One-to-Many.
3. Many-to-Many.

These relationships are essential for designing relational databases.

## 8.1 One-to-One Relationship (1:1)

One record in Table A is associated with at most one record in Table B, and vice versa.

Example:

```text
USER
  |
  | 1:1
  |
USER_PROFILE
```

A user has one profile.

### Tables

**users**

| id | name |
|---:|---|
| 1 | John |
| 2 | Alex |

**user_profiles**

| id | user_id | bio |
|---:|---:|---|
| 1 | 1 | Developer |
| 2 | 2 | Designer |

### SQL

```sql
CREATE TABLE users (

    id INT AUTO_INCREMENT PRIMARY KEY,

    name VARCHAR(100)

);
```

```sql
CREATE TABLE user_profiles (

    id INT AUTO_INCREMENT PRIMARY KEY,

    user_id INT UNIQUE,

    bio TEXT,

    FOREIGN KEY (user_id)
    REFERENCES users(id)

);
```

Notice:

```sql
user_id INT UNIQUE
```

The unique constraint prevents multiple profile records from referencing the same user.

## 8.2 One-to-Many Relationship (1:M)

One record in Table A can be associated with multiple records in Table B.

Example:

```text
USER
  |
  | 1:M
  |
EXPENSES
```

One user can create multiple expenses.

### Tables

**users**

| id | name |
|---:|---|
| 1 | John |
| 2 | Alex |

**expenses**

| id | user_id | amount |
|---:|---:|---:|
| 101 | 1 | 500 |
| 102 | 1 | 300 |
| 103 | 1 | 700 |
| 104 | 2 | 200 |

Here:

- John has three expenses.
- Alex has one expense.

### SQL

```sql
CREATE TABLE expenses (

    id INT AUTO_INCREMENT PRIMARY KEY,

    user_id INT NOT NULL,

    amount DECIMAL(12, 2),

    FOREIGN KEY (user_id)
    REFERENCES users(id)

);
```

The foreign key is placed on the many side.

## 8.3 Many-to-Many Relationship (M:N)

Multiple records in Table A can be associated with multiple records in Table B.

Example:

```text
USERS
  |
  | M:N
  |
ROLES
```

A user can have multiple roles.

A role can belong to multiple users.

### Why Do We Need a Junction Table?

Relational databases generally implement many-to-many relationships using an intermediate table.

```text
USERS
  |
  | 1:M
  |
USER_ROLES
  |
  | M:1
  |
ROLES
```

### Tables

**users**

| id | name |
|---:|---|
| 1 | John |
| 2 | Alex |

**roles**

| id | name |
|---:|---|
| 1 | Admin |
| 2 | Editor |
| 3 | User |

**user_roles**

| user_id | role_id |
|---:|---:|
| 1 | 1 |
| 1 | 2 |
| 2 | 3 |

John has Admin and Editor roles.

Alex has the User role.

### SQL

```sql
CREATE TABLE user_roles (

    user_id INT NOT NULL,

    role_id INT NOT NULL,

    PRIMARY KEY (user_id, role_id),

    FOREIGN KEY (user_id)
    REFERENCES users(id),

    FOREIGN KEY (role_id)
    REFERENCES roles(id)

);
```

### Relationship Summary

| Relationship | Example | Implementation |
|---|---|---|
| One-to-One | User → Profile | Foreign key with UNIQUE constraint |
| One-to-Many | User → Expenses | Foreign key on many side |
| Many-to-Many | Users ↔ Roles | Junction table |

# 10. What Is Database Normalization?

Database normalization is the process of organizing database tables to reduce unnecessary duplication and improve data integrity.

Consider this table:

| order_id | customer_name | product1 | product2 |
|---:|---|---|---|
| 1 | John | Laptop | Mouse |
| 2 | Alex | Keyboard | Monitor |

This design has problems:

- What if an order contains five products?
- What if an order contains only one product?
- How do we search for all orders containing a particular product?
- How do we store product information separately?

Normalization helps solve these problems.

### Main Normal Forms

1. First Normal Form (1NF).
2. Second Normal Form (2NF).
3. Third Normal Form (3NF).
4. Boyce-Codd Normal Form (BCNF).

Let's understand the first three.

---

# 11. First Normal Form (1NF)

A table satisfies First Normal Form when:

- Each column contains a single value for each row.
- There are no repeating groups of columns.
- Each row can be uniquely identified.

### Bad Example

| id | name | phone_numbers |
|---:|---|---|
| 1 | John | 12345, 67890 |
| 2 | Alex | 55555, 99999 |

The `phone_numbers` column contains multiple values.

### Better Design

**users**

| id | name |
|---:|---|
| 1 | John |
| 2 | Alex |

**user_phones**

| id | user_id | phone |
|---:|---:|---|
| 1 | 1 | 12345 |
| 2 | 1 | 67890 |
| 3 | 2 | 55555 |
| 4 | 2 | 99999 |

Now each phone number is stored separately.

### Key Concept

One column should represent one attribute value per row.

---

# 12. Second Normal Form (2NF)

A table must:

1. Satisfy 1NF.
2. Have no partial dependency of a non-key attribute on a proper subset of a candidate key.

This is particularly relevant when a table has a composite candidate key.

### Example

Consider:

| student_id | course_id | student_name | course_name |
|---:|---:|---|---|
| 1 | 101 | John | JavaScript |
| 1 | 102 | John | Node.js |
| 2 | 101 | Alex | JavaScript |

Suppose the primary key is:

```text
(student_id, course_id)
```

But:

- `student_name` depends only on `student_id`.
- `course_name` depends only on `course_id`.

These are partial dependencies.

### Better Design

**students**

| student_id | student_name |
|---:|---|
| 1 | John |
| 2 | Alex |

**courses**

| course_id | course_name |
|---:|---|
| 101 | JavaScript |
| 102 | Node.js |

**student_courses**

| student_id | course_id |
|---:|---:|
| 1 | 101 |
| 1 | 102 |
| 2 | 101 |

Now each table stores information related to its key.

### Important

If a table has a single-column candidate key and satisfies 1NF, it cannot have partial dependency on a proper subset of that key.

---

# 13. Third Normal Form (3NF)

A table satisfies Third Normal Form when:

1. It satisfies 2NF.
2. Non-key attributes do not have inappropriate transitive dependencies on candidate keys.

### Example

Consider:

| employee_id | employee_name | department_id | department_name |
|---:|---|---:|---|
| 1 | John | 10 | IT |
| 2 | Alex | 20 | HR |
| 3 | David | 10 | IT |

Here:

- `employee_id` determines `department_id`.
- `department_id` determines `department_name`.

Therefore, department name is transitively dependent on employee ID.

### Better Design

**employees**

| employee_id | employee_name | department_id |
|---:|---|---:|
| 1 | John | 10 |
| 2 | Alex | 20 |
| 3 | David | 10 |

**departments**

| department_id | department_name |
|---:|---|
| 10 | IT |
| 20 | HR |

Now department information is stored separately.

### Normalization Summary

| Normal Form | Main Rule |
|---|---|
| 1NF | Atomic values and no repeating groups |
| 2NF | No partial dependency on a candidate key |
| 3NF | No inappropriate transitive dependency of non-key attributes on candidate keys |

### Should Every Database Be Fully Normalized?

Not necessarily.

Normalization improves data integrity and reduces duplication.

However, sometimes carefully planned denormalization improves read performance.

For example, an order may store the product price at the time of purchase.

Even though the product price also exists in the products table, the historical order price must remain unchanged if the product's current price changes.

This is intentional duplication to preserve historical business data.

# 14. What Are Database Constraints?

Constraints are rules enforced by the database to maintain data integrity.

Important MySQL constraints:

### 14.1 NOT NULL

Prevents NULL values.

```sql
name VARCHAR(100) NOT NULL
```

### 14.2 UNIQUE

Ensures uniqueness.

```sql
email VARCHAR(255) UNIQUE
```

### 14.3 PRIMARY KEY

Uniquely identifies a record.

```sql
id INT PRIMARY KEY
```

### 14.4 FOREIGN KEY

Maintains referential integrity.

```sql
FOREIGN KEY (user_id)
REFERENCES users(id)
```

### 14.5 CHECK

Enforces a condition.

```sql
amount DECIMAL(12, 2)
CHECK (amount > 0)
```

Modern MySQL versions enforce CHECK constraints.

### 14.6 DEFAULT

Provides a default value.

```sql
status VARCHAR(20) DEFAULT 'pending'
```

### Why Use Constraints?

Do not rely only on backend validation.

For example, even if your Node.js API validates that an expense amount is positive, a database constraint provides another layer of protection.

# 15. What Is a Database Index?

An index is a data structure that helps the database locate records more efficiently.

Suppose you frequently execute:

```sql
SELECT *
FROM expenses
WHERE user_id = 10;
```

You can create an index:

```sql
CREATE INDEX idx_expenses_user_id
ON expenses(user_id);
```

Now MySQL may use the index to locate the matching rows without scanning the entire table.

### Types of Indexes

| Index | Purpose |
|---|---|
| Primary Index | Index associated with the primary key |
| Unique Index | Prevents duplicate indexed values |
| Composite Index | Index containing multiple columns |
| Full-Text Index | Supports full-text search |
| Spatial Index | Supports spatial data queries |

### Composite Index Example

```sql
CREATE INDEX idx_expenses_user_date
ON expenses(user_id, expense_date);
```

Useful for queries such as:

```sql
SELECT *
FROM expenses
WHERE user_id = 10
AND expense_date >= '2026-11-01'
AND expense_date < '2026-12-01';
```

### Indexing Best Practices

- Index frequently queried columns where beneficial.
- Index foreign key columns appropriately.
- Analyze query execution plans.
- Avoid creating unnecessary indexes.
- Consider column order in composite indexes.
- Measure write-performance impact.

# 16. What Is Soft Delete?

Soft delete means marking a record as deleted instead of physically removing it from the database.

### Hard Delete

```sql
DELETE FROM expenses
WHERE id = 101;
```

The row is physically removed.

### Soft Delete

Add a column:

```sql
ALTER TABLE expenses
ADD COLUMN deleted_at DATETIME NULL;
```

Instead of deleting:

```sql
UPDATE expenses
SET deleted_at = NOW()
WHERE id = 101;
```

Retrieve active records:

```sql
SELECT *
FROM expenses
WHERE deleted_at IS NULL;
```

### Soft Delete vs Hard Delete

| Soft Delete | Hard Delete |
|---|---|
| Record remains stored | Record is removed |
| Can support restoration | Usually cannot be restored without backups |
| Useful for audit/history | Useful for permanent deletion |
| Requires filtering deleted records | Simpler queries |

### Sequelize Paranoid Mode

Sequelize supports soft deletion through paranoid models.

```javascript
const Expense = sequelize.define(
    "Expense",
    {

        amount: {

            type: DataTypes.DECIMAL(12, 2),

            allowNull: false

        }

    },
    {

        paranoid: true,

        timestamps: true

    }
);
```

Sequelize uses a `deletedAt` column for paranoid deletion.

Delete:

```javascript
await Expense.destroy({

    where: {

        id: 101

    }

});
```

Restore:

```javascript
await Expense.restore({

    where: {

        id: 101

    }

});
```

### Important

Soft deletion is not a substitute for a proper data-retention and privacy policy. Some data may need to be permanently deleted.

# 17. What Are Audit Columns?

Audit columns store information about when and by whom a record was created or modified.

Common audit columns:

```text
id
created_at
updated_at
created_by
updated_by
deleted_at
```

### Example

```sql
CREATE TABLE expenses (

    id INT AUTO_INCREMENT PRIMARY KEY,

    user_id INT NOT NULL,

    amount DECIMAL(12, 2) NOT NULL,

    created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,

    updated_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP
        ON UPDATE CURRENT_TIMESTAMP,

    created_by INT,

    updated_by INT

);
```

### Why Are Audit Columns Useful?

They help answer:

- When was this record created?
- When was it last updated?
- Who created it?
- Who modified it?
- Was it deleted?

### Audit Columns vs Audit Logs

These are different.

Audit columns track metadata on the current row.

Audit logs preserve a history of changes.

Example:

```text
expense_audit_logs
------------------
id
expense_id
action
old_value
new_value
changed_by
changed_at
```

For applications requiring detailed historical tracking, use a dedicated audit log.

# 18. Database Naming Conventions

Consistent naming improves readability and maintainability.

Recommended conventions for this example:

| Item | Convention | Example |
|---|---|---|
| Tables | snake_case, plural | `users` |
| Columns | snake_case | `created_at` |
| Primary key | `id` | `id` |
| Foreign key | referenced table + `_id` | `user_id` |
| Junction table | combined names | `user_roles` |
| Boolean columns | `is_` or `has_` prefix | `is_active` |

Example:

```sql
CREATE TABLE user_profiles (

    id INT AUTO_INCREMENT PRIMARY KEY,

    user_id INT NOT NULL,

    first_name VARCHAR(100),

    last_name VARCHAR(100),

    is_active BOOLEAN DEFAULT TRUE,

    created_at DATETIME DEFAULT CURRENT_TIMESTAMP

);
```

The most important rule is consistency across the project.

## 19.2 Define Relationships

```text
  |
  | 1:M
  |

  | M:1
  |
CATEGORIES


USERS
  |
  | 1:M
  |
```

## 19.3 Database Schema

### USERS

```sql
CREATE TABLE users (

    id BIGINT AUTO_INCREMENT PRIMARY KEY,

    name VARCHAR(100) NOT NULL,

    email VARCHAR(255) NOT NULL UNIQUE,

    password VARCHAR(255) NOT NULL,

    is_active BOOLEAN NOT NULL DEFAULT TRUE,

```

### CATEGORIES

```sql
CREATE TABLE categories (

    id BIGINT AUTO_INCREMENT PRIMARY KEY,

    user_id BIGINT NULL,

    name VARCHAR(100) NOT NULL,

    type ENUM('expense', 'income') NOT NULL,

    is_default BOOLEAN NOT NULL DEFAULT FALSE,

    created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,

    FOREIGN KEY (user_id)
        REFERENCES users(id)

);
```

Here:

- `user_id = NULL` represents a global/default category.
- A non-NULL `user_id` represents a user-specific category.
- `type` distinguishes expense and income categories.

In a production design, add appropriate uniqueness rules to prevent duplicate user-specific categories.

### EXPENSES

```sql
CREATE TABLE expenses (

    id BIGINT AUTO_INCREMENT PRIMARY KEY,

    user_id BIGINT NOT NULL,

    category_id BIGINT NOT NULL,

    amount DECIMAL(12, 2) NOT NULL,

    description TEXT,

    expense_date DATE NOT NULL,

    created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,

    updated_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP
        ON UPDATE CURRENT_TIMESTAMP,

    deleted_at DATETIME NULL,

    FOREIGN KEY (user_id)
        REFERENCES users(id),

    FOREIGN KEY (category_id)
        REFERENCES categories(id),

    CHECK (amount > 0)

);
```


### BUDGETS

```sql
CREATE TABLE budgets (

    id BIGINT AUTO_INCREMENT PRIMARY KEY,

    user_id BIGINT NOT NULL,

    category_id BIGINT NOT NULL,

    amount DECIMAL(12, 2) NOT NULL,

    month TINYINT NOT NULL,

    year SMALLINT NOT NULL,

    created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,

    FOREIGN KEY (user_id)
        REFERENCES users(id),

    FOREIGN KEY (category_id)
        REFERENCES categories(id),

    CHECK (amount > 0),

    CHECK (month BETWEEN 1 AND 12)

);
```

Add a uniqueness constraint if the business rule allows only one budget per user, category, and month:

```sql
ALTER TABLE budgets
ADD CONSTRAINT uq_budget_user_category_period
UNIQUE (user_id, category_id, month, year);
```

### Define Associations

```javascript
User.hasMany(Expense, {

    foreignKey: "userId",

    as: "expenses"

});

Expense.belongsTo(User, {

    foreignKey: "userId",

    as: "user"

});

Category.hasMany(Expense, {

    foreignKey: "categoryId",

    as: "expenses"

});

Expense.belongsTo(Category, {

    foreignKey: "categoryId",

    as: "category"

});
```

### What Do These Associations Mean?

```javascript
User.hasMany(Expense);
```

One user can have multiple expenses.

```javascript
Expense.belongsTo(User);
```

Each expense belongs to one user.

### Important

Define associations during application initialization before using queries that depend on them.

For production database management, prefer Sequelize migrations rather than relying on `sequelize.sync()` to modify an existing production schema.

# 23. Interview Questions and Answers

**Q1. What is database schema design?**

Database schema design is the process of defining tables, columns, relationships, constraints, and indexes.

**Q2. What is an entity?**

An entity is a real-world object or business concept about which the application stores information.

**Q3. What is an attribute?**

An attribute is a property of an entity, such as a user's name or email.

**Q4. What is a primary key?**

A primary key uniquely identifies each record in a table.

**Q5. What is a foreign key?**

A foreign key references a candidate key in another table and helps maintain referential integrity.

**Q6. What is a composite primary key?**

A primary key consisting of multiple columns.

**Q7. What is a one-to-many relationship?**

One record in a table can be associated with multiple records in another table.

**Q8. What is a many-to-many relationship?**

Multiple records in one table can be associated with multiple records in another table, typically through a junction table.

**Q9. What is an ER diagram?**

A visual representation of database entities, attributes, and relationships.

**Q10. What is normalization?**

Normalization organizes data to reduce unnecessary duplication and improve integrity.

**Q11. What is 1NF?**

A table should have atomic values and no repeating groups.

**Q12. What is 2NF?**

A table must satisfy 1NF and have no partial dependency of non-key attributes on a proper subset of a candidate key.

**Q13. What is 3NF?**

A table must satisfy 2NF and have no inappropriate transitive dependency of non-key attributes on candidate keys.

**Q14. What is denormalization?**

Denormalization intentionally introduces redundancy or precomputed data to improve read performance or preserve business requirements.

**Q15. What is a database index?**

An index is a data structure that helps the database locate records more efficiently.

**Q16. What is a composite index?**

An index created using multiple columns.

**Q17. What is a junction table?**

An intermediate table used to implement many-to-many relationships.

**Q18. What is soft delete?**

Soft delete marks a record as deleted without physically removing it.

**Q19. What are audit columns?**

Columns that track record metadata, such as creation time, update time, and the user responsible for a change.

**Q20. Why use database constraints?**

Constraints enforce data integrity at the database level.
